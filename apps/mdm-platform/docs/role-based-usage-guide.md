# MDM 平台角色化使用手册

> 适用范围：`apps/mdm-platform/` 当前实现。
> 目标读者：需要演示、调试或继续开发 MDM 平台的人。
> 当前阶段提醒：流程和组织资料的真源仍在 `docs/`，MDM 平台只承接结构化查看、状态记录、角色工作台和后续治理验证，不反向覆盖 `docs/norms/`。

## 1. 先说结论

现在的平台不是“没有功能”，而是功能分散在页面、角色、接口和脚本里，缺少一条按角色走下去的说明线。

开发者先按这四条主线理解：

| 主线 | 当前能做什么 | 主要入口 | 当前限制 |
|---|---|---|---|
| 角色与权限 | 登录、改密码、账号入库、基础角色/项目角色分配、权限矩阵、批量导入 | `#/roleWorkbench`、`#/roleGuide`、`#/rbac` | 顶部菜单仍按基础角色显示；项目角色主要影响工作台和部分接口权限 |
| 流程治理快照 | 查看流程治理快照、部门标签、A1 明细、跨部门风险、映射待办、治理问题单 | `#/processGovernance` | 平台只记录处理状态；整改仍要回源修改 `docs/norms/` 后重新导入 |
| 流程映射与字段台账 | 查看映射、字段台账、审批任务、提交/审核/驳回/发布、Excel 导入导出接口 | `#/mySubmissions`、`#/reviews`、`#/todos`、`/api/import/field-entries`、`/api/export/excel` | 从零新建映射和字段手工编辑的前端入口不完整，接口存在 |
| 基础主数据 | 组织、人员、产品族、产品、数据质量概览、黄金源进度 | `#/orgUnits`、`#/persons`、`#/products`、`#/quality` | 组织架构页面只读；黄金源维护主要是接口能力，页面只显示进度 |

建议开发者第一次体验时，不要从“菜单有哪些”开始，而是从 `角色工作台` 开始：它会识别当前账号的基础角色和项目角色，给出 1 到 3 个下一步动作。

## 2. 启动与账号准备

在 PowerShell 中启动：

```powershell
cd apps/mdm-platform
npm install
$env:MDM_ADMIN_EMPLOYEE_NO="ADMIN001"
$env:MDM_ADMIN_PASSWORD="change-me-very-long"
npm run init-db
npm start
```

访问 `http://localhost:3000`。

平台不会自动创建默认管理员。首次初始化必须通过 `MDM_ADMIN_EMPLOYEE_NO` 和 `MDM_ADMIN_PASSWORD` 创建管理员。管理员在页面或接口新增 / 重置普通账号时，平台会生成一次性初始密码并要求用户首次登录后修改。

可选数据准备：

```powershell
$env:ALLOW_PROJECT_USER_SETUP="true"
node scripts/setup-mdm-project-users.js
```

这会从 `docs/organization/花名册.md` 建立项目参与人、部门负责人和项目工作角色。脚本会为新增账号生成本次一次性初始密码并要求首次登录后修改；如需指定受控初始密码，可设置 `MDM_INITIAL_USER_PASSWORD`。

```powershell
$env:ALLOW_DEMO_SEED="true"
node scripts/seed-demo-data.js
```

这会写入演示部门、用户、流程、映射、字段、术语和待办。它是演示数据，只在明确需要演示时使用。

## 3. 角色怎么理解

平台里有两类角色：

| 类型 | 角色 | 用途 |
|---|---|---|
| 项目工作角色 | `it_lead`、`project_lead`、`workgroup_lead`、`business_contact`、`data_quality`、`decision_group` | 决定“这个人在项目里该干什么”，角色工作台按它们生成下一步动作 |
| 基础权限角色 | `submitter`、`owner`、`reviewer`、`admin` | 决定顶部菜单显示和传统权限边界 |

一个人可以同时有多个项目工作角色。工作台会合并展示为“我的工作台”，事项卡片会显示来源角色。

重要现状：顶部导航的显示仍主要看 `users.role` 这个基础角色，而不是所有 RBAC 项目角色。因此，一个 `business_contact` 如果基础角色不是能看到某菜单的角色，可能在工作台里知道要做什么，但顶部菜单不一定完整显示。继续开发时要优先统一这个权限口径。

## 4. 角色使用路径

### 信息化负责人 `it_lead`

目标：看全局阻塞，协调一般冲突，必要时升级决策。

日常路径：

1. 进 `角色工作台`，先看“我现在该做什么”。
2. 有升级或冲突时，进 `冲突管理` 查看字段/术语冲突。
3. 有流程治理阻塞时，进 `流程治理` 查看映射待办、治理问题单和跨部门风险。
4. 有账号或角色边界问题时，和管理员一起看 `角色权限`。

完成标准：阻塞事项有负责人、有处理结论、有下一步记录。

### 项目组长 `project_lead`

目标：推进本部门流程、字段和跨部门衔接事项。

日常路径：

1. 进 `流程治理`，用部门标签切到本部门。
2. 看 `A1 明细` 和 `跨部门风险`，确认输入来源和输出目标。
3. 在 `映射待办` 打开详情，记录处理过程：标记处理中、提交处理、补充备注。
4. 如果是映射审批任务，到 `待办收到` 或 `评审记录` 打开映射详情，通过或驳回。

完成标准：本部门待办清零或有明确责任人，跨部门风险有确认状态。

### 工作组组长 `workgroup_lead`

目标：组织本工作组成员处理流程治理、跨部门衔接和待办闭环。

日常路径：

1. 进 `角色工作台`，先看本工作组的流程治理问题和映射待办。
2. 进 `流程治理 -> 映射待办`，优先处理跨部门衔接、部门确认类事项。
3. 将事项分派给业务对接人或数据质量员处理，并跟踪是否回源整改。
4. 如果本工作组无法闭环，升级给项目组长或信息化负责人协调。

完成标准：本工作组事项有责任人、有处理状态，跨部门衔接风险有确认或升级记录。

### 业务对接人 `business_contact`

目标：把真实业务动作、字段和流程节点补充到平台中。

日常路径：

1. 进 `角色工作台`，优先处理字段确认、术语补充、映射待办。
2. 如果待办来自流程映射，进 `流程治理 -> 映射待办`，看 L3/A1、来源文件和整改建议。
3. 如果待办来自字段台账，进对应 `流程映射详情`，看字段名称、数据对象、字段类型、消费系统、同步方式和备注。
4. 如果要补术语，进 `术语词典` 填术语、定义、范围、禁用表述和所属流程。

完成标准：流程映射和字段台账可被审核人复核，相关待办已处理或说明原因。

当前限制：字段台账手工新增/编辑的前端入口不完整；接口和 Excel 导入能力存在。Excel 导入接口是 `POST /api/import/field-entries`，需要 `mapping_id` 和文件，工作表应包含 `数据对象`、`字段说明`，可选 `中文字段名`、`英文字段名`、`字段类型`、`消费系统`、`同步方式`。

### 数据质量员 `data_quality`

目标：检查字段完整性，确认黄金源，处理字段冲突和流程治理质量问题。

日常路径：

1. 进 `数据质量` 看组织、人员、产品、外部映射数量，以及黄金源确认进度。
2. 进 `流程治理 -> 治理闭环`，处理 BLOCK/WARN 问题单。
3. 对问题单执行：标记整改中、提交整改、补充备注。关闭必须等重新导入后问题进入 `source_resolved` 状态。
4. 进 `冲突管理` 处理字段冲突，先看字段台账、消费系统和 A1 场景，再给协调意见。

完成标准：字段完整性、黄金源候选和冲突处理状态都有记录。

当前限制：黄金源维护接口存在，页面主要展示进度。相关接口为 `/api/field-identities/:fieldEntryId` 和 `/api/field-identities/:fieldEntryId/confirm`。

### 项目决策组 `decision_group`

目标：处理需要项目层面拍板的升级事项。

日常路径：

1. 进 `角色工作台`，优先看升级事项。
2. 进 `冲突管理` 打开已升级冲突。
3. 阅读双方立场、事件时间线、字段/术语差异。
4. 执行终裁，写清最终决议和终裁意见。

完成标准：升级事项已有终裁结论，处理记录可追溯。

### 报送人 `submitter`

目标：提交本人负责的流程映射和字段台账。

日常路径：

1. 进 `报送管理` 查看本人报送记录。
2. 草稿状态可以提交；提交后进入审批流。
3. 如被驳回，打开映射详情，看高亮字段和驳回原因，再修正后重新提交。
4. 进 `待办收到` 处理通用待办和术语申报待办。

完成标准：草稿已提交，字段台账至少满足审核所需信息。

当前限制：`报送管理` 目前偏“列表和提交”，从零新建映射的可见表单不完整。后端 `POST /api/mappings` 可创建草稿，前端函数存在但缺少完整页面控件。

### 业务负责人 `owner`

目标：确认本部门流程和字段口径，推动跨部门确认。

日常路径：

1. 进 `待办收到` 看本部门待办。
2. 有映射审批时，打开映射详情查看字段台账和审批记录。
3. 通过则进入下一节点；驳回则必须至少选择一个字段并填写具体原因。
4. 进 `业务地图` 或 `流程治理` 查看上下文，确认流程、字段和跨部门输入输出。

完成标准：本部门待办已有处理记录，字段口径明确。

### 审核员 `reviewer`

目标：审核映射、处理阻断冲突，推动流程映射和字段台账进入可发布状态。

日常路径：

1. 进 `评审记录` 查看待处理审批任务。
2. 打开映射详情，复核字段台账和历史意见。
3. 需要驳回时，必须写到具体字段，不能只写笼统意见。
4. 进 `冲突管理` 处理冲突协调、提前升级、终裁、重开。

完成标准：审核动作有意见，阻断事项进入协调或解决状态。

### 管理员 `admin`

目标：保持账号、角色、权限、基础数据和发布动作可用。

日常路径：

1. 进 `角色权限 -> 用户管理` 新增账号、重置密码、分配基础角色和项目工作角色。
2. 进 `角色权限 -> 角色列表 / 权限矩阵` 维护角色权限。
3. 进 `能力与流程申报` 新建或审核业务能力、业务流程。
4. 进 `人员管理`、`产品主数据` 维护基础主数据。
5. 对终审完成的映射执行发布。

完成标准：用户、角色、权限和基础数据状态一致；用户登录后能在角色工作台看到自己的下一步动作。

## 6. 核心流程怎么走

### 6.1 登录后第一屏

1. 登录后默认进入 `角色工作台`。
2. 先看顶部的当前身份、当前部门、今天优先处理事项数。
3. 左侧“我现在该做什么”是优先队列，优先级高于自己猜菜单。
4. 点击事项里的处理入口，进入待办、流程治理、冲突管理或报送管理。
5. 如果不知道自己为什么看到这些事项，切到 `角色使用说明` 看当前角色卡片。

### 6.2 流程治理闭环

这条线处理的是 `docs/norms/` 解析后进入 MDM 的流程治理快照。

1. 仓库侧先运行流程治理解析和导入：

```powershell
cd apps/mdm-platform
npm run sync:process-org
npm run import:process-governance
npm run check:process-governance
```

2. 平台里进入 `流程治理`。
3. 选择全公司或某个部门标签。
4. 看 `流程地图` 定位部门、L2、L3、A1 和建议落位应用。
5. 看 `A1 明细` 确认业务行为、输入来源、输出目标。
6. 看 `跨部门风险` 判断是否存在未确认、需复核或未映射关系。
7. 看 `映射待办` 和 `治理闭环`，打开详情后记录处理过程。
8. 真正整改必须回到来源文件，重新解析导入后，平台问题才会进入可关闭状态。

状态流：

```text
open/assigned -> rectifying -> submitted -> source_resolved -> closed
reopened 可回到继续跟踪
```

### 6.3 流程映射审批

这条线处理 `mappings`、`field_entries`、`approval_tasks`。

理想业务流：

```text
draft -> submitted -> dept_reviewed -> cross_confirmed -> fields_confirmed -> final_reviewed -> published
```

实际操作：

1. 报送人或管理员创建映射草稿。
2. 为映射补字段台账，当前主要通过接口或 Excel 导入。
3. 报送人在 `报送管理` 提交草稿。
4. 平台生成审批任务：
   - 第 2 步：部门内审
   - 第 3 步：跨部门确认
   - 第 4 步：字段台账确认
   - 第 5 步：信息化项目组终审
5. 审核人在 `待办收到` 或 `评审记录` 打开映射详情。
6. 通过会推进到下一节点；驳回会退回草稿，并要求按字段写明原因。
7. 终审完成后，管理员发布。

注意：第 3 步如果存在未解决的 error 字段冲突，会被自动阻断，需要先处理冲突。

### 6.4 冲突处理

冲突分字段冲突和术语冲突。

1. 审核员或管理员进 `冲突管理`。
2. 打开冲突详情，看双方字段/术语差异、责任人、截止时间、事件时间线。
3. 被指派的责任人提交本方立场：采用 A、采用 B 或折中方案。
4. 双方都提交后，审核员/管理员可以终裁。
5. 超期或需要提前处理时可升级。
6. 已解决冲突可以重开；管理员可以归档。

当前限制：后端支持指定/改派责任人，前端有相关函数但详情页没有完整入口按钮，主要依赖检测时自动指派和已有待办进入处理。

### 6.5 角色权限维护

管理员路径：

1. `角色权限 -> 用户管理`：新增账号、编辑部门岗位、分配基础角色和项目工作角色、重置密码。
2. `角色权限 -> 角色列表`：查看角色，非系统角色可新建、编辑、删除。
3. `角色权限 -> 权限矩阵`：选择角色，勾选权限并保存。
4. `角色权限 -> 用户角色分配`：按用户搜索并替换角色集合。
5. `角色权限 -> 用户角色一览`：按部门查看谁缺项目角色。
6. `角色权限 -> 批量导入`：下载模板，上传 `.xlsx` 或 `.csv`，给已有用户分配角色或定义角色权限。

最容易踩坑：只给用户基础角色，不给项目工作角色。这样用户可能能进页面，但角色工作台不知道他在项目里应该先做什么。

### 6.6 基础主数据维护

组织：

1. 进 `组织架构` 查询组织。
2. 只能查看详情；页面不支持手工新增或编辑。
3. 修改组织真源后，应通过同步脚本进入平台。

人员：

1. 进 `人员管理` 查询人员。
2. 可新增人员，必须选择已启用岗位。
3. 保存后回列表，可激活、编辑；管理员可删除。

产品：

1. 进 `产品主数据`。
2. 先新增产品族，再新增产品。
3. 产品族可激活；产品可发布或废止。
4. 管理员可删除产品族或产品，删除会清理关联属性、分类关系等。

## 7. 当前“能用”和“还没接好”的地方

| 能力 | 当前状态 | 开发者判断 |
|---|---|---|
| 登录、会话、改密码 | 可用 | 首次登录默认密码会触发改密码弹窗 |
| 角色工作台 | 可用 | 角色说明、下一步动作、角色桑基图都来自接口 |
| 页面工作流提示 | 可用 | 除角色工作台外，多数页面会插入“我现在该做什么 / 本页工作流” |
| 流程治理快照查看 | 可用 | 依赖已导入快照 |
| 治理问题单/映射待办处理 | 基本可用 | 关闭动作依赖重新导入后的 `source_resolved` 状态 |
| 映射审批 | 部分可用 | 查看、提交、审核、驳回、发布可用；从零新建映射的前端入口不完整 |
| 字段台账 | 部分可用 | 详情查看和 Excel 导入接口可用；手工编辑页面不完整 |
| 黄金源 | 部分可用 | 进度展示和接口可用；缺少完整前端维护页 |
| 冲突管理 | 部分可用 | 查看、提交立场、终裁、升级、重开、归档可用；指定责任人入口未完整接到详情页 |
| 组织架构 | 只读可用 | 设计上不在平台手工维护 |
| 人员/产品维护 | 可用 | 需要配套岗位、产品族等基础数据 |
| 集成、外部系统、分类、属性 | 接口可用为主 | 当前没有完整顶部页面入口，属于后续主数据平台能力 |

## 8. 开发者最短走读路线

如果你只想快速知道平台现在有什么，请按这个顺序走：

1. 用管理员登录，看 `角色工作台` 和 `角色使用说明`。
2. 到 `角色权限 -> 用户管理`，确认用户是否同时有基础角色和项目工作角色。
3. 到 `流程治理`，看是否存在当前快照；没有快照就先运行导入脚本。
4. 到 `流程治理 -> 映射待办 / 治理闭环`，打开一个详情，看状态动作是否能记录。
5. 到 `业务地图`，点一个流程节点，看流程详情和字段台账汇总。
6. 到 `报送管理 / 评审记录 / 待办收到`，看流程映射审批链是否有可处理记录。
7. 到 `冲突管理`，看是否有字段或术语冲突。
8. 到 `数据质量`，看黄金源进度。
9. 到 `人员管理 / 产品主数据`，验证基础主数据表单。

这条路线走完，基本就能判断当前平台在“角色引导、流程治理承接、基础主数据维护、流程映射审批”四条线上分别成熟到什么程度。

## 9. 后续最值得补的使用性缺口

1. 统一项目角色和顶部菜单权限：让 `business_contact`、`data_quality`、`project_lead` 的实际入口和工作台一致。
2. 补完整 `报送管理` 的新建映射和字段台账编辑页。
3. 给黄金源维护做前端页面，把 `/api/field-identities/*` 接到字段详情。
4. 把冲突指定/改派责任人的入口接到冲突详情页。
5. 给流程治理问题单和映射待办增加“为什么现在不能关闭”的提示，避免按钮可见但被接口拒绝。
6. 把接口可用但无页面的外部系统、外部身份、分类、属性能力放入明确的后台维护入口，或标注为后续能力。
