# MDM平台 角色化使用手册

本手册按当前仓库实现说明办理入口和固定角色边界，不表示正式实例已经部署、功能开关已经开启或已经通过业务验收。实际办理以该实例开放的页面、当前对象状态和服务端允许动作为准。当前代码模型为`rbac-raci-v5-2026-10-19`，共九个固定角色、二十二项权限、十三项RACI说明活动；其中MDM组七个角色，系统及目录维护组各一个；页面名称或旧角色提示不能恢复已经退役的操作。

流程事实依据用户指定的原始材料、实际业务说明和明确确认。历史`docs/`、旧程序和上传文件中的审核字段不自动构成业务确认或部门决定证据。

## 1. 先确认自己的身份

登录后，工作台顶部显示：

- 当前人员；
- 当前部门；
- 全部有效MDM工作角色；
- 当前优先事项数量；
- 治理模型版本。

一人可以有多个MDM工作角色。系统合并展示为“我的工作台”，但每个事项和按钮仍按角色、部门、任务关系和对象状态分别校验。

如果页面提示账号已失效、权限已变化或必须修改密码，请重新登录或先完成改密。前端显示按钮不代表最终授权，服务端会在提交时再次检查。

当前流程可在MDM平台“流程编制与草稿”中编制、显式保存及续修，也保留3001主动下载、上传原生V9/V8/V7文件的兼容方式。3001独立、无状态，两者不自动互写。已有明确编制归属时由当前编制者保存，归口主对接人独立提交；旧案例未建立编制归属时保留原主对接人路径。提交形成案例修订，相关部门负责人分别本人核对；核对完成后由组长明确选择主档并受控提升，再由主对接人提交正式草稿，部门负责人本人确认，组长按门槛发布。正式正文及旧意见不直接覆盖。具体条件见[流程编制合同](../PROCESS_AUTHORING.md)及[角色分工](../ROLE_HANDOFFS.md)。

| 办理内容 | 仓库实现的独立页面 | 兼容入口及边界 |
|---|---|---|
| 编制、保存及原案例续修 | “流程编制与草稿”`/app/process-authoring` | 独立开关有效时使用；编制者保存、主对接人提交，导回正文不继承审核状态 |
| 上传、核对及返修上传 | “流程预览与核对”`/app/process-preview` | “流程治理→V7预览核对”；名称中的V7保留兼容含义，接口支持原生V9及受支持V8/V7 |
| 提升、提交正式审核、审核及发布 | “流程正式流转”`/app/process-formal?case=<案例ID>` | 同一案例的原完整入口；预览页本身不承担正式操作 |
| 字段或术语冲突 | “冲突管理”`/app/conflicts` | 原`/#/conflicts`；按当前分派或已升级事项范围办理 |
| 通用待办查阅及关联办理 | “待办收到”`/app/todos` | 原`/#/todos`；按页面提供的真实来源和关联办理，不猜测目标记录 |

功能入口按目标实例的实际开关及当前资格开放；未开启或权限不足时先处理页面列出的条件，不恢复退役UI或绕过服务端卡口。事项优先从“我的工作台”进入，避免混淆不同案例或修订。部署及恢复记录见[Docker说明](../DOCKER.md)，实际开启与业务验收分别核对。

## 2. MDM系统管理员

角色编码：`admin`

### 目标

保证账号入口、授权记录和访问审计可用。

### 第一步

进入“账号与授权”，查看待启用、锁定或停用账号。

### 可以做

- 查看人员、账号、部门和固定角色。
- 为行政人事已维护的员工手工赋予待启用账号，不在账号页新增或修改员工资料。
- 授予或撤销MDM工作角色。
- 启用、恢复、停用账号。
- 重置临时密码。
- 查看账号和授权审计记录。
- 在“角色可见标签”中只读查看固定标签和权限依据。
- 只读查看治理材料。

### 不能做

- 修改组织及员工资料；叠加人事角色也保持目录只读。
- 起草、修改或提交部门材料。
- 审核部门材料或记录部门业务决定。
- 处理业务冲突。
- 发布流程地图、数据地图或术语版本。

### 开户步骤

1. 按已确认工号查找行政人事已维护的员工，核对姓名及所属部门；缺少员工资料时交人事维护。新账号登录名与工号一致。
2. 选择固定MDM工作角色。
3. 填写授权依据、生效日期和可选失效日期。
4. 核对所选多个角色的“可见标签并集”。该预览不能编辑，也不替代服务端权限。
5. 创建待启用账号。
6. 核对账号和角色后执行启用。
7. 只通过受控渠道交付本次响应中的一次性临时密码。

### 常见错误

- 不得根据旧角色、岗位名称或历史名单自动授权。
- 部门角色只能授权到人员所属部门。
- 员工调部由行政人事办理；存在有效部门角色等关联时，先明确调整原授权和责任，再由人事保存，管理员随后按依据授予新部门角色。系统不自动撤权或任命。
- 停用和撤销必须填写原因。
- 不得停用或撤销最后一个有效管理员。

### 完成标准

账号状态、人员部门、有效角色、授权依据、有效期和访问审计一致。

## 3. MDM工作组组长

角色编码：`mdm_lead`

### 目标

在业务责任已经明确的前提下，使治理版本具备发布条件。

### 第一步

进入“我的工作台”。“待办优先”只列出当前最需要处理的1至3项；按待办打开当前V9/V8/V7案例的归口、范围、提升或发布事项。处理字段、术语争议时进入“冲突管理”，处理其他待办时进入“待办收到”。数据治理工作包在实例开放且具备条件时按用户明确选择的固定`process_version_id`办理；当前工作包支持已发布原生V9或受支持V8/V7，发布新版本不会自动建立工作包，也不会改变旧工作包的来源。

### 可以做

- 查看全公司治理材料。
- 分派治理事项。
- 为字段或术语冲突指定、改派当前有效的数据冲突处理人；历史分派不代表当前办理权。
- 为归口部门待定的V9/V8/V7预览案例分派有效部门，并查看各部门核对进度。
- 在V9/V8/V7预览核对完成后，明确选择新建流程主档或已有流程主档，把当前修订提升为正式草稿。
- 检查结构、证据和责任链。
- 提请升级治理争议。
- 在发布卡口全部通过后发布治理版本。
- 在正式V9/V8/V7审核任务与当前修订号、内容摘要一致且审核通过后，发布相应原生版本并取得`process_version_id`。
- 对固定流程版本生成待定候选，认定数据对象和主数据，核对统一对象匹配，判断关键字段和生命周期规则，并记录依据。
- 缺少流程事实时，一次提出一个业务人员能够回答的具体问题，指定一个有效部门；答复后记录采用情况并关闭问题。

### 不能做

- 代替部门负责人确认业务事实。
- 直接改写部门业务材料。
- 以全局角色跳过部门决定。
- 管理账号或角色。
- 把系统候选或业务部门答复直接当作MDM治理结论。
- 要求业务部门代替MDM认定主数据、决定关键字段或制定生命周期规则。

### 发布步骤

1. 核对同一案例的当前修订、内容摘要、实际V9/V8/V7格式和目标主档。
2. 核对参与部门的当前意见、归口和范围依据，以及页面列出的阻断问题。
3. 条件满足后明确选择新建或已有主档，提升当前修订；提升只形成正式草稿。
4. 由归口主对接人提交当前正式草稿，再由归口部门负责人本人记录正式确认结论和依据。
5. 核对正式审核已经通过、任务仍绑定当前修订与摘要，且部门责任、结构、版次及当前版本指针检查通过。
6. 明确执行发布，保留返回的`process_version_id`并按该固定版本核对正文、摘要和版本记录。

正文需要修改时，在MDM平台从原案例续修并保存，由主对接人提交新修订；也可经3001主动下载、上传文件交接。已提交、审核通过或拒绝的正式草稿须按撤回／退回条件恢复，不能用新修订绕过原卡口；已发布版本保持不可变，旧审核决定和意见留存。

### 完成标准

发布版本具备完整责任证据、结构检查结果、版本检查结果和发布记录。

## 4. 部门主对接人

角色编码：`department_contact`

### 目标

将本部门确认的流程、数据和术语事实整理为可审核材料。

### 第一步

编制功能开启时，进入“流程编制与草稿”，新建本部门流程或从原案例续修，保存草稿并补齐来源材料及实际参与部门，再由主对接人提交。已有明确编制归属的草稿由当前编制者保存，主对接人不代其保存，提交职责仍由主对接人承担。也可在3001编制后主动下载原生文件，上传“流程预览与核对”。提升后从同一案例的“流程正式流转”提交正式草稿。

### 可以做

- 查看本部门治理材料。
- 起草、修改和整改本部门材料。
- 按编制归属在MDM平台修改并保存草稿，或通过3001人工文件交接；核对修订、流程图、数据关系及本部门事实，结构提示不代表业务确认。
- 提交本部门材料。
- 在归口部门已经明确时，提交编制草稿或上传本部门原生文件建立案例；收到修改意见后在原案例续修，不另建同名案例绕开原记录。
- V9/V8/V7被受控提升后，在本人仍有当前案例提交权限时提交正式草稿审核；不能直接改写已提交或已发布正文。
- 收到“补充业务事实”待办时，只回答页面中的具体问题；有来源时写明制度、表单或台账位置，不适用时说明实际原因。

### 不能做

- 查看其他部门材料。
- 审核本部门材料。
- 把个人判断写成部门负责人决定。
- 发布全局治理版本。
- 查看数据生命周期治理工作包全量内容，或认定主数据、统一对象匹配、关键字段和生命周期规则。

### 典型处理

根据制度、表单和业务人员说明补齐流程材料。答复定向事实问题时只回答被问到的内容，不扩写MDM治理结论。无法确认的内容明确说明缺口，不用默认值补齐。

问题和待办从当前工作台或对应页面办理。需要整改原始材料时说明具体问题，在用户提供的材料、MDM平台编制草稿或3001中按各自边界修改，再按该事项要求提交新修订或人工上传；判断不构成问题时填写事实和依据。“待办收到”中的完成、办公室任务办结和补充事实答复，都不表示问题已经关闭或流程已经审核通过。

### 完成标准

材料已经提交，缺失信息、证据和暂不能确认事项均有明确记录。

## 5. 部门负责人

角色编码：`department_mdm_reviewer`

### 目标

审核本部门材料，并使部门最终责任可以追溯。

### 第一步

进入“我的工作台”查看本部门核对或正式审核事项。预览核对进入“流程预览与核对”或兼容“V7预览核对”；正式审核进入同一案例的“流程正式流转”或原完整入口。先确认当前修订、内容摘要和本部门范围。

### 可以做

- 查看本部门治理材料。
- 审核或退回本部门材料。
- 在组织最终负责人登记与本部门有效授权一致时，本人核对并记录最终确认，不由其他人员代记录。
- 核对跨部门事项中本部门的确认记录。
- 对V9/V8/V7核对项记录本部门的“已确认、需要修改、待补证据、存在分歧”和依据。
- 对已经提交的正式V9/V8/V7草稿记录审核结论；审核任务显示的修订号或内容摘要过期时停止处理，并要求按当前允许状态重新办理。
- 收到发给本部门的“补充业务事实”待办时，可以回答具体事实并提供来源位置；该答复不等于部门作出主数据或生命周期治理决定。

### 不能做

- 审核其他部门材料。
- 让其他人员代为确认，或替另一部门作决定。
- 修改部门主对接人提交的业务事实。
- 发布全局治理版本。
- 代替MDM工作组认定主数据、合并统一数据对象、决定关键字段或制定生命周期规则。

### 核对与正式审核步骤

1. 核对本人为已登记的部门最终负责人，并具备本部门有效账号和角色授权；缺少任一条件时不办理确认。
2. 打开本人待办指向的案例和当前修订，核对制度、表单、实际事实及本部门依据。
3. 预览阶段明确选择“已确认、需要修改、待补证据、存在分歧”之一并保存本部门意见；预览核对不替代正式审核。
4. 正式审核任务出现后，再核对任务绑定的修订号与摘要，选择“通过、需要修改、拒绝”（接口值为`approve`、`needs_changes`、`reject`）并填写正式意见。
5. 提交后核对本部门结果、部门最终负责人及审核记录；不能把其他部门意见或旧修订的通过记录套用于本次审核。

若系统返回`RESPONSIBILITY_CHAIN_INCOMPLETE`，按当前专用授权入口明确登记部门最终负责人并核对交接，不能根据姓名或历史角色猜测任命。

固定部门决定接口仍保留`approved`、`returned`、`rejected`和依据、时间、证据引用等原合同；该记录不能替代当前正式审核任务的`approve`、`needs_changes`、`reject`，也不能据此推进已退役的承接链。

### 完成标准

审核结果、部门最终负责人、决定依据、决定时间和记录人均可追溯。

## 6. 数据冲突处理人

角色编码：`data_conflict_handler`

### 目标

处理本人被明确分派的数据或术语冲突。

### 第一步

进入“冲突管理”（`/app/conflicts`或原`/#/conflicts`），核对字段或术语冲突类型、编号和当前分派，只处理本人当前被分派的事项。通用待办未提供稳定冲突类型和编号时，先在当前可见冲突列表核对，不能从待办正文或旧映射编号猜测目标。

### 可以做

- 查看被分派冲突及完成处理所需的上下文。
- 记录双方立场、协调证据和协调方案。
- 处理普通冲突。
- 常规协调无法解决时，记录依据并按当前状态提请升级；已升级事项交项目决策组处理。

### 不能做

- 查看或处理未分派事项。
- 代替受影响部门确认业务事实。
- 决定重大升级争议。
- 发布治理版本。

### 完成标准

冲突已有协调记录、各部门决定，或有完整证据的升级记录。

协调或处理决定不会自动改写字段、术语定义，也不自动成为流程审核结论。

## 7. 数据质量审计人

角色编码：`data_quality_auditor`

### 目标

识别数据完整性、准确性和一致性问题，并跟踪整改证据。

### 第一步

进入“数据质量”，核对人工审计已开启、当前准确设计已由相关部门负责人本人同意，再登记发现或处理待复核整改。

### 可以做

- 全局读取数据治理信息。
- 选择已获本人同意的当前设计，记录发现、依据、责任部门及整改要求。
- 提出整改要求。
- 复核主对接人提交的整改证据，填写依据并退回或关闭；设计变化须先重新确认，再明确更新依据，旧轮次保留。

### 不能做

- 修改部门源数据或部门材料。
- 代替部门作出业务决定。
- 发布数据地图或其他治理版本。

### 完成标准

审计结论有依据，整改事项有责任部门、处理状态和复核记录。

## 8. 项目决策组

角色编码：`decision_group`

### 目标

处理常规协调无法解决且已经升级的重大跨部门争议。

### 第一步

进入“冲突管理”（`/app/conflicts`或原`/#/conflicts`），查看已经升级的字段或术语争议，核对双方内容、协调历史和决定依据。只有已升级事项可按当前状态办理决定。

### 可以做

- 查看已升级事项及必要上下文。
- 对已升级重大争议记录处理决定和依据；不能以此修改字段、术语正文或代替部门、流程审核决定。

### 不能做

- 查看普通未升级冲突。
- 日常编辑或部门审核。
- 发布治理版本。
- 管理账号和角色。

### 完成标准

升级事项已有决定、依据、影响范围和后续责任记录。

## 8.1 MDM治理经办人

角色编码：`mdm_steward`。从工作台或收到的待办进入组长明确分派的案例或工作包，核对固定来源并记录治理材料及依据，交组长审核。案例与工作包分派分别核验；没有有效分派时不沿用历史办理权，不读取全公司治理材料，不代部门确认，不审核、发布或完成工作包审核。

## 8.2 行政人事信息维护员

角色编码：`hr_directory_manager`。进入“组织架构”或“花名册”，新增或修改已明确的部门、办公室、员工及归属关系，填写原因，核对差异后保存直接生效；Excel/CSV仅作为明确导入材料。结果在同一目录的导入与维护记录查阅，前后内容、操作人及原因留痕。人员保存不自动开户或授予系统角色，需要开户时明确交管理员核对同一员工。管理员叠加人事角色仍只读；涉及有效账号、部门角色或未办结任务时先调整关联，再重新核对。完整边界见[目录接口](../DIRECTORY_API.md)。

## 9. 多角色与临时代办

- 多角色用户按每个动作所需权限分别校验，不会因为拥有一个全局读取角色而获得其他写权限。
- 顶部功能标签按全部有效角色取并集；“角色可见标签”页面可查看每个标签的访问方式和权限依据。
- 标签可见性由固定模型生成，不提供按角色或按账号自定义。
- 部门角色始终绑定人员所属部门。
- 跨部门临时代办通过独立委托关系处理，不修改永久角色范围。
- 委托只覆盖明确对象、时间和动作，不能变成全部门或全局访问。

实例开启编制归属功能且案例已有明确记录时，当前编制者保存草稿，归口主对接人独立提交案例修订及正式草稿，不因转办改变提交责任。主对接人只在页面允许的编制前窗口内明确指定或转办给本部门有效人员；已有保存或提交证据后窗口关闭，关闭功能也不重新开放。旧记录没有明确编制归属时按原主对接人路径办理，不自动转办或补任命。接收者只取得该案例所需资格，不新增固定角色、全部门读取、正式确认或发布权，也不自动取得办公室成员、任务办理或问题关闭资格。

## 10. 常见提示

| 提示 | 处理方式 |
|---|---|
| `ROLE_ASSIGNMENT_EVIDENCE_REQUIRED` | 补充角色、授权依据或生效日期 |
| `ROLE_SCOPE_DEPARTMENT_MISMATCH` | 将部门角色范围改为人员所属部门 |
| `RESPONSIBILITY_CHAIN_INCOMPLETE` | 补齐部门最终负责人或必需部门决定 |

| 会话已失效 | 重新登录；账号、部门或角色可能已变化 |

## 11. V9/V8/V7实际办理与未提交意见

当前原生V9及受支持V8/V7按编制保存、主对接人提交、部门核对、提升、正式提交与确认、发布链路办理；3001人工文件交接兼容保留。功能开放情况以目标实例为准，不从历史截图推断。历史截图和合成身份只用于追溯，见文末历史快照。

### 11.1 从哪里开始，何时算办完

登录后先看“我的工作台→待办优先”。每项说明当前动作、来源角色和办理对象；点击后进入同一案例的当前修订，部门核对任务还会定位到对应意见框。“待办优先”只展示最优先的1至3项，其他事项可在“全量职责”或对应工作区查看。多角色合并不改变各动作的部门和权限要求；同时具有管理员角色时，对治理业务保持只读。

| 办理角色 | 第一步与办理依据 | 当前步骤的完成标准及下一步 | 退回或缺少条件时 |
|---|---|---|---|
| 部门主对接人及已明确的当前编制者 | 从工作台进入本部门原案例或编制草稿，核对当前修订与来源 | 编制者保存，主对接人提交新修订；部门分别本人核对，组长提升后仍由主对接人提交正式草稿 | 阅读退回原因，在原案例续修或经3001交接；保存后由主对接人提交，受影响部门重新核对，不另建同名案例绕开原记录或沿用失效资格 |
| 归口部门负责人 | 打开“核对本部门事实”，对照当前修订、制度、表单及实际办理事实，填写本部门依据并选择结论 | 保存“已确认”后，本部门该项从待办消失；另一部门仍须独立核对。正式审核任务出现后，再填写正式意见并明确选择结论 | “需要修改”须写清具体问题，主对接人据此返修；“待补证据”仍属于未办完事项，补齐后重新核对；不得预填或沿用未经核对的结论 |
| 承接部门负责人 | 从本人的核对待办进入对应行为，核对承接输入、输出和完成标准 | 只保存本部门结论，不代替归口部门确认；双方结果均满足条件后进入提升准备 | 说明本部门发现的问题及依据；新修订影响本项时，待办重新出现，须核对新内容 |
| MDM工作组组长 | 从工作台处理归口或范围依据；核对各部门进度和页面列出的前置条件 | 范围卡口解除后该待办消失；核对完成后明确选择正式主档并提升；审核通过后核对当前修订和依据，再发布并读取固定版本 | 缺少部门结论时交对应部门处理；缺少流程事实时由编制人员补充。审核记录与当前修订不一致时先核对原因，不代写部门意见或自动认定主数据 |
| MDM系统管理员 | 先处理“账号与授权”中的身份事项；进入V9/V8/V7时只读查看案例和记录 | 账号维护按第2节标准办完；流程业务仍由对应业务角色办理 | 维护访问条件，不能以管理员身份核对、审核或发布；叠加业务角色也不显示业务办理按钮 |
| 数据冲突处理人、数据质量审计人、项目决策组 | 分别进入第6至8节规定的当前指派、质量核查或升级事项 | 按既有职责和对象权限记录处理结果；没有向这些角色新增流程审核或发布权力 | 将V9/V8/V7事实或修订问题交归口部门和MDM工作组，不能借只读材料入口代办其他角色动作 |

“已确认”只表示该部门完成当前核对步骤；提升、正式审核和发布分别办理。正式审核“拒绝”后，由当前有权部门负责人按页面允许的退回修改动作恢复，填写原因并绑定修订及当前审核任务；主对接人不能用新预览绕过原正式确认。页面不自动新建草稿或改写旧决定。

### 11.2 尚未提交的文字如何处理

核对依据、核对结论、归口选择、范围决定、正式承接字段和正式审核意见，只在明确点击各自的保存或提交按钮后发送。保存同页另一项、点击页面“刷新”或重绘时，其他意见继续保留；本项保存不等于其他项也已提交。正式审核结论初始为空，必须由办理人选择。

切换案例、切换工作区、上传新修订或退出登录时，页面先提示处理未提交内容。选择取消会保留原文；明确放弃后才能离开。上传失败、取消比较或退出失败时原文仍保留。上传期间后来输入的文字不会随先前的放弃确认一并丢弃，必须对照新修订再办理。

浏览器刷新或关闭使用Edge原生离页提示。取消后可以继续编辑；明确选择离开会结束当前页面，未提交文字不会自动恢复。保留内容仅存放在当前页面内存，不自动上传，也不写入浏览器长期存储；浏览器崩溃、强制结束进程或断电不在恢复保证范围内。

| 页面情况 | 办理人应执行的动作 |
|---|---|
| 提示修订或办理状态冲突 | 原意见仍保留。先读取当前修订并核对变化，按页面提示明确继续编辑或放弃后重新办理；不能自动套用旧结论，也不能把过期绑定直接重试到新修订 |
| 登录失效 | 保持当前页面，用原账号重新登录后核对保留内容；切换其他账号前必须明确放弃原意见，不能把甲人员意见交给乙人员继续提交 |
| 网络失败或保存未确认成功 | 保留原文，恢复连接后刷新核对服务器结果，再决定是否重试；不要把提示失败直接理解成服务器一定零写入 |
| 工作台暂不可用 | 点击“重试读取待办”，恢复后再办理。不可用不等于没有待办；不要据此认定任务已经完成 |
