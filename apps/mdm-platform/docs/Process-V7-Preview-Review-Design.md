# V7预览核对功能设计

## 1. 要解决的问题

3001不会保存账号、待办、核对意见或处理进度。跨部门核对在线下进行时，归口部门、承接部门和MDM工作组难以确认谁还没有处理、哪一项需要修改、哪一版文件已经核对。

3000新增“V7预览核对”工作区，接收用户主动上传的`process-governance-v7`文件，保存部门核对进度和操作记录。预览核对阶段不写正式流程草稿和版本；只有预览核对完成、原生V7正式基础迁移通过、用户明确选择新建或已有主档，并且正式功能开关开启后，受控提升才能把精确修订写入正式链路。正式草稿继续经过提交、部门审核和发布，发布后生成不可变`process_version_id`。

## 2. 本期范围

- 部门主对接人或MDM工作组组长上传一个V7文件，建立预览核对案例。
- 归口部门尚未明确时，案例进入“归口部门待分派”，由MDM工作组组长选择有效部门。
- 3000根据V7中的归口部门、固定执行部门、业务行为、相连流程关系和数据关系，生成跨部门核对项。
- 归口部门和承接部门的部门MDM审核员分别记录“已确认、需要修改、待补证据、存在分歧”及依据。
- 编制人从3001修改后上传新文件。3000依据稳定引用和核对内容摘要保留未变化项的核对结果；内容变化的核对项重新变为待核对。
- 3000显示案例、修订、核对项和操作记录。所有部门均只查看本部门参与的案例；全局只读或全局治理角色按现有权限查看。
- MDM工作组组长在核对完成后明确选择新建主档或已有主档，并提升当前修订。系统不按名称或近似编号自动匹配。
- 正式V7草稿正文在3000中只读。部门主对接人提交审核，部门MDM审核员核对绑定的修订号和摘要，MDM工作组组长在审核通过后发布。
- 发布成功后，3000按`process_version_id`读回完整V7，并重新计算内容摘要。

## 3. 不在本期处理的事项

- 3000不编辑V7业务内容，不把核对意见写回V7文件。
- 预览核对接口不创建`process_design_drafts`或`process_design_versions`记录。正式提升使用单独接口，必须保留原生V7，不得转换为V3。
- 核对完成不等于流程审核、批准、发布或生效。
- 3000不调用3001接口。编制人通过下载和上传文件完成版本交接。
- 动态责任部门只有在运行时才能确定，本期不把它自动认定为固定跨部门核对项。
- V7没有明确固定执行部门时，3000只显示待处理提示，不允许用户在3000中猜测或补写业务部门；编制人员需要回到3001补充后上传新修订。

## 4. 责任分工

| 责任主体 | 本期动作 | 不得执行的动作 |
|---|---|---|
| 部门主对接人 | 上传本部门V7文件；根据核对意见在3001修改后上传新修订 | 代替部门审核员确认事实；在3000修改V7内容 |
| 部门MDM审核员 | 记录本部门对每个核对项的结论和依据 | 代替另一部门确认；把个人意见写成部门负责人决定 |
| MDM工作组组长 | 上传待分派案例；分派归口部门；记录范围决定；查看整体进展；明确选择正式主档；提升当前修订；在正式审核通过后发布 | 代替业务部门确认流程事实；改写V7正文；把`review_complete`当作审核或发布结论 |
| MDM系统管理员 | 全局只读查看和排查系统问题 | 上传、分派、核对、修改或发布治理材料 |

## 5. 状态和处理顺序

1. 3000校验上传文件确为V7，并计算内容摘要。
2. 归口部门为空时，案例状态为`pending_owner`；归口部门明确后，案例状态为`under_review`。
3. 3000为每个固定跨部门行为生成一条核对项，并为归口部门和承接部门分别保存核对状态。
4. 任一部门选择“需要修改”时，案例状态为`needs_revision`；选择“待补证据”或尚未处理时，案例保持`under_review`；选择“存在分歧”时，案例状态为`disputed`。
5. 两个部门对全部核对项均选择“已确认”时，案例状态为`review_complete`。没有固定跨部门项时，必须由MDM工作组组长明确记录范围决定后才能完成。该状态只表示预览核对完成。
   页面在核对项尚未确认时显示“执行角色待确认”；核对项状态为`confirmed`后显示“执行角色”。该标签只反映当前核对项状态，不代替流程审核、批准或发布。
6. 上传新修订时，3000比较每个核对项的业务行为、执行部门、相连流程关系和数据关系。内容未变化时保留双方结果；内容变化时双方重新核对。
7. MDM工作组组长把`review_complete`的当前修订提升为正式V7草稿；重复提升相同修订返回原结果。
8. 归口部门主对接人提交草稿。审核任务绑定草稿修订号和内容摘要，部门MDM审核员只能处理仍与当前正文一致的任务。
9. 审核通过后，MDM工作组组长发布原生V7。发布事务锁定草稿、主档、当前版本和审核任务，只允许一个并发请求形成正式版本。

## 6. 可检查结果

- V7上传后只写预览核对专用表，正式V3草稿和版本数量不变。
- 相同案例和相同内容重复上传不新增修订。
- 上传新修订必须提交当前修订号；旧修订号返回409。
- 部门审核员只能处理本部门一侧的核对结果。
- 管理员执行任何写操作均返回403。
- 每次上传、分派、核对、保留结果和重新打开均形成操作记录。
- 所有核对项完成后只进入`review_complete`。预览响应仍不返回正式流程版本标识；正式提升和发布使用独立受控动作。
- `PROCESS_V7_PREVIEW_ENABLED`和`PROCESS_V7_FORMAL_ENABLED`默认关闭；开关关闭或数据库结构未就绪时，服务端返回受控错误，不在运行时建表。
- 隔离MySQL已经验证重复提升、过期审核摘要拒绝、并发发布一成一拒、发布读回和空表回退。该技术证据不能代替真实业务角色对流程事实的核对。
