# 3000 当前页面与操作说明

本文整理当前工作树的技术行为和维护限制，实际启用、部署和验收分别核对目标实例。业务依据来自用户指定的外部原始材料及有权确认；实现不单独证明业务要求。文中代码路径以 `apps/mdm-platform/` 为基准。

## 旧数据地图基础兼容维护

旧库升级先运行显式 `migrate:data-map-legacy-compatibility` 预检，再按获准范围执行该维护及 定义版本 定义迁移。维护只对已知旧结构调整三处新记录默认值，并扩充字段系统关系、字段身份的 CHECK 允许值；原有 `master_data_candidate`、`candidate`、`candidate_authority` 原样保留，不转换为认定结论，不补填部门或所属对象。新建记录继续使用现行默认值，身份维护仍按现有服务端权限、并发和审计规则办理。公开 API、审批链和正式认定权限不变。

维护没有启动时 DDL，必须显式注入 MySQL 环境及匹配目标；先停写并取得一致性备份/恢复证据和该目标授权。未知结构、未执行 CHECK、排序规则漂移或已登记后结构回退均拒绝。每张表的 ALTER 原子执行，多表之间不承诺事务回滚；中断后先 inspect，再续跑已知未完成项。无自动缩窄 CHECK 或旧值回写入口；回退应停用新增写入、保留原值及历史，按获准的完整恢复方案处理，不能删除历史来回退。命令和隔离测试详见 scripts/README.md。本地隔离验证不代表正式库已升级。

维护与恢复限制：七张基础表任一缺失、部分字段或引用漂移均阻止全部维护；定义版本在旧默认/CHECK结构下拒绝，兼容维护后保留原来源快照及未明确归属。中断后未知漂移阻止续跑，恢复到已知结构后仅处理pending项；标记失败不伪造ready。本轮未改变维护DDL、CHECK或标记合同，精确字段/引用及恢复说明见同批次`field-legacAX4261006-01/compatibility.md`和`update-recovery.md`。

## 角色与责任说明

`/app/role-guide` 复用现有 `GET /api/rbac/model`，向已登录人员只读展示固定角色目标、使用说明、当前账号有效角色、允许动作、可见功能标签、角色级及完整 RACI、常见动作的权限缺口。第一步入口沿用模型中的原办理目标；当前待办数只读复用 `GET /api/role-workbench?mode=todo`，读取失败显示暂不可用而非零。选择的角色编码保留在 `?role=` 中；刷新或返回可恢复查看位置。具体事项仍由服务端按权限、部门、状态和责任证据核验，页面不授予角色或推断业务责任。角色定义、人员授权和权限矩阵的详细管理查阅继续使用 `/app/roles`。

本增量没有后端接口、数据、权限或审批链变化。固定模型中的非角色参与主体标识原样展示，不把机器标识推断成已确认的部门或人员。正式切换留 编制协调；隔离浏览器测试不代表人工体验或业务验收。复验入口见 [scripts/README.md](../scripts/README.md#当前npm命令)。

## 数据地图台账查阅

`/app/data-map` 提供上下文查阅、创建及关联字段台账；`?context=<原上下文ID>` 支持刷新和返回定位。页面使用原 `/api/data-map/contexts`、`/api/field-entries/mapping/:contextId`，权限、部门范围、ID和状态保持。上下文不代表对象身份，原质量状态不构成新治理认定。字段身份与黄金源办理见下节；本页新增流程与数据关系图，台账导出见下节。

### 字段身份与黄金源办理

在 /app/data-map 选择上下文和字段，可查阅原字段身份、黄金源及当前确认记录；identityField 查询参数与 context 一起定位，支持刷新和历史返回。本部门编制权限用于维护系统名称、代码、置信度、备注及获准的维护责任，本部门审核权限用于单独确认已保存的系统。沿用 GET /api/field-identities/field/:id、PUT /api/field-identities/:id 和 POST /api/field-identities/:id/confirm；原角色、部门范围和确认接口保持。保存置为 needs_review、未确认，不代表新模板对象或权威来源已认定。

字段身份编辑复用受支持后端能力。维护部门仅限字段所属部门，负责人仅限该部门有效人员。页面通过 responsibility-options 读取最小名单，服务端复核人员在职、启用及部门有效期；未知责任允许为空，不自动指定。原责任引用未编辑时保留，历史用户编号只读；只有旧用户编号而无人员编号的记录继续暂停维护，禁止自动映射。

输入绑定人员、部门和字段，仅存页面内存；切换上下文、刷新、错误和同身份重登保留，跨身份不展示，明确离开或放弃才清除。提交前复读原记录，变化时阻止写入；结果不明时须先刷新核对，再放弃本次输入并重新办理，不自动重试。新页面同时提交 expected_identity 原快照，服务端取得字段行锁后比较当前记录，不一致返回409；旧调用方可省略该增量参数，但不具备过期快照检测。无幂等回执，响应丢失后仍须人工核对，不能自动重放。

字段维护与部门确认分开：维护 PUT 拒绝 confirmed 为真或 status 为 confirmed 的请求并返回403，部门确认必须使用原专用入口；该入口继续复核本部门审核权限。已有确认数据保留。历史记录存在 owner_user_id 而 owner_person_id 缺失时，页面暂停维护、PUT返回409，防止旧规范化器静默推断人员编号；查阅和原确认接口继续可用。未变更表结构，无自动迁移或正式数据回填。旧调用方通过维护接口直接确认的行为不再受支持。

维护及部门确认与操作记录在同一事务内提交，记录失败全部回滚。复用 data_map_change_sets / data_map_version_log，entity_type 为 data_map_field_identity、entity_id 为原字段ID；不新增表、自动DDL或回填。GET /api/field-identities/field/:id/history 按原读取权限分页展示操作人、时间及前后快照，明确旧历史缺失，不能将第一条快照冒充旧审核事件。确认请求与已保存系统不一致或重复确认返回409，审核入口不再修改维护内容。新增责任选择接口为 GET /api/field-identities/field/:id/responsibility-options，仅本部门编制权限可读，不返回手机号、账号等无关信息。缺少原审计表时操作历史读取及维护/确认写入返回503，写入不会脱离记录单独成功；基本身份读取不依赖审计表。

维护与恢复限制：新版维护和确认实际携带已保存完整快照，服务端锁后拒绝过期身份/责任及读写间变化。旧调用仍可省略快照，两个维护可依次成功，省略确认内容确认锁内当前保存状态，不能检测旧页面过期。管理员含叠加部门编制/审核角色继续治理只读；字段接口及页面共同执行拒写。readiness增加原系统关系及两张字段审计表的字段探测，缺表/字段准确不可用，健康响应结构保持。模块没有新增开关或标记；核心ready不代替旧值兼容inspect或定义版本准备。

验证：先运行 npm.cmd run build:frontend，再运行 npm.cmd run test:field-identity-browser -- --output <仓库artifacts内全新目录>。使用已有 Edge、Playwright、mysql:8.4 与自有隔离夹具，验证真实保存/确认、权限、并发变化、输入保护及旧记录。仅 Edge 100%、1699×828 桌面测试；403/409/503、断网、迟到响应及写入后丢失响应为显式注入。正式切换仍属于编制协调，隔离结果不等于人工体验或业务验收。

### 原生流程与数据关系图

`/app/data-map` 的图形面板复用原案例列表、案例详情和正式版本正文接口。案例存在当前已发布版本时读取该固定版本并复核摘要标志；否则明确显示预览修订。支持受支持的原生 V7/V8，保持原正文、ID和状态，不转换文档，不向3001通信。原列表最多返回100项，页面明确此限制；图形版本选择器通过原正式草稿详情列出该流程受支持的正式版本，可独立查阅历史版本；版本正文仍由后端复核权限和摘要，失败不回退到其他版本。

流程图、数据关系图使用原 `/api/process-diagrams/assets/` 本地只读组件，支持节点原文、键盘查阅、平移缩放、完整/清晰视图和含流程名称及版本来源的PNG下载。`diagramCase`、`diagramVersion`、`diagramMode`、`diagramData` 查询参数保留选择，不覆盖台账的 `context` 参数；无数据对象显示空态。刷新或请求失败清除旧图，切换、离页或身份变化使迟到结果失效，图形动作不提交或清除相邻台账输入。

验证：先 `npm.cmd run build:frontend`，再 `npm.cmd run test:native-diagrams-browser -- --output <仓库artifacts内全新目录>`。使用已有Edge、Playwright和本地mysql:8.4，测试只创建自有隔离MySQL/HTTP/浏览器并写合成数据，结束按归属清理。输出浏览器结果、几何数据、PNG及Edge 100%、1699×828桌面截图（不执行窄屏测试）；检查来源、权限、错误重试、输入保护、迟到请求及新旧兼容。不改变后端API、权限、审批或数据库，正式切换仍留编制协调，自动验证不替代人工业务验收。
独立页面补充：在正式流转页的“主档已发布版本查阅”中明确选择版本后，可分别打开该固定版本的流程图、数据关系图；链接在新标签页打开，原页未提交意见保留。`/app/data-map?diagramVersion=<固定版本ID>&diagramMode=process|data` 在没有 `diagramCase` 时直接读取原版本正文接口，不依赖案例列表或草稿详情，仍由服务端检查部门范围与正文摘要。页面检查版本标识、状态和原生格式；失败清除旧图且不回退到预览或当前版本。刷新、返回、视图切换和PNG来源继续绑定该版本，可返回原案例选图方式。这是已知版本的独立查阅入口，不提供全局版本搜索，也不推断主档或案例关联；后端接口、权限、审批及旧数据保持。

## 数据质量独立前端

`/app/quality` 提供字段身份总体确认进度与按对象名称分组的明细，两个视图读取同一次 `/api/quality/field-identities/progress` 响应，沿用后端身份与部门范围；只统计已有字段身份记录，同名对象可能合并统计。“已确认”是原记录状态，不代表数据值质量合格或新模板权威来源认定。已退役的产品、外部标识质量总览不恢复。

页面只读，刷新失败清除旧统计并提供重试，取消或迟到响应不回写；身份变化重新读取。没有业务输入、保存或审批动作，不改变接口、数据库及历史数据。构建后执行 `npm.cmd run test:quality-browser -- --output <仓库 artifacts 内全新目录>`，验证自有隔离 MySQL、合成身份和真实 Edge；正式开启仍属于 编制协调，人工体验与业务验收另行记录。

## 主数据发布与历史版本独立前端

`/app/publications` 提供主数据表格导入、唯一标识列选择、导入新版、增改移除数量核对和明确确认发布，并可按主数据、组织架构、花名册查阅历史版本、下载 Excel 或完整 JSON。`kind` 与 `id` 查询参数保留发布类型和选中版本，支持刷新、返回及前进；列表沿用原接口最近 200 个版本上限，不表示全部历史。

复用 `DirectoryPublication`、现有身份与输入保护，以及 `/api/publications` 原接口。新建导入使用解析接口分配的数据集标识；“导入新版”沿用所选版本的数据集和唯一标识列，核对基线仍由后端读取最新版本。版本中移除的行保留在历史版本，不删除对象台账；发布也不等于完成台账治理认定。主数据接口只提供增改移除数量，不提供逐行差异，页面明确提示结合文件和历史版本复核。

草稿仅保存在身份绑定的页面内存。刷新列表及请求失败保留输入；离开或切换类型需确认放弃；替换文件或工作表需确认清除旧映射和核对结果。浏览器整页刷新/关闭由未提交提示保护，不承诺重启后恢复文件。同身份重登恢复草稿，其他身份清除。409 撤销旧核对，重新核对后才能发布；未改动内容的发布重试复用原 `requestId`。管理员只能准备核对，正式发布权限和事务内身份校验仍由后端执行。

## 当前身份与权限模型

### 手工导入与发布

分组侧栏提供组织架构、花名册、流程治理、数据治理、数据地图和主数据发布入口。治理活跃保留在工作台首屏；桑基图保留在“全量职责”；角色与责任、冲突管理继续使用原有接口和数据范围。

组织架构和花名册页面的“手工导入”，以及“主数据发布”中的三个导入入口，均接受.xlsx或UTF-8编码.csv。用户先选择文件和工作表，确认列对应关系，再查看原始内容、逐行变更和问题提示，最后明确确认发布。单次限制为5MB、5000行、64列。模板为空白Excel，文件中的额外列和值保留在发布快照中；公式须先转换为明确的值。

组织架构按组织编码更新部门和办公室，花名册按工号更新，沿用已有组织和人员标识。文件中未出现的目录记录继续保留。上级部门缺失、层级循环、部门无法匹配、同一标识重复或账号与在职状态冲突时，先修正再发布。导入不创建账号，不更改密码或MDM角色；管理员身份不能通过业务花名册改写。

组织表的“组织层级”填写“部门”或“办公室”。办公室行填写“归口部门编码”，通过“办公室负责人工号”明确负责人；负责人须为已导入的有效在职人员。首次建立目录时，可先导入部门、花名册，再导入带负责人的办公室。旧组织文件没有“组织层级”列时继续按部门处理。办公室复用`org_unit`，历史办公室保留原编号和上级关系；没有明确部门关系的历史记录显示“归口部门待明确”，不能承接新任务。

花名册的“办公室编码”可用分号分隔多个编码，例如`OFFICE_A;OFFICE_B`。人员所属部门与办公室成员关系分别保留，允许人员同时属于多个办公室。未对应办公室列时保留已有归属；明确对应该列后，空值表示移除该人员全部办公室归属，核对明细会显示变化。办公室成员关系不授予正式流程审核或发布权限。

“办公室工作台”对已登录人员提供入口，服务端按办公室负责人、成员关系或已有全局读取权限返回内容。具备`governance:assign-work`的人员将任务交办到有效办公室；只有该办公室负责人可以向当前有效成员分配或重新分配，只有当前办理人可以填写结果并办结。负责人无需另加MDM角色即可分配本办公室任务。管理员仍为只读。任务可关联已发布原生V8或受支持V7流程版本和具体业务行为，流程归口部门继续取自固定正式版本。办公室分配和办结不替代正式流程核对、审核及发布状态。

办公室任务复用`mdm_todos`，`mdm_todo_office_assignments`保存承接办公室、办理人、固定来源、请求标识及修订号，`office_membership`保存多办公室成员关系。分派、人员调整、办结与事件在同一事务保存；重复交办请求和过期修订返回409。旧部门待办保持未指定办公室状态，由治理分派人员明确选择原接收部门下的办公室；承接后，旧待办完成和删除接口拒绝处理。存在未办结任务时，不允许移除当前办理人的对应成员关系或改变办公室归口部门；办公室有有效成员或未办结任务时不能停用。

办公室结构使用`npm run migrate:offices:inspect -- --target host:port/database`检查，再用`migrate:offices:apply`增量准备。命令要求显式MySQL环境变量，只增加可空的`org_unit.department_id`、两个关系表及迁移记录，不推断或回填历史归属。执行前保存目标库备份并核对DDL；同名异构表拒绝执行，重复执行不改写数据。回退时保留新增关系和任务数据，使用含办公室权限保护的应用版本；已经使用办公室任务后，不能直接回到缺少该保护的旧版本，否则会恢复旧的部门办理权限。需要完全恢复时，在维护窗口按已核对备份恢复目标库及对应应用，不自动删除新增表。

主数据发布不限定对象类型，由用户选择唯一标识列。新数据集首次发布后，可以从发布记录“导入新版”；同一数据集沿用唯一标识列，每个版本保留完整内容。核对结果显示新版移除的记录数，历史版本仍可逐版查看、下载Excel或JSON。重复提交使用同一请求标识返回原发布记录；核对后内容或目标目录变化时返回409，要求重新核对。

发布沿用`governance:publish`及现有管理员只读边界。管理员可选择文件和核对内容；实际发布在事务中再次检查当前账号和权限，并记录发布人、时间、内容摘要和变更日志。既有流程审核和审批链路不变。

### 模板导入预览与确认

新前端 `/app/template-import` 提供选择文件、检查对象/字段/逐单元格来源、返回源文件修正、明确确认导入和重新查询结果。记录默认新建独立实体；如需修订已有记录，逐条选择“明确关联已有对象/字段的新修订”，填写已有台账的平台编号并核对名称和修订号，然后重新检查。关联字段必须属于该次明确关联的对象。文件编号如OBJ-001不用于平台身份匹配，同名和相同内容不自动覆盖已有台账。

新增同源API位于 `/api/master-data-template`：

模板导入无DDL、角色、权限项或正式审批链变更。复用定义版本七张增量表；未关联旧对象、旧字段、空归属字段及历史版本保持原样。显式修订保留原ID、key、既有上下文和历史版本；旧路径读写兼容，旧基础记录被其他入口改动时继续返回DEFINITION_LEGACY_SOURCE_CHANGED。定义版本物理source_kind仍使用定义版本的manual，表示用户明确保存；实际模板来源写在definition.source和来源表中，不冒充无来源手工事实。导入追加definition_saved事件，不追加事实核对或正式认定；主数据、权威来源、组合标识和治理结论不自动确认，也不创建正式流程工作包、问题或待办。

上传仅在内存解析，不保存原件文件副本；数据库保留可追溯原值。模板解析的5MB文件、ZIP解压及单元格限制继续生效，另校验台账名称/字段长度及64KB定义上限，拒绝截断。错误包络为 `{error,code,field_errors?}`，沿用DEFINITION_*及TEMPLATE_*，401为失效身份、403为无权、409为预览/版本/幂等/批次冲突、413为超限、503为迁移或依赖不可用。错误不返回SQL或堆栈。

### 对象与字段管理

`/app/objects` 提供对象清单、对象详情、字段明细、保存修订、版本回查及停用确认。模板导入回执可跳转到对应对象。对象信息按“对象是什么、从哪里来、谁维护、怎样使用、规则与待确认事项”分组；模板原始列值仍可从源单元格回查。来源补充与原模板定位分别保存，不改写原件或覆盖来源批次。维护部门、岗位、建议权威来源和待确认主体均是待核实说明，不因此改变组织归属、账号权限或治理结论。

新增对象归属当前有效部门，不由客户端选定其他部门。新增字段直接引用明确父对象的稳定ID和当前固定版本；服务端首次为该对象建立 `manual` 字段维护上下文，事务失败时一起回滚。修订旧字段保留其原上下文、父对象、稳定ID和历史版本。字段来源独立填写，必填支持待确认/必填/非必填；枚举NULL与空数组分别表示未知和明确无项。单字段标识与组合标识由用户明确选取字段固定版本；组合成员的顺序和组ID保持，不从名称或模板行序推断。

新增同源API前缀为 `/api/data-map-definitions`：

| 方法与路径 | 行为与门槛 |
|---|---|
| GET `/capabilities`、`/objects?search=&after=` | 返回当前编制资格、表单说明和授权对象清单；每页100条，next明确指向后续页 |
| GET `/detail/:type/:id?after=` | 当前定义及所属字段；字段按其原上下文范围过滤，每页100条。旧基础记录变化或缺定义版本时拒绝，不自动补快照 |
| GET `/history/:type/:id?before=`、`/version/:id`、`/source/:id` | 分页版本索引、不可变历史快照、来源批次和源单元格；仍由服务端验证读取范围 |
| POST `/save` | entity_type、definition补丁、request_id；修订另含entity_id和expected_revision；字段另含object_id和object_version_id。新增部门和上下文由服务端决定。嵌套补丁保留其他已知值和原始来源定位 |
| GET `/impact/:type/:id` | 返回当前修订、相关引用数量和impact_digest；不改变数据 |
| POST `/retire/:type/:id` | request_id、expected_revision、impact_digest、confirm=true及非空reason；锁定后重算影响，变化返回409，确认后追加版本和definition_saved审计事件 |

写入继续要求 `governance:draft-department`、有效身份、本部门范围、CSRF、状态和并发检查；admin即使兼具编制角色仍只读。可修订和停用的对象状态为draft/active，字段仅draft；已提交、确认或冲突字段沿用原办理流程。本页不授予正式确认、撤销审核或发布权限。错误包络沿用 `{error,code}`；新增DEFINITION_PARENT_INACTIVE、DEFINITION_PROPERTY_INVALID、DEFINITION_RETIRE_CONFIRM_REQUIRED、DEFINITION_IMPACT_CHANGED，其他错误复用既有DEFINITION_*。401/403/409/503分别表示身份、权限、冲突和依赖问题，不回传SQL或堆栈。

对象停用使用既有inactive，字段停用使用既有archived；不增加DDL或状态枚举。停用保留全部记录、审查事件、来源和固定引用，不级联改写字段；停用对象下禁止新增或修订字段，原有字段仍可查阅。影响清单覆盖现有字段、固定定义引用、标识组、系统关系、冲突、质量问题、来源映射和事实核对记录；后续新增引用模块时须同步扩展。无删除、重建或自动恢复入口。既有定义版本迁移和恢复边界保持，旧字段缺父对象等不能自动推断的记录继续保留原读取方式并等待明确处理。

输入仅保存在页面内存。保存失败、取消离开/刷新/切换/停用均保留输入；401后同身份重登可继续，身份或部门变化时隐藏旧输入。409不自动覆盖新版，用户先保留修改，再重新读取核对。请求UUID在未改内容的重试中复用；输入变化产生新UUID。版本选择和对象切换废止旧异步响应，不持久化表单或身份数据。运行 `npm.cmd run test:data-map-management -- --output <artifacts内全新目录>` 做隔离MySQL、真实API及Edge验证；正式开启、人工输入法体验及业务验收仍需独立完成。

### 流程正式流转独立前端

当前3000正式流转已于2026-10-19 17:38开启，原生V8与受支持V7沿用同一权限及部门卡口。每个部门有且只有一个最终负责人；管理员在“账号与授权办理”的“新增角色授权”中选择“部门负责人”，同时登记其本部门最终责任。尚未登记或有效授权不齐时不能最终确认，配置由用户在前端完成。运行、备份及验证以[Docker说明](../DOCKER.md)为准，模块开启不表示业务验收。

“主档已发布版本查阅”复用当前草稿详情中的版本列表，明确选择原生 V7/V8 的 published/superseded 固定版本后核对正文或下载 Markdown 程序文件。页面校验主档、版本标识、格式和摘要，读取失败清除旧结果，切换选择取消迟到下载。不会自动选择最新版本，也不修改未提交意见。列表刷新清除版本选择；整页刷新或返回后须重新读取并选择，避免把旧选择当作当前结果。历史版本不代表当前有效制度；此入口不覆盖跨草稿的完整审核历史，不恢复退役格式。后端 API、权限、状态、数据库及旧版本保持。

正式草稿区支持核对原生正文及下载 JSON，复用原 `/api/process-design/drafts/:id/content` 和 `/export`。读取结果必须与当前草稿的修订、摘要和 V7/V8 格式一致；导出内容还须与刚读取的正文一致，变化或失败时停止下载并提示重新核对。下载文件保留正文和稳定标识，是当前 JSON 的重新序列化，不是原始上传字节；草稿导出不表示审核通过或发布。正文读取与下载不应用、清空未提交意见，切换案例或身份后取消迟到响应。接口、权限、状态、数据库与旧记录不变。

`/app/process-formal?case=<案例ID>` 承接同一预览案例的正式提升、提交审核、需要修改/拒绝/通过及发布。使用原 `/api/process-v7-preview` 和 `/api/process-design` 接口，动作与结论来自后端允许集合。V8 与既有 V7 正文按实际版本保留，不改审批链、权限、数据范围、默认开关或数据库结构。原案例入口继续保留；切换正式访问入口仍须 编制协调 授权。

提升时明确选择新建主档，或按完整制度编号精确查找已有主档，再确认写入。审核不预选结论；每个动作固定案例、修订、摘要和审核任务。刷新保留输入，发现来源、任务或允许动作变化后阻断旧输入提交，由用户明确放弃并重新核对。同身份重新登录恢复内存输入，换身份清除；离页前提示未提交输入，没有浏览器存储或自动保存。

已发布来源通过原提升记录核对案例与版本；案例当前修订改变后，旧固定已发布来源仅供历史查阅，不允许新答复。原成功请求在当前有效编制身份下仍可按同键同内容核对，不制造新记录。原生V8及受支持V7按固定来源及实际版本办理；旧记录保留，不猜测转换、撤销或回填结论。来源是否可答复取决于当前案例修订、编制资格、关联范围及摘要，不由V7兼容名称决定。关联入口明确检查原编制、对象定义、V7映射、分析运行、问题、办公室及任务迁移标记；缺标记、所用表或字段时返回503，不由readiness代替，也不自动迁移。答复成功提示区分是否关联办公室任务。本增量无DDL、角色或正式审批变化，实际部署和启用前置见同批次 `authoring-issues-20261006-01/report.md`；本轮技术验证不表示实际运行已更新。

## 独立系统维护身份

用户确认admin不关联真实员工或部门，由本人使用独立admin维护登录和另一个mdm_lead治理登录。普通人员继续person→user_accounts→person_roles、一人一账号；旧人员admin及历史审计保留。新增system_admin_accounts/system_admin_events，不改写旧身份表，不新增固定角色或权限。MDM_SYSTEM_ADMIN_ENABLED默认关闭；打开时readiness检查增量表及迁移标记，应用启动不执行DDL。

显式入口：manage:system-admin使用--inspect/--dry-run/--apply及准确--target <host>:<port>/<database>，默认只检查；bootstrap:system-admin要求--apply、同一准确target、受控环境注入MDM_SYSTEM_ADMIN_PASSWORD（至少12字符）及MDM_SYSTEM_ADMIN_AUTHORIZATION_BASIS，不加载私有环境文件、不打印密码。先维护结构，再在已迁移目标显式初始化唯一admin。bootstrap不执行DDL、不创建person、不重复初始化或复制旧密码；已有人员登录名admin时拒绝冲突。

系统维护权限取既有固定admin角色当前有效权限，并限制在其原权限集合。账号维护操作在原事务中重查系统账号状态/auth_version，原人员审计保留且同事务追加系统账号操作者关联。首次改密、CSRF、旧会话撤销及治理写入拒绝仍强制执行；系统账号编号不能冒充person_id。首次登录改密由当前前端办理；新前端从统一/app/核对本人身份及密码状态，通过后进入账号与授权办理，身份页明确不关联员工/部门。

2026-10-08 编制协调只读接口补修：发布目录及数据治理状态接口沿用已认证的 `system-admin:<account_id>` 类型化主体查询既有权限，不再将该主体转换为人员编号。独立系统管理员可按原有权限查阅发布记录和功能状态，仍不关联人员或部门，不能发布或办理数据治理写操作。普通人员沿原人员编号和数据范围校验；接口、角色、权限集合、开关、结构及旧记录均不变。V7预览关闭时 `/api/process-v7-preview/cases` 继续返回 `503/V7_PREVIEW_DISABLED`，不表示登录或MySQL整体不可用，也不因本修复开启。验证使用 `test:system-admin` 的隔离系统／人员／无权／匿名身份及写入拒绝路径；实际部署状态以同批次执行记录为准。

## 工作台与问题卡维护约束

- 登录后默认第一屏为 `roleWorkbench`。顶部显示当前身份、当前部门和今天优先处理事项数；“待办优先”视图的第一块是“我现在该做什么”，只列 1 至 3 个下一步动作。“全量职责”才展示完整职责链路。
- 多角色用户合并展示为“我的工作台”，事项和角色卡片必须标明来源角色。每个角色的使用说明包含角色目标、第一步入口、典型样例、常见误区和完成标准。
- 角色职责图的层级固定为“角色 → 业务能力 → L3流程 → A1业务行为 → 处理入口”。用户点击节点后，页面显示对应事项、样例解释和可执行入口。
- `/api/org/me` 返回人员、账号、部门、全部有效 MDM 工作角色、权限、数据范围和治理模型版本。`GET /api/role-workbench?mode=todo|all` 返回角色、工作流步骤、职责图数据、待办、样例说明和跳转目标。
- 流程治理问题卡面向业务人员，只说明用户能执行的动作。“在哪发现”优先定位用户指定的制度或表单原始文件、段落、页码或表格位置；暂时只能定位到流程治理输入基线时，必须标明尚未定位原文证据。
- 问题卡的处理方式只允许“修改用户指定的制度或表单原始文件后重新导入”或“说明这条核验项不是问题”。“问题原因”只在用户选择不是问题时出现；“当前问题卡缺少来源证据”和“制度或表单原文没写清”不得混写。处理历史必须显示用户名和时间戳，打开卡片时不得预设审核意见标签。

## 导出规模、连接中断与站点安全策略

字段台账导出设有行数上限（`MDM_EXPORT_MAX_ROWS`，默认20000）、并发上限（`MDM_EXPORT_MAX_CONCURRENCY`，默认2）及时间上限（`MDM_EXPORT_TIMEOUT_MS`，默认60000毫秒），数据库连接同时受操作预算约束。取完整字段值前按可见范围检查行数并限制SQL结果；超行数返回413，并发超出返回503 `EXPORT_BUSY`，不排队。两个工作表流式生成，保留字段说明、已保存的黄金源及维护部门投影。客户端中断或超时取消读取及压缩生成；若响应已开始，失败以连接终止表示，不再改发JSON。超限不会提供截断台账，下载范围和原输入保护方式保持。

当前候选源码的内容安全策略由 `server/cspPolicy.js` 集中定义，为 `script-src 'self' 'sha256-…'`：保留页唯一的内联脚本块按**哈希**放行，其他内联脚本一律阻断；该页原有的 116 处内联事件处理器属性已改为 `data-click`/`data-change`/`data-input` 声明和委托监听器，处理器白名单见 `PAGE_ACTIONS`。`script-src` 不包含 `unsafe-inline`。哈希按浏览器解析后的脚本文本计算，CRLF 和独立 CR 先归一为 LF，因此仅换行编码差异不要求改动哈希；其他字符或空白变化仍须同步更新。`node scripts/test-csp-policy-contract.js` 与 `node scripts/audit-inline-script-inventory.js --require-clean` 检查唯一脚本哈希、缺失或额外脚本及内联事件处理器；事件属性使用双引号、单引号或无引号时均会被拒绝。`style-src` 保持不变。实际部署策略按目标响应核对；桌面 Edge、100%、1699×828 仍是唯一支持环境。
