# MDM平台 RBAC 与 RACI 迁移手册

## 1. 适用范围

当前代码模型为`rbac-raci-v5-2026-10-19`，包含九个固定角色、二十二项权限和十三项RACI说明活动。系统组一个、MDM组七个、目录维护组一个；技术清单见[权限与RACI说明](Permission-RACI.md)，已确认业务分工见[角色交接](../ROLE_HANDOFFS.md)。部署记录与实时目标状态分别核对，本文不证明已经迁移、开启或业务验收。

本手册区分旧身份基线转换与已有固定模型的增量升级。`migrate:rbac-raci-v2:*`、脚本名和迁移表名保留兼容含义，名称中的v2不能说明目标模型版本。不得在已有v3/v4/v5目标上重放会停用旧账号、撤销授权的基线转换，以此代替当前升级。

## 2. 先确定目标和恢复条件

实施前核对以下事项；缺少对应条件时只完成可审查的本地准备：

1. 明确目标服务器、端口、库名及当前模型、迁移标记和已用功能，不从文档中的历史端口、库名或管理员工号推定目标。
2. 取得该目标的只读检查、结构变更、停写及运行操作授权；这些授权分别核对，不因脚本存在而推定齐备。
3. 对需要写入的维护，完成当次停写、完整备份和独立实际恢复，并核对当前新增数据、结构及授权的保留方式。
4. 使用独立维护身份安全注入显式`MYSQL_*`变量，并传入匹配的`--target host:port/database`。只检查私有配置是否存在及由哪个入口使用，不输出Secret或把密码写入命令。
5. 按应用`package.json`、下表及[脚本说明](../scripts/README.md)选择准确入口；检查源码、参数和副作用后执行，先inspect，不能用运行请求或`init:mysql`修复在用库。

## 3. 已有固定模型的增量升级

| 目标当前状态 | 维护入口与处理顺序 | 数据保留及核对 |
|---|---|---|
| v3目标 | 先用`migrate:governance-responsibilities:inspect`核对，获准后由对应`:apply`准备v4；再按下行准备v5 | 保留原角色ID、人员授权、正文和历史，不自动任命治理经办人或流程负责人 |
| v4目标 | 使用`migrate:hr-directory-role:inspect`或`:dry-run`核对，获准后由`:apply`准备v5 | 显式扩展目录分组约束、角色、权限及迁移记录，不自动给人授权，不新建并行人员源 |
| 需要部门负责人本人确认策略的目标 | 在具备相应v4前提后，用`migrate:department-accountability:inspect`核对，再按授权选择`:apply` | 保留`department_mdm_reviewer`机器标识及旧决定；本人实际确认仍须组织最终负责人登记和本部门有效授权，不设置中间审核员 |
| 已为v5的目标 | 核对同版代码、迁移标记、角色、权限及实际授权，保留正常使用后的增量 | 不重新执行基线转换、批量撤权或停用账号，不重放已完成部署 |
| 模型未知、部分结构或存在漂移 | 先盘点并报告准确差异 | 不猜测模型、不补默认值、不据历史脚本直接apply |

上表命令在应用目录使用，具体参数和恢复限制见[治理职责迁移](../scripts/README.md#治理职责迁移与专项验证)及[组织与员工目录专项](../scripts/README.md#组织与员工目录专项)。代码与模型迁移须同版切换；只换v5代码会因严格模型匹配拒绝旧角色权限。运行请求不执行DDL。

部门负责人角色授权与组织最终责任登记的专用办理见[当前接口合同](RBAC-RACI-API-Contract.md#post-apiorgaccountspersonidrole-assignments)及[技术规格](../Tech-Spec.md#6-写入事务)。任命或换人须明确核对当前登记和交接，不从历史角色自动补任命。

## 4. 迁移后的核对

按当次目标记录核对，不沿用旧批次的七角色、十九权限或十一项RACI数量：

- 模型为预期版本，v5技术模型返回九角色、二十二权限、十三项RACI说明活动；角色分组和固定权限准确。
- 迁移前后已有人员、账号、角色ID及授权保持，允许变化仅限当次批准的模型和结构范围；审计、迁移备份及标记可定位。
- 人事维护角色拥有目录维护权限，管理员对组织与员工资料只读；没有自动开户、给人授权或改变真实任命。
- 部门负责人须本人符合组织登记和有效同部门授权；主对接人提交，明确编制者保存，不代确认或发布。
- 同版就绪检查、旧数据兼容、最小运行权限和恢复验证具备对应证据。静态或隔离检查不能替代实时就绪与业务验收。

只有另有运行授权时才使用[Docker说明](../DOCKER.md#当前恢复入口)中的准确目标和维护入口。应用目录的`service:start`、`service:check`只管理自有Windows副本，不管理Docker；单一MDM任务不得使用会同时操作PMO的共同启动脚本。

## 5. 补偿与失败处理

职责迁移及人事角色迁移使用各自`:compensate`入口，先inspect并核对脚本规定的新增授权、办理历史和补偿顺序。有新角色授权或新办理记录时，不得把空表补偿当作在用系统通用回滚；需要保留当前增量的专门恢复方案。部门确认策略如需补偿，先核对有无新策略办理记录及与职责模型的依赖。

提交结果不明时先核对当次迁移标记、原请求和实际结构，不盲目重放apply。结构部分完成、事务失败或恢复未成功时保留当前记录，准确报告未完成项。不得恢复旧dump覆盖后续增量，也不得直接重启旧写版本替代当前服务。

## 6. 旧身份转换与空库初始化

旧`migrate:rbac-raci-v2:dry-run/apply/rollback/compensate`入口仍保留用于明确的历史兼容任务。整理前手册中的`ADMIN001`、历史连接参数、七角色数量、批量停用及撤权步骤仅描述旧基线批次，不能作为现行升级指令。真正的历史转换仍须按准确脚本版本、目标、授权、批次备份和恢复条件制定执行方案。

空库初始化不与已有库升级混用。`bootstrap:admin`和独立系统维护身份的用途按[身份与事务合同](Identity-Transaction-Contract.md)及当前脚本核对；已有人员或账号的目标不得当作空库重建。初始密码通过既有受控渠道交付，不读取、输出或保存至文档。
