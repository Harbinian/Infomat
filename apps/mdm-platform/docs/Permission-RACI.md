# MDM平台 权限与 RACI 说明

## 1. 固定模型

当前代码模型版本为`rbac-raci-v5-2026-10-19`，共九个固定角色、二十二项权限、十三项RACI说明活动。九角色包括系统组一个、MDM组七个、目录维护组一个；七个MDM角色不等于全模型角色总数。技术模型由`server/roleDefinitions.js`维护，管理页面只读；业务分工依据用户明确确认，见[角色分工与办理交接](../ROLE_HANDOFFS.md)。目标部署、功能开启与业务验收分别核对，不因代码存在而认定生效。

MDM工作角色只用于MDM平台治理授权，不等同于：

- `person`人员身份；
- 人员岗位；
- 正式流程工作角色`WR-*`；
- 制度或源文件中的原文角色称谓。

## 2. 权限清单

### 2.1 身份管理

| 权限码 | 含义 |
|---|---|
| `identity:read` | 查看账号、角色和责任配置 |
| `identity:manage-account` | 创建、启用、停用和维护账号 |
| `identity:assign-role` | 授予和撤销MDM工作角色 |
| `identity:read-audit` | 查看账号和授权审计记录 |

### 2.1.1 组织与员工目录

| 权限码 | 含义 |
|---|---|
| `directory:read` | 读取MDM平台统一组织与人员基础目录 |
| `directory:maintain` | 维护组织架构与员工资料，保存直接生效并记录前后内容、操作人和原因 |

目录维护由行政人事信息维护员办理；管理员为已有员工开户及授权，不取得通用目录编辑权。字段及历史读取范围见[目录接口](../DIRECTORY_API.md)。

### 2.2 治理读取

| 权限码 | 含义 |
|---|---|
| `governance:read-global` | 查看全公司治理材料 |
| `governance:read-department` | 查看本部门治理材料 |
| `governance:read-assigned-context` | 查看本人被分派事项及必要上下文 |
| `governance:read-escalated-context` | 查看已升级重大争议及必要上下文 |

### 2.3 部门治理

| 权限码 | 含义 |
|---|---|
| `governance:draft-department` | 起草和修改本部门治理材料 |
| `governance:submit-department` | 提交本部门治理材料 |
| `governance:review-department` | 审核和退回本部门治理材料 |
| `governance:record-department-decision` | 由部门负责人本人作出并记录本部门最终确认 |

### 2.4 全局治理

| 权限码 | 含义 |
|---|---|
| `governance:assign-work` | 分派治理事项 |
| `governance:handle-assigned-work` | 办理本人被明确分派的治理事项，不含审核发布 |
| `governance:structure-gate` | 检查结构、证据和责任链 |
| `governance:publish` | 发布流程地图、数据地图和术语治理版本 |

### 2.5 质量与冲突

| 权限码 | 含义 |
|---|---|
| `governance:quality-audit` | 登记数据质量发现及整改要求，复核整改并退回或关闭 |
| `governance:handle-assigned-conflict` | 处理本人被分派的数据或术语冲突 |
| `governance:escalate-conflict` | 提请升级治理争议 |
| `governance:decide-escalation` | 决定已升级的重大争议 |

## 3. 角色权限矩阵

| 角色 | 读取范围 | 写入权限 |
|---|---|---|
| `admin` | 全局治理只读；身份全局 | `identity:manage-account`、`identity:assign-role`；无业务写权限 |
| `mdm_lead` | 全局治理 | 分派、结构卡口、发布、升级 |
| `mdm_steward` | 本人被明确分派的案例或工作包 | 整理治理材料和依据；不代确认、不审核发布 |
| `department_contact` | 本部门 | 起草、修改、提交 |
| `department_mdm_reviewer` | 本部门 | 已登记且有本部门有效授权的负责人本人核对、退回及最终确认；不设中间审核员 |
| `data_conflict_handler` | 本人被分派事项 | 处理被分派冲突、提请升级 |
| `data_quality_auditor` | 全局数据治理 | 审计发现和整改要求 |
| `decision_group` | 已升级事项 | 决定已升级重大争议 |
| `hr_directory_manager` | 全公司组织与员工目录 | 目录维护及有原因的保存；无账号授权或治理发布权 |

禁止使用`*:*`。固定角色不得继承自定义角色，也不提供自定义权限矩阵。

## 3.1 角色可见标签

- `/api/rbac/model`为每个角色返回`visibleTabs`，包括标签代码、名称、访问方式和权限依据。
- 顶部标签按当前用户全部有效角色取并集；账号创建、编辑和角色授权页面显示相同的并集预览。
- “角色可见标签”只读，不提供按角色或按账号自定义。
- 标签可见性只减少无关入口，不能替代服务端权限、部门范围、事项参与关系和状态校验。

## 4. RACI

R表示执行，A表示对该项结果负责，C表示征询或协作，I表示知悉。已确认的业务矩阵及保障活动统一见[角色分工与办理交接的RACI](../ROLE_HANDOFFS.md#raci)，本说明不另建一份不同的职责矩阵。

接口返回的十三项活动是固定模型的技术说明项，不能用活动数量推断新增审批链、人员任命或授权。主对接人提交、部门负责人本人确认；明确编制者可以保存草稿，但不代主对接人提交。治理经办只办有效分派事项；质量审计人对审计及复核结论负责；重大争议由项目决策组作决定，相关部门仍分别重新核对。C/I关系不自动开放数据或发送通知。

## 5. 责任证据

- 部门最终负责人只从`departments.final_responsible_person_id`读取。
- 系统不得按姓名、岗位、职务或旧名单补齐责任人。
- 部门最终负责人登记可以先于开户；本人实际办理确认时，须同时具备有效账号、本部门有效角色授权及组织最终负责人登记。
- `department_mdm_reviewer`保留兼容标识，中文职责为部门负责人本人核对和最终确认，不另设中间审核员或代记录人。
- 跨部门事项必须逐部门记录决定。
- 3001上传文件中的审核状态、审核人和批准人信息不构成决定证据。
- `admin`不能确认导入、补充承接、记录部门决定或执行结构卡口。
- 承接动作除角色权限外，还必须校验事项参与人、所属部门、`can_act`、当前修订、对象状态和事项关联。
- 部门主对接人只能补充本部门实际内容；部门负责人只能本人记录本部门决定；MDM工作组组长不能代替业务部门确认。
- 承接决定的最终责任人只从当前`departments.final_responsible_person_id`读取。
- 决定记录只追加，不覆盖。
- 责任人缺失或必需部门尚未确认时，记录决定或发布返回`RESPONSIBILITY_CHAIN_INCOMPLETE`。

## 6. 按钮不可用原因

前端应展示服务端可以核对的具体原因，包括：

- 账号未启用、已锁定或已停用；
- 首次登录尚未修改密码；
- 缺少有效角色、授权依据或生效日期；
- 当前角色没有该权限；
- 当前数据不在本部门、被分派事项或已升级事项范围内；
- 当前对象状态不允许该动作；
- 当前用户不是任务处理人或本部门审核员；
- 部门最终负责人或必需部门决定不完整；
- 阻断问题、结构检查或版本检查未通过。

“没有管理员权限”不能作为业务按钮的统一提示，因为管理员本身也没有业务写权限。
