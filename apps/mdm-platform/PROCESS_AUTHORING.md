# 3000内流程编制实施合同

2026-10-21已按用户部署授权在3000开启流程编制、保存及续修入口；正式目标新增三张草稿表，当前运行与恢复证据见[Docker说明](DOCKER.md)。本轮未停止3001，既有无状态编制和人工JSON交接仍可使用。业务分工依据用户明确确认；软件部署、隔离技术验证与业务验收分别记录，本轮未代替真实业务办理或业务验收。

## 使用与职责

`/app/process-authoring`复用已有流程图、表格、数据对象、表单和生命周期编制能力。新建流程由本部门当前有效主对接人建立编制草稿；既有案例可按当前来源另存续修。已有明确编制归属时仅当前编制者保存，主对接人独立提交；旧案例未建立编制归属时保留现有主对接人路径。部门核对、负责人确认、MDM办理和发布权限不因新增编辑入口扩大，管理员保持只读。

保存仅将草稿及所填材料存入3000；业务缺项允许保留，结构错误和失效引用须修正。主对接人可在不修改已保存正文的前提下，明确填写并随提交发送本次材料；提交把已保存正文及本次材料加入新案例或原案例，形成不可变预览修订，再按原链办理。已提交、审核中、已通过或已拒绝的正式草稿继续受原撤回/退回卡口约束；新增编制草稿不能绕过恢复。已发布版本及旧意见不改写。

上传、下载JSON草稿用于用户主动带到Governance-Knowledge知识库AI对话中编辑后再导入；平台不自动调用外部AI，也不向第三方发送业务材料。导入先检查并显示兼容结果，失败时保住当前草稿和输入，不修改源文件。下载只导出正文，不应用未确认输入、不构成审核凭证，也不代表已保存到服务器。相同流程续修保留流程与材料包稳定标识；其他流程另建草稿。

部门提示来自3000当前有效目录；当前未提供完整岗位目录时由用户显式填写业务岗位并核对，不据字符串推断人员任命或权限，不以旧目录快照清空或替换历史值。

### 重新提交后的展示与追溯

重新提交成功后，编制页根据回执提示当前办理结果，并提供进入原案例的入口。案例当前修订及其选中列表项结合核对项、原意见时间和对应参与方的决定事件，区分“已提交，待负责人重新核对”与“当前修订需要修改”。列表其他行、部门全貌或时间与事件证据不足时，使用中性说明，不仅凭`needs_revision`机器状态把已提交的新修订写成“仍待上传”，也不把本次新提出的修改要求误写成待重新核对。正文未变、未形成新修订等成功回执提示进入案例查看当前状态，不据修订号推断下一步。

工作台的退回办理卡片另按当前身份读取对应案例详情，仅在案例、修订和摘要一致且能确定等待重新核对时，提示“已提交，查看负责人重新核对进度”。读取失败、来源变化或仍需修改时提示进入案例查看当前意见；不继续要求用户重复上传。该读取不增加权限，切换身份或工作台视图时取消旧读取。仅替换系统生成的操作说明，原退回依据及其他事项保持原样。工作台和角色使用页在编制能力开启时，同步展示3000编制、保存与原案例续修步骤；不改变角色、权限或RACI模型。

旧意见、机器状态及其绑定的修订、内容摘要、办理人和依据继续保留。重新提交不自动把“需要修改”改为“已确认”，也不解除仍然有效的核对卡口；页面区分当前待办与历史意见，不回填或改写旧数据。历史争议决定的`return_for_revision`枚举保持原值，其中文续修说明随编制能力启用状态展示，不替换原决定依据。编制能力已开启时，提示在3000从原案例续修，保存并提交新修订后重新核对；未开启时，仅提示完成修订后上传原案例。

## 前后端合同

前端React源码在`frontend/`，后端Express源码在`server/`。前端只通过同源API访问，不导入服务端实现、不直连MySQL。开发前端继续使用`frontend/devBoundary.js`限定的回环候选后端及代理，不能指向3000/3001正式端口。编制器与领域代码在构建和服务进程内复用，不请求3001服务。模板和技术校验由纯模块`scripts/process-governance/authoring-contracts.js`提供，Ajv由各调用方注入，不依赖另一个HTTP应用的初始化。

后端前缀`/api/process-authoring`，需要有效登录和CSRF：

| 方法与路径 | 用途 |
|---|---|
| `GET /status` | 独立功能开关、结构准备情况、支持格式 |
| `GET /drafts` | 当前授权范围内的草稿列表和新建资格 |
| `POST /drafts` | 提供`document`、可选`submission`及UUID `request_id`建立草稿 |
| `POST /drafts/from-case/:caseId` | 按`expected_revision_no`和`expected_content_hash`固定案例当前来源另存续修 |
| `GET /drafts/:id` | 草稿正文、保存版本、来源绑定及`allowed_actions` |
| `PUT /drafts/:id` | 提供正文、保存版本与摘要、UUID请求标识，显式保存 |
| `POST /drafts/:id/submit` | 提供保存版本与摘要、UUID请求标识、当前提交材料，提交已保存正文 |
| `GET /editor/template`、`GET /editor/schema` | 空白模板和按`version`读取技术契约 |
| `GET /editor/enums` | 有效部门及岗位信息可用状态，不返回人员隐私 |
| `POST /editor/validate` | `{data, validation_profile?}`只读检查，不保存或确认 |
| `GET /assets/:file` | 明确白名单中的本地编制资源，未知文件返回404 |

草稿响应为`{draft,allowed_actions}`；`draft`含`id`、`document`、`submission`、`revision_no`、`content_hash`、`case_id`和固定来源修订及摘要。提交另返回`case_detail`。创建、保存和提交的UUID请求标识绑定人员与完整请求；同标识重试返回同一回执，不重复形成修订。409来源/修订冲突保留输入，401/403失去资格时拒绝写入，422结构或引用无效时拒绝替换，503功能或结构未就绪时保持关闭。

编制专用HTTP请求上限10MB，正文保存上限8MB，提交附属材料上限128KB；超限明确拒绝，不截断。草稿内容不写浏览器业务存储；未应用、已应用未保存、服务器已保存和已下载分别判断。保存回执到达期间新产生的编辑不能被误标已保存。

## 结构与兼容

默认关闭`PROCESS_AUTHORING_WORKSPACE_ENABLED`，显式设为`1`才开放入口；当前3000已开启，开发及测试目标仍须按各自实际配置判断。`process_authoring_drafts`为可编辑头，`process_authoring_revisions`只追加保存/提交快照，`process_authoring_requests`保存幂等回执。结构准备由`server/processAuthoringWorkspaceSchema.js`显式执行；运行启动和业务请求不执行DDL，不清空、迁移或回填既有流程。

V9、V8、V7正文按原生格式保存，不降级或重写已有正式摘要。编辑器沿用受支持早期文件的校验、内存迁移和历史归档，兼容导入后的当前正文须通过保存合同；失败不安装内容。现有已提交案例、正式草稿、核对历史和下游固定版本不自动改成编制草稿，由用户有权主动续修。保存不触发真实通知、后续工作包或正式发布。

## 隔离验证与候选检查

在应用目录运行`npm run test:process-authoring-editor`检查纯编辑合同；`npm run test:process-authoring-mysql -- --output <artifacts内全新目录>`使用自有临时MySQL与合成账号验证保存、提交及原治理链。运行前核对对应脚本及参数，不传私有配置。

在`frontend/`执行`npm test`。候选构建使用`npm run build -- --outDir <artifacts内构建目录>`，不覆盖其他候选产物。真实Edge浏览器验证使用`node scripts/test-process-authoring-browser.js --frontend-dist <artifacts构建目录> --output <全新证据目录>`；仅Edge100%、1699×828桌面，自动化不等于人工IME或业务验收。

供用户检查候选：`node scripts/serve-process-authoring-candidate.js --frontend-dist <artifacts构建目录> --output <全新候选目录> --serve`。该命令只创建带所有权标签的临时MySQL与随机回环HTTP，输出合成登录入口，关闭时只清理自己创建的容器。合成候选数据是临时的，重要试编成果先下载JSON；不能用作正式治理记录。

## 正式切换条件

正式结构通过`node scripts/manage-process-authoring-schema.js`专用维护入口盘点和准备，绑定准确数据库、服务器UUID、受控代次、实际停写、全库备份及成功独立恢复凭证。入口仅创建缺失的三张编制表和迁移标记；原结构、历史内容、职责和`controlled`代次保持。使用参数、幂等及部分创建后的重新盘点见[脚本说明](scripts/README.md#已受控目标的编制草稿结构准备)。

本次3000发布从原正式镜像提取v4基线，排除工作树中无关的人事和全局界面改动；先关闭编制入口启动并核验，再开启`PROCESS_AUTHORING_WORKSPACE_ENABLED=1`。旧`PROCESS_V7_AUTHORING_ENABLED=0`保持，未建立新编制分派或迁移人员角色。专属V9编制资源在3000镜像内使用独立目录，旧编辑入口的V7/V8共享资源保留。受限权限HTTP链和Edge合成操作覆盖保存、JSON往返、退回重提及原审核发布；正式目标本轮未新增合成流程、核对或发布记录，仍需由实际有权人员办理及验收。

3001停用是独立操作，不删除源码、JSON或历史证据。当前编制开关同时关闭草稿读写，并非只读维护开关。回退前须在受控维护窗口暂停办理、导出或备份新增草稿及回执，并验证读取恢复；关闭开关后用户暂时不能通过新入口读取草稿。新增表和记录继续保留，不得回滚数据库备份覆盖切换后的新保存或新审核记录。旧应用是否能安全读取新结构须在隔离环境验证后决定，不能将停止服务等同恢复。
