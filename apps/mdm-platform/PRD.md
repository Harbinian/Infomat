# MDM流程治理统一入口、身份与责任产品需求

## 1. 文档状态

- 产品：Infomat 3000
- 版本：`rbac-raci-v3-2026-07-31`＋正式编制`process-governance-v3`＋V7预览核对＋原生V7正式基础
- 状态：正式M1/M2结构已准备且当前只读检查一致；历史事后演练不替代本次代码的隔离验收。本轮未启动3000，未开启V7开关，也未配置试点`process_ref`；新的全库备份恢复、隔离MySQL验收和真实业务试点待分别批准
- 适用范围：流程编制、跨部门承接、承接冲突、V7预览核对、人员身份、账号生命周期、MDM工作角色、权限、责任记录、访问审计和3001格式适配

## 2. 业务目标

3000改为内部治理平台，不再向全员开放。普通账号只能由MDM系统管理员手工创建、授权和启用。

本次重构解决七个问题：

1. 账号来源不受控，历史接口和脚本可以绕过管理员开户。
2. 旧角色同时混用系统权限、项目职责和业务责任，管理员可以绕过业务责任链。
3. 部门决定缺少可追溯记录，系统无法证明谁最终负责。
4. 身份数据存在`person`、`user_accounts`、`person_roles`与旧`users/user_roles`并行读取的问题。
5. 流程治理入口分散，用户无法从一个页面完成编制、承接和冲突处理。
6. 承接待办曾通过“待确认问题”形成第二份业务事实，状态和责任容易不一致。
7. 用户只能看到抽象角色说明，不能判断当前流程走到哪里、下一步由谁处理。
8. V7在3001中保持无状态，线下跨部门核对的处理人、进度和结果无法持续回传和追踪。

## 3. 范围

本期包括：

- 固定七个MDM工作角色和十九项权限。
- 管理员手工开户、启用、恢复、停用、密码重置、部门变更、角色授予和撤销。
- 账号与授权操作审计。
- 部门决定记录和发布责任核验。
- 流程、数据、术语、冲突、字段和工作台接口的统一权限判断。
- 旧身份数据盘点、备份、迁移、回滚和补偿。
- 只读“角色与责任”页面。
- 账号与授权下只读“角色可见标签”页面，以及多角色标签并集预览。
- 流程治理唯一顶部入口及“流程编制、跨部门承接待办、承接冲突待办、V7预览核对”四个工作区。
- MySQL完整流程JSON草稿、修订号、内容哈希、并发冲突和v2导出。
- 兼容v1/v2的3001预览、审核导入、内容哈希和幂等修订。
- 前置输入与后续承接的统一对象、直接承接待办、故事链、双方决定、结构卡口和发布阻断。
- 承接冲突的分派、协调方案、双方确认、项目决策和只追加事件。
- V7预览案例、逐次修订、双方部门核对结果、依据、进度和只追加操作记录。

本期不包括：

- 重做流程地图、数据地图和术语治理的其他业务数据模型。
- 自定义角色、自定义权限包或页面编辑RACI。
- 根据姓名、岗位、职务或历史常量推测部门负责人。
- 修改`docs/norms/`、PMO页面或组织真源。
- 把正式流程工作角色`WR-*`、岗位或人员身份当作MDM工作角色。
- 停止或代管3001。3001继续作为无状态单流程编制工具独立运行。
- 按角色或账号自定义菜单；可见标签只由固定模型计算。
- 把V7转换成V3；绕过预览核对、人工主档选择、审核或正式功能开关直接发布V7。

## 4. 用户与职责

| 角色 | 主要工作 | 禁止事项 |
|---|---|---|
| MDM系统管理员 | 管理账号、MDM工作角色和访问审计；全局只读 | 修改、审核、确认或发布业务内容 |
| MDM工作组组长 | 分派事项、检查结构和责任证据、发布治理版本 | 代替部门确认业务事实 |
| 部门主对接人 | 起草、修改、提交和整改本部门材料 | 部门审核和全局发布 |
| 部门MDM审核员 | 审核本部门材料，记录部门负责人线下决定 | 代替部门负责人作决定 |
| 数据冲突处理人 | 处理本人被分派的冲突并提请升级 | 查看或处理未分派事项 |
| 数据质量审计人 | 全局读取数据治理信息，记录审计发现和整改要求 | 修改部门源数据或发布版本 |
| 项目决策组 | 决定已经升级的重大跨部门争议 | 日常编辑、部门审核、发布和账号管理 |

## 5. 核心业务规则

### 5.1 身份与账号

- 唯一运行时身份链路为`person -> user_accounts -> person_roles`。
- 未登录用户只能看到登录页。
- 不提供自助注册、批量开户或RBAC导入入口。
- 新账号初始状态为`pending_activation`，不能登录。
- 管理员启用账号时生成一次性临时密码；密码只在该次响应中显示。
- 首次登录只能修改密码或退出。
- 账号状态为`active`且人员状态有效时，系统才继续计算角色和权限。
- 账号、部门或角色变化时递增`auth_version`，旧会话从下一次请求起失效。

### 5.2 角色授权

- 角色清单、权限包和RACI由版本化固定模型维护，页面只读。
- 每项角色授权必须填写授权依据和生效日期；失效日期可为空，但授权仍必须保留有效期语义。
- `department_contact`和`department_mdm_reviewer`只能授权到人员所属部门。
- 人员变更部门时必须填写原因并同时提交新部门角色安排；旧部门角色自动撤销。
- 撤销角色必须填写原因。
- 撤销最后一个有效角色时，管理员必须同时停用账号。
- 不得停用最后一个有效管理员，也不得撤销其管理员角色。

### 5.3 最终授权

业务写操作必须同时满足：

1. 人员和账号有效。
2. 会话`authVersion`与当前账号一致。
3. 角色处于固定模型的有效状态。
4. 角色授权处于有效期内并有授权依据。
5. 用户拥有所需权限。
6. 数据在该用户的部门、被分派事项或已升级事项范围内。
7. 当前对象状态允许该动作。
8. 当前用户与任务、部门或争议存在要求的责任关系。
9. 需要部门决定或发布时，责任证据完整。

RBAC只决定用户最多可以做什么；RACI和对象状态决定当前事项是否轮到该用户处理。

### 5.4 部门决定与发布

- 部门最终负责人以`departments.final_responsible_person_id`为准，可以没有3000账号。
- 部门MDM审核员只能记录本人所属部门的决定。
- 记录内容包括治理领域、对象、版本、部门、系统确认的最终负责人、记录人、决定、依据、可选证据引用和决定时间。
- 决定值固定为`approved`、`returned`、`rejected`。
- 新记录只追加；替代旧决定时保留被替代记录。
- 跨部门事项按部门分别记录决定。
- 责任人缺失或必需部门决定不完整时返回`RESPONSIBILITY_CHAIN_INCOMPLETE`。
- 发布前必须同时满足：所需部门决定完整、阻断问题关闭、结构检查通过、版本检查通过。

### 5.5 3001受控导入

- 预览接口兼容v1/v2并在服务端重新校验，只返回摘要、承接候选、治理提示和内容哈希，不写数据库。
- 审核导入只允许归口部门`department_mdm_reviewer`执行。系统重新接收原始数据、预览哈希和审核依据，并再次校验版本、内容和部门范围。
- 上传文件中的`approved`、`status`、审核人和批准人信息不作为审核凭证。
- 审核导入在一个MySQL事务中写入流程草稿、承接修订、参与关系、事件和导入审计，失败时全部回滚；不再新建“待确认问题”承接投影。
- 幂等键为流程稳定标识和规范化内容哈希。相同版本返回既有对象；内容变化新增修订并重新审核，不覆盖历史决定。
- 3001继续独立运行。MDM不远程读取3001服务，只接收用户选择的v1、v2、v3文件；服务端统一规范化、保存和导出`process-governance-v3`。
- MDM本地流程编辑器与3001使用同一套纸质表单字段录入方式。用户选择现状表单或拟设计表单，逐字段确认主表或具体明细表归属；MDM不得按字段名称、数据类型、表单编号或明细数量推断。
- v1、v2表单进入MDM时，服务端只补`form_design_state=unspecified`。历史字段、主明细分组、标题、顺序和技术标识原样保留；无法无损规范化时停止保存或迁移并返回具体字段位置。

### 5.6 跨部门承接闭环

- 前置输入与后续承接使用统一承接对象。责任部门未知时进入`pending_assignment`，由MDM工作组组长分派。
- 归口部门先审核候选关系；外部门再确认范围、补充本部门流程和行为、记录本部门决定；MDM工作组组长最后检查结构和双方责任证据。
- 部门主对接人只能补充本部门实际承接内容；部门MDM审核员不能代替另一部门作决定；MDM工作组组长不能代替业务部门确认。
- 操作必须同时满足有效角色、参与人记录、部门范围、`can_act`、对象状态和事项关联。
- 决定的最终责任人只从当前`departments.final_responsible_person_id`读取。
- 承接待办直接按承接状态、当前角色、部门和参与关系生成，不再通过“待确认问题”保存或投影第二份业务事实。
- 承接详情显示固定故事链：责任部门分派（需要时）→归口部门审核→外部门确认范围→外部门补充实际承接内容→外部门审核→MDM结构卡口→确认完成。
- 故事链显示已完成步骤、当前步骤、下一责任角色、处理人、部门、时间、依据及退回或冲突分支，不使用百分比推测进度。
- 存在当前承接未确认或未按决定关闭时，流程不得发布。

### 5.7 V7预览核对

- V7由用户主动上传，不由3000远程读取3001。上传正文上限为2MB。
- 归口部门和固定执行部门来自V7，并且必须与3000有效部门对应。归口部门未填写时，只允许MDM工作组组长建立案例并分派；3000不得按岗位名或个人判断猜测部门。
- 3000按固定跨部门业务行为生成核对项。归口部门和承接部门的部门MDM审核员分别记录本部门的结论和依据，不能代替另一部门处理。
- 编制人员在3001修改后上传新修订。稳定引用和核对内容均未变化时沿用原结论；内容变化时双方重新核对。
- 预览操作只写入`process_v7_preview_*`专用表。页面和接口必须明确标记为预览；只有核对完成后，MDM工作组组长使用单独的受控提升动作，才能把精确修订写入正式草稿链路。
- 全部核对项均由双方确认后，案例进入“核对完成”。该状态不表示流程已经审核、批准、发布或生效。
- 原生V7正式基础迁移只增加可空结构和提升审计，不改写现有V3业务数据。提升必须明确选择新建或已有主档；正式草稿正文只读；审核任务绑定修订号和摘要；发布成功返回不可变`process_version_id`。
- 已发布V7主档不得通过3000通用“创建下一版草稿”或旧结构化导入入口生成V3草稿。V7内容需要修改时，编制人员必须回到3001修改、上传新修订、重新核对并受控提升；路由层和仓储层均返回`409 V7_CONTENT_READ_ONLY`。

### 5.7 承接冲突

- “退回补充”只回到上一责任步骤，不自动创建冲突。
- 部门明确拒绝或MDM结构卡口提请争议处理时，系统创建承接冲突，并将承接置为`conflict_open`。
- MDM工作组组长分派数据冲突处理人；处理人记录双方立场、证据和协调方案。
- 双方部门MDM审核员均接受方案后，冲突关闭，承接返回MDM结构卡口。
- 任一部门不接受时，冲突处理人可以提请项目决策组。项目决策组只能选择继续承接、认定无需承接或退回修订，并记录依据。
- 冲突事件只追加；管理员只能查看，所有业务写接口返回403。

## 6. 主要使用流程

### 6.1 创建并交付账号

1. 管理员取得已确认的人员、工号、部门、MDM工作角色、授权依据和生效日期。
2. 管理员创建待启用账号。
3. 系统在同一事务中创建或复用人员、创建账号、写入角色授权和审计事件。
4. 管理员核对账号和角色后执行启用。
5. 系统返回一次性临时密码。
6. 用户首次登录后修改密码。

### 6.2 记录部门决定

1. 部门负责人在线下作出决定。
2. 部门MDM审核员打开对应治理对象。
3. 系统核对审核员部门、对象部门和部门最终负责人。
4. 审核员记录决定、依据、时间和可选证据。
5. 系统追加责任记录，不覆盖历史。

### 6.3 发布治理版本

1. MDM工作组组长发起发布。
2. 系统核对发布权限、对象状态、各必需部门最新决定、阻断问题、结构检查和版本检查。
3. 任一条件不满足时，系统返回具体原因并禁止发布。
4. 全部条件满足后，系统记录版本和发布人。

### 6.4 3001导出到承接确认

1. 用户在继续独立运行的3001中导出未审核的v1或v2单流程文件。
2. 3000服务端预览并返回规范化摘要、承接候选和内容哈希。
3. 归口部门审核员核对内容并填写审核依据，确认导入。
4. 系统把每条承接关系建立为独立待办；责任部门未知时先由MDM工作组组长分派。
5. 归口部门与外部门按状态分别完成审核、补充和决定。
6. MDM工作组组长执行结构卡口；退回只返回上一责任步骤，拒绝或提请争议处理会创建承接冲突。
7. 所有承接确认或有依据地关闭后，发布卡口才允许继续。

### 6.5 在MDM中编制并保存

1. 部门主对接人从流程治理统一入口新建或选择本部门草稿。
2. 用户编辑“单流程治理JSON”，或导入3001的v1/v2文件。
3. 保存时提交`expected_revision`。修订号与数据库不一致时返回409，页面要求重新载入，不覆盖他人修改。
4. 数据库以完整v2 JSON为编制内容真源；承接和待办表只保存治理投影。完整内容、治理投影和事件必须在同一事务中更新。
5. 未变化的承接保留原待办和决定；承接内容变化时新增修订。已有治理记录的承接从JSON中移除时，页面要求用户填写作废原因，系统保留历史。
6. 用户可以导出v2备份。切换草稿、切换工作区或关闭页面前，未保存内容必须明确提醒。

## 7. 异常与错误

| 错误码 | 含义 |
|---|---|
| `LEGACY_IDENTITY_API_RETIRED` | 旧身份写接口已经停用 |
| `CORE_GOVERNANCE_MODEL_READ_ONLY` | 固定角色、权限或RACI不允许页面修改 |
| `ROLE_ASSIGNMENT_EVIDENCE_REQUIRED` | 缺少角色授权依据、生效日期或初始角色 |
| `ROLE_SCOPE_DEPARTMENT_MISMATCH` | 部门角色范围与人员所属部门不一致 |
| `DEPARTMENT_ROLE_REPLACEMENT_REQUIRED` | 部门变更未提交新部门角色安排 |
| `LAST_ACTIVE_ADMIN` | 操作会导致系统没有有效管理员 |
| `RESPONSIBILITY_CHAIN_INCOMPLETE` | 部门最终负责人或必需部门决定不完整 |
| `ACCOUNT_REQUIRES_ACTIVATION` | 待启用账号不能直接恢复 |
| `ACCOUNT_DISABLE_REASON_REQUIRED` | 停用账号未填写原因 |
| `DRAFT_REVISION_CONFLICT` | 草稿修订号不一致，必须重新载入后再保存 |
| `HANDOFF_VOID_REASON_REQUIRED` | 已有治理记录的承接被移除，必须填写作废原因并保留历史 |
| `PROCESS_GOVERNANCE_CONTENT_INVALID` | 单流程治理JSON不符合v2结构规则 |
| `PROCESS_GOVERNANCE_MANUAL_CONVERSION_REQUIRED` | 历史记录不能无损转换，需要人工补齐指定字段 |
| `V7_PREVIEW_REVISION_CONFLICT` | 当前案例已上传新修订，必须刷新后重试 |
| `V7_PREVIEW_ITEM_SUPERSEDED` | 当前核对项已被新修订替代 |
| `V7_PREVIEW_OWNER_PENDING_REQUIRES_LEAD` | V7未明确归口部门，必须由MDM工作组组长建立并分派案例 |

## 8. 验收标准

- 七个固定角色只能获得固定权限，`*:*`和旧管理员业务权限不生效。
- 管理员可以完成身份管理，但业务写接口返回403。
- 部门角色不能跨部门使用。
- 冲突处理人不能查看或处理未分派事项。
- 项目决策组只能处理已升级事项。
- 待启用、停用、锁定账号不能登录。
- 部门变更、角色撤销或账号停用后，旧会话立即失效。
