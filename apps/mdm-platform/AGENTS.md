# AGENTS.md

本文件仅约束 `apps/mdm-platform/` 下的 MDM 平台开发工作。根目录 `AGENTS.md` 中关于当前"流程地图与数据地图梳理"阶段的约定仍然有效；当任务明确进入 MDM 平台代码、接口、数据库、权限或前端开发时，额外遵守本文件。

## 1. 先判断，再编码

动手前先明确：

- 本次任务目标。
- 修改边界。
- 可能涉及的文件。
- 验收方式。
- 是否影响接口响应结构、数据库结构、权限逻辑或状态流转。

阻塞性歧义必须先提问。非阻塞性歧义应写明假设，并按最小可验证方案继续。

## 2. 简单优先

只实现用户明确要求的内容。

禁止：

- 添加未要求的新功能。
- 添加未要求的配置项。
- 为单次使用场景设计复杂抽象。
- 引入不必要依赖。
- 把局部修复扩大成架构重构。
- 为了页面效果引入新的 UI 框架。

如果更简单方案能够满足需求，优先选择简单方案，并说明取舍。

## 3. 外科手术式修改

修改已有代码时：

- 只改与本次任务直接相关的代码。
- 不顺手重构无关模块。
- 不格式化无关文件。
- 不改动无关注释。
- 不删除历史遗留代码，除非它是本次修改造成的废弃代码。
- 保持项目现有代码风格。

每一处 diff 都应能解释为：它为什么是完成本次任务所必需的。

## 4. 验收驱动执行

执行前将需求转化为可验证目标。

示例：

- 修复 bug：先复现，再修复，再验证问题消失。
- 增加校验：补非法输入场景，再验证通过。
- 调整接口：明确请求、响应、错误场景，并验证调用成功。
- 重构代码：先确认重构前行为，再确认重构后行为一致。

多步骤任务建议使用如下格式：

1. 修改点：xxx
   验证方式：xxx

2. 修改点：xxx
   验证方式：xxx

## 5. 清理规则

只清理本次修改造成的问题。

允许清理：

- 本次新增后又废弃的 import。
- 本次改动造成的未使用变量。
- 本次改动造成的重复函数。
- 本次改动造成的明显孤儿文件。

禁止清理：

- 原本就存在的历史死代码。
- 与本任务无关的格式问题。
- 与本任务无关的命名问题。
- 与本任务无关的架构问题。

发现无关问题时，只记录，不擅自修改。

## 6. MDM 平台特别约束

- 当前目标平台形态是 Express.js + MySQL + 单文件前端 `public/index.html`，不要擅自改成其他后端、数据库或前端框架。
- 不得绕过现有 Express API 路由结构。新增接口优先放在 `server/routes/` 并在 `server/index.js` 注册。
- MySQL 配置统一使用 `MYSQL_HOST`、`MYSQL_PORT`、`MYSQL_USER`、`MYSQL_PASSWORD`、`MYSQL_DATABASE`、`MYSQL_CONNECTION_LIMIT`。
- 遗留 SQLite 代码只作为待删除实现、迁移兼容和既有测试隔离机制保留；公开命令必须使用`legacy-sqlite:`前缀，不得重新提供`init-db`、`sync:process-org`、`import:process-governance`或`check:process-governance`等含糊入口。不要新增 SQLite 专用能力、正式运行回退或当前主线口径。
- 不得擅自修改数据库表结构；确需改表时，必须说明兼容策略、历史数据影响和验证方式。
- 不得随意更改已有接口路径、请求字段或响应结构。确需调整时，必须说明影响范围。
- 不得把临时调试代码、临时账号、临时密码或本地数据提交为正式代码。
- 涉及 RBAC 时，优先使用 `server/auth.js` 中已有的 `requireAuth`、`requirePermission`、`requireAnyPermission`、`applyFieldConstraints` 和 `server/access.js` 的范围校验能力，不得在路由中按角色名称放行，也不得为管理员增加业务写入旁路。
- 正式身份链路固定为 `person -> user_accounts -> person_roles`。`users/user_roles`、`users.role`、`requireRole` 和 SQLite 人员接口只允许保留为隔离测试或明确的只读兼容，不得参与正式运行授权。
- 固定治理模型版本`rbac-raci-v3-2026-07-31`、七个MDM工作角色、十九项权限、角色可见标签和RACI由 `server/roleDefinitions.js` 维护，并由测试固化。管理页面只能读取，不得新增自定义角色、角色继承、通配权限、权限矩阵或角色可见标签编辑。
- `admin` 只负责账号、角色授权和访问审计，并对治理材料全局只读；任何业务路由都不得因用户拥有 `admin` 角色而绕过审核、责任证据、数据范围或对象状态。
- 部门角色只能授权到人员所属部门。部门最终负责人只从 `departments.final_responsible_person_id` 读取，不得按姓名、岗位、职务或历史常量推测。
- 账号、角色、部门、接口字段或状态变化必须与旧数据迁移一并处理。正式迁移入口、回滚和补偿步骤见 `docs/RBAC-RACI-Migration-Runbook.md`。
- 涉及流程治理、字段台账、术语、冲突、导入导出、通知/待办时，必须说明是否影响现有状态流转或审批链路。
- 流程治理前端保留流程编制、跨部门承接待办、承接冲突待办和V7预览核对四个工作区。V3正式链路继续以完整`process-governance-v3` JSON为内容真源，承接和待办表是治理投影；草稿保存必须校验`expected_revision`。v1、v2只作为V3兼容输入，表单状态统一迁移为`unspecified`，不得推断现状或拟设计状态。
- V7预览操作只能写入`process_v7_preview_*`专用表，必须返回`preview_only=true`、`publishable=false`和空的正式流程版本标识。预览接口不得写正式草稿或版本。受控提升使用单独接口，只能在M0、M1、M2、权限、并发和回退门槛通过后开启；必须原生保存V7，不得转换为V3。正式审核绑定修订号和内容摘要，发布成功后下游只使用`process_version_id`。
- `PROCESS_V7_PREVIEW_ENABLED`、`PROCESS_V7_FORMAL_ENABLED`默认关闭。任何V7预览或正式写操作还必须由`PROCESS_V7_TRIAL_PROCESS_REF`精确限定一个流程；该配置不接受列表、通配符、前缀或正则匹配。路由检查后，仓储必须使用锁定记录中的`process_ref`再次检查；只读接口不受该配置限制。
- 流程版本后续数据治理默认关闭。只有`PROCESS_DATA_GOVERNANCE_ENABLED=1`且`PROCESS_DATA_GOVERNANCE_TRIAL_PROCESS_VERSION_ID`精确指向一个不可变V7正式版本时才允许进入候选试点；不得接受列表、通配符、流程名称或部门范围。迁移不得自动为历史版本回填工作包。
- 后续数据治理以MDM工作组为责任主体。业务部门只答复定向的具体流程事实问题并提供制度、表单或台账依据；不得要求业务部门认定主数据、合并统一对象、决定关键字段、制定生命周期规则或发布数据地图。系统候选必须保持待定，不调用AI、不自动确认。
- 数据生命周期工作包固定绑定`process_version_id`、来源内容摘要和候选规则版本。每次写入前复核固定来源摘要；工作包不复制完整流程正文，不读取预览案例或原始3001文件，不向3001写回。
- `admin`对后续数据治理继续全局只读。MDM写入、目标部门答复、乐观并发、最小来源上下文和未提交修改保护均须在服务端和真实浏览器分别验证。
- V7核对摘要版本固定为`process-v7-review-item-v2`，内容包括完整业务行为、相连流程关系、相连数据对象及字段和生命周期、相连表单的操作、区域和字段。相关内容变化或旧记录缺少摘要版本时必须重新打开；只改变无序数组排列或无关对象时不得重新打开。
- `ACTOR_DEPARTMENT_UNRESOLVED`不能由人工范围决定解除。提升、正式提交、审核通过和发布必须按当前有效部门重新计算未解决卡口；审核阶段有卡口时仍保留“需要修改”和“拒绝”入口。
- 3001继续独立运行。V7只允许通过用户主动下载和上传进入3000；MDM改造不得停止、重绑、远程读取或代管3001。3000预览、提升和发布必须分别调用共享纯校验入口，不能信任客户端状态或旧审核结果。
- 前端修改应延续现有 `public/index.html` 的单文件 HTML/CSS/JS 结构；除非任务明确要求，不引入构建链或 UI 框架。
- 导入/导出相关修改必须覆盖 Excel 模板、字段校验、错误提示和权限控制。

如未来 MDM 平台迁移到 Flask、SQL Server、Vue/Vite 或其他技术栈，应先更新本文件和相关设计文档，再按新架构执行。

## 7. 文档同步

MDM 平台的代码、接口、数据库结构、权限逻辑、前端交互、启动命令或测试命令发生变化时，必须同步检查并更新相关文档。

优先检查：

- `README.md`
- 本文件
- `docs/role-based-usage-guide.md`
- `scripts/README.md`
- 根目录 `CODEX.md` / `AGENTS.md`
- `docs/glossary.md`

如果确认无需同步文档，最终交付说明必须写明原因。新增术语、新缩写或改变既有术语含义时，必须同步更新 `docs/glossary.md`。

## 8. 输出要求

完成后说明：

- 本次修改目标。
- 实际修改的文件。
- 每个文件的修改原因。
- 验证步骤与结果。
- 未解决问题或风险。
- 是否存在需要用户决策的后续事项。

不得只输出"已完成"。
