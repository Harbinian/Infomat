# Local review API contract

Scope: isolated local implementation of the decisions confirmed on 2026-11-05. No calls to MDM platform, 3001 or formal databases. Machine fields are English; UI is Chinese. Synthetic identities are explicitly marked as rehearsal identities, never real employee authority.

## Transport

- Default listener is 127.0.0.1:3090. Docker uses REVIEW_BIND_HOST=0.0.0.0 with a private IPv4 in REVIEW_LAN_IP and publishes 3090 on that host address and loopback. Ports 3000/3001 are rejected.
- GET /api/health: service, version, mode=local-isolated, storage=isolated-sqlite, formalIntegration=false, network=loopback|lan.
- GET /api/session: {users,currentUser,csrfToken,mode,network}; users contain id,name,department,roles. Role selection is for rehearsal only.
- POST /api/session {userId}: creates HttpOnly SameSite=Strict session cookie and returns the session object. An explicit empty userId revokes the current cookie's session, expires the cookie and returns currentUser=null. Allow only configured IPv4 hosts or the loopback hosts, and require the service port. Writes require exact same-origin Origin and application/json.
- GET /api/bootstrap: {storageVersion,revision,currentUser,users,departments,organizationCatalog,themes,materials,batches,opinions,issues,observations,audit,mode}. Auth required; material entries are metadata only, not raw content. organizationCatalog contains source metadata and roles_by_department from the bundled config/organization-catalog.json. It is added to responses, never persisted in review state. Initialization creates 12 empty planned theme templates, without selecting effective material or assigning business participants.
- GET /api/materials/:id: material metadata plus document (unaltered parsed JSON) and rawText. Auth required.
- POST /api/import {files:[{sourcePath,content}],expectedRevision}: PMO only, X-Review-CSRF required; content is source text, sourcePath is a label, never a server filesystem path to read. Validate all files before transaction. Supports process-governance-v8; preserve unknown fields, original bytes/text and source IDs. Material identity uses service ID plus source path/hash, not process_ref. Same path + hash is idempotent; same ID/name in different files never overwrites. Respond {state}.
- POST /api/commands {type,payload,expectedRevision}: cookie, X-Review-CSRF; return {state}. Optimistic revision check on every mutation: 409 {error,code}; no silent overwrite. Other errors use the same shape. HTTP permissions enforced independently of UI.
- GET /api/export: authenticated export package containing original materials, reviews, issues, observations and audit. Does not write any external service. Attachment filename in English.

## State records

- theme: {id:T01..T12,name,description}.
- material: {id,name,sourcePath,sourceDepartment,declaredDepartment,sourceRef,sha256,schemaVersion,themeId,status:pending|confirmed,confirmedBy,confirmationNote,predecessorId,changeNote,warnings,createdAt}. `themeId` is a suggested grouping until explicitly confirmed; sourceDepartment is directory provenance, never confirmed responsibility.
- batch: {id,title,themeId,materialIds,memberIds,leadId,recorderId,requiredDepartments,status:planned|frozen,coverage:{[materialId]:{status:pending|needs_followup|reviewed,note,feedbackByDepartment}},presenter:{materialId,nodeRef},createdBy}. Freeze requires confirmed materials and explicit participants/lead/recorder; any batch member must be able to read all review material. `requiredDepartments` are explicitly selected, not inferred from source.
- opinion: {id,materialId,batchId,nodeRef,relationRef,text,status:draft|submitted,authorId,history,createdAt}. Drafts visible only to author. Submitted corrections append history.
- issue: {id,title,description,impact,materialIds,opinionIds,scope:department|cross_department|policy,affectedDepartments,assigneeId,dueDate,reviewerIds,authorityId,status:open|in_progress|awaiting_review|closed,responses,reviews,authorityEvidence,history,createdBy}. All roles are explicitly selected from rehearsal users. A policy issue also needs designated authority evidence before closure.
- observation: {id,title,materialIds,issueIds,phenomenon,timePattern,variables,hypotheses,feedback,delays,evidence,counterEvidence,nextEvidence,history,createdBy}. Text fields preserve uncertainty; no simulation or automatic causal conclusions.

## Commands and payloads

- material.confirm {materialId,themeId,note}: source department representative only (PMO cannot substitute for business confirmation); blank sourceDepartment requires explicit matching department in payload.sourceDepartment. Local confirmation is rehearsal only.
- material.link_version {materialId,predecessorId,changeNote}: PMO, explicit linkage; prohibit self/cycles, keep both snapshots; do not inherit review/issue closure. Store impacted issue IDs for attention without silently reopening them.
- batch.create {title,themeId,materialIds,memberIds,leadId,recorderId,requiredDepartments}: PMO. materialIds may be empty for initial plans. No material in more than one primary batch; historical successor versions are independent snapshots.
- batch.update {batchId,title,materialIds,memberIds,leadId,recorderId,requiredDepartments}: PMO, only planned batch. Frozen roster/material membership immutable.
- batch.freeze {batchId}: PMO.
- batch.feedback {batchId,materialId,note}: member representative, frozen batch only; stores own department feedback against exact snapshot.
- batch.coverage {batchId,materialId,status,note}: batch lead/recorder; reviewed requires frozen batch, feedback from all requiredDepartments and nonblank walk-through note. Open issues do not block reviewed.
- batch.present {batchId,materialId,nodeRef}: lead or recorder, frozen batch; personal browsing remains independent.
- walk.create {materialId,batchId?,kind:step|relation,changes,reason}: participant. A new step requires behavior_name and defaults to node_type=action. A new relation requires unambiguous from_behavior_ref and to_behavior_ref and defaults to relation_type=sequence. An identical relation is rejected. The service assigns a stable reference and appends a new element position.
- walk.edit {materialId,batchId?,kind:step|relation,index,changes,reason}: participant. Step fields are behavior_name, node_type, current_actor_role, actor_assignment_mode, actor_position_rule, behavior_description, input_description, output_description, completion_standard, trigger, precondition and timing. Relation fields are from_behavior_ref, to_behavior_ref, relation_type and condition. Editing endpoints requires both to resolve uniquely. Existing non-text values require separate review. No-op submissions leave the revision unchanged.
- New or changed nonempty fixed-department current_actor_role values must identify a department-position pair from the bundled catalog. The UI writes `department / position`, while existing recognized concatenated or separated strings remain accepted. Unchanged legacy roles remain byte-for-byte intact when editing unrelated fields. Switching a rule-based actor to fixed-department also validates its pair. For rule-based assignment, role edits may preserve or clear the original; use actor_position_rule for the rule. Original snapshots and previous audit events retain their existing representation.
- walk.remove {materialId,batchId?,kind:step|relation,index,reason}: participant. Removes the element from the shared graph. Removal checks references to the element throughout the material, including lifecycle flow_relation_refs. Step removal also checks incident relations and presenter positions. Ambiguous duplicate element identifiers block removal. The UI previews the same blockers before requesting a reason, and the server rechecks them transactionally. The transaction retains the removed element in the audit record. Historical opinion anchors remain readable and valid for correction.
- Relation edits validate duplicate endpoint/type/condition combinations even when endpoints remain unchanged. Updating an endpoint requires both to resolve uniquely. An unrelated type or condition edit preserves existing unresolved endpoints. Unknown existing select values are retained when editing other fields; their unavailable options stay visibly marked. Structural saves return keyboard focus to the relevant edit or create action.
- Walkthrough commands require a nonblank reason and reject stale revisions. A supplied batch must include the material. Each successful change appends one audit event with materialId, batchId, kind, index, elementRef, before, after and reason in detail, plus the authenticated actor and server time. Create has before=null and removal has after=null. The stable zero-based index starts at the original array position, and new positions are appended and never reused. The walkthrough replays the events in sequence over the original snapshot. GET /api/materials/:id, comparison and export continue to expose the original material. GET /api/bootstrap and GET /api/export include the shared revisions in audit. Batch freeze and coverage continue to refer to the original snapshot.
- Local projection mode and handoff emphasis are browser-only display preferences; they do not alter batch.present or persisted state. Relation selection is not published as an empty nodeRef: the UI disables publishing until a step or the whole-flow position is selected. Handoff classifications read source roles and assignment rules, never write organization/actor assignments, and are not confirmation records.
- Department swimlanes are derived display geometry using the same conservative actor classification over the current walkthrough content. Every node belongs to one explicit department lane or the final unresolved lane. Lane membership, coordinates, viewport and department focus are not persisted or exported as source facts. A line crossing another lane does not introduce an extra handoff. Publishing is disabled during department focus because batch.present has no lane reference; select a step or explicitly return to the whole-flow view first. The relation recording entry retains the existing opinion.save -> recorder issue.create workflow and preserves locked opinion anchors.
- Entry navigation is derived from the current walkthrough graph. A sole zero-incoming step that reaches all steps can be focused directly. Multiple zero-incoming steps are offered as candidates. Cycles, disconnected components and unresolved references allow explicit step selection. These navigation actions do not write state or establish a business start condition.
- Presenter followers apply each published position once per follow session and wait while the opinion editor or a dialog has focus. Comparison displays each selected snapshot independently and ignores superseded responses. These behaviors do not add server-side state.
- The batch plan previews freeze prerequisites and starts a fresh confirmation on each opening. Independent browsing can open the existing batch at the same snapshot. Issue forms preview required departmental reviewer coverage, and server-side freeze and issue validation remain authoritative.
- Unsaved opinion input stays in the browser page session for each identity, material snapshot, and batch. Opening a saved opinion in another scope preserves the first scope's input. If the destination already has unsaved input, the editor opens that input. Following a successful action on the selected issue, the ledger clears any conflicting status filter and keeps the selected issue and search query.
- Search updates the results in My Opinions, Issue Ledger, and Materials and Versions while keeping the active field. Saving an action on a selected issue returns focus to its title. The walkthrough discussion refreshes from the next bootstrap poll, independently of the opinion editor. It waits while focus is inside the discussion or a dialog is open. These interactions use the existing server visibility rules and add no API fields.
- The Data and Forms view renders data fields and form-area items as separate tables. A selected step prioritizes objects and forms explicitly linked by the material's behavior_links. Required flags are displayed as stated, with missing flags shown as pending confirmation. The tables use the existing material and add no API fields.
- opinion.save {opinionId?,materialId,batchId?,nodeRef?,relationRef?,text,submit:boolean}: self only, drafts can edit; submitted corrections always retain before/after.
- issue.create {title,description,impact,materialIds,opinionIds,scope,affectedDepartments,assigneeId,dueDate,reviewerIds,authorityId?}: recorder role; referenced opinions must be submitted. All scopes need designated representative coverage for every affected department. Cross-department issues need >=2 departments; department issues require exactly one. Policy needs authority role. Assignee and due date may remain unset, displayed as pending assignment; never invent assignments.
- issue.assign {issueId,assigneeId,dueDate,reviewerIds,authorityId?}: recorder, not closed; reviewer changes reset review decisions with history.
- issue.respond {issueId,text,evidence}: assignee only, evidence required, sets awaiting_review and resets prior review decisions.
- issue.review {issueId,decision:approve|return,note}: designated reviewer only, nonblank note, only awaiting_review; all designated reviewer approvals close except missing policy evidence blocks close. Return sets in_progress and resets current approvals while retaining history.
- issue.authority {issueId,evidence}: designated authority only, nonblank evidence, recorded during awaiting_review for the current response cycle; does not replace reviewer approvals.
- issue.reopen {issueId,reason}: designated reviewer or authority, closed only; preserve prior closure, reset current reviews.
- observation.save {observationId?,title,materialIds,issueIds,phenomenon,timePattern,variables,hypotheses,feedback,delays,evidence,counterEvidence,nextEvidence}: any participant, creator edits with revision/history; no blank title, links validated.

All reference IDs, enums, date formats, arrays, actor capabilities and state transitions are validated server-side. Audit records are append-only actor/time/operation/detail; submitted history and raw material cannot be replaced. Deletion is not exposed in this first local version.

New departmental feedback changes previously reviewed coverage to needs_followup. Reassignment of the handler or reviewers invalidates current approvals and returns awaiting_review to in_progress. A new response, returned review or reopened issue invalidates current authority evidence; prior evidence and decisions remain in history. These are software protections against applying stale confirmation to changed work.
