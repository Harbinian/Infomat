# Local review API contract

Scope: isolated local implementation of the confirmed decisions in the 2026-11-16 joint-review handoff and audited process JSON. Existing material, batch and issue contracts remain compatible. No calls to MDM platform, 3001 or formal databases. Machine fields are English; UI is Chinese. Synthetic identities are explicitly marked as rehearsal identities, never real employee authority.

## Transport

- Default listener is 127.0.0.1:3090. Docker uses REVIEW_BIND_HOST=0.0.0.0 with a private IPv4 in REVIEW_LAN_IP and publishes 3090 on that host address and loopback. Ports 3000/3001 are rejected.
- GET /api/health: service, version, jointReviewContract=continuous-joint-review-v1, mode=local-isolated, storage=isolated-sqlite, formalIntegration=false, network=loopback|lan; reviewContextDigest and reviewContext summary when REVIEW_CONTEXT_PATH is configured.
- GET /api/session: {users,currentUser,csrfToken,mode,network}; users contain id,name,department,roles. Role selection is for rehearsal only.
- POST /api/session {userId}: creates HttpOnly SameSite=Strict session cookie and returns the session object. An explicit empty userId revokes the current cookie's session, expires the cookie and returns currentUser=null. Allow only configured IPv4 hosts or the loopback hosts, and require the service port. Writes require exact same-origin Origin and application/json.
- GET /api/bootstrap: {storageVersion,revision,currentUser,users,departments,organizationCatalog,themes,materials,batches,opinions,issues,observations,jointReviews,audit,mode}. Auth required; material entries are metadata only, not raw content. organizationCatalog contains source metadata and roles_by_department from the bundled config/organization-catalog.json. It is added to responses, never persisted in review state. Initialization creates 12 empty planned theme templates, without selecting effective material or assigning business participants.
- GET /api/materials/:id: material metadata plus document (unaltered parsed JSON), rawText and optional reviewContext matched by the original material SHA-256. Auth required. Shared walkthrough revisions do not rewrite this evidence snapshot.
- POST /api/import {files:[{sourcePath,content}],expectedRevision}: PMO only, X-Review-CSRF required; content is source text, sourcePath is a label, never a server filesystem path to read. Validate all files before transaction. Supports process-governance-v8 and process-governance-v9; preserve the declared version, lifecycle, unknown fields, original bytes/text and source IDs. Material identity uses service ID plus source path/hash, not process_ref. Same path + hash is idempotent; same ID/name in different files never overwrites. Respond {state}. Supporting proposals and data-review records are not process imports.
- GET /api/review-support/:sha256: authenticated, read-only download of the exact original supplementary JSON present in the configured evidence pack. Digest and bytes are checked at startup; unknown digests return 404. No caller-supplied filesystem paths are accepted.
- POST /api/commands {type,payload,expectedRevision}: cookie, X-Review-CSRF; return {state}. Optimistic revision check on every mutation: 409 {error,code}; no silent overwrite. Other errors use the same shape. HTTP permissions enforced independently of UI.
- GET /api/export: authenticated export package containing original materials, reviews, issues, observations and audit. Does not write any external service. Attachment filename in English.

## Read-only review context

REVIEW_CONTEXT_PATH optionally loads a review-evidence-context-v1 JSON snapshot. GET /api/bootstrap adds reviewContext metadata (digest, revision, source counts, warnings, process summaries and supplementary file metadata); it does not send raw supplementary content. Material details add only the context for the exact source SHA-256. GET /api/export adds reviewContext and reviewContextDigest, preserving all existing materials and review history.

The 2026-11-14 pack contains 69 week-19 process models, 2 supplementary JSON files, and 49 week-16 reference contexts. Offline forms are peer sources alongside U8, Qinzhe and KFU8QZ in the matrix service. Object/action declarations and the 71 cross-source field mappings remain evidence or candidates; no role, effective version, review completion, synchronization or business fact is inferred. The browser can open a precise 9992 field link, but this service does not call that API or share its store. Supplemental context does not create review opinions, issues, batch coverage or authority decisions.

## State records

- theme: {id:T01..T12,name,description}.
- material: {id,name,sourcePath,sourceDepartment,declaredDepartment,sourceRef,sha256,schemaVersion,themeId,status:pending|confirmed,confirmedBy,confirmationNote,predecessorId,changeNote,warnings,createdAt}. `themeId` is a suggested grouping until explicitly confirmed; sourceDepartment is directory provenance, never confirmed responsibility.
- batch: {id,title,themeId,materialIds,memberIds,leadId,recorderId,requiredDepartments,status:planned|frozen,coverage:{[materialId]:{status:pending|needs_followup|reviewed,note,feedbackByDepartment}},presenter:{materialId,nodeRef},createdBy}. Freeze requires confirmed materials and explicit participants/lead/recorder; any batch member must be able to read all review material. `requiredDepartments` are explicitly selected, not inferred from source.
- opinion: {id,materialId,batchId,nodeRef,relationRef,text,status:draft|submitted,authorId,history,createdAt}. Drafts visible only to author. Submitted corrections append history.
- issue: {id,title,description,impact,materialIds,opinionIds,scope:department|cross_department|policy,affectedDepartments,assigneeId,dueDate,reviewerIds,authorityId,status:open|in_progress|awaiting_review|closed,responses,reviews,authorityEvidence,history,createdBy}. All roles are explicitly selected from rehearsal users. A policy issue also needs designated authority evidence before closure.
- observation: {id,title,materialIds,issueIds,phenomenon,timePattern,variables,hypotheses,feedback,delays,evidence,counterEvidence,nextEvidence,history,createdBy}. Text fields preserve uncertainty; no simulation or automatic causal conclusions.

Walkthrough material selection applies client-side sourceDepartment and text filters to the current batch materialIds or the explicitly selected current/history material scope, optionally narrowed to theme candidates. Text matches name, sourcePath and sourceDepartment, case-insensitively, with all whitespace-separated terms required. Filtering changes only selector options and the match count; it does not switch the open material, redraw its graph, alter opinion buffers or write review state. A new explicit batch/theme/material scope clears the filters. Batch association provides review context (feedback, coverage and presenter location), separate from material predecessor linkage and shared edit history. The inventory scope does not modify source JSON or approval fields.

## Current-round inventory and historical browsing

REVIEW_ROUND_PATH optionally loads a read-only review-material-round-v1 file containing label, sourceRoot, capturedAt, files and supportingFiles. Each process entry has sourcePath, relativePath, department and exact sha256. Binding prefers exact path plus digest, then a unique prior source under the same round root, then a unique digest; name and process_ref never establish identity. Missing, ambiguous, repeated or department-conflicting bindings fail startup. The configuration does not confer confirmation, modify original metadata or migrate reviews. Unconfigured legacy stores retain their previous all-material browsing behavior.

Health adds reviewRound {label,digest,retainOnly,capturedAt,currentCount,historyCount,departments}. Authenticated bootstrap, mutation state, material detail and export keep every existing record and add the round inventory and/or currentSource metadata; stored sourcePath and all review anchors remain unchanged. currentSource gives the current checked source location. Material arrays contain every record in the selected operational store. A retain-only store contains only the explicitly retained round; removed IDs return 404 and old reviews are available only in the offline backup. When retainOnly=true, all stored materials must belong to the inventory or startup fails; the active UI has no history entry or scope selector. Existing batches keep their exact frozen/planned selections; new batch selections offer current materials while retaining already selected old materials. The lineage list uses the same current scope and marks missing digest-matched supplementary evidence.

The preparation script writes only the requested catalog outside the explicit source folder. It recursively checks JSON bytes, separates non-process supporting records and rejects incomplete or unsupported process declarations. Operators import only missing originals, verify the inventory against an isolated copy, back up the live store, then switch the read-only catalog and application image together. Source moves do not create new snapshots when a unique original binding exists; changed content is a new snapshot and never inherits old review results.

With retainOnly=true, POST /api/import returns 403 REVIEW_ROUND_LOCKED before any write; the page import control is hidden. Unconfigured legacy instances retain the existing import contract. Scope reduction is an explicitly authorized maintenance operation: read a complete backup, create a separate compatible store containing only retained objects and their intact records, and switch data volumes. Mixed-scope records, external predecessor links and dangling references stop preparation. The original database and audit are never rewritten; full backups retain removed records. The new store records review.scope_retain_only and advances the optimistic revision.

## Continuous joint reviews

`GET /api/bootstrap`, command responses and export add `jointReviews`. This is additive to storageVersion=1; each item has formatVersion=1. Legacy reads provide an empty array in memory, without writing or mapping batch/issue statuses into approval. The first explicit transaction persists the additive field with the same revision check and append-only audit. Unknown supported fields survive. Unsupported item formats fail with INVALID_STORAGE and preserve the database. Scope-retention preparation refuses scope reduction when joint reviews exist; no migration or deployment is implicit.

`GET /api/health` adds `jointReviewContract: "continuous-joint-review-v1"` so an explicitly selected candidate can identify this implementation contract. The field is not deployment or business-acceptance evidence for another running instance.

Item: `{id,title,basis,organizerId,materialIds,plan,stage,epoch,versions,currentVersionId,preparations,currentPreparationId,preparationRecords,submissions,currentSubmissionId,sessions,currentSessionId,issues,confirmations,rounds,currentRoundId,packages,activePackageId,handovers,currentHandoverId,originReturns,events,actionPlans?}`. `stage` is preparing|ready|reviewing|voting|approved|passed|handover|completed. `approved` means the exact current round was unanimous and still awaits package freeze; `completed` means actual receipt, never implementation completion. No legacy role or status establishes these outcomes.

Every `joint.*` mutation uses the existing POST /api/commands envelope, authenticated actor, CSRF and expectedRevision transaction. Payloads use explicit `reviewId`; content-dependent commands also require `versionId=currentVersionId`. All identities are synthetic. PMO capabilities permit organization only; issue-level decisionMakerId and authorityBasis are explicit rehearsal declarations, not real employee authentication or inferred business authority. Required attendance/voter rosters remain immutable; no person replacement or exclusion endpoint exists.

- `joint.create {title,materialId,basis,scope,schedule,requirements,ownerId,verifierIds,receiverIds,requiredIds,voterIds}`: PMO; one continuous item per explicitly linked material. Required and voter sets are nonempty, onsite owner, receivers, voters and organizer belong to the explicit attendance scope. Internal verifiers are independently designated and need not attend or vote. Captures an immutable original-plus-walkthrough projection as the first current version. Does not import the management-process JSON or change retained inventory.
- `joint.plan.amend {reviewId,scope,schedule,requirements,affectedIds,note}`: PMO, preparing only; records previous plan and a new preparation instance. `joint.preparation.reopen {reviewId,note}`: PMO, ready only; records a discovered gap and resumes preparation. A meeting already started returns to preparation only through the origin-change path.
- `joint.preparation.record {reviewId,versionId,kind:verification|preread|informed,scopePaths,note,unresolved?,position?,responderId?}`: actual assigned actor only. JSON Pointer array scopePaths uses empty string for the full document. Preread requires the exact current submission; unresolved feedback requires location and actual responder. Records are append-only.
- `joint.submit {reviewId,versionId,recordIds,note}`: designated owner only; explicitly selects actual current verification records covering every designated verifier. `joint.preparation.reuse {reviewId,versionId,recordId,note}`: PMO; original record, original actor/version and unaffected scope stay identifiable, reusedFromId and reuseBasis distinguish reuse from a fresh statement. Changed scopes or affected actors cannot be reused.
- `joint.preparation.check {reviewId,versionId,recordIds,note}`: PMO explicitly selects current preparation records. The server calculates gaps in verification, submission, preread and informed preparation; gaps persist with responsible subject IDs and cannot set ready.
- `joint.attendance {reviewId,versionId,presentIds,questionerIds,note}`: PMO, ready only. Every prescribed person must actually be present before reviewing starts. Failed checks persist without starting. questionerIds explicitly expresses actual clockwise seat order, with PMO last as a separate step. On entry, actual unresolved preparation feedback becomes an anchored issue requiring classification, retaining its original record identity across reuse.
- `joint.meeting.speak {reviewId,versionId,kind:introduction|receiving|question|pmo,note}`: designated actual actor at the next sequence position only. Owner, receivers, explicit clockwise questioners, then PMO. No-question is an explicit note. `joint.summary {reviewId,versionId,note}`: PMO after the sequence; ties summary to the exact version and content/issue epoch.
- `joint.version.revise {reviewId,versionId,beforeDigest,document,removedPaths,affectedIds,reason}`: prescribed participant, preparing/reviewing only. Stores complete new content only for an actual semantic change, preserves unknown fields unless their removal is explicitly listed, requires unchanged schema and source process identity, preserves parent/source and original bytes. No-op leaves revision/version count unchanged. `joint.version.select` takes materialId instead of document, PMO only, explicitly relates an existing inventory snapshot and its current walkthrough to this item. A material already belonging to another item cannot be silently merged. Both invalidate current global confirmations, submissions and issue closure bindings; original preread stays against its original version. removedPaths must exactly match actual removals. This is a local content-shape check, not a complete V9 or business acceptance validator.
- `joint.issue.register {reviewId,versionId,title,description,location,kind:definition|crud|raci|responsibility|origin,responderIds,scopePaths,decisionMakerId?,authorityBasis?,sourceOpinionIds?,sourceLegacyIssueIds?}`: prescribed participant. Source opinions must be submitted and point to this item's explicitly linked materials; original IDs are retained. Legacy closure does not close this issue. Non-definition conflicts require an explicit authority and basis. `joint.issue.classify {reviewId,versionId,issueId,kind,responderIds,decisionMakerId?,authorityBasis?}`: PMO classifies actual imported unresolved feedback or non-agreeing ballot concerns before substantive handling; no inference from text.
- `joint.issue.statement {reviewId,versionId,issueId,note}`: related business actor's actual current-session statement. `joint.issue.decide {reviewId,versionId,issueId,note,newOwnerId?}`: explicit issue authority (definition: related business actor), after all related current-version/session statements. Effective decision, synchronization and immediate confirmations are separate records.
- `joint.issue.sync {reviewId,versionId,issueId,modelNote,impactNote}`: PMO maps the effective decision to the actual current model and checks implications. `joint.issue.confirm {reviewId,versionId,issueId,note}`: every related business and explicit authority actor immediately confirms the current synchronization in this meeting. Only the complete set creates a current resolution. No asynchronous attachment/legacy status provides a substitute. `joint.issue.reuse {reviewId,versionId,issueId,resolutionId,note}`: PMO explicitly reuses a prior resolved scope only when actual document differences do not overlap that scope; original confirmation records stay intact.
- `joint.origin.return {reviewId,versionId,issueId,affectedIds,verifierIds,receiverIds,note}`: PMO after an origin issue has effective decision, model synchronization and all immediate confirmations. New owner comes from that decision; new preparation targets affected scope, keeps item/issue identities, versions, unaffected records and prescribed rosters. An already consumed origin decision cannot trigger another return. Voting is blocked while a new effective origin decision has not completed this return/preparation/attendance route.
- `joint.confirm {reviewId,versionId,scope,note}`: self, after actual sequence, current summary and necessary issue closure. Binds actual actor/scope, session, version and epoch; old preread/confirmation does not become current confirmation.
- `joint.vote.open {reviewId,versionId}`: PMO, reviewing. Requires the current summary, all issue closure and actual current-version confirmations from voters, owner, receivers and organizer. Creates an empty round with the immutable prescribed voter set. `joint.vote.cast {reviewId,versionId,roundId,choice:agree|oppose|abstain|conditional,note,condition?}`: self only, once per current round/version. Agree with an unresolved condition is rejected; a note is required for every non-agreeing choice but optional for explicit agreement. Old votes never carry forward. `joint.vote.finish {reviewId,versionId,note}`: PMO; only every prescribed voter explicitly agreeing is unanimous. Otherwise records missing votes and returns to this review; actual non-agreeing concerns become linked issues requiring classification, not implementation tasks.
- `joint.package.freeze {reviewId,versionId,storageLocation,custodian,note}`: PMO, approved only, rechecks current version/round/epoch. Appends exact content, provenance, plan, preparation, sessions, issues/ownership, confirmations and complete current ballot set; packages never overwrite. `joint.resume {reviewId,versionId,note}` explicitly resumes the same approved/passed/handed-over item, preserves old packages/receipts and clears active approval bindings. Later content must obtain fresh confirmation/ballots.
- `joint.action.plan {reviewId,description,responsibleIds,expectedResult,authorityBasis,followup}`: PMO after package freeze; explicitly prepares a follow-up action for the current package, without conferring authority. `joint.handover.send {reviewId,packageId,recipientIds,actions:[{description,responsibleIds,expectedResult,authorityBasis,followup}],note}`: PMO, current passed package only; responsibilities must be included among actual recipients. Empty actions is allowed with factual explanation, while the package still requires receipt. `joint.handover.receive {reviewId,handoverId,note}`: each designated recipient personally records actual receipt and responsibility scope. Only full actual receipt sets completed. `joint.action.complete {reviewId,handoverId,actionId,note}`: assigned actor who actually received records separate actual implementation evidence; receipt never completes actions automatically.

Every substantive change preserves event/actor/time and existing IDs. The full original material endpoint still returns original bytes/document; the exact current version and each pass package are separate in jointReviews and export. Shared walkthrough edits never silently alter a selected current version or old pass package. No external API, formal publication, personnel master, real notification, database synchronization or migration is triggered.

## Commands and payloads

- material.confirm {materialId,themeId,note}: source department representative only (PMO cannot substitute for business confirmation); blank sourceDepartment requires explicit matching department in payload.sourceDepartment. Local confirmation is rehearsal only.
- material.link_version {materialId,predecessorId,changeNote}: PMO, explicit linkage; prohibit self/cycles, keep both snapshots; do not inherit review/issue closure. Store impacted issue IDs for attention without silently reopening them.
- batch.create {title,themeId,materialIds,memberIds,leadId,recorderId,requiredDepartments}: PMO. materialIds may be empty for initial plans. No material in more than one primary batch; historical successor versions are independent snapshots.
- batch.update {batchId,title,materialIds,memberIds,leadId,recorderId,requiredDepartments}: PMO, only planned batch. Frozen roster/material membership immutable.
- batch.freeze {batchId}: PMO.
- batch.feedback {batchId,materialId,note}: member representative, frozen batch only; stores own department feedback against exact snapshot.
- batch.coverage {batchId,materialId,status,note}: batch lead/recorder; reviewed requires frozen batch, feedback from all requiredDepartments and nonblank walk-through note. Open issues do not block reviewed.
- batch.present {batchId,materialId,nodeRef}: lead or recorder, frozen batch; personal browsing remains independent.
- walk.create {materialId,batchId?,kind:step|relation,changes,reason}: participant. A new step requires behavior_name and defaults to node_type=action. A new relation requires unambiguous from_behavior_ref and to_behavior_ref and defaults to relation_type=sequence. An identical relation is rejected. The service assigns a stable reference and appends a new element position.
- walk.edit {materialId,batchId?,kind:step|relation,index,changes,reason}: participant. Step fields are behavior_name, node_type, current_actor_role, actor_assignment_mode, actor_position_rule, behavior_description, input_description, output_description, completion_standard, trigger, precondition and timing. Relation fields are from_behavior_ref, to_behavior_ref, relation_type and condition. Editing endpoints requires both to resolve uniquely. Existing non-text values require separate review. No-op submissions leave the revision unchanged.
- New or changed nonempty fixed-department current_actor_role values must identify a department-position pair from the bundled catalog. The UI writes `department / position`, while existing recognized concatenated or separated strings remain accepted. Unchanged legacy roles remain byte-for-byte intact when editing unrelated fields. Switching a rule-based actor to fixed-department also validates its pair. For rule-based assignment, role edits may preserve or clear the original; use actor_position_rule for the rule. Original snapshots and previous audit events retain their existing representation.
- walk.remove {materialId,batchId?,kind:step|relation,index,reason}: participant. Removes the element from the shared graph. Removal checks references to the element throughout the material, including lifecycle flow_relation_refs. Step removal also checks incident relations and presenter positions. Ambiguous duplicate element identifiers block removal. The UI previews the same blockers before requesting a reason, and the server rechecks them transactionally. The transaction retains the removed element in the audit record. Historical opinion anchors remain readable and valid for correction.
- Relation edits validate duplicate endpoint/type/condition combinations even when endpoints remain unchanged. Updating an endpoint requires both to resolve uniquely. An unrelated type or condition edit preserves existing unresolved endpoints. Unknown existing select values are retained when editing other fields; their unavailable options stay visibly marked. Structural saves return keyboard focus to the relevant edit or create action.
- Walkthrough commands require a nonblank reason and reject stale revisions. A supplied batch must include the material. Each successful change appends one audit event with materialId, batchId, kind, index, elementRef, before, after and reason in detail, plus the authenticated actor and server time. Create has before=null and removal has after=null. The stable zero-based index starts at the original array position, and new positions are appended and never reused. The walkthrough replays the events in sequence over the original snapshot. GET /api/materials/:id, comparison and export continue to expose the original material. GET /api/bootstrap and GET /api/export include the shared revisions in audit. Batch freeze and coverage continue to refer to the original snapshot.
- Local projection mode and handoff emphasis are browser-only display preferences; they do not alter batch.present or persisted state. Relation selection is not published as an empty nodeRef: the UI disables publishing until a step or the whole-flow position is selected. Handoff classifications read source roles and assignment rules, never write organization/actor assignments, and are not confirmation records.
- Department swimlanes are derived display geometry using the same conservative actor classification over the current walkthrough content. Every node belongs to one explicit department lane or the final unresolved lane. Lane membership, coordinates, viewport and department focus are not persisted or exported as source facts. A line crossing another lane does not introduce an extra handoff. Publishing is disabled during department focus because batch.present has no lane reference; select a step or explicitly return to the whole-flow view first. The relation recording entry retains the existing opinion.save -> recorder issue.create workflow and preserves locked opinion anchors.
- Entry navigation is derived from the current walkthrough graph. A sole zero-incoming step that reaches all steps can be focused directly. Multiple zero-incoming steps are offered as candidates. Cycles, disconnected components and unresolved references allow explicit step selection. These navigation actions do not write state or establish a business start condition.
- Presenter followers apply each published position once per follow session and wait while the opinion editor or a dialog has focus. Comparison displays each selected snapshot independently and ignores superseded responses. These behaviors do not add server-side state.
- The batch plan previews freeze prerequisites and starts a fresh confirmation on each opening. Independent browsing can open the existing batch at the same snapshot. Issue forms preview required departmental reviewer coverage, and server-side freeze and issue validation remain authoritative.
- Unsaved opinion input stays in the browser page session for each identity, material snapshot, and batch. Opening a saved opinion in another scope preserves the first scope's input. If the destination already has unsaved input, the editor opens that input. Following a successful action on the selected issue, the ledger clears any conflicting status filter and keeps the selected issue and search query.
- Search updates the results in My Opinions, Issue Ledger, and Materials and Versions while keeping the active field. Saving an action on a selected issue returns focus to its title. The walkthrough discussion refreshes from the next bootstrap poll, independently of the opinion editor. It waits while focus is inside the discussion or a dialog is open. These interactions use the existing server visibility rules and add no API fields.
- The Data and Forms view renders data fields and form-area items as separate tables. A selected step prioritizes objects and forms explicitly linked by the material's behavior_links. Required flags are displayed as stated, with missing flags shown as pending confirmation. The tables use the existing material and add no API fields.
- Field and form-item names in Data and Forms can open the matrix at `http://<current hostname>:9992/matrix?material=<materialId>&pointer=<original JSON Pointer>`. This is a browser navigation to the independent matrix catalog, not an API write or shared-store integration. It identifies an occurrence in the original snapshot; shared step/relation edits do not rewrite those positions. An absent catalog occurrence remains an explicit unresolved link, never a same-name fallback.
- opinion.save {opinionId?,materialId,batchId?,nodeRef?,relationRef?,text,submit:boolean}: self only, drafts can edit; submitted corrections always retain before/after.
- issue.create {title,description,impact,materialIds,opinionIds,scope,affectedDepartments,assigneeId,dueDate,reviewerIds,authorityId?}: recorder role; referenced opinions must be submitted. All scopes need designated representative coverage for every affected department. Cross-department issues need >=2 departments; department issues require exactly one. Policy needs authority role. Assignee and due date may remain unset, displayed as pending assignment; never invent assignments.
- issue.assign {issueId,assigneeId,dueDate,reviewerIds,authorityId?}: recorder, not closed; reviewer changes reset review decisions with history.
- issue.respond {issueId,text,evidence}: assignee only, evidence required, sets awaiting_review and resets prior review decisions.
- issue.review {issueId,decision:approve|return,note}: designated reviewer only, nonblank note, only awaiting_review; all designated reviewer approvals close except missing policy evidence blocks close. Return sets in_progress and resets current approvals while retaining history.
- issue.authority {issueId,evidence}: designated authority only, nonblank evidence, recorded during awaiting_review for the current response cycle; does not replace reviewer approvals.
- issue.reopen {issueId,reason}: designated reviewer or authority, closed only; preserve prior closure, reset current reviews.
- observation.save {observationId?,title,materialIds,issueIds,phenomenon,timePattern,variables,hypotheses,feedback,delays,evidence,counterEvidence,nextEvidence}: any participant, creator edits with revision/history; no blank title, links validated.

All reference IDs, enums, date formats, arrays, actor capabilities and state transitions are validated server-side. Audit records are append-only actor/time/operation/detail; submitted history and raw material cannot be replaced. Deletion is not exposed in this first local version.

New departmental feedback changes previously reviewed coverage to needs_followup. Reassignment of the handler or reviewers invalidates current approvals and returns awaiting_review to in_progress. A new response, returned review or reopened issue invalidates current authority evidence; prior evidence and decisions remain in history. These are software protections against applying stale confirmation to changed work.
