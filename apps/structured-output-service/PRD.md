# 3001 单流程编制功能需求

## 1. 业务目标

3001 为业务人员提供无状态的流程编制页面。用户可以直接新建流程，也可以导入现行或历史结构化 JSON 继续整理。用户主动导出的 JSON 是唯一保存方式。

流程是本功能的管理抓手：一份 JSON 只对应一个流程；流程向下管理业务行为、判断节点、现行执行岗位、已有工作角色、输入输出和跨部门关系，向上为未来生成并关联正式制度提供依据。

## 2. 使用角色

- 编制人：在3001中整理流程并导出未审核 JSON。
- Codex：在线下对 JSON 做预审，输出独立问题清单，不在 JSON 中写入审核意见。
- 归口部门的部门MDM审核员：在MDM平台中核对预览摘要和审核依据，确认后执行受控导入。
- 外部门联系人和外部门审核员：在MDM平台承接待办中分别补充本部门实际内容、记录本部门决定。

编制人通过公司局域网直接访问3001。3001不登录、不识别账号，也不产生审核任务。

## 3. 本期范围

本次升级3001页面、五方面评审准备、业务提示、结构评分和共享结构为`process-governance-v5`。v5移除活动结构中的`cross_department_handoffs`，跨部门由业务行为的固定执行部门和流程归口部门自动识别；流程先后统一使用普通流程关系，数据传递和返回统一使用数据行为关系。`/api/template`、`/api/schema`和`/api/validate`的路径及外层请求响应保持不变，也不创建或修改3000正式待办。

### 3.1 新建和导入

- 页面提供“新建流程”入口，打开空白单流程编辑页。
- 新建时不自动填写流程名称、制度编号、业务行为或判断节点。
- 页面只提供结构化 JSON 导入，不再提供制度、表单、操作说明或其他参考材料上传入口。
- 历史 `document-structured-output-v2` 文件包含多个流程时，3001拆成多个候选，用户逐一编辑并分别导出。
- `process-governance-v1`至`process-governance-v4`可以继续导入；一份`process-governance-v5`JSON只能包含一个流程。历史文件只在当前页面内存中升级，源文件不修改，3001导出统一使用v5。

### 3.2 分区式文字编制

- 页面使用“左侧任务栏＋右侧编辑区”。左侧任务栏固定为300px，右侧编辑区占满剩余宽度，不再使用1500px居中页面上限。
- 左侧任务栏顶部显示紧凑产品标识和“无状态临时工具”，按工作阶段放置“新建流程、导入结构化文件、导出当前流程、清空当前页面”。导出常驻任务栏底部，清空与导出分隔并保留危险操作样式；操作反馈在任务栏中完整显示且不自动消失。
- 历史文件拆出多条候选流程时，左侧任务栏使用可滚动列表显示流程名称、当前项和“未导出修改”状态。列表保持原顺序，不提供排序；切换当前流程不清除其他候选、不修改JSON，也不触发未保存确认。长流程名称通过悬停提示和可访问名称提供全文。
- “文字编制”和“跨职能流程图预览”切换进入左侧任务栏。未创建或导入流程时，候选列表显示空状态，视图切换、导出和清空不可用。
- “文字编制”内部设置“基本信息、目的与范围、术语定义、流程步骤、表单与记录、流程评审”六个分区，一次只显示一个工作区。
- “流程步骤”内部设置“业务流程、流程关系、输出物与数据、关系总览”四个子分区，不提供跨部门待办汇总或“部门内调用”填写入口。“业务流程”只显示业务行为和控制节点，并根据执行部门自动标记跨部门行为。
- “流程关系”顶部常驻显示“顺序、判断分支、流程内部回路和并行路线怎么选？”，不折叠，也不在每张关系卡片中重复。没有流程关系或存在多条关系时均只显示一次。
- 常驻说明使用并列卡片：顺序表示当前节点完成后默认进入下一业务行为，判断分支按某个明确结果进入后续步骤，流程内部回路退回本流程前面已经存在的步骤重新处理，并行路线从并行开始节点同时启动多条路线。
- 常驻说明必须强调：承接顺序或判断分支的后续节点仍可以是普通业务行为；只有该节点本身还需要继续判断时，才选择判断节点。并固定显示“审核通过后顺序进入下一业务行为、审核不通过时回路退回”的示例。
- 每张关系卡片的“关系类型”字段下方提示：“默认继续下一步选择‘顺序’；按判断结果进入后续步骤选择‘判断分支’；退回前序步骤选择‘流程内部回路’；同时启动或汇合多条路线选择‘并行路线’。”
- “业务流程、流程关系、输出物与数据、术语定义”使用条目侧栏。用户在左侧选择条目，右侧一次只编辑当前条目；术语新增后自动选中，删除后选中相邻项。
- 业务行为不再分别要求用户重复填写“何时触发、开始前需要满足什么、需要什么输入、最终交付什么”。有前序关系的行为由流程关系自动显示进入方式；只有流程入口填写“流程如何开始”。“其他开始条件”只记录流程关系和输入数据不能表达的额外限制，“怎样算完成”继续由业务行为维护。
- “输出物与数据”是行为输入和输出关系的唯一编辑入口。业务行为页只读显示当前行为使用和产生的数据，并提供跳转按钮；新增或修改数据关系时同步现有`input_data_refs`、`output_data_refs`、`produced_by_behavior_ref`和`consumed_by_behavior_refs`，不建立第二套数据事实。
- 四类侧边栏使用拖动把手调整顺序，不显示上下箭头；支持鼠标、触屏和键盘开始、移动、确认、取消及长列表边缘自动滚动。排序只交换`behaviors[]`、`flow_relations[]`、`data_objects[]`或`terms[]`中对应完整对象的位置，不重新生成技术标识，也不改写任何对象内容或跨数组引用。完成后保持当前项选中；取消或位置未变化时不标记草稿已修改。
- “导出检查”必须把业务内容问题标明为“提示项（不阻止导出）”，把JSON结构或技术引用损坏标明为“阻断项”。系统生成的每条提示只定义一个确定缺陷，不得使用“或”合并问题。每个提示项可以点击，页面按问题对象切换到相应编制分区；字段问题直接聚焦存在问题的输入控件并显示红色呼吸高亮，没有具体字段的结构性问题才高亮卡片或分区。
- 新建流程默认进入“基本信息”。候选切换、未导出内容保护和导出失败保留当前页面继续沿用。
- process-governance-v5以1920×1080为主要桌面验收尺寸，并在390×844验证页面滚动、触屏拖动和内容不丢失；窄屏不得阻断导入、编辑或导出。
- “信息类型”下拉中的每个枚举项直接显示例子。例子只帮助用户理解和选择，不写入导出JSON；数据关系总览仍使用不带例子的标准类型名称。

### 3.2.1 流程评审五方面标准

- 用户导入现行或历史JSON后，进入“流程评审”即可按`process-review-readiness-v4`从第一方面走到第五方面。
- 五方面固定为“流程目的、范围和结束边界”“A1业务行为和责任角色”“业务行为逐动作可执行性”“条件分支、退回和跨部门流转”“表单、业务对象和数据输入输出”。顺序、名称和含义不得由页面临时配置。
- 第三方面只检查业务行为。编制人必须在“具体做什么”中按实际顺序写清每个动作、处理对象和结果，不得用“确保……可以完成”“保证……真实性、合理性”等抽象、定性表述代替实际动作。
- 页面自动提示未填写“具体做什么”、明显抽象定性表述和没有具体动作三类问题，并定位到对应输入控件。复杂语义和每个动作是否完整由业务部门现场确认；提示不进入普通导出确认框，不阻止草稿导出。
- 每方面显示现场确认口径和自动识别问题。问题项复用既有定位元数据，点击后切换到原分区、选中对象并聚焦实际输入控件。
- 页面总状态根据技术结构和业务提示显示。结构错误阻止下载；业务提示不阻止下载；自动检查无缺项时显示“可下载并提交部门核对”，不得显示正式评审通过。
- 没有登记数据或表单时，第五方面提示部门确认是否确实不适用，不要求用户为满足检查虚构对象。
- 多个具有完成标准的真实末端业务行为属于合法结束位置。页面只有在没有可识别结束位置时提示核对，不得要求整个流程只有一个出口。
- 五方面结果、展开状态、现场确认和依据不得写入JSON、浏览器持久化空间或服务端。归口部门MDM审核员仍在3000执行正式审核和受控导入。

### 3.2.2 结构化学习评分

- “导出检查”顶部自动显示“结构化学习评分 v1（试行）”，包括结构完整性、展示分、A—D等级、有效行为链长度、行为链系数和六个维度得分。
- 结构完整性满分100分：技术结构15分、基础信息10分、业务行为25分、行为关系20分、数据与承接20分、表单结构10分。各维度先保留1位小数，再相加。
- 技术结构由序列化解析3分、当前版本兼容3分、结构规则及技术引用4分、导出回读3分、内容与引用保持2分组成。当前文件发生技术阻断时，展示分最高为59分。
- 展示分为“结构完整性×行为链系数”。有效行为链长度为0—1、2、3、4、5个及以上时，系数分别为0.80、0.85、0.90、0.95和1.00。显式回路边不重复计数，孤立行为不增加最长有效链。
- 展示等级按展示分确定：A不低于90，B不低于75，C不低于60，D低于60。
- 判断节点至少有两条完整出口。出口只能由普通流程关系中的判断分支、默认顺序或流程内部回路表达。一条无条件顺序关系可以作为默认继续路径；判断分支和回路必须填写条件；出口目标节点可以是普通业务行为或跨部门行为。
- 每个行为按节点类型、名称、执行岗位、进入方式和完成标准五项检查。非入口行为有有效前序来源时，进入方式自动通过；流程入口必须填写“流程如何开始”。并行控制节点的完成标准自动按不适用处理。
- 数据对象的产生和使用关系不符合流程先后顺序时，数据对象关联项不得分，并逐项给出可定位的数据时序提示。该项与导出检查共用`dataFlowConsistencyDetails()`。
- 本期不判断分支条件是否互斥、流程设计是否合理、部门职责是否正确或业务事实是否真实。评分结果不是正式PMO评审结论。
- 必填项中的“待填写、待补充、待确认、未知、暂无、无、不适用、N/A”按未完成处理；选填项可以留空或使用占位说明。
- 无数据对象时，数据对象子项为0/15；无表单时，表单结构维度为0/10；没有跨部门行为时，跨部门行为完整性子项按不适用计5/5。存在跨部门行为时，只检查执行部门、岗位和有效普通流程关系。页面明确提醒用户不得为提高分数虚构对象。
- 每条已登记承接关系按五项各1分检查：方向、本流程有效锚点、外部门或“待在MDM平台明确责任部门”、传递数据或承接事项、触发条件或完成标准。外部门流程与行为、外部门是否确认、外部门完成标准、返回路径、证明材料以及前置输入实际属于哪条外部流程均不扣当前编制人的结构分。
- `behavior_description`、其他开始条件和办理时限等字段本期不计分。`behavior_description`由流程评审第三方面直接检查；其他字段按既有范围作后续集中评审预告。历史输入说明和输出说明不再要求补填。
- 计分扣项按维度显示，并复用导出检查的点击定位能力。评分只存在当前页面，不写入JSON、不改变未导出状态、不使用浏览器持久化。
- 页面复用现有结构版本和校验接口执行技术评分。校验服务不可用或前后端版本不一致时，页面显示“暂不能生成最终分数”并允许重新评分，不把系统故障算作用户扣分。

### 3.3 只读跨职能流程图预览

- 主工作区设置“文字编制”和“跨职能流程图预览”两个互斥标签。新建空白流程默认打开文字编制；导入包含已命名业务行为的文件后，自动打开预览。
- 文字编制页不显示流程图预览条件提示条或“已可查看”重复入口。跨职能流程图标签显示当前状态；系统仍不得按行为录入顺序或名称推测关系。
- 预览采用BPMN 2.0.2最小图形子集，不生成BPMN XML，也不向业务用户展示完整BPMN术语。画布上方常驻七类业务图例和阅读提示，并提供画布外的三步示例。阅读提示必须补充：“带条件的前进箭头表示判断分支；标有‘回路’的返回箭头表示退回前序步骤。”
- 每个执行部门形成一条横向泳道。归口部门在已参与执行时排在最上方，其他参与部门按组织目录顺序排列；执行岗位显示在节点第二行。无法识别部门的历史执行值进入“执行部门待明确”泳道，原值不得改写。
- 业务行为使用圆角矩形，判断使用带“×”菱形，并行拆分和并行汇合使用带“＋”菱形，节点类型为空时使用虚线矩形。会签只显示“会签×N”标记，完整会签部门继续在文字编制中查看。
- 本流程关系使用实线实心箭头。判断条件写在对应箭头上，回路使用带“回路”文字的实线回返箭头；回路和返回关系不参与主线前后层级计算。
- 判断节点表达条件判断，流程内部回路表达在明确触发条件下返回本流程前序行为。回路是关系，不要求另建一个位于判断节点之后的节点。判断节点的明确出口由普通流程关系中的顺序、判断分支或流程内部回路构成；一条顺序关系可以作为不填条件的默认继续路径。目标节点可以是普通业务行为或跨部门行为，不因承接判断结果而自动成为判断节点。
- 节点名称、岗位和关系条件必须完整显示，不得截断。业务节点正文不得小于15px，外部门节点不得小于14px，关系文字不得小于13px。预览可以按中文字符增加显示用换行，并按实际行数调整节点高度；判断和并行菱形必须同时扩大宽度和高度，使名称和岗位留在图形内部。
- 相邻层级为两个节点的半宽、最长220图形单位的关系标签和48图形单位安全间距预留空间，中心间距不得小于440图形单位。全部关系只使用直线或由直线段组成的折线，不使用曲线。单一相邻顺序关系和相邻并行路线优先使用直线；判断结果根据目标节点的上下位置进入直线、上方轨道或下方轨道；跨层并行路线根据起点所在的上下位置使用更外侧的独立折线轨道。显式“流程内部回路”和返回关系使用下方独立折线轨道。同一方向的多条绕行关系按稳定关系顺序外扩，线路、标签和点击区域不得重合，也不得让外层路线穿过内层判断路线。
- 对非回路关系构建的有向图如果形成闭环，参与闭环的判断分支、顺序或并行关系进入可定位的“关系类型请核对”清单。页面说明“该关系与其他非回路关系形成闭环；如果这是退回前序行为，请选择‘流程内部回路’。”该提示不阻止导出，不自动改关系类型，也不改变图中关系语义。
- 有关联外部门行为时，流程图直接把该行为节点放入其执行部门泳道，不再生成第二个待办节点。前置输入按“外部门行为 → 本流程行为”绘制；后续承接按“本流程行为 → 外部门行为”绘制，有返回要求时再用虚线空心箭头连接恢复位置。只有无本文件关联行为的兼容记录使用独立待办节点，部门不明时进入“承接部门待明确”泳道。
- 导入JSON中已有的内部流程调用在调用部门泳道内显示为粗边框节点。3001不提供新增或编辑入口；用户点击该节点时，页面说明由MDM平台正式功能维护。
- 主图不显示数据对象、表单、完整会签部门、流程阶段或推测的开始和结束事件。用户点击本流程节点、关系或承接卡时，页面返回文字编制并定位对应卡片。
- 关系类型、起点、终点或跨部门发送行为缺失或引用无效时，流程图不得绘制错误箭头，并显示可定位的未绘制提示。
- 用户可以平移、缩放、适应画布、重置视图和展开查看，但不能拖动节点、增删图形或连接箭头。完整画布拟合比例不低于0.60时默认显示全图；低于0.60时默认聚焦泳道表头和前两层节点，并显示“当前已聚焦流程开头，点击‘适应画布’查看完整流程”。“适应画布”始终显示全部内容，“重置视图”恢复自适应默认视野。桌面端画布高度不超过约520像素。
- 图例示例状态、展开状态和计算坐标只存在当前页面运行内存，不写入JSON。图形加载失败时，页面必须保留文字内容、导入和导出能力。

### 3.4 无状态边界

- 服务默认监听`0.0.0.0:3001`，公司局域网用户通过服务器局域网地址直接访问。
- 不写数据库。
- 不使用 `localStorage`、`sessionStorage`、IndexedDB、Cookie或服务端草稿恢复。
- 导入的结构化文件只在当前浏览器内存中处理，处理完成后不写服务端文件。
- 刷新或关闭页面后内容清空。
- 新建、导入另一文件或清空当前页面前，向用户提供“取消、先导出、放弃当前内容”。
- 3001不得通过API、数据库、队列、回调、共享会话或状态轮询与MDM平台通信。
- 3001不得调用DeepSeek，也不得把MDM-AI助手或认证网关作为启动、访问或导出的前置条件。

### 3.5 流程内容

归口部门在MDM平台确认审核导入前，流程至少应补齐：

- 发起部门、编制人、流程名称、归口部门。
- 流程目的和适用范围。
- 至少一个业务行为。
- 每个实际业务行为明确执行主体并填写完成标准。流程入口说明如何开始；其他行为只由普通前序流程关系说明进入方式。输入和输出通过“输出物与数据”登记。

能力域和业务能力属于可选归类结果，缺失时保持“未归类”，不阻止3001导出或MDM平台受控预览。

制度名称、制度编号和制度关联不是新流程审核或导入的前置条件。正式制度在流程生效后另行生成和关联。

### 3.6 流程、执行岗位和工作角色

- 新增步骤时，步骤类型默认留空，由用户主动选择业务行为、判断节点、并行开始（同时启动多条路线）或并行汇合（等待多条路线完成）。并行节点是控制节点，不承担实际业务动作。
- “业务行为或节点名称”是流程节点的主内容，用于流程图、流程关系和工作角色绑定。编制人在“具体做什么（逐动作说明）”中按实际顺序写明每个动作、处理对象和结果，帮助PMO和部门业务人员判断该行为能否直接执行。
- `behavior_name`保存业务行为或节点名称，`behavior_description`保存“具体做什么”。逐动作说明不替代名称，不显示在流程图节点上。留空或使用抽象、定性表述时，流程评审第三方面显示业务提示；该提示不阻止草稿导出、部门业务核对或3000受控预览。
- 导入缺少`behavior_description`的历史文件时，3001在当前页面内存中补为空字符串。3001不得把业务行为名称复制成补充说明，也不得推测实际操作。
- `trigger`只在没有有效前序来源的流程入口作为“流程如何开始”编辑。有前序来源时，页面根据非回路普通流程关系生成只读进入说明；不得根据数组顺序推测先后。
- `precondition`作为“其他开始条件（可选）”保留，只填写流程关系和数据关系不能表达的额外限制。`completion_standard`继续表达实际业务行为的完成判定；并行开始和并行汇合作为控制节点不要求填写完成标准。
- `input_description`和`output_description`不再提供新增编辑入口。历史非空值在折叠的只读补充中原样显示并随导出保留，3001不得自动清空、改写或据此生成数据对象。
- 判断节点至少有两条明确出口。判断分支和回路的条件应互斥并覆盖相应结果；一条顺序关系可以作为默认继续路径，不要求填写条件。3001只提示，不阻止草稿导出。
- 允许有明确退出条件的流程内部回路；非回路普通流程关系形成闭环时提示用户核对关系类型。
- 并行开始至少需要2条指向不同后续行为的并行路线。并行汇合至少需要2条普通并行路线来源。导出检查与结构评分共用同一套计数规则。
- 每个行为先选择“执行主体确定方式”：固定部门和岗位、全公司通用、按前序数据动态确定。三种方式互斥，不得用同一输入同时表达。
- 选择“固定部门和岗位”时，执行部门可从全部组织部门中选择，执行岗位只显示所选部门花名册中的岗位。岗位目录由`/api/enums`从仓库花名册只读提供，不调用MDM平台。流程归口部门未填写时也允许先选择，归口部门补齐后再识别本部门行为和跨部门行为。
- 归口部门是本部门行为和跨部门行为的识别基准。当前草稿已经填写执行主体、能力归类、正式工作角色或历史部门内调用时，编制人选择新的归口部门后，页面必须在写入新值前显示旧值、新值、重置数量、保留内容和待复核内容。编制人取消时，归口部门和当前草稿均保持不变。
- 编制人确认变更归口部门后，页面在草稿副本中清空固定执行部门和岗位，将动态责任部门恢复为“固定部门和岗位—未选择”，并把能力域、业务能力和归类状态恢复为未归类。“全公司通用”不依赖归口部门，继续保留。行为、普通流程关系、数据、表单、技术标识、正式工作角色和历史部门内调用保持不变。副本通过技术校验后才能替换当前草稿；失败时原草稿不变。
- 选择“全公司通用”时，不再选择部门和岗位，`current_actor_role`保存为`全公司`。全公司通用不是一个真实部门，也不算跨部门。
- 选择“按前序数据动态确定”时，编制人必须选择一项在本行为开始前已经形成的数据，并填写办理人员确定规则。该行为在设计时不认定为固定跨部门行为；运行时取得责任部门后，只有责任部门与流程归口部门不同时才形成跨部门办理。同一数据包含多个责任部门时，每个不同责任部门分别形成一项办理，不向全公司广播。
- 外部门执行值是合法业务行为信息。导入旧JSON后，页面按v5转换规则处理旧交接记录；无法唯一判断时不得猜测，只读保留原记录和原因，并提示用户补录业务行为、流程关系或数据关系。
- 新增行为默认使用“固定部门和岗位”，但不默认选择部门或岗位。具体岗位以“部门名称 + 岗位名称”保存到`current_actor_role`。
- 导入值未被当前花名册收录时，3001保留原值并醒目标注；花名册岗位加载失败时，也不得清除已有值。
- 工作角色与岗位严格区分。岗位容纳工作角色，一个工作角色可以由多个岗位容纳；3001不得根据岗位生成或推测正式工作角色。
- 普通编制页面不新增或编辑正式工作角色，新业务行为的`work_role`为`null`。导入文件中已有的合法`work_role`隐式保留并随再次导出带回。
- 已有工作角色仍必须绑定具体业务行为，并保持“XX行为的发起／办理／审核／批准／判断／发送／接收／会签角色”的全称，不得退化为“申请人、审核人、批准人”等孤立名称。

本期不增加“业务流程／行政流程”分类字段，统一按不存在行政流程处理。

### 3.7 跨部门行为、旧记录转换、内部调用预览和会签

- 固定执行部门与流程归口部门不同时，页面自动标记“跨部门行为”。外部门动作、执行部门、执行岗位、完成标准、表单和数据关系只保存在一个普通`behaviors[]`对象中，不增加手工跨部门字段。
- 跨部门行为的前后关系、返回和并行全部使用`flow_relations[]`。发送、接收、创建、更新和使用的数据全部使用`data_objects[].behavior_links[]`；行为选择项不得过滤外部门泳道中的行为。
- “全公司通用”不算跨部门；“按前序数据动态确定”在设计阶段不认定为固定跨部门行为。
- v1至v4旧交接记录能够唯一转换时，前置输入转换为“外部门行为→本流程行为”，后续承接转换为“本流程行为→外部门行为”，需要返回时增加“外部门行为→恢复行为”。旧记录没有关联外部门行为，但部门和办理动作明确时，页面创建对应业务行为后再转换。
- 无法唯一判断方向、锚点、恢复位置或数据关系时，页面不得猜测。原记录、转换结果和原因只读保存在`migration.legacy_cross_department_records[]`；页面分别提示用户补录业务行为、普通流程关系或数据关系。
- 重复导入不得生成重复行为、流程关系、数据关系或迁移记录。转换只处理页面内存副本；失败或导入取消时原草稿不变，用户选择的源文件始终不修改。
- 迁移记录不参与当前流程计算、评分或图形生成。MDM-AI助手不得通过受限Patch修改该记录。
- 部门内调用属于MDM平台正式功能的预览。新建流程保持`internal_process_calls: []`；3001不新增、不编辑也不校验业务完整性。导入文件中已有的`internal_process_calls[]`在当前页面内存中隐式保留，流程图可以预览，再次导出时不得清空或改写。
- 会签表示知悉，不表示审核、批准或承接。3001记录需要确认知悉的部门；全部会签对象确认知悉后，会签行为才完成。
- 会签未完成时流程不得结束，即使批准行为已经完成。

### 3.8 数据和表单

- 用户填写的输出物登记为待治理数据对象，生成隐藏技术标识。
- 3001只记录数据对象名称、产生行为和使用行为，不判断主数据、黄金源、数据责任或质量规则。“输出物与数据”是产生和使用关系的唯一编辑入口，业务行为页只读汇总。
- 数据是否可用按显式流程关系的可达性判断，不按`behaviors[]`数组顺序判断。产生行为只能把数据提供给明确可达的后续行为；同一行为不能把自己产生的数据同时作为自身输入，并行兄弟路线之间不能互相引用，汇合后的行为可以引用已完成分支的产出。
- 用于动态确定责任部门的数据执行相同的数据时序规则。只有存在有效产生位置或跨部门可用起点，并且能够沿非回路关系到达当前行为的数据才可选择；未登记产生位置的数据、当前行为及后续行为产生的数据均不可作为责任部门来源。
- `relation_type=loop`不放宽数据时序。外部输入通过`source_relations[]`记录流程开始时可用或从某个业务行为起可用；跨部门行为产生的数据通过普通流程关系判断后续可达性。
- 新建不符合时序的产生行为和使用行为选项不显示。导入历史JSON中的不符合时序引用原样保留并标记为待整改项，导出检查和结构评分使用同一套数据时序规则；提示不阻止历史草稿导出。
- “表单与记录”按整张纸质表单展示字段。用户不需要先拆分或命名数据库表；每个字段必须由用户选择“待确认”“主表字段”或具体明细表，3001不得按名称或数据类型推断归属。
- 新增表单提供“录入现有表单”和“设计新建／优化表单”两个入口，分别写入`form_design_state=current_state`和`proposed_design`。v1、v2历史表单在内存中写入`unspecified`，由用户确认后再修改。
- 同一流程可以同时保存现状表单和拟设计表单。现状表单有几张明细表就保留几张；新建或优化表单也只能由用户主动增删、命名和排序明细表。
- 每张表单使用一个紧凑表格，列为序号、字段名称、数据类型、字段归属、必填、填写说明、排序和删除。主表、全部明细表和归属待确认字段在同一表格内分组显示；明细表标题和明细表排序保留在分组标题行。业务数据归属、取值方式和多个取值来源通过字段名称下方的“数据关系”入口统一编辑，不占用独立列。每条取值来源可以选择本流程已登记的数据，或选择“外部系统”并填写系统名称和来源数据名称；外部系统来源不得自动创建本流程行为或数据关系。表格超过右侧编辑区宽度时，只在表格容器内横向滚动。
- 新增字段默认进入“字段归属待确认”。选择“新建明细表”后，页面在内存中创建空标题明细分组，并移动完整字段对象；`item_ref`、名称、类型、必填状态和填写说明必须保持不变。
- 字段和明细分组支持上移、下移。删除明细表前显示其中的字段数量并确认；用户取消时不修改数据。字段移走后不自动删除空明细表。
- “数据类型”使用标准类型下拉选择，不提供自由填写入口。标准类型为文本、长文本、数字、日期、日期时间、金额、枚举、布尔、部门、人员、文件编号、签名、图片、附件和二维码。
- 导入旧JSON中的非标准填写项类型时，3001保留原值并标注“当前类型字典未收录”，不得静默清空或猜测替换；用户主动修改后只能选择标准类型。类型字典读取失败时，选择器不可修改已有值，其他编制和导出功能继续可用。
- 内部继续使用`area_type="基本信息"`保存主表字段，使用`area_type="明细清单"`保存明细表字段，使用`areas[].items[]`保存字段；页面不得新增字段级重复归属数据，也不得生成DDL或物理数据库表。
- 表单状态待确认、字段归属待确认和多张无标题明细表逐项形成可定位提示。主表标题不提示、不计分；多张明细表本身不提示、不扣分；明细表标题暂缺不形成技术阻断。
- 本期不还原纸质表单的合并单元格、坐标、打印版式或签章位置，只保留字段、纸面顺序、主表归属和明细分组。

### 3.9 编制参考材料

- 页面暂停提供编制参考材料入口、拖放区、编辑区和缺失提示。
- 新建流程的`reference_materials`为空数组。
- 导入的旧JSON如果已有参考材料，3001在当前页面内隐式保留，再导出时原样带回；页面不展示、不编辑，也不自动清空。
- 导入的现行或历史JSON如果已有`internal_process_calls[]`，3001只在流程图中预览，并在再次导出时原样带回；页面不提供填写入口。
- 服务端确定性解析能力保留用于历史文件迁移和回归测试，不作为业务用户页面功能。

### 3.10 导出和审核边界

- 3001允许导出不完整草稿。
- 导出文件名统一为 `未审核-发起部门-流程名称-导出时间.json`。
- JSON不包含审核状态、审核意见或批准标记。
- Codex预审材料、PMO行动项和3000审核准备材料与流程JSON严格分开。
- 3001硬校验只保证JSON可读和单文件引用不损坏。唯一入口、结束条件、循环、会签、并行关系、外部门历史行为和跨流程关系只提示或原样导出。
- 导出检查和结构评分中的每条问题均按“当前情况＋建议”显示。当前情况只陈述页面可以从草稿确认的对象、数量、关系类型和缺失字段；建议列出用户需要执行的具体操作。提示不得把推测写成事实，也不得在已有对象可以修改时一律建议新增。
- 判断节点出口检查同时统计从该节点发出的有效本流程顺序、判断分支、流程内部回路和完整的后续承接。顺序出口可以作为默认继续路径，不要求填写条件，但必须填写目标行为；判断分支和回路必须填写条件及目标行为；后续承接至少满足本节五项结构信息。前置输入不是判断出口。显式流程内部回路不参与主线入口和出口数量计算。
- 3001导出仍标记为“未审核”。只有归口部门MDM审核员登录MDM平台完成审核，且服务端复核和原子写入成功后，内容才能进入治理数据。
- “导出检查”在评分和提示项之后、导出按钮之前显示两张静态卡片。第一张卡说明业务评审完成后的MDM平台受控导入和正式编辑路径；第二张卡将系统动力学评价明确标记为“后续规划”。
- 系统动力学评价预告只说明未来将结合正式流程、运行数据和实际反馈观察长期运行影响。预告不得给出分数、上线时间或固定评价模型，也不得替代业务评审、审核和管理决策。
- 两张卡片不提供按钮、链接、上传或状态写入，不调用MDM平台接口，也不写入导出JSON。

- 不在页面提供编制参考材料上传或编辑。
- 不在3001新增或编辑部门内调用；该能力由MDM平台正式功能维护。
- 不在普通编制页面新增或编辑正式工作角色。
- 不要求局域网用户通过MDM-AI助手或认证网关访问3001。
- 不在3001生成制度、维护制度审批或关联正式制度。

## 5. 桌面任务栏

3001左侧任务栏显示工具名称、操作入口、候选流程、查看方式、操作反馈和唯一保存方式警示。页面不显示DeepSeek停用说明、MDM平台通信或线下审核边界的通用声明。3000本地流程编辑器本期保持现状；3001任务栏只为未来迁入3000保留“开始、当前流程、查看方式、完成与清理”的操作分组，不共享运行状态，也不调用3000接口。

## 6. 验收标准

1. 用户无需先上传文件即可创建空白流程。
2. 页面刷新后无法恢复内容，浏览器存储中不存在草稿。
3. 新建、导入其他文件或清空前出现三选一保护。
4. 新增步骤的类型为空，不默认认定业务行为或判断节点。
5. 3001导出符合`process-governance-v5`，根对象只有一个`process`；v1至v4导入后只在页面内存中升级，导出统一为v5。
6. 旧版多流程JSON可拆分为多个候选，候选逐一导出后内容不串流程。
7. 导出文件名包含“未审核”、发起部门、流程名称和导出时间。
8. 左侧任务栏不显示DeepSeek停用说明或系统边界通用声明；页面及服务端不包含DeepSeek调用入口或健康状态。
