# 3001 单流程治理编制工具

> 状态：局域网无状态临时工具
> 端口：`3001`
> 导出结构规则：`docs/contracts/process-governance-v5.schema.json`

3001用于编制一条流程。用户可以直接新建，也可以导入现行或历史结构化JSON继续整理。页面中的内容只存在于当前浏览器运行内存；用户主动导出的JSON是唯一保存结果。

页面使用桌面专用布局。左侧300px任务栏显示工具名称、新建与导入入口、候选流程、查看方式、操作反馈、导出、清空和唯一保存方式警示；右侧编辑区占满剩余宽度。页面不重复展示模型停用、系统通信或线下审核边界的通用声明，相关边界仍按本README和目录`AGENTS.md`执行。

## 运行

```powershell
npm install
npm start
```

服务启动后，局域网用户访问`http://<服务器局域网IP>:3001`。服务器维护人员也可以使用`http://127.0.0.1:3001`检查本机服务。需要隔离监听地址或端口时：

```powershell
$env:STRUCTURED_OUTPUT_HOST='127.0.0.1'
$env:STRUCTURED_OUTPUT_PORT='3101'
npm start
```

服务默认监听`0.0.0.0:3001`，公司局域网用户无需DeepSeek、MDM-AI助手或认证网关即可直接使用。不得把3001映射到公网；部署主机应通过公司网络边界和防火墙限制访问来源。

当前`process-governance-v5`把业务行为、普通流程关系、输出物、数据、表单和字段连成可核对关系链。跨部门状态由固定执行部门与流程归口部门自动判断，不再创建独立交接对象。数据行为关系只保存在`data_objects[].behavior_links[]`；表单行为操作、字段业务数据归属和字段取值来源分别保存在表单关系与字段关系中。接口路径及外层请求响应保持不变，也不创建或修改3000正式待办。

## 用户操作

1. 在左侧任务栏点击“新建流程”，或导入`.json`结构化文件。导入文件包含多条历史候选时，任务栏按原顺序列出流程名称和未导出状态；点击流程可以切换当前编辑对象，不会清除其他候选。
2. 在“文字编制”中依次切换“基本信息、目的与范围、术语定义、流程步骤、表单与记录、流程评审”，一次只处理一个工作区。“业务流程”只显示业务行为和控制节点；固定执行部门与归口部门不同时，页面自动标记“跨部门行为”。
3. 填写业务行为或节点时，先选择固定部门和岗位、全公司通用、按前序数据动态确定三种方式之一。固定部门可选择任意组织部门及其花名册岗位；全公司通用不算跨部门；动态责任部门要选择前序数据并填写办理人员确定规则。流程入口填写“流程如何开始”，后续行为的进入方式由流程关系自动带出；输入和输出统一到“输出物与数据”维护。
4. 在“流程关系”中建立全部前后关系，包括跨部门行为之间的先后、返回和并行关系。在“输出物与数据”中添加创建、更新或使用行为；选择项列出本部门和跨部门的全部业务行为，并显示执行部门。
5. 业务流程、流程关系、输出物与数据和术语定义都通过左侧拖动把手调整条目顺序。拖动只整理列表，不改变技术标识、流程关系或其他引用。
6. 在左侧任务栏切换到“跨职能流程图预览”，核对执行部门泳道和流程关系。普通流程关系跨越不同部门泳道时，页面自动显示跨部门箭头。
7. 进入“流程评审”，按照五方面标准从第一项走到第五项。页面显示当前操作状态、现场确认口径和可点击问题；点击问题后返回原字段整改。结构化学习评分折叠为辅助信息。
8. 点击左侧任务栏底部的“导出当前流程”。文件名统一为`未审核-发起部门-流程名称-导出时间.json`。
9. 业务评审完成后，把导出的未审核JSON交给归口部门继续核对。3000当前只承接v1至v3，v5文件不能直接导入3000。

3001不提交审核、不记录审核结果，也不与MDM平台通信。“流程评审”中的两张卡片只说明后续处理路径和规划方向，不提供跳转、上传或状态写入。系统动力学评价尚未上线，不属于当前结构化学习评分。

## 流程评审五方面标准

页面使用固定规则版本`process-review-readiness-v4`，按以下顺序组织部门现场核对：

1. 流程目的、范围和结束边界：确认流程为什么启动、适用于什么范围、从哪里开始，以及在哪些真实结果形成后结束。
2. A1业务行为和责任角色：逐个确认做什么、由哪个部门和岗位执行，以及做到什么程度才算完成。
3. 业务行为逐动作可执行性：逐个核对“具体做什么”是否按实际顺序写清每个动作、处理对象和结果。不得用“确保……可以完成”“保证……真实性、合理性”等抽象、定性表述代替实际动作。
4. 条件分支、退回和跨部门流转：逐条确认判断、退回、并行，以及跨部门行为的执行部门、岗位、前后流程关系和数据关系。
5. 表单、业务对象和数据输入输出：逐张确认表单主表和各明细表字段，逐个确认输出物与数据的产生行为和使用行为。

页面显示“存在结构错误”“有业务提示，可以下载”或“可下载并提交部门核对”。技术检查进行中或服务不可用时，页面单独说明运行状态，不把系统故障算作部门问题。页面自动检查未发现缺项时，每方面仍显示“待部门确认”；业务部门必须确认JSON与真实做法一致。当场不能确认的事项应在会议记录中写明缺少的依据和确认主体，不得在JSON中补造结论。

五方面评审结果、现场确认和依据只存在于本次查看过程，不写入JSON。第五方面只自动识别业务行为说明缺失、明显抽象定性表述和没有具体动作三类问题；每个动作是否完整仍由业务部门现场确认。多个末端业务行为只要分别具有真实完成标准，就可以作为合法结束位置；页面不得要求整个流程只有一个出口。

“流程评审”页同时提供节点组合关系表和九类设计图例：基础顺序、判断分支、单层循环、会签接并行汇合、并行内判断、并行内循环、嵌套循环、嵌套并行、并行路线提前中止。九类图例使用与“跨职能流程图预览”相同的节点、泳道、关系线和布局组件，用户可以平移、缩放、适应画布、重置视图和展开查看。图例只在“流程评审”显示，不进入其他编制分区，也不修改当前JSON。

循环和并行按以下规则核对：

- 每条显式回路必须从回路检查节点另设退出路线。嵌套循环逐层退出；内层退出可以进入外层循环，最外层必须退出到循环外后续行为。
- 并行开始的全部路线必须共同到达同一个并行汇合。并行路线内部可以包含判断、循环和内层并行，但内层结构必须先闭合。
- 任一并行路线在共同汇合前成为流程结束位置时，该结构不得按并行通过评审。实际只执行一条结果路线时，应使用判断节点和判断分支。
- 页面只根据明确节点和关系判断结构。业务人员仍须确认某个行为是否会中止整个流程；3001不得根据行为名称猜测。

## 结构化学习评分 v1（试行）

“流程评审”中可以展开辅助评分并查看两个分数：

- 结构完整性：六个结构维度得分之和，满分100分。
- 展示分：结构完整性乘以有效行为链系数，用于本期结构化学习成果展示。

六个维度为：

| 维度 | 分值 | 检查内容 |
|---|---:|---|
| 技术结构 | 15 | JSON解析、当前版本兼容、结构规则及技术引用、导出回读、内容与引用保持 |
| 基础信息 | 10 | 发起部门、编制人、流程名称、归口部门、目的、范围 |
| 业务行为 | 25 | 节点类型、名称、执行岗位、流程入口或已有前序来源、完成标准 |
| 行为关系 | 20 | 关系字段、节点覆盖、判断出口、回路条件、并行结构 |
| 数据与跨部门行为 | 20 | 数据对象15分，跨部门行为完整性5分 |
| 表单结构 | 10 | 表单名称、唯一主表、区域结构、填写项结构 |

有效行为链长度为0—1、2、3、4、5个及以上时，展示系数分别为0.80、0.85、0.90、0.95和1.00。显式流程内部回路不重复计数，孤立行为不增加最长有效链。展示分达到90、75、60时，等级分别进入A、B、C；低于60为D。当前文件发生技术阻断时，展示分最高为59分。

判断节点可以使用一条无条件顺序关系作为默认继续路径。判断分支和流程内部回路必须填写条件；承接判断结果的后续节点仍可以是普通业务行为。并行开始和并行汇合都是控制节点，不承担实际业务动作；并行开始至少需要2条流向不同后续行为的并行路线，并行汇合至少需要2条普通并行路线来源。评分不判断条件是否互斥，也不判断流程设计、部门职责或业务事实是否正确。

必填项使用“待填写、待补充、待确认、未知、暂无、无、不适用、N/A”时，按未完成处理；选填项可以留空或使用占位说明。无数据对象时，数据对象子项为0/15；无表单时，表单结构维度为0/10；没有跨部门行为时，跨部门行为完整性子项按不适用计5/5。不要为提高分数虚构数据、表单、行为或关系。

每条已登记承接关系只检查五项结构信息，每项1分：承接方向、本流程有效锚点、外部门或“待在MDM平台明确责任部门”、传递数据或承接事项、触发条件或完成标准。外部门流程、外部门行为、是否确认承接、返回路径、证明材料以及前置输入实际属于哪条外部流程，都不扣当前编制人的结构分；缺口只形成治理提示。

“具体做什么”、其他开始条件和办理时限等字段本期不计分。“具体做什么”仍由流程评审第三方面检查，其他字段按既有范围作为后续治理提示。历史输入说明和输出说明按原值保留，不再要求补填。

评分结果只存在当前页面，不写入导出JSON，也不改变候选流程的未导出状态。校验服务不可用或前后端版本不一致时，页面暂停生成最终分数；服务恢复后点击“重新评分”。这种运行异常不会形成用户扣分。

本评分只反映当前JSON展示出的结构化学习成果，不参与五方面评审状态计算，不代表流程设计正确、部门职责正确或业务事实已经确认。

### 顺序、判断分支和流程内部回路怎么选

“流程步骤—流程关系”顶部常驻显示以下说明；没有流程关系或存在多条流程关系时，说明都只显示一次：

- 顺序：当前节点完成后，默认进入下一业务行为。判断节点可以用一条顺序关系表示默认继续路径，不需要填写条件，但必须填写要去的业务行为。
- 判断分支：需要按某个明确判断结果进入后续步骤时使用。需要填写判断条件和要去的步骤。
- 流程内部回路：因为审核不通过、材料有误等原因，退回本流程前面已经存在的步骤重新处理。需要填写退回条件和退回位置。

承接顺序或判断分支的后续节点仍可以是普通业务行为。该节点只有在自身还需要继续判断时，才选择“判断节点”。流程内部回路是一条返回关系，不是一个新节点，也不需要另外创建“回路节点”。

例：部门负责人审核报销单。审核通过 → 使用顺序关系进入财务复核；审核不通过 → 使用流程内部回路退回申请人补充材料。财务复核仍是普通业务行为。

“关系类型”下方同时提示：默认继续下一步选择“顺序”；按明确判断结果进入后续步骤选择“判断分支”；需要退回前面步骤重新处理，选择“流程内部回路”；同时启动或汇合多条路线选择“并行路线”。四类说明在支持的桌面宽度并列显示。

## 跨职能流程图预览

- “文字编制”和“跨职能流程图预览”互斥显示，图形不会长期占用文字表单面积。新建空白流程默认打开文字编制；导入包含已命名业务行为的JSON或历史候选后，页面自动打开预览。
- 预览采用BPMN 2.0.2的最小图形子集，但页面继续使用业务语言。画布上方说明业务行为、判断、并行、普通流程关系、跨部门流程关系、内部流程调用和类型待判断，并可展开三步读图示例。
- 每个执行部门形成一条横向泳道。归口部门在已参与执行时排在最上方，其他部门按组织目录顺序排列；节点第二行显示执行岗位。无法识别部门的历史执行值进入“执行部门待明确”泳道，原值保持不变。
- 业务行为使用圆角矩形，判断使用带“×”菱形，并行拆分或汇合使用带“＋”菱形，未选择节点类型时使用虚线矩形。会签只在对应节点右上角显示“会签×N”，完整部门清单仍在文字编制中查看。
- 本流程关系使用实线实心箭头，判断条件直接写在箭头上，回路使用带“回路”文字的实线回返箭头。图例旁固定提示：“带条件的前进箭头表示判断分支；标有‘回路’的返回箭头表示退回前序步骤。”只有关系类型、起点和终点都明确且引用有效时才绘制箭头；没有关系的行为保持孤立，3001不会按录入顺序推测先后。
- 节点名称、岗位和关系条件按中文字符自动换行并完整显示，不做省略。业务节点正文使用15px，外部门节点使用14px，关系文字使用13px；节点会按文字行数增高，判断和并行菱形同步扩大，相邻层级会为节点和关系标签保留安全间距。
- 所有关系线只使用直线或由直线段组成的折线，不使用曲线。单一相邻顺序关系和相邻并行路线优先使用直线；判断结果根据目标节点的上下位置进入直线、上方轨道或下方轨道。跨层并行路线从当前节点所在一侧继续向外绕行，不与内层判断路线共用通道；“流程内部回路”和返回关系使用独立下方折线轨道。同一方向出现多条绕行关系时，后续路线依次外扩，使线路、标签和点击区域保持分离。
- “判断节点”负责表达条件判断，“流程内部回路”负责表达在某个条件下返回本流程前序行为。回路是从当前节点发出的关系，不是必须另建在判断节点之后的节点；跨部门去向仍使用指向外部门行为的普通流程关系。
- 如果判断分支、顺序或并行关系与其他非回路关系形成闭环，预览下方显示“关系类型请核对”。该提示不阻止导出，也不会自动改关系类型；如果业务含义确为退回前序行为，编制人应在文字编制中选择“流程内部回路”。
- 有关联外部门行为时，流程图直接把该行为节点放入实际执行部门泳道，不再生成第二个待办节点。前置输入按“外部门行为 → 本流程行为”绘制；后续承接按“本流程行为 → 外部门行为”绘制，有返回要求时再用虚线空心箭头连接恢复位置。只有无本文件关联行为的兼容记录使用独立待办节点，部门不明时进入“承接部门待明确”泳道。
- 主图不显示数据对象、表单、完整会签部门、流程阶段或推测的开始和结束事件。用户可以平移、缩放、适应画布、重置视图、展开查看或点击图形定位文字卡片，但不能拖动节点、增删图形或连接箭头。完整画布拟合比例不低于0.60时默认显示全图；更大的流程默认聚焦泳道表头和前两层节点，并显示查看全图提示。“适应画布”显示全部内容，“重置视图”恢复自适应默认视野。
- 图例展开状态、预览展开状态和计算坐标只存在当前页面内存，不写入JSON。图形加载失败时，文字内容、导入和导出功能继续可用。

## 新建规则

- 一份JSON只对应一个流程。
- 页面通过`/api/template?version=process-governance-v5`读取服务端空白模板，不在前端维护第二份结构定义。v1至v4只作为兼容导入版本。
- 新建时不自动生成流程名称、制度编号、业务行为或判断节点。
- 新增节点类型默认留空，由编制人选择业务行为、判断节点、并行开始（同时启动多条路线）或并行汇合（等待多条路线完成）。实际操作使用业务行为类型，需要并行时另建控制节点。
- 制度名称、制度编号和正式制度关联不是本阶段的前置条件。
- 能力域和业务能力可以不填，不阻止草稿导出、部门业务核对或3000受控预览。
- 页面暂不要求用户提供编制参考材料。新建流程仍按结构规则导出`reference_materials: []`。

## 纸质表单字段录入

- “录入现有表单”和“设计新建／优化表单”分别创建现状表单和拟设计表单；空白流程不会自动生成表单。
- 每张表单使用一个紧凑编辑表格，列为序号、字段名称、数据类型、字段归属、必填、填写说明、排序和删除。主表、全部明细表和归属待确认字段在同一表格内分组显示；业务数据归属、取值方式和多个取值来源从字段名称下方的“数据关系”统一编辑，不占用独立列。取值来源可以选择本流程已登记的数据，也可以直接选择“外部系统”并填写系统名称和来源数据名称；外部系统来源不要求关联本流程行为。表格超过右侧编辑区宽度时，只在表格容器内横向滚动。

## 桌面支持范围

- process-governance-v5以1920×1080为主要桌面验收尺寸，并在390×844验证滚动、触屏拖动和内容不丢失。
- 页面不显示低分辨率专门提示。低于支持尺寸时保持桌面布局并允许滚动；导入、编辑和导出继续可用，页面不会因此丢失内容。
- 3000本地流程编辑器本期不修改。3001保留“开始、当前流程、查看方式、完成与清理”的任务分组，供未来迁入3000时映射到草稿打开、保存和提交审核；本期不共享组件、页面状态或接口。
- 主表不填写标题。明细表标题按纸质单据填写；没有标题时页面显示顺序占位，但不把猜测名称写入JSON。
- 字段和明细表支持排序。字段改变归属时保留完整对象和`item_ref`；删除明细表前显示字段数量，取消删除不修改当前内容，空明细表不自动删除。
- 多张明细表本身不是问题。表单状态、字段归属或多张明细表的区分标题未确认时，导出检查逐项提示并定位到对应控件。

## 执行岗位和工作角色

- “业务行为或节点名称”是流程节点的主内容，用于流程图、流程关系和工作角色绑定。“具体做什么”用于按实际顺序写清每个动作、处理对象和结果，帮助PMO和部门业务人员判断该行为能否直接执行。
- `behavior_name`保存业务行为或节点名称，`behavior_description`保存“具体做什么”。逐动作说明不替代名称，不显示在流程图节点上。留空或使用抽象、定性表述时，第五方面显示可定位业务提示，但不阻止草稿导出。
- 执行岗位来自仓库中的`docs/organization/花名册.md`。3001通过本服务的`/api/enums`只读取得岗位，不调用MDM平台接口、数据库或会话。
- 每个行为先选择执行主体确定方式：固定部门和岗位、全公司通用、按前序数据动态确定。
- 固定部门模式提供全部组织部门，执行岗位只显示所选部门花名册中的岗位。归口部门未填写时也可以先选择，补齐后页面再识别本部门行为和跨部门行为。
- 归口部门是本部门和跨部门识别的基准。已有相关内容时，选择新的归口部门不会立即改写草稿；页面先列出影响范围。确认后，页面清空固定部门和岗位及动态责任部门设置，并把能力归类恢复为未归类。普通流程关系、数据关系和表单关系保持不变；取消或技术校验失败时不修改草稿。
- 归口部门变更不会删除“全公司通用”行为、行为名称和说明、普通流程关系、输出物与数据、表单、技术标识、正式工作角色或历史部门内调用。正式工作角色和历史部门内调用会在确认框中标记为保留但需复核。变更前可以在同一确认框先导出当前草稿。
- 全公司通用不是一个部门，不算跨部门，也不生成跨部门关系。该模式保存`actor_assignment_mode=company_wide`和`current_actor_role=全公司`。
- 动态责任部门必须选择本行为开始前已经形成的数据，并填写办理人员确定规则。该模式在设计阶段不认定为固定跨部门行为；运行时责任部门与归口部门不同时才按跨部门办理，涉及多个不同责任部门时分别办理，不向全公司广播。
- 导入历史JSON时，外部门执行值原样保留。旧交接记录能唯一转换时，页面自动形成业务行为、普通流程关系和数据行为关系；不能唯一转换时只读保留原记录并提示补录，不再提供归并向导。
- 新增业务行为默认使用固定部门模式，但不默认选择部门或岗位。选择具体岗位后，`current_actor_role`保存为“部门名称 + 岗位名称”。
- 导入值未被当前花名册收录时，页面保留原值并标注“当前花名册未收录”。用户主动修改固定部门模式后只能选择有效岗位。
- 花名册岗位暂时不可用时，3001不会清除已有执行岗位，其他内容仍可继续编制和导出。

岗位不等同于正式工作角色，3001不会根据岗位生成工作角色。新业务行为的`work_role`为`null`；导入文件中已有的合法`work_role`会在内存中隐式保留并随再次导出带回。

历史正式工作角色仍不能脱离业务行为保存，其全称保留业务行为和职责，例如：

- `费用申请行为的发起角色`
- `费用审核行为的审核角色`
- `费用批准行为的批准角色`

岗位、人员和花名册不由3001维护；3001只是读取花名册岗位供编制人选择。花名册归属存在疑问时，由行政人事部修正花名册真源，3001不得自行改写。

## 跨部门行为、旧记录转换和部门内调用预览

- 固定执行部门与流程归口部门不同时，页面自动标记“跨部门行为”。行为的名称、执行部门、岗位、完成标准、表单和数据关系只在普通业务行为中维护，不再创建独立跨部门待办或交接字段。
- 跨部门前后关系、返回和并行全部使用`flow_relations[]`。数据传递和返回使用`data_objects[].behavior_links[]`；创建、更新和使用关系都可以选择外部门业务行为。
- v1至v4旧交接记录能够唯一判断时，前置输入转换为“外部门行为→本流程行为”，后续承接转换为“本流程行为→外部门行为”，需要返回时增加“外部门行为→恢复行为”。旧记录没有关联外部门行为，但部门和办理动作明确时，页面创建对应业务行为后再转换。
- 页面创建外部门行为时保留v4业务流程列表的原显示位置：前置输入放在锚点行为之前，后续承接放在锚点行为之后；同一锚点的多条同方向记录保持旧记录顺序。页面不会把这些外部门行为统一移到业务流程末尾，流程先后仍以普通流程关系为准。
- 无法唯一判断方向、锚点、恢复位置或数据关系时，页面不猜测。原值、转换结果和原因只读保存在`migration.legacy_cross_department_records[]`，不参与当前流程计算、评分或图形生成。
- 重复导入不得生成重复业务行为、流程关系、数据关系或迁移记录。转换只处理页面内存中的副本，用户选择的源文件及其SHA-256不变。
- 部门内调用属于MDM平台正式功能。3001不提供新增或编辑入口；新建流程保持`internal_process_calls: []`。
- 导入JSON中已有的`internal_process_calls[]`只在流程图中预览，并在当前页面内存中隐式保留。再次导出时不得清空或改写。为保护历史数据，被部门内调用引用的业务行为或数据对象不得在3001中删除。
- 会签只表示确认知悉。3001记录需要确认知悉的部门；全部会签完成前，流程不得视为结束。

## 数据和表单

- “信息类型”下拉逐项显示例子：业务信息如申请金额、客户名称；业务结论如审核结论、验收结论；业务状态如已提交、已完成；标识符如申请单号、合同编号；文件或附件如报价单文件、验收照片；其他信息输出如提示信息、说明文字。例子不写入导出JSON。
- “输出物与数据”是行为输入和输出的唯一编辑入口。业务行为页只读显示进入方式、使用数据和产生数据，并可直接跳转到该入口。
- 输出物按待治理数据对象登记，记录创建、更新和使用行为。行为选择项显示“序号＋执行部门＋行为名称”，跨部门行为增加标记；不得因行为位于外部门泳道而过滤。产生后的数据只能提供给流程关系明确可达的后续行为；同一行为自身、明确的前序行为和并行兄弟路线不能引用，汇合后的行为可以引用已完成分支产出。
- 动态责任部门来源数据执行同一套先后规则：必须有明确产生位置或跨部门可用起点，并且能够沿非回路流程关系到达当前行为。当前行为和后续行为产生的数据不可选。
- 跨部门前置输入从关联行为起可用；跨部门返回数据从恢复行为起可用。显式流程内部回路不放宽数据先后规则。
- 新建时不显示不符合流程先后顺序的产生和使用选项。历史JSON中的不合规引用继续保留并显示整改提示，不自动删除，也不阻止草稿导出。
- 3001不判断主数据、黄金源、数据责任、质量规则或共享范围。
- “表单与记录”是独立工作区。用户先选择表单或记录，再在同一张紧凑表格中编辑主表、各明细表和归属待确认字段。
- 页面使用“表单或记录名称”“表单或记录编号（如有）”“主表字段”“明细表标题”“字段归属”和“数据类型”。
- 新建表单只建立一个空主表框架，不自动生成名称、编号、标题或填写项。每张表单正常情况下只有一个主表，可以增加多张明细表。
- 表单与业务行为可以关联，也可以暂不关联。
- “填写项类型”必须从3001提供的标准类型中选择，不允许自由填写。当前类型包括：文本、长文本、数字、日期、日期时间、金额、枚举、布尔、部门、人员、文件编号、签名、图片、附件和二维码。
- 导入旧JSON时，如果填写项类型不在当前字典中，3001保留原值并标注“当前类型字典未收录”；用户主动修改后只能改选标准类型。类型字典暂时不可用时，选择器不可修改，但已有值和其他编制内容不受影响。
- JSON结构不变：`area_type: "基本信息"`表示主表，`area_type: "明细清单"`表示明细表，`areas[].items[]`保存各自填写项。
- 导入缺少主表、包含多个主表或存在未分类结构的旧文件时，页面保留全部内容并提示确认，不自动改写，也不把该提示作为技术性导出阻断。

## 编制参考材料

- 页面不提供“导入参考材料”、拖放区或参考资料编辑区，也不提示用户补充参考材料。
- 新建流程导出空的`reference_materials`数组。
- 导入的旧JSON如果已经包含参考材料，3001在当前页面内隐式保留，再次导出时原样带回；页面不展示、不编辑，也不自动清空。
- 服务端确定性解析能力仅保留用于历史文件迁移和回归测试，不再作为业务用户页面功能。

## 历史文件兼容

确定性文档解析器继续在内存中生成`document-structured-output-v2`结果。页面不会把旧版结构直接导出：

1. 旧文件按`process_ref`拆分。
2. 每条流程成为一个页面候选。
3. 关联步骤、行为详情、已有工作角色、表单、旧跨部门记录和部门内调用跟随当前流程；旧记录按v5规则转换或只读归档。
4. 用户逐一检查并分别导出`process-governance-v5`。

旧版主表和不同明细表分别迁移，不合并不同明细表。无法直接归入当前单流程结构的证据和额外角色绑定会保留在“旧版结构化补充信息”参考材料中，避免静默丢失历史成果。

旧版`process-governance-v1`和`document-structured-output-v2`没有独立的“具体做什么”补充说明。导入时，3001保留原业务行为名称，并在当前页面内存中把`behavior_description`补为空字符串；系统不得把业务行为名称复制成补充说明，也不得推测实际操作。早期v5字段取值来源没有`source_type`时，按“本流程输出物与数据”读取，并在再次导出时补齐来源类型和空的外部系统字段；源文件不修改。

## 无状态和安全边界

- 服务端使用内存上传，不保存原文件和业务内容。
- 页面不使用浏览器持久化保存草稿。
- 刷新或关闭页面后，本次内容无法恢复。
- 新建、导入其他文件或清空前，页面提供“取消、先导出当前流程、放弃当前内容”。
- `/api/data`和`/api/export`不可用。
- 3001不调用MDM平台的API、数据库、队列或任何共享状态。
- 3001不调用DeepSeek，不依赖MDM-AI助手或认证网关；这些服务不可作为3001启动或访问的前置条件。

## 校验边界

3001导出前只硬校验：

- JSON符合`process-governance-v5`；v1至v4可以导入，旧流程、数据和表单关系只在当前页面内存中转换，导出统一升级为v5。
- 一份文件只有一个流程。
- 技术标识不重复。
- 当前文件内的行为、数据、关系和表单引用没有损坏。

“导出检查”把下列内容标为“提示项（不阻止导出）”。每条提示分为“当前情况”和“建议”：当前情况只描述系统能够从草稿确认的事实，建议直接说明用户应进入的位置及应执行的动作。系统不得把缺条件、缺目标等不同问题合并为一条提示。用户点击提示后，页面返回相应分区，聚焦存在问题的输入控件，并显示红色呼吸高亮；没有具体输入控件的结构性问题仍定位到对应卡片或分区。流程入口说明缺失时定位“流程如何开始”；数据先后不成立时定位对应数据对象的产生行为或使用行为。

- 发起部门、编制人、目的和范围是否补齐。
- 固定部门模式是否已经选择执行部门和花名册岗位。
- 动态责任部门是否已经选择有效前序数据并填写办理人员确定规则。
- 旧跨部门记录是否存在无法唯一转换的方向、锚点、恢复位置或数据关系。该项分别定位到业务行为、流程关系或数据关系补录位置，不阻止草稿导出。
- 表单是否缺少主表。
- 表单是否包含多个主表。
- 表结构类型是否已选择。
- 流程入口、出口、可达性和回路触发条件。
- 判断节点是否有至少两个明确出口，以及各出口是否补齐必要信息。出口只能由普通流程关系中的顺序、判断分支或流程内部回路表达；作为默认继续路径的顺序关系可以不填条件，但必须填写目标行为。判断分支和回路必须填写条件及目标。显式回路不参与主线入口和出口数量计算。
- 并行开始的并行路线是否达到2条，并行汇合的有效来源是否达到2个。已经存在但类型为“顺序关系”的相关连线会在当前情况中逐项说明，并直接建议把现有关系改为“并行路线”；只有没有可利用的现有关系时才建议新增。结构评分与导出检查共用同一套计数和建议规则。
- “流程评审”单独检查业务行为逐动作可执行性、每层循环的退出路线、每个并行开始的共同汇合，以及并行路线是否在汇合前形成流程结束位置。这些评审专用提示不进入普通导出确认框。
- 数据产生行为是否明确位于使用行为之前；结构评分、选择器和导出检查共用同一套可达性规则。
- 会签对象是否完整。
- 外部目标流程、接收行为和责任部门是否待在MDM平台继续治理；这些缺口不阻止3001导出。

业务事实由真实责任人审核；MDM平台负责身份、部门决定、最终责任人、状态流转、发布卡口和跨对象可执行性校验。

## 常见故障

页面提示“3001前端与服务端版本不一致”时，用户应保持当前页面打开，不要刷新或关闭。维护人员重启3001服务后，用户在原页面再次执行“新建流程”或“导出当前流程”；重启服务不会清除已经打开页面中的编制内容。旧后端把首页HTML返回给空白模板接口时，页面必须显示版本或服务异常提示，不得直接显示JSON解析错误。

维护人员可以用以下命令确认服务端默认结构版本：

```powershell
(Invoke-RestMethod http://127.0.0.1:3001/api/schema).properties.schema_version.const
```

命令应返回`process-governance-v5`。如果仍返回v1至v4或`document-structured-output-v2`，说明端口3001仍由旧进程提供服务。

`/api/schema`响应头和`/api/template`响应同时提供结构摘要，用于确认当前页面与3001服务端结构一致。该检查只比较3001自身版本，不依赖外部助手。
