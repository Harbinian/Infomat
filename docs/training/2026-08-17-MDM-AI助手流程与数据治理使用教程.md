# MDM-AI助手流程与数据治理使用教程

> 版本：V1.0  
> 日期：2026-08-17  
> 适用范围：MDM-AI助手五账号试点  
> 主要使用人：丁硕、工程技术部研发、工程技术部批产、行政人事部  
> 管理员：张广懿  
> 当前输出结构：`process-governance-v4`

## 一、这份教程解决什么问题

本教程用于指导试点人员把一条真实业务流程及其数据、表单和跨部门关系整理成一份可继续核对的结构化文件。

当前完整操作路线如下：

> 准备证据 → 登录并新建DSH治理工作区 → 绑定本人Key → AI对话填报 → 下载未经独立预审的v4 JSON → 独立结构预审 → 下载预审后的JSON和问题处理记录 → 手工导入3001核对 → 业务部门确认事实

`process-governance-v4`是3001当前使用的单流程结构。教程中的“JSON”指按该结构保存的未审核流程文件。业务人员不需要手工编辑JSON代码。

当前成果停在经过结构预审、3001核对和部门业务核对的v4文件。3000目前仍按v3承接，不得把v4文件直接导入3000。MDM工作组应在v4兼容或迁移方案另行审核通过后，再组织受控承接。

## 二、先记住六条边界

1. 一份JSON只整理一条流程，同一时间只有一名编制人维护当前JSON。
2. 业务部门说明并确认实际做法；MDM工作组维护结构规则；AI只负责追问、整理和结构检查。
3. AI答复、自动校验、流程图和结构评分都不代表业务事实已经确认。
4. AI不得决定部门责任、主数据分类、权威来源、对象合并、审批是否合理或使用哪个应用系统。
5. 信息不足时，用户应回答“暂不清楚”，并记录缺少的证据和确认主体。不得为了填满页面而猜测。
6. 当前治理工作区只在本次登录会话的DSH子进程内存中保存。刷新页面可以恢复；退出、会话到期、结束工作区、DSH故障或服务重启后，用户只能用此前主动下载的文件恢复。

## 三、五个账号分别做什么

| 账号 | 部门字段 | 主要责任 | 不得执行的动作 |
|---|---|---|---|
| 张广懿管理员 | 信息化项目组 | 发布和维护试点服务；查看账号Key/DSH会话状态及非内容用量；按要求切换DSH与经典应急入口；处理版本和结构故障 | 不查看其他账号余额、指纹、案例名称或完整Key；不代替业务人员确认流程事实 |
| 丁硕 | 信息化项目组 | 完成1个统一基准案例 | 不替业务部门确认真实流程或数据责任 |
| 工程技术部研发 | 工程技术部 | 完成1个统一基准案例和1个经授权的研发真实案例 | 不与其他人员并行修改同一份JSON |
| 工程技术部批产 | 工程技术部 | 完成1个统一基准案例和1个经授权的批产真实案例 | 不与其他人员并行修改同一份JSON |
| 行政人事部 | 行政人事部 | 完成1个统一基准案例和1个经授权的行政人事真实案例 | 不与其他人员并行修改同一份JSON |

统一基准材料由试点负责人统一提供。真实案例的流程名称、范围、编制人、业务核对人和材料权限由对应部门确认，本教程不预设真实流程名称。

## 四、开始前准备

### 1. 确认人员和流程

开始填报前，编制人应完成以下确认：

| 检查项 | 通过标准 | 未通过时怎么处理 |
|---|---|---|
| 当前流程 | 流程名称、业务目的、起点和结束结果能够说明 | 暂停填报，由业务核对人确认流程边界 |
| 当前编制人 | 同一时间只有一人维护当前JSON | 先确定唯一当前文件和唯一编制人 |
| 业务核对人 | 能够核对实际步骤、岗位、表单、字段、条件和异常 | 暂停形成确认结论，只保留待核对草稿 |
| 资料范围 | 制度、规程、表单、台账或业务说明的版本及允许使用范围明确 | 不上传或粘贴未授权材料 |
| 脱敏情况 | 材料不包含密码、API Key、无权使用的个人信息或其他敏感内容 | 先完成脱敏并由材料提供方确认 |
| 证据位置 | 能够记录文件名、版本或日期，以及条款、页码、表格或记录位置 | 无法定位时标为待补证据 |

### 2. 准备可读取材料

MDM-AI助手可以直接接收：

- 对话框中输入的文字；
- `.docx`、`.txt`和`.md`文字材料；
- 3001导出的部分完成或待继续完善的`process-governance-v4` JSON。

MDM-AI助手不处理PDF、扫描件、图片或光学字符识别（Optical Character Recognition，OCR）。需要使用这些材料时，材料提供方应先提供经授权、已脱敏、可以直接读取文字的版本。

旧版v1、v2或v3 JSON不得直接作为MDM-AI助手的当前草稿。编制人应先把旧文件导入3001，由3001在当前页面内存中升级并重新导出v4，再将v4文件导入MDM-AI助手。

## 五、登录、新建治理工作区并绑定本人DeepSeek API Key

### 步骤1：登录

1. 使用试点负责人提供的内网HTTPS地址打开MDM-AI助手。
2. 在“用户名”和“密码”中输入本人的试点账号信息。
3. 点击“登录”。
4. 系统默认进入“DSH流程与数据治理工作区”，并显示本人账号和“DeepSeek API Key”状态卡后，登录成功。

用户电脑不需要安装DSH，也不需要复制Infomat仓库、结构规则或运行配置。服务器上的DSH只提供治理功能，不向业务用户开放编码Agent、命令、任意文件访问、技能、子Agent、网页检索或模型设置。

### 步骤2：新建治理工作区

1. 在“DSH治理工作区”区域输入本次案例名称。名称只用于本人当前登录会话内识别案例，不代表流程事实已经确认。
2. 点击“新建工作区”。
3. 页面显示当前案例和版本号后，开始本案例的填报。

一个工作区只处理一个治理案例。用户可以在下拉框中切换本人当前会话内的工作区。点击“结束当前工作区”会立即清除该工作区的材料、对话、草稿、预审问题和核对记录；执行前必须先下载需要保留的文件。

同一登录Cookie的多个标签页共享工作区。两个标签页同时修改同一案例时，旧标签页会显示`STATE_CONFLICT`。旧标签页保留尚未提交的输入；用户先复制需要保留的文字，再点击“重新加载最新状态”，不得直接覆盖新版本。

### 步骤3：配置Key

1. 点击“配置Key”。
2. 在密码掩码输入框中粘贴本人的DeepSeek API Key。
3. 点击“验证并用于当前会话”。
4. 页面显示“已验证”以及类似`SHA-256: a1b2c3d4e5f6`的不可逆指纹后，Key绑定成功。

页面不会显示完整Key，也不提供查看完整Key的功能。用户不得把本人Key发送给管理员或其他试点人员，不得把Key写入JSON、材料、聊天内容、截图或问题记录。

### 步骤4：理解Key状态

| 页面状态 | 含义 | 用户操作 |
|---|---|---|
| 未配置 | 当前登录会话没有可用Key | 点击“配置Key”并输入本人Key |
| 已验证 | 当前登录会话可以调用模型 | 继续对话填报或独立结构预审 |
| 余额偏低 | Key已经保存，但余额不足或低于20元 | 根据费用安排决定是否继续；系统不会自动充值 |
| 已失效 | DeepSeek拒绝当前Key，系统已经清除该会话Key | 重新配置有效Key；当前治理工作区和本页输入仍保留 |

Key只保存在当前登录会话对应的助手服务内存中。刷新页面时，同一登录会话的Key继续有效；退出、会话到期、模型认证失败或服务重启后，用户必须重新输入Key。同一账号的不同登录会话不共享Key。结束DSH工作区不会清除仍有效的Key。

未配置Key时，用户仍可导入、编辑、校验和下载JSON，但不能发送填报对话或启动独立结构预审。

## 六、使用“对话填报”整理流程

### 步骤1：从空白流程或已有v4文件开始

从空白流程开始时，编制人先确认已经新建本案例的治理工作区，再在“回复AI”中说明当前已知信息。

继续已有成果时，编制人展开“补充材料（可选）”，在“继续编辑已有3001格式JSON”中点击“选择JSON草稿”。导入成功后，该文件成为当前页面的唯一草稿，原有对话、字段确认状态和文字材料会被清空。

导入会覆盖当前页面草稿。执行导入前，编制人应先下载并保存需要保留的现有JSON。

### 步骤2：使用首次输入模板

编制人可以复制以下模板，并只填写已经掌握的事实：

```text
我要梳理一条真实业务流程。

流程名称：
归口部门：
业务目的：
流程从什么事件或条件开始：
流程形成什么结果后结束：
目前已经确认的主要步骤：
已经确认的参与部门和岗位：
已经确认的表单、记录或台账：
已经确认的输出物或数据：
本轮依据的资料及具体位置：
目前暂不清楚的事项：

请先从最影响继续整理的一项信息开始提问。
```

编制人勾选“我输入的是已授权、已脱敏的信息”后，点击“发送”。AI每轮只提出一个主问题，并沿当前业务行为继续追问。

### 步骤3：逐项回答业务行为

AI询问某项业务行为时，编制人应根据实际情况回答以下内容。用户不需要一次填完全部项目，应先回答AI本轮提出的问题。

```text
业务行为名称：
触发事件或进入条件：
执行部门：
执行岗位：
具体做什么：
1.
2.
3.
收到的表单、记录、输出物或数据：
产生或修改的表单、记录、输出物或数据：
下一步交给哪个部门或岗位：
办理时限或时间要求：
完成标准：
是否存在判断、退回、循环、并行、会签或跨部门承接：
事实依据及具体位置：
暂不清楚或不适用的项目：
```

“具体做什么”应按实际顺序写清动作、处理对象和结果。例如，不能只写“保证信息真实”“确保流程完成”或“加强过程管理”。

责任主体、业务条件或处理对象发生变化时，编制人应拆成不同业务行为或分别说明。系统按钮和页面操作只能用于说明实际做法，不能代替业务行为。

### 步骤4：说明判断、退回、循环和并行

编制人应按实际关系说明流程路径：

- 默认进入下一步时，说明前一步完成后进入哪个业务行为；
- 根据明确结果选择不同路径时，分别说明判断条件和去向；
- 材料有误或审核不通过时，说明退回条件和返回到哪个已有业务行为；
- 多项工作同时启动时，说明每条并行路线以及全部路线共同汇合的位置；
- 任一路线可能在汇合前结束整个流程时，不得把该结构描述为并行；
- 跨部门办理时，说明发送方、接收部门、办理事项、传递数据、触发条件、完成标准、是否返回，以及返回后从哪里继续。

编制人不能确认某条路径时，应回答“暂不清楚”，并说明应由谁确认。AI不得根据业务行为名称或录入顺序自动推断流程关系。

## 七、从流程中整理数据和表单

流程与数据治理应从实际业务行为、输出物、表单和字段开始，不要从“申报本部门主数据”开始。

### 1. 整理输出物和数据

编制人应对每项实际存在的输出物或数据逐项说明：

| 需要说明的内容 | 回答示例格式 |
|---|---|
| 数据名称 | 名称：…… |
| 业务含义 | 这项数据表示……，用于…… |
| 信息类型 | 文件、记录、编号、状态、日期、数量或其他实际类型 |
| 产生或更新位置 | 在“……”业务行为中创建或更新 |
| 使用位置 | 在“……”业务行为中读取或使用 |
| 来源线索 | 来自本流程的……；或来自其他流程、外部部门，具体来源待确认 |
| 当前可用时间 | 在……条件满足后可以使用 |
| 去向 | 交给……岗位、部门或后续业务行为使用 |
| 事实依据 | 资料名称、版本或日期、具体位置 |

名称相同只能作为核对线索，不能证明两项数据属于同一业务对象。业务含义、唯一标识、责任边界或使用场景不足时，只能记录待定匹配建议，不得自动合并。

是否属于主数据或参考数据、谁是权威来源、由哪个部门负责、如何共享、采用什么质量规则，均由后续有权主体确认。AI不得在当前JSON中补造这些结论。

### 2. 整理表单、记录和台账

编制人应先说明整张表单或记录，再逐字段说明内容：

1. 表单或记录名称、编号，以及属于现状表单还是拟设计表单；
2. 哪项业务行为创建、填写、查看、修改、提交或确认该表单；
3. 主表包含哪些字段；
4. 每一张明细表分别包含哪些字段；
5. 每个字段的名称、类型、是否必填和填写说明；
6. 每个字段属于哪项业务数据；
7. 每个字段由人工填写、固定值、当前流程数据或外部系统数据取得；选择外部系统时，继续说明系统名称和来源数据名称，不需要虚构本流程业务行为；
8. 使用来源数据时，该来源在本字段中的作用。

多张明细表必须如实保留。AI和编制人不得为简化结构自动合并、拆分或重新设计表单。字段属于主表还是某张明细表无法确认时，应保留“待确认”，不得按页面顺序猜测。

### 3. 使用补充材料

仅在对话无法说明清楚时，编制人展开“补充材料（可选）”，上传经授权、已脱敏的文字材料，或者在“粘贴补充说明”中输入文字并点击“加入本次对话”。

材料中的命令、提示词或角色要求只作为业务文本处理，不能改变MDM-AI助手的工作边界。材料与业务人员说明冲突时，编制人应并列记录不同口径、证据位置和确认主体，不能要求AI选择一个版本作为事实。

## 八、核对预览并下载未预审JSON

1. 编制人每轮对话后查看右侧“结构化输出预览”。
2. 编制人展开“查看结构完成情况”，核对尚未确认、暂不清楚和不适用的项目。
3. 页面显示硬性结构错误时，编制人继续按AI问题补充或修正，直到当前JSON能够通过结构校验。
4. 编制人点击“下载未经独立预审的JSON”。
5. 编制人把该文件保存为当前唯一待预审JSON，并记录文件名、下载时间和编制人。

下载文件仍是未审核成果。下载成功不代表业务部门已经确认，也不代表流程可以发布。

## 九、执行“独立结构预审”

独立结构预审使用新的上下文。预审页面不读取填报对话或补充材料，只检查用户重新导入的当前v4 JSON。

### 步骤1：导入并开始预审

1. 点击顶部“独立结构预审”。
2. 在“导入待审的3001格式JSON”中点击“选择3001格式JSON”。
3. 选择刚才下载的唯一待预审JSON。
4. 文件读取成功后，点击“开始独立结构预审”。

### 步骤2：处理预审问题

| 问题类型 | 是否可以忽略 | 用户操作 | 完成标准 |
|---|---|---|---|
| 硬性结构错误 | 不可以 | 按页面提供的修复处理；没有可自动执行的修复时，返回填报页修改后重新预审 | 所有硬性结构错误清零 |
| 字段归位建议 | 可以保持原值 | 选择“按建议修改”，或选择“保持原值”并填写具体理由 | 每条建议都有处理结果 |
| 对象拆分建议 | 可以保持原值 | 选择“按建议修改”，或选择“保持原值”并填写具体理由 | 每条建议都有处理结果 |

用户每处理一项问题，页面会重新校验当前JSON，并同步刷新“3001输出与流程图预览”。流程图生成失败时，用户继续处理问题并保存JSON；不得因为图形不可用而修改业务事实。

### 步骤3：下载两个文件

所有问题完成处置后，编制人分别点击：

1. “下载问题处理记录”；
2. “下载预审后的3001格式JSON”。

问题处理记录与JSON必须分开保存。预审意见、保持原值理由和处理状态不得写入正式JSON。

## 十、手工导入3001核对

1. 编制人点击“打开结构化工具”，或者使用试点负责人提供的3001局域网地址。
2. 编制人把预审后的v4 JSON手工导入3001。
3. 编制人依次核对“基本信息、目的与范围、术语定义、流程步骤、表单与记录、流程评审”。
4. 编制人打开“跨职能流程图预览”，核对执行部门、业务行为和流程关系。
5. 编制人进入“流程评审”，按五方面逐项核对：
   - 流程目的、范围和结束边界；
   - A1业务行为和责任角色；
   - 业务行为逐动作可执行性；
   - 条件分支、退回和跨部门承接；
   - 表单、业务对象和数据输入输出。
6. 编制人在3001中只修改能够确认的内容。业务事实不明确时，编制人把问题登记到部门业务核对记录，不得用占位内容冒充确认结果。
7. 编制人导出当前流程，再把导出的文件重新导入3001，核对业务内容、对象数量和稳定引用是否保持一致。
8. 编制人下载并保存最终待部门核对的v4 JSON。

3001不保存草稿、不记录审核结论，也不自动把业务内容发送给MDM-AI助手或3000。用户主动下载和手工导入是两个工具之间唯一的业务内容传递方式。

## 十一、部门业务核对和待定事项

业务核对人应逐项核对流程事实、岗位、条件、表单、字段、数据用途、来源、异常和跨部门交接。页面自动检查没有发现问题时，业务核对人仍须确认JSON是否符合实际做法。

业务核对记录至少包含：

| 核对对象 | 当前事实 | 证据位置 | 核对结论 | 缺少的证据 | 确认主体 | 后续动作和期限 | 关闭条件 |
|---|---|---|---|---|---|---|---|
|  |  |  | 已确认/待定/不适用 |  |  |  |  |

信息不足时，业务核对人应保留“待定”，并记录：

- 缺少什么事实或证据；
- 由哪个角色或部门确认；
- 确认后影响哪些流程、数据、责任或系统关系；
- 计划完成时间；
- 什么证据能够关闭该事项。

待定状态本身不自动升级。跨部门无法形成一致意见、事项影响已发布流程版本、事项影响部门责任边界或事项超过已批准期限时，PMO再按现行规则登记并组织升级。

## 十二、文件保存和交接

编制人应至少分别保存以下四类文件：

```text
01-未经独立预审的未审核JSON/
02-预审后的未审核JSON/
03-独立问题处理记录/
04-部门业务核对和待定事项记录/
```

每次交接应记录文件名、SHA-256摘要、交出人、接收人、时间和用途。多人可以分别提出核对意见，但只有当前编制人可以把已确认修改顺序写入唯一当前JSON。

需要计算文件摘要时，MDM工作组可以在Windows PowerShell中执行以下只读命令，并把输出的`Hash`记录到交接表：

```powershell
Get-FileHash -Algorithm SHA256 -LiteralPath '待交接JSON的完整路径'
```

不得把API Key、登录密码、未经授权的原始材料或个人敏感信息写入上述文件。

## 十三、常见异常处理

| 情况 | 页面或系统表现 | 用户操作 | 内容是否保留 |
|---|---|---|---|
| 未配置Key | 对话发送和独立结构预审不可用 | 点击“配置Key”并输入本人Key | 当前页面JSON仍保留 |
| Key无效 | 验证失败，新Key不保存 | 核对Key后重新输入；不得发给管理员排查明文 | 当前页面JSON仍保留 |
| 余额不足或低于20元 | 显示“余额偏低”或余额不足提示 | 根据费用安排决定是否继续；系统不会自动充值 | Key可以保留，当前页面JSON仍保留 |
| 模型认证失败 | 显示“已失效”，系统清除当前会话Key | 不刷新页面，重新配置有效Key | 当前页面JSON仍保留 |
| 未新建DSH工作区 | 对话发送和独立结构预审不可用 | 输入案例名称并点击“新建工作区” | 模板读取、JSON导入、编辑、校验和下载仍可用 |
| DSH实例达到上限或启动失败 | 登录后无法进入治理工作区 | 记录提示时间并联系管理员；不得改用未经限制的原生DSH | 本页尚未关闭的内容不应被自动改写 |
| DSH实例异常结束 | 页面提示运行实例需要重新启动 | 先下载本页仍可下载的内容，再返回登录入口重新启动实例和导入文件 | 当前打开页面的内存输入暂时保留；刷新后不能依赖服务器恢复 |
| 服务重启、会话到期或退出 | Key状态恢复为“未配置”，或要求重新登录；DSH工作区被清除 | 使用最近下载的文件重新登录、新建工作区并配置本人Key | 只有已下载文件保留 |
| 版本变化或维护状态 | 页面提示先下载当前草稿再刷新 | 先点击“下载当前草稿”，再刷新并重新导入 | 已下载草稿保留 |
| 3001不可用或版本不一致 | 模型调用或结构读取被阻止 | 停止调用，联系MDM工作组处理版本或服务问题 | 当前页面JSON不应被自动改写 |
| PDF、扫描件或图片无法读取 | 页面不接收或无法提取文字 | 请求材料提供方提供经授权、已脱敏的可读文字版本 | 原材料保持不变 |
| 流程图生成失败 | 显示流程图不可用提示 | 继续核对文字、问题和JSON；向MDM工作组登记技术问题 | 当前JSON仍保留 |
| 刷新当前页面 | 页面重新读取同一登录会话的DSH工作区 | 等待恢复完成后继续；不要重复提交 | 当前DSH实例仍有效时可以恢复 |
| 关闭页面或浏览器异常退出 | 重新打开后是否恢复取决于原登录Cookie和DSH实例是否仍有效 | 优先使用最近下载的唯一当前JSON；不能把工作区当作长期保存 | 退出、到期、实例结束或服务重启后无法恢复 |
| 多标签页版本冲突 | 显示`STATE_CONFLICT`和“重新加载最新状态” | 先复制本页尚未提交的文字，再重新加载最新状态并重新填写 | 系统不覆盖新版本；本页输入在重新加载前保留 |

## 十四、七个案例怎么验收

业务验收共7个案例，包括4个统一基准案例和3个真实案例：

| 案例类型 | 责任账号 | 数量 | 材料要求 |
|---|---|---:|---|
| 统一基准案例 | 丁硕、工程技术部研发、工程技术部批产、行政人事部各1个 | 4 | 使用试点统一提供的合成或标准材料 |
| 真实案例 | 工程技术部研发、工程技术部批产、行政人事部各1个 | 3 | 由对应部门确认流程范围、编制人、业务核对人、资料权限和脱敏结果 |

每个案例必须完成：

1. 使用本人Key完成对话填报；
2. 下载未经独立预审的未审核JSON；
3. 完成独立结构预审；
4. 消除全部硬性结构错误；
5. 对全部字段归位和对象拆分建议作出处置；
6. 分别下载预审后JSON和问题处理记录；
7. 手工导入3001，完成查看、必要编辑、导出和重新导入；
8. 确认业务内容和稳定引用没有丢失；
9. 对真实案例形成部门业务核对和待定事项记录。

正式发布后，5名用户还要分别使用合成材料完成一次Key绑定、一次填报和一次独立结构预审，以验证每个账号的模型调用链路。该验证会产生实际费用，执行前必须取得明确确认。管理员不得集中收集其他账号的Key。

## 十五、管理员操作附录

### 1. 管理员可以查看什么

张广懿登录后可以进入“试点管理”，查看：

- 当前应用提交、结构版本和维护状态；
- 五个账号是否存在有效Key会话；
- 每个账号的有效Key会话数量；
- 每个账号的有效DSH运行实例数量；
- 当前全局入口是DSH还是经典应急入口；
- 不包含材料、对话、草稿和模型答复的用量汇总。

管理员不得查看其他账号的余额、Key指纹、工作区名称、案例名称或完整Key，也不得要求用户把Key发送给管理员。

### 2. 发布或维护时怎么处理

1. 发布前，管理员开启维护状态，并通知用户下载当前草稿。
2. 用户看到维护或版本变化提示后，应先点击“下载当前草稿”。
3. 管理员完成固定版本发布和烟测后，解除维护状态。
4. 用户刷新页面，并重新导入已下载草稿。
5. 服务重启清除所有内存Key后，每名用户重新输入本人Key。

管理员需要切换入口时，在“试点管理”中选择“DSH治理工作区”或“经典应急入口”，填写具体原因后提交。入口切换只影响用户随后进入的前端，不复制两个入口中的业务内容，也不终止仍有效的Key。DSH兼容门禁或运行故障未排除时，管理员可以切换到经典入口；不得临时向业务用户开放原生DSH。

### 3. 管理员怎么处理Key问题

- 用户忘记或丢失Key时，管理员只指导用户到DeepSeek账号侧处理，不收集Key明文；
- 用户Key认证失败时，管理员检查非内容错误码和服务状态，不读取用户Key；
- 用户余额不足时，管理员不查询其他账号余额，不执行自动充值；
- 用户草稿丢失时，管理员只能协助查找用户主动下载的文件，服务端没有业务草稿可以恢复。
- DSH实例故障时，管理员只能查看实例是否有效和数量，不能查看工作区名称、案例名称、材料、对话或草稿。
