# 3001 流程结构化编制一页操作路线

> 版本：V1.2  
> 培训日期：2026-08-17  
> 修订日期：2026-08-17  
> 适用人员：编制人、业务核对人、部门 MDM 审核员  
> 重要边界：3001 不保存草稿。刷新或关闭页面前，编制人必须下载当前 JSON。

## 一、先记住五句话

1. 一条流程只维护一份当前 JSON，一个文件只编制一个流程。
2. 业务部门确认事实，MDM 工作组检查结构，PMO 跟踪过程。
3. 不知道的内容写“待定”，同时写明谁确认、缺什么证据。
4. MDM-AI助手或Codex形成的结构预审问题、部门核对记录和后续审核依据都不能写进JSON。
5. 当前3001输出v4，3000仍按v3承接；v4兼容或迁移方案审核通过前，不得把v4文件直接导入3000。

## 二、开始前

| 操作人 | 检查内容 | 通过标准 |
|---|---|---|
| 编制人 | 确认自己是当前 JSON 的唯一维护人 | 同一时段没有第二人编辑另一份副本 |
| 业务核对人 | 确认制度、表单和实际做法的核对范围 | 来源文件版本和授权范围明确 |
| 部门 MDM 审核员 | 了解当前版本边界 | 不把v4文件直接导入当前只承接v3的3000 |
| MDM 工作组 | 确认服务版本 | Git提交、`process-governance-v4`和结构摘要已记录 |

## 三、3001 四轮编制顺序

1. 编制人打开 3001，选择“新建流程”或导入本部门上一份当前 JSON。
2. 第一轮“流程骨架”：编制人填写流程名称、归口部门、目的和范围，再按真实顺序填写主要业务行为、执行部门、岗位和行为关系。能力域和业务能力没有依据时保持未归类。完成后下载第一轮JSON。
3. 第二轮“完成与异常”：编制人补充流程入口行为的“流程如何开始”、每个业务行为的完成标准，并在“具体做什么”中按实际顺序写清每个动作、处理对象和结果；不得用“确保……可以完成”“保证……真实性、合理性”等抽象、定性表述代替实际动作。编制人同时补充实际存在的判断、退回、并行和异常路径，不得靠数组顺序或文字名称推测关系。完成后下载第二轮JSON。
4. 第三轮“数据与表单”：编制人从真实输出物识别待治理数据对象，并关联产生行为和使用行为；再逐张填写表单或记录，确认主表字段和每一张明细表字段。名称相同不代表同一对象，不同明细表不得合并。完成后下载第三轮JSON。
5. 第四轮“跨部门核对”：编制人填写跨部门行为、交接关系、触发条件、完成标准和返回要求。责任部门不明确时保持待定，不得猜测。完成后下载第四轮JSON。
6. 编制人打开“流程评审”，按`process-review-readiness-v4`依次核对“流程目的、范围和结束边界”“A1业务行为和责任角色”“业务行为逐动作可执行性”“条件分支、退回和跨部门承接”“表单、业务对象和数据输入输出”。编制人展开“节点组合、循环退出与嵌套并行图例”，逐层核对循环退出和并行汇合；问题项可以点击并返回原字段。
7. 编制人将第四轮JSON重新导入3001，核对数量、内容和稳定引用，再下载最终待核对JSON。

流程标准评审准备只发现缺项和定位整改，不记录正式评审结论。结构评分只提供次要学习反馈，不代表业务已经正确，也不作为下载、审核或发布门槛。

## 四、业务核对和预审

1. 业务核对人逐项确认流程事实、条件分支、岗位、表单、字段、数据用途、来源和异常处理。
2. 业务核对人不能确认时，在核对表中记录“待定”、确认主体、缺少证据和后续动作。待定本身不自动升级。
3. 五账号试点人员使用MDM-AI助手的“独立结构预审”检查当前v4 JSON；其他受控场景可以由Codex执行线下结构预审。两种方式都要另存问题处理记录，不修改审核状态，不替业务部门作结论。
4. 编制人处理结构问题。硬性结构错误必须关闭；字段归位和对象拆分建议可以保持原值，但必须记录理由。业务问题由业务核对人确认；技术问题由MDM工作组处理；跨部门分歧由PMO登记，不由编制人、MDM-AI助手或Codex代判。

## 五、当前成果交接和3000版本边界

1. 编制人把预审后的v4 JSON手工导入3001，完成查看、必要编辑、导出和重新导入核对。
2. 业务核对人逐项确认流程事实，并把未确认事项、缺少的证据、确认主体和关闭条件记录在JSON之外。
3. 编制人分别交接最终v4 JSON、结构预审问题处理记录和部门业务核对记录。
4. MDM工作组核对文件版本、内容摘要、业务内容和稳定引用，并保留当前唯一文件记录。
5. 3000当前仍按v3承接。MDM工作组未完成v4兼容或迁移方案、旧数据影响分析、验证和审核前，任何人员不得把v4文件直接导入3000。

## 六、文件命名和交接

3001 导出文件名由系统生成：

```text
未审核-发起部门-流程名称-导出时间.json
```

受控工作目录至少分开保存：

```text
01-current-json/
02-department-review/
03-structure-pre-review/
04-pending-items/
```

每次交接记录文件名、SHA-256 摘要、交出人、接收人、时间和用途。编制人收到修改意见后，只在唯一当前 JSON 上顺序修改。

## 七、遇到问题找谁

| 问题类型 | 示例 | 处理入口 |
|---|---|---|
| 技术问题 | 页面打不开、校验服务异常、引用损坏、导入报错、版本不一致 | MDM 工作组 |
| 业务问题 | 实际步骤、责任岗位、表单字段、条件分支不明确 | 本部门业务核对人 |
| 跨部门分歧 | 两部门对承接事项、责任或数据含义意见不同 | PMO 登记事实和证据；满足升级条件后按现行规则升级 |
| 权限问题 | MDM-AI助手不能登录、账号或Key会话状态异常 | 管理员核对账号和非内容状态；用户自行保管并重新配置本人Key |

## 八、禁止事项

- 不多人并行编辑后再合并 JSON。
- 不把六张业务视图合成一张，不把多张明细表合并。
- 不删除条件分支来赶进度。
- 不把任一路线可能中止整个流程的结构设置为并行；这种互斥结果使用判断分支。
- 不让嵌套循环共用一个含义不清的退出条件；每一层分别填写继续条件和退出去向。
- 不把系统当前保存位置直接写成权威来源。
- 不把同名对象自动合并。
- 不把改进建议改写为当前流程事实。
- 不把教学样例导入3000形成正式记录。
- 不把未审核 JSON、问题清单或审核材料写入 `docs/norms/`。
- 不把当前v4 JSON直接导入只承接v3的3000。
- 不用`admin`代替业务人员填写、确认或处理业务问题。
