# GL/FM客户文件承接治理升级计划

> 状态：首版已执行并验证
> 日期：2026-06-23
> 背景：当前流程地图与数据地图梳理中，部分 `GL*` 文件和 `FM*` 表单属于客户文件或客户体系表单，不能直接等同于昌兴自有流程。后续需要建立“客户要求 -> 昌兴承接责任 -> 昌兴流程/表单/系统入口 -> 证据成熟度”的治理层。

## 一、目标

建立客户文件承接审计层，先识别 `GLG/GLC/GLB/FM` 客户要求，保护 `GLTX` 昌兴自有文件，生成对象链承接任务，并让 PMO/部门桑基图显示“客户要求-待承接”状态。

首版不批量删除历史映射，不急着做完整平台操作闭环，先完成审计、任务生成、页面标识和质检规则。

## 二、硬规则

1. `GLTX*` 是昌兴自有文件，可作为昌兴承接证据。
2. `GLG*`、`GLC*`、`GLB*`、`FM*` 默认按客户文件或客户体系表单处理。
3. 无前缀但正文明显写客户组织、客户表单或客户流程的文件，进入“来源边界待确认”。
4. 客户文件只能证明客户要求、客户表单、客户流程约束，不能单独证明昌兴责任部门、审批链、输入来源部门、输出目标部门或系统落位。
5. 历史已入正式 DCM/BBM、但主要依据为客户文件的映射，不批量撤回；先做语义降级和承接任务生成。

## 三、承接状态机

| 状态 | 含义 |
|---|---|
| 未识别承接 | 客户要求存在，但未找到昌兴承接责任 |
| 已识别承接责任 | 已明确昌兴责任部门、责任角色或工作组 |
| 已形成昌兴承接流程 | 有昌兴内部流程、实际执行记录或部门确认，并明确责任部门、动作和输出物 |
| 已入正式映射 | 通过受控入库进入 DCM/BBM、MDM 建设要求或流程地图 |

承接任务以“要求对象链”为最小治理单元，例如设计输入清单、DRD、评审行动项、EBOM、工艺文件、技术协调单等，不按整份文件粗粒度处理，也不按每一句话机械拆分。

## 四、首版实施范围

### 4.1 文件与证据识别

- 在候选流水线和源文件清单中落实来源边界识别。
- 识别规则必须区分 `GLTX` 与 `GLG/GLC/GLB/FM`。
- 候选项、对象链、角色候选、审批链候选和受控传递候选继承来源边界。
- 输出客户文件影响清单，至少包含部门、文件、对象链、当前映射位置、承接状态和建议动作。

### 4.2 历史映射语义降级

- 保留现有 DCM/BBM 行，避免流程地图断裂。
- 对主要依据为客户文件且缺少昌兴承接证据的条目标注为“客户要求-待昌兴承接”。
- 对已有 `GLTX`、内部确认、实际执行记录或部门确认支撑的条目，可标注为“已形成昌兴承接流程”。
- 不从正式映射中批量删除条目。

### 4.3 承接任务生成

- 在流程治理任务数据中生成“客户文件承接”任务。
- 默认按已有映射部门派发；无法判断部门时进入流程治理负责人兜底池。
- 每条任务至少包含：客户文件、要求对象链、涉及部门、当前映射位置、承接状态、缺口说明、建议动作、责任人或确认对象。
- 同一对象链来自多个客户文件或表单时合并为一条任务，并保留多来源引用。

### 4.4 页面与图谱标识

- 部门桑基图和 PMO 流程地图继续展示待承接链路，但用独立证据颜色和标签标明“客户要求-待昌兴承接”。
- 已承接条目可展示为“客户要求-已形成昌兴承接流程”。
- 页面不得把待承接项显示成普通正式映射。

### 4.5 质检规则

- `check-dcm-bbm` 增加客户文件边界检查。
- 客户文件证据不得单独支撑正式审批链、输入来源部门、输出目标部门或昌兴自有系统落位。
- `audit-a1-transfer-evidence` 保持外部客户、供应商、泛称部门不得进入输入/输出部门字段的规则。
- 增加 `GLTX` 保护测试，确保 `GLTX-*` 不被误判为客户文件。

## 五、建议实现路径

1. 先扩展源文件识别和候选流水线，生成客户文件影响清单。
2. 扩展映射差异审计，将客户文件引用转为承接任务，不直接改正式表。
3. 扩展解析器输出的证据状态，让部门桑基图和 PMO 图能显示待承接颜色。
4. 扩展质检脚本，拦截客户文件直接支撑正式结论。
5. 选择工程技术部作为首个试点，复核 `GLG/GLC/GLB/FM` 与 `GLTX` 分界是否正确。
6. 试点通过后再推广到项目管理部、物资保障部、质量管理部等已大量引用 GL/FM 的部门。

- `GLG1201`、`GLC120101`、`GLB140410-*`、`FM1201-*` 被识别为客户文件或客户体系表单。

- 已有 `GLTX` 或部门确认补证时，可进入“已形成昌兴承接流程”。
- PMO/部门桑基图中待承接项显示独立颜色和标签。

## 七、执行补充约定

### 7.1 本轮首版边界

本轮先实现规则识别、审计输出、承接任务和展示/质检保护，不做 MDM 平台第三入口，不批量调整正式 DCM/BBM 行。

首版允许改动：

- 仓库级脚本与测试：`scripts/`、根 `package.json` 测试入口。
- 流程证据链技能脚本与测试：`.agents/skills/process-evidence-mapping/`。
- PMO / 部门桑基图展示生成逻辑：以 parser 输出为入口，不手工重造 PMO 数据。
- 报告或计划类沉淀：`docs/reports/`、`docs/superpowers/plans/`。

首版禁止改动：

- 不批量删除或改写 `docs/norms/{部门}部门-能力-流程-系统映射关系.md` 的正式映射。
- 不把客户文件证据直接提升为昌兴审批链、输入来源部门、输出目标部门或系统落位。
- 不把待承接链路显示成普通正式映射。

### 7.2 向量回归策略

本机当前瓶颈在向量回归。首版执行时：

- 最小 embedding 探测可用于确认 Ollama 与 `qwen3-embedding:latest` 可用。
- 全量向量回归允许放宽等待时间；若仍超时，按技能规则降级为规则/关键词抽取。
- 降级时必须在报告、候选输出或测试说明中写明“本轮未使用向量检索”，不得隐含为已完成向量召回。

### 7.3 推荐执行顺序

1. 先用 TDD 补来源边界识别测试，覆盖 `GLTX` 保护和 `GLG/GLC/GLB/FM` 客户文件识别。
2. 再扩展源文件清单、候选流水线和对象链输出，让候选项继承来源边界。
3. 再生成客户文件影响清单和承接任务，不写入正式映射表。
4. 最后接入 parser / PMO / 部门桑基图的待承接状态标识，并扩展 `check-dcm-bbm` 边界检查。

## 八、后续增强

首版完成后，再考虑在 MDM 平台 `流程治理` 首屏新增第三入口：`客户文件承接`，与 `治理已有流程`、`创建新流程` 并列。

平台增强范围包括：

- 承接任务列表
- 承接状态流转
- 部门确认记录
- 承接证据上传或引用
- 审核通过后进入数据库治理版本

这些功能不进入首版，避免一次性同时改资料、parser、PMO、MDM 前端和后端。

## 九、关键假设

- 当前仓库阶段仍以流程地图与数据地图梳理为主。
- `docs/norms` 是当前基线真源，不由平台反向覆盖。
- 客户文件承接结果先进入治理任务和审计层，再通过受控入库影响正式 DCM/BBM。
- 首版目标是止住证据边界风险，不是重做完整流程治理平台。
