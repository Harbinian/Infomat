# MDM 新建流程治理线与流程治理前端改造计划

> 交付目标：把 MDM 的流程治理从“模块罗列”升级为“双工作区 + 步骤向导 + 成果反馈”的治理建模闭环。
> 执行原则：`docs/norms` 保持当前基线真源，不由 MDM 回写；新增流程、字段、证据、发布版本在数据库中治理和生效。

## 1. 总体原则

1. **先问任务，不先摆模块**
   - 用户进入 `流程治理` 后，先选择：
     - `治理已有流程`
     - `创建新流程`
   - 原有横排标签降级为材料区或详情区。

2. **人定规则，系统做整理**
   - 填报人讲清业务事实。
   - 审核人确认 L1/L2/L3、A1、证据和发布判断。
   - 系统只做预检、缺项提示、相似项提示、风险定位和成果统计。
   - 不做 AI 自动拆 A1、自动归类、自动发布判断。

3. **每一步都有成果反馈**
   - 告诉用户：已经形成了什么、现在能走到哪一步、还差什么。
   - 文案理性、具体、正向，不空泛夸赞。

## 2. 前端改造

### 2.1 流程治理首屏

`流程治理` 页面顶部改为两个大工作区入口：

| 工作区 | 前端文案 | 说明 |
|---|---|---|
| 存量治理线 | 治理已有流程 | 处理已导入快照中的流程问题、证据、待办、关闭 |
| 增量创建线 | 创建新流程 | 创建当前快照中没有的新流程，补步骤、在线表单、字段和证据 |

原有标签：

- `总览`
- `待确认问题`
- `流程图谱`
- `证据来源`
- `映射工作`
- `治理闭环`

不再作为第一层导航，改为 `治理已有流程` 下的材料区。

### 2.2 治理已有流程向导

步骤：

1. 看本部门有哪些问题
2. 找到问题来自哪里
3. 修改或补充说明
4. 提交处理结果
5. 等待重新验证
6. 确认关闭

每一步显示成果反馈卡：

| 区块 | 内容 |
|---|---|
| 已形成 | 处理记录、备注、问题状态 |
| 当前能做 | 标记处理中、提交整改、等待验证、确认关闭 |
| 还差什么 | 来源未补、重新验证未通过、状态未到 `source_resolved` |
| 下一步按钮 | 继续处理、查看证据、提交处理、确认关闭 |

### 2.3 创建新流程向导

步骤：

1. 流程说明
2. 实际步骤
3. 在线表单
4. 字段与证据
5. 提交审核
6. 成果预览

创建时不要求填报人懂 A1，也不强制填写 L1/L2。
发布前必须补齐 L1/L2/L3。

### 2.4 成果反馈卡

每一步固定显示：

| 区块 | 示例 |
|---|---|
| 已形成 | 已形成 1 条流程草稿、6 个字段、2 条证据说明 |
| 当前能做 | 当前内容可以保存草稿 / 提交部门内审 |
| 还差什么 | 发布前还需补 1 条来源锚点、确认 L1/L2 |
| 下一步 | 继续补字段 / 提交审核 / 查看成果预览 |

文案要求：

- 不写“太棒了”等空泛夸赞。
- 必须基于真实动作反馈。
- 必须告诉用户劳动已经转化成什么治理资产。

## 3. 新建流程业务规则

### 3.1 创建入口

填报人从：

- `流程治理 -> 创建新流程`
- 或 `角色工作台 -> 我现在该做什么`

进入。

所属部门自动取当前登录人员的组织信息：

| 用户类型 | 部门规则 |
|---|---|
| 普通填报人 | 只能为本人部门创建 |
| 多部门 / 工作组角色 | 可在授权范围内切换 |
| 管理员 / 信息化负责人 | 可代建，必须记录代建部门和代建原因 |
| 无部门人员 | 禁止提交，提示先维护人员组织信息 |

### 3.2 草稿必填项

创建流程草稿时必填：

- 流程名称
- 为什么新增
- 依据类型
- 依据说明
- 是否涉及其他部门

L1/L2 可空或选 `待归类`。
发布前必须由审核人确认 L1/L2/L3。

### 3.3 结构化步骤表

填报人填写业务语言步骤表：

| 字段 | 示例 |
|---|---|
| 步骤名称 | 填写采购申请 |
| 谁来做 | 需求部门经办人 |
| 什么时候做 | 发现需要采购物资时 |
| 输入材料 | 采购需求、规格型号、数量 |
| 输出结果 | 采购申请单 |
| 是否需要别人确认 | 是，部门负责人确认 |
| 涉及其他部门 | 物资保障部 |
| 依据 | 采购管理制度条款 / 现场实际 / 访谈记录 |

审核人 / 流程治理人员再将步骤整理为正式 A1。

### 3.4 L1/L2 治理

| 动作 | 规则 |
|---|---|
| 选择已有 L1/L2 | 审核人可直接选择 |
| 创建新 L1/L2 | 进入候选能力层级 |
| 候选 L1/L2 | 需要信息化负责人或数据治理负责人复核 |
| 发布前 | L1/L2/L3 必须完整 |
| 未复核候选 L1/L2 | 不得作为正式能力结构直接沉淀 |

## 4. 在线表单与字段台账

### 4.1 表单定位

表单不是 A4 附件，而是流程对象。

规则：

- 在线表单挂到具体流程步骤。
- 表单字段进入字段台账草稿。
- A4 / PDF 只作为归档、打印、外部提交的派生产物。
- 不优先做 A4 输出。

### 4.2 字段状态

字段状态分为：

| 状态 | 含义 |
|---|---|
| 建议字段 | 填报人提出，未治理 |
| 业务确认字段 | 业务负责人确认确实需要 |
| 数据治理字段 | 已检查命名、类型、枚举、数据对象 |
| 发布字段 | 已进入在线表单发布版本 |
| 废止字段 | 历史保留，不再允许新填 |

### 4.3 字段权限

当前 `data_map_contexts` 创建偏管理员权限，需要调整：

| 角色 | 权限 |
|---|---|
| submitter / business_contact | 可创建本人部门字段上下文 |
| owner / reviewer / data_quality | 可审核或确认字段 |
| admin / it_lead | 可跨部门创建、维护和发布 |
| 代建 | 必须留痕 |

## 5. 证据标准

### 5.1 证据类型

支持以下证据类型：

| 类型 | 填写要求 |
|---|---|
| 制度 / 规程 | 文件名称、文件号、条款、页码 |
| 表单 / 台账 | 表单名、字段名、样例行、使用场景 |
| 系统截图 / 记录 | 页面名称、记录编号、发生时间、说明 |
| 会议 / 访谈 | 会议名称、日期、确认人、结论摘要 |
| 现场实际 | 发生场景、执行人角色、输入物、输出物、确认人 |
| 暂无证据 | 暂缺原因、预计补证人、预计补证时间 |

### 5.2 证据成熟度

前端显示证据当前能支撑到哪个阶段：

| 成熟度 | 含义 |
|---|---|
| 可保存草稿 | 信息不足，但可以先记录 |
| 可提交审核 | 至少有依据类型和说明 |
| 发布前需补 | 可进入审核，但不能发布 |
| 可支撑发布 | 有来源名称、锚点、确认人或记录时间 |

原则：允许轻量证据先行，但不允许无证据发布。

## 6. 风险提示

风险提示必须逐项挂到对象上：

| 挂点 | 示例 |
|---|---|
| 流程级 | 还没说明这个流程属于哪类工作 |
| 步骤级 | 这一步做完后没有写清会产生什么结果 |
| 表单级 | 表单没有归档规则 |
| 字段级 | 这个字段可能和已有字段重复 |
| 证据级 | 有来源文件，但没写清具体页码、条款或位置 |

前端要求：

- 不显示规则码。
- 说人话，望文生义。
- 点击风险能定位到对象行。
- 对象行高亮。
- 审核人可逐项处理：
  - 已确认
  - 需补正
  - 接受风险
  - 驳回

示例文案：

- “这一步需要质量管理部确认，但还没有指定确认部门。”
- “这个字段要从固定选项里选，但选项还没列出来。”
- “这个依据还不够支撑正式发布。”

## 7. 数据库设计

新增 `process_design_*` 域，承接新增流程治理建模。
不要硬塞进现有 `mdm_mapping_records`，因为现有表依赖已存在的 `process_mapping_records`，更适合存量流程审批。

### 7.1 新增表组

| 表 | 作用 |
|---|---|
| `process_design_drafts` | 新建流程草稿 |
| `process_design_steps` | 结构化步骤 |
| `process_design_forms` | 在线表单草稿 |
| `process_design_form_fields` | 表单字段草稿 |
| `process_design_evidence` | 证据记录 |
| `process_design_risks` | 对象级风险提示 |
| `process_design_review_tasks` | 审核任务 |
| `process_design_events` | 事件流水 |
| `process_design_versions` | 已发布流程版本 |

### 7.2 三层数据库模型

| 层 | 作用 |
|---|---|
| 原始证据层 | 保存证据、来源、锚点、确认信息 |
| 候选治理层 | 保存草稿、步骤、表单、字段、风险、审核 |
| 正式发布层 | 保存已发布流程版本，作为新增流程数据库真源 |

### 7.3 生效规则

双点生效改为数据库内双层生效：

| 生效点 | 含义 |
|---|---|
| 平台发布生效 | `process_design_versions` 中产生发布版本 |
| 流程地图生效 | 发布版本进入数据库流程地图视图 |

`docs/norms` 不回写，不由 MDM 修改。

## 8. API 设计

新增路由前缀：`/api/process-design`

建议接口：

| Method | Path | 用途 |
|---|---|---|
| GET | `/summary` | 获取新建流程工作区统计 |
| POST | `/drafts` | 创建流程草稿 |
| GET | `/drafts/:id` | 查看草稿详情 |
| PUT | `/drafts/:id` | 更新草稿 |
| POST | `/drafts/:id/steps` | 新增步骤 |
| PUT | `/steps/:id` | 更新步骤 |
| POST | `/drafts/:id/forms` | 新增在线表单 |
| PUT | `/forms/:id` | 更新表单 |
| POST | `/forms/:id/fields` | 新增表单字段 |
| PUT | `/form-fields/:id` | 更新字段 |
| POST | `/drafts/:id/evidence` | 新增证据 |
| GET | `/drafts/:id/risks` | 获取风险提示 |
| GET | `/drafts/:id/outcome-preview` | 获取成果预览 |
| POST | `/drafts/:id/submit` | 提交审核 |
| POST | `/review-tasks/:id/decision` | 审核通过 / 驳回 / 补正 |
| POST | `/drafts/:id/publish` | 发布流程版本 |

## 9. 前端实现范围

第一版实现：

- `流程治理` 双工作区入口。
- `治理已有流程` 保留现有功能，但换成步骤化引导。
- `创建新流程` 新增向导：
  - 流程说明
  - 实际步骤
  - 在线表单
  - 字段与证据
  - 提交审核
  - 成果预览
- 成果反馈卡。
- 对象级风险提示。
- 人话文案。
- 字段上下文创建权限调整。
- 发布后流程进入数据库流程地图。

第一版不做：

- 完整流程运行时引擎。
- 复杂低代码表单设计器。
- AI 自动拆 A1。
- AI 自动定 L1/L2。
- AI 自动发布判断。
- `docs/norms` 回写。
- A4 表单优先设计。

## 10. 测试计划

### 10.1 API 测试

覆盖：

- 普通填报人创建草稿时自动使用本人部门。
- 普通填报人不能替其他部门创建。
- 管理员代建必须填写代建原因。
- 草稿可保存。
- 缺必填项不能提交。
- 发布前必须有 L1/L2/L3、步骤、字段、证据成熟度。
- 审核人可创建候选 L1/L2。
- 候选 L1/L2 未复核时不能直接正式发布。
- 发布写入 `process_design_versions`。
- 发布不修改 `docs/norms`。

### 10.2 前端测试

覆盖：

- `流程治理` 首屏显示两个工作区，而不是直接显示横排标签。
- `创建新流程` 向导完整显示 6 个步骤。
- 每一步显示成果反馈卡。
- 风险提示是人话文案。
- 点击风险能定位到对象。
- 字段上下文可由授权填报人在本人部门创建。
- 发布后新增流程能进入数据库流程地图视图。

## 11. 验收标准

功能验收：

- 用户进入 `流程治理` 后能立刻判断自己该治理已有流程，还是创建新流程。
- 填报人无需理解 A1 或 L1/L2，也能创建合格草稿。
- 审核人能看到逐项风险，不需要读一大段总评。
- 每次保存、提交、导入字段、补证据后，用户都能看到明确成果反馈。
- 新增流程发布后进入数据库流程地图。
- `docs/norms` 没有被 MDM 回写。

体验验收：

- 前端不出现治理规则码。
- 风险文案望文生义。
- 反馈文案具体、正向、指向下一步。
- A4 / PDF 不作为新表单设计的主目标。

## 12. 关键假设

- `docs/norms` 保持当前基线真源，只读导入。
- 后续新增流程的正式来源是数据库发布版本。
- 第一版目标是治理建模闭环，不是流程执行引擎。
- 审核人负责规则判断，系统负责整理和提示。
- AI 不进入定标准、立规矩、发布判断环节。
