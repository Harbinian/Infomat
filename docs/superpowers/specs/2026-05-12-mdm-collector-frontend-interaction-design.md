# MDM Collector 前端交互规范与信息架构设计

**日期**: 2026-05-12
**来源**: 需求访谈（grill-me session），基于现有 7-tab 单页 HTML 重构为三层/四层信息架构

---

## 一、用户角色与核心路径

| 角色 | 系统入口 | 核心任务（占 80% 时间）|
|------|---------|----------------------|
| 报送人（部门人员）| 我的报送 | 填写字段台账，处理驳回后修改重新提交 |
| 部门负责人 | 待办列表 | 审核本部门报送，逐字段驳回或通过 |
| 跨部门 reviewer | 冲突待办 | 指定责任人协调、逐字段给出最终决议 |

**导航方案：C+B**

- **C（Dashboard 统一入口）**：Dashboard 作为所有角色可见的第一个 Tab，提供角色定制的快捷卡片，用户可从 Dashboard 一键进入核心工作流。登录后按角色直达对应 Tab（非强制先看 Dashboard），但可随时切回。
- **B（角色差异化导航）**：不同角色看到不同的 Tab 集合，无关 Tab 直接隐藏（而非禁用），减少认知负担。

采用 C+B 组合：Dashboard 提供跨角色的统一信息视图，差异化 Tab 减少日常操作的信息噪音。登录后默认跳转规则见 4.7。

**角色→Tab 可见性**：

| Tab | 报送人 | 部门负责人 | reviewer | admin |
|-----|--------|-----------|----------|-------|
| 统计看板 | 可见 | 可见 | 可见 | 可见（默认）|
| 我的报送 | 可见（默认）| - | - | 可见 |
| 能力与流程申报 | - | - | - | 可见 |
| 待办 | 可见 | 可见（默认）| 可见 | 可见 |
| 评审记录 | 可见 | 可见 | 可见 | 可见 |
| 术语词典 | 可见 | 可见 | 可见 | 可见 |
| 冲突管理 | - | - | 可见（默认）| 可见 |

## 二、对象模型与状态机

### 2.1 核心对象

| 对象 | 说明 | 生命周期状态 |
|------|------|-------------|
| **Submission**（报送单）| 部门人员创建的一个流程映射提交 | `draft` → `submitted` → `dept_reviewed` → `cross_confirmed` → `fields_confirmed` → `final_reviewed` → `published`；驳回一律退回 `draft` |
| **Todo**（待办）| 分配给某个角色/用户的任务 | `pending` → `done`（完成即从列表消失，不归档、不可见、不提供删除入口）|
| **Conflict**（冲突）| 跨部门字段或术语定义冲突 | `pending`（待处理）→ `coordinating`（协调中）→ `resolved`（已解决）→ `archived`（已归档）；驳回可退回 `pending` |
| **ApprovalTask**（审批任务）| 审批流中的单步任务 | `pending` → `approved` / `rejected` |
| **Term**（术语）| 术语词典条目 | `pending`（待审）→ `approved`（已通过）/ `rejected`（已驳回）|

### 2.2 状态机：Submission 生命周期（事件驱动）

| 事件 (action) | 触发角色 | 当前状态 | 目标状态 | 说明 |
|--------------|---------|---------|---------|------|
| `submit` | 报送人 | `draft` | `submitted` | 提交进入审批流 |
| `dept_approve` | 部门负责人 | `submitted` | `dept_reviewed` | 部门审核通过 |
| `dept_reject` | 部门负责人 | `submitted` | `draft` | 部门驳回，退回可编辑 |
| `cross_approve` | reviewer | `dept_reviewed` | `cross_confirmed` | 跨部门审核通过 |
| `cross_reject` | reviewer | `dept_reviewed` | `draft` | 跨部门驳回，退回可编辑 |
| `fields_confirm` | reviewer | `cross_confirmed` | `fields_confirmed` | 字段确认通过 |
| `fields_reject` | reviewer | `cross_confirmed` | `draft` | 字段确认驳回，退回可编辑 |
| `final_approve` | admin | `fields_confirmed` | `final_reviewed` | 终审通过 |
| `final_reject` | admin | `fields_confirmed` | `draft` | 终审驳回，退回可编辑 |
| `publish` | admin | `final_reviewed` | `published` | 发布（终态）|

关键规则：
- **驳回一律退回 `draft`**：报送人在 draft 状态下编辑修改，修改完成后重新 `submit` 进入 `submitted`，重走完整审批链
- 任何一个字段无效 = 整单驳回（不存在部分驳回部分通过）
- 每轮驳回/修改/重提交均需记录在 `approval_history`
- `published` 为终态，不可再变更

### 2.3 各角色在不同状态下的可操作动作

仅列出**当前角色直接可操作**的动作（非数据查看权限）：

| 状态 | 报送人 | 部门负责人 | reviewer | admin |
|------|--------|-----------|----------|-------|
| `draft` | 编辑、提交、删除 | - | - | 查看、删除 |
| `submitted` | 查看（等待审核）| **通过**、**驳回（逐字段）** | - | 查看 |
| `dept_reviewed` | 查看 | 查看 | **通过**、**驳回** | 查看 |
| `cross_confirmed` | 查看 | 查看 | **确认字段**、**驳回** | 查看 |
| `fields_confirmed` | 查看 | 查看 | 查看 | **终审通过**、**驳回** |
| `final_reviewed` | 查看 | 查看 | 查看 | **发布** |
| `published` | 查看 | 查看 | 查看 | 查看（终态，不可操作）|

**动作显隐规则**：
- 当前角色在当前状态下无可用动作 → 不显示操作按钮
- 禁止用 disabled 按钮代替隐藏（避免用户困惑 "为什么我不能点"）
- 查看权限不在此表约束（部门负责人只能看本部门数据由 API 层保证）

### 2.4 Conflict 事件驱动状态机

| 事件 (action) | 触发角色 | 当前状态 | 目标状态 | 说明 |
|--------------|---------|---------|---------|------|
| `detect` | 系统/手动 | - | `pending` | 冲突检测创建（系统检测或手动发起）|
| `assign_owner` | reviewer | `pending` | `coordinating` | 指定提交人所在部门的部门长为责任人，冲突进入协调阶段 |
| `reassign_owner` | reviewer | `coordinating` | `coordinating` | 改派责任人（当原责任人离岗或选错时）|
| `submit_coordination` | 责任人 | `coordinating` | `coordinating` | 提交协调结果，每次提交追加一条历史记录，展示以最新一条为准 |
| `final_decide` | reviewer | `coordinating` | `resolved` | reviewer 终裁，逐字段给出最终决议 |
| `reopen` | reviewer | `resolved` | `pending` | 重开已解决的冲突重新分配（重开后须重新指定责任人）|
| `archive` | admin | `resolved` | `archived` | 软删除，从默认列表隐藏但审计记录保留 |

关键规则：
- `assign_owner` 将冲突分配给提交人所在部门的部门长（单一责任人）。若部门长为空或离岗，由 reviewer 手动指定
- `submit_coordination` 由责任人在系统内录入本部门与对方部门协商后的统一口径。每次提交追加一条历史记录，前端展示以最新一条为准
- `final_decide` 为终态操作，reviewer 对冲突字段给出最终决议
- `reopen` 后冲突回到 `pending`，需重新指定责任人
- `archive` 后冲突不计入"未解决冲突"统计指标，从默认冲突列表隐藏，可通过筛选"已归档"查看

**冲突类型**：`field`（字段冲突）、`term`（术语冲突）

> **term 冲突的 submitter 定义**：term 冲突由术语词典条目触发，其"提交人所在部门"取术语创建时关联的 `process_id` 所属的 `owner_dept_id`。若术语未关联流程，则取术语创建者所在部门。默认责任人为此部门的部门长。
**严重度**：`blocking`（阻断）、`high`、`medium`、`low`

## 三、信息架构：三层 + 四层

### 3.1 基础三层（报送→审核流程）

```
L1 列表层（我的报送 / 待办列表）
  ├─ 概览卡片：关键数字
  ├─ 筛选/搜索栏
  ├─ 表格列表
  └─ 分页/加载更多
      │
      ▼ 点击某条记录
  L2 详情层（独立页面，替换当前视图）
  ├─ 面包屑：待办列表 > 流程映射 #42 > 审核
  ├─ 元信息区：流程名称、报送部门、提交人、时间、步骤、状态
  ├─ 内容区：字段台账表格（含搜索、状态筛选、变更高亮）
  ├─ 变更对比区：新旧内容并排（驳回后重提交时出现）
  ├─ 历史区：完整审批记录时间线
  └─ 操作入口：通过 / 驳回（逐字段标注原因）
      │
      ▼ 点击操作
  L3 操作层（通过=轻量确认框，驳回=完整确认页）
  ├─ 通过：意见文本（可空）+ 确认按钮
  └─ 驳回：逐字段驳回原因（必填）+ 确认按钮
```

### 3.2 四层（冲突协调流程）

```
L1 冲突概览
  ├─ 分段表格：按严重度分段（阻断 / 高 / 中 / 低），每段内按创建时间降序
  ├─ 状态筛选（待处理 / 协调中 / 已解决 / 已归档）。"已归档"仅 admin 视角可见
  └─ 冲突列表表格
      │
      ▼ 点击某条冲突
  L2 冲突详情（独立页面）
  ├─ 双部门定义并排对比
  ├─ 冲突字段完整上下文
  ├─ 历史协调记录
  └─ 指定责任人入口
      │
      ▼ 责任人操作
  L3 责任人协调
  ├─ 责任人从待办列表进入
  ├─ 录入协调结果：选择 A 部门口径 / B 部门口径 / 折中方案 + 协调说明
  └─ 提交协调结果
      │
      ▼ reviewer 操作
  L4 reviewer 终裁
  ├─ 责任人协调结果 + 完整协调历史
  └─ 逐字段给出最终决议
```

## 四、交互规范

### 4.1 破坏性操作确认机制

| 操作类型 | 确认方式 | 说明 |
|---------|---------|------|
| 审批通过 | 轻量确认弹窗 | 意见可选填，单按钮+取消 |
| 驳回（含字段级原因）| 完整确认页 | 至少标记 1 个字段为驳回，每个被标记驳回的字段必须填写原因；原因必填 |
| 提交流程 | 轻量确认弹窗 | 提交后不可修改的提示 |
| 普通保存/编辑 | 无需确认 | button loading + toast 反馈 |
| 删除 | 二次确认弹窗 | 明确告知影响范围（关联数据也会受影响）。删除对象及权限见下方 |

**删除对象权限矩阵**：

| 删除对象 | 允许角色 | 允许状态 | 说明 |
|---------|---------|---------|------|
| 流程映射（报送单）| 报送人、admin | `draft` | 仅草稿可删除，提交后不可删除 |
| 字段台账行 | 报送人、admin | 所属 mapping 为 `draft` | 仅草稿期可删除单行字段 |
| 术语 | admin | `pending`（待审）| 仅待审术语可删除，已通过/已驳回的不可删除 |
| 冲突 | admin | `resolved` | 软删除（archived）。archived 冲突在冲突列表默认隐藏，可通过筛选"已归档"查看；在评审记录中仍可追溯。不计入统计看板"未解决冲突"指标 |

**弹窗/确认页键盘与焦点规范**：

| 规则 | 说明 |
|------|------|
| Esc 关闭 | 所有弹窗按 Esc 等同于点击取消/关闭 |
| 回车确认 | 弹窗内按 Enter 触发主操作按钮（通过/确认/提交），驳回页除外（防误触发）|
| 打开焦点 | 弹窗打开时焦点落入第一个输入框（如有），否则落入确认按钮 |
| 关闭焦点 | 弹窗关闭后焦点回到触发弹窗的按钮 |

### 4.2 系统反馈

| 场景 | 实现 | 说明 |
|------|------|------|
| 普通操作 loading | 按钮内置 spinner + "提交中…" 文案 + disabled | 不打断用户，不弹全局遮罩 |
| 成功反馈 | 右上角 toast，3 秒自动消失 | 绿色，带 ✅ 图标 |
| 业务错误 | toast 红色，显示后端返回的 error message | 不弹 alert，不阻塞 |
| 网络/权限错误 | toast 红色 + 内联提示 | 区分 "你的问题" 和 "系统的问题" |
| 401 未认证 | 清空本地会话，跳转登录页，toast 提示 "登录已过期，请重新登录" | 轮询遇到 401 立即停止 |
| 403 无权限（模块级）| toast 提示 "无权访问" + 重定向到 Dashboard | 角色不允许访问该功能模块时返回 403 |
| 404 不存在/无权限（对象级）| 显示空页 + "记录不存在或无权访问" + 返回上一页 | 对象级：记录不属于当前部门、或 ID 无效时统一返回 404，不暴露存在性 |
| 文件导入/导出 | 按钮 loading + 完成后 toast + 结果摘要（如 "已导入 42 行，跳过 3 行"）|

### 4.3 表单校验

**规则 1：即时校验，失焦触发。**
- 输入框 onblur 时校验格式
- 行内红色小字提示，放在输入框下方
- 提交时再做完整性校验（阻止提交但不清除已填内容）

**规则 2：校验文案必须有用。**
- 不说 "名称必填" → 说 "请输入能力名称"
- 不说 "格式错误" → 说 "日期格式应为 YYYY-MM-DD"
- 每一条错误信息直接告诉用户怎么修

### 4.4 导航

- **面包屑**：L2/L3 页面顶部显示完整路径，每级可点击跳回
  - 格式：`待办列表 > 流程映射 #42 > 驳回审核`
- **返回按钮**：L2/L3 页面左上角 ← 返回，保留列表的筛选状态和页码
- **面包屑独立于 Tab 运作**：进入 L2 时 Tab 栏保留，来源 Tab 保持高亮（active 状态），面包屑覆盖在内容区顶部。跨 Tab 进入同一详情页时（如从待办列表和从评审记录都可进入同一个映射详情），active tab 跟随当前路由来源判定，而非被访问的对象

### 4.5 数据刷新策略

| 层级 | 刷新策略 | 注意事项 |
|------|---------|---------|
| L1 列表 | 进入时自动加载 + 手动刷新按钮 + 每 60s 自动轮询 | 轮询只刷新列表数据，不改变用户交互状态 |
| L2 详情 | 进入时加载一次 | 操作完成后自动刷新当前页面 |
| L3/L4 操作提交 | 无轮询 | 提交时后端校验状态一致性 |
| 编辑模式 | 暂停轮询 | 防止自动刷新覆盖用户正在填写的表单内容 |

**冲突处理**：提交时后端检测到状态冲突 → 前端显示 "数据已被其他人修改，请刷新后重试"，不静默覆盖。

### 4.6 编辑保护（前端 only，后端不做草稿快照）

| 场景 | 保护策略 |
|------|---------|
| 系统内导航跳转（面包屑/返回/Tab 切换）| 检测未保存内容 → 弹出 "你有未保存的更改，确定离开吗？" 确认框 |
| 浏览器关闭/刷新 | `beforeunload` 事件拦截，浏览器原生提示 |
| 长时间滞留 | 无后端草稿自动保存（安全风险，不做）|

### 4.7 角色差异化行为

| 行为 | 规则 |
|------|------|
| Tab 可见性 | 按角色隐藏无关 Tab（报送人看不到冲突管理，reviewer 看不到能力与流程申报）|
| 默认 Tab | 登录后按角色跳转：报送人→我的报送、部门负责人→待办、reviewer→冲突管理、admin→统计看板。Dashboard 始终作为第一个 Tab 对所有角色可见，用户可随时切回查看全局数据 |
| 按钮可见性 | 非本角色操作按钮隐藏（而非禁用）——报送人看不到 "审核通过/驳回" 按钮 |
| 数据范围 | 部门负责人只能看到本部门的报送和待办，reviewer 只能看到分配给自己的冲突 |

## 五、列表页规范

### 5.1 待办列表行信息

| 字段 | 说明 |
|------|------|
| 来源 | 谁报送的 / 哪个部门 |
| 流程名称 | 所属业务流程 |
| 待办类型 | 新报送待审 / 驳回重审 / 冲突协调 |
| 提交时间 | 报送提交时间 |
| 紧急程度 | 高/中/低（新增字段，需后端支持）|
| 截止时间 | 到期日期（新增字段，需后端支持）|

### 5.2 默认排序

| 列表 | 默认排序 | 空状态文案 |
|------|---------|-----------|
| 待办列表 | 紧急程度降序 → 截止时间升序 → 提交时间升序 | "暂无待办事项" + 报送人看到 "去 [我的报送] 查看提交状态" |
| 我的报送 | 提交时间降序（最新在前）| "暂无报送记录，去 [新建报送] 开始" |
| 冲突列表 | 分段表格：按严重度降序分组（阻断 > 高 > 中 > 低），段内按创建时间降序 | "暂无冲突" + reviewer 看到 "待冲突发生时系统将自动通知" |
| 审批历史 | 操作时间降序 | "暂无审批记录" |

**空状态规则**：不只是占位文字，必须包含引导用户进入下一步操作的链接或按钮。

## 六、驳回规范

### 6.1 逐字段驳回原因

- 驳回时字段表格每一行旁边出现【标记驳回】勾选框 + 驳回原因输入框
- 至少勾选 1 个字段为驳回，未勾选的字段不展示原因输入框
- 被勾选驳回的字段，其驳回原因输入框变为必填
- 驳回原因文本存储到数据库，与字段 ID 绑定
- 驳回=整单驳回（任何一个字段无效整单就不生效）
- 驳回后重新提交必须重走完整审批链（不从当前步骤继续）

**前端校验规则**：
```
if (被标记驳回的字段数 === 0) → "请至少标记一个字段的驳回原因"
if (任一被标记驳回的字段原因为空) → "请填写该字段的驳回原因"
```

### 6.2 驳回—修改—重新提交循环

- 每轮驳回/修改/重提交均需记录，在 L2 历史区完整展示
- 重新提交后在 L2 详情页展示变更对比区（新旧内容并排）
- 驳回次数无限制（可来回多次）

## 七、字段台账表格交互

### 7.1 基础能力

- **关键字搜索**：搜索字段中文名，即时过滤
- **按状态筛选**：全部 / 新增 / 修改 / 删除 / 无变化
- **变更高亮**：被驳回修改过的字段行有视觉标记（如左侧红边或浅红底色）

### 7.2 数据规模

- 字段数范围 10-300（通常 ≤100）
- 不分页，一次滚动加载（100 行内不需要分页）
- 虚拟滚动在超过 300 行时才需要，当前不做

## 八、冲突协调详细流程

```
L1 冲突概览 → L2 冲突详情（双部门并排对比）
  → L3 reviewer 指定提交人所在部门的部门长为责任人
    → 责任人收到待办 → 录入协调结果（A 部门口径 / B 部门口径 / 折中方案）
      → L4 reviewer 查看责任人协调结果 → 逐字段给出最终决议
```

- 责任人为提交人所在部门的部门长（单人）。若部门长为空，reviewer 手动指定
- 协调结果必须在系统内录入（不光是在外部沟通）
- reviewer 必须对每个冲突字段给出决议

### 冲突待办与普通待办的关系

- 冲突协调产生的责任人待办与普通待办共用同一个 `todos` 表
- 通过 `type = 'conflict_resolution'` 区分，前端在待办列表中显示为 "冲突协调" 类型
- 每个冲突只有一条责任人待办（单责任人模型），分配给提交人所在部门的部门长
- 责任人从待办列表点击进入冲突 L2 详情页（而非普通报送 L2）
- 待办列表增加 "类型" 筛选器：全部 / 报送审核 / 驳回重审 / 冲突协调
- reviewer 和部门负责人的待办列表默认只显示各自相关类型

## 九、实施影响范围

### 9.1 前端重构

| 范围 | 说明 |
|------|------|
| HTML 结构 | 从单文件 616 行拆分为多文件或保持单文件但重新组织 DOM 结构 |
| 路由模拟 | 前端需实现客户端路由支持 L1→L2→L3 递进。**默认使用 hash 路由**（`#/todos/42/review`），避免静态部署时 pushState 刷新导致 404。后续如需 SEO 友好 URL，在确认有反向代理 rewrite 支持后再迁移到 pushState |
| 组件化 | 抽取可复用组件：面包屑、toast、确认弹窗、字段表格（搜索+筛选+高亮）|
| CSS | 在已确定的配色方案基础上扩展：变更高亮行样式、驳回输入框样式、面包屑样式等 |

### 9.2 后端变更

| 变更 | 说明 |
|------|------|
| todos 表 | 新增 `urgency` 字段（枚举：high/medium/low，默认 medium）和 `due_date` 字段（截止时间，可为空）|
| 驳回 | 新增字段级驳回原因存储（需新表，字段：mapping_id, field_entry_id, rejection_reason, rejected_by, created_at）|
| 冲突协调 | 新增 conflict_assignments 表（字段：conflict_id, assignee_user_id, assigned_by, created_at）和 conflict_coordination_history 表（字段：conflict_id, assignee_user_id, result, note, created_at）。conflict_assignments 用于记录改派历史（每次 assign/reassign 追加一条），当前有效责任人取 `conflict_id` 下 `created_at` 最新的一条 |
| 角色数据范围 | 确保 API 层按角色过滤数据（部门负责人只能看到本部门数据）|

**冲突协调接口验收点**：

| 验收项 | 检查内容 |
|--------|---------|
| 指定责任人 | POST `/api/conflicts/:id/assign`，body: `{ assignee_user_id }`。若未指定则默认取提交人所在部门的部门长 |
| 改派责任人 | PUT `/api/conflicts/:id/assign`，body: `{ assignee_user_id }`。仅 reviewer 可操作，仅 coordinating 状态可改派 |
| 提交协调结果 | POST `/api/conflicts/:id/coordination`，body: `{ result: 'A'|'B'|'compromise', note }`。追加到 coordination_history |
| 终裁 | POST `/api/conflicts/:id/final-decide`，body: `{ resolution, opinion }`。reviewer 逐字段决议 |
| 重开 | POST `/api/conflicts/:id/reopen`。resolved→pending，需重新分配责任人 |
| 归档 | POST `/api/conflicts/:id/archive`。resolved→archived，admin 操作 |

**接口级验收点**：

| 验收项 | 检查内容 |
|--------|---------|
| 待办排序 | SQLite 可执行表达式：`ORDER BY urgency_weight DESC, (due_date IS NULL) ASC, due_date ASC, created_at ASC`。urgency_weight 为应用层计算列：high=3, medium=2, low=1 |
| 字段级驳回原因 | 批量驳回接口：POST `/api/mappings/:id/reject`，body: `{ opinion, rejections: [{field_entry_id, reason}] }`。整单驳回一次性提交，后端原子写入（全部成功或全部回滚）。读取：GET `/api/mappings/:id/rejection-details` |
| 角色数据过滤 | 部门负责人请求待办列表时，后端只返回 `to_dept_id = 当前用户部门` 的记录；40x 状态码不暴露数据存在性（不存在或无权限的资源统一返回 404）|
| 错误码约定 | 401=未认证（清空会话，跳转登录）；403=模块级权限禁止（角色不可访问该功能，重定向 Dashboard）；404=对象级无权限或不存在（统一隐藏存在性，显示空页+返回）；409=状态冲突（提示刷新重试）；422=校验失败（返回字段级错误详情）|

### 9.3 不做的事项

- 后端草稿自动保存（安全风险）
- 前端框架/构建工具引入（保持原生 HTML/CSS/JS）
- 移动端适配（桌面端优先）
- WebSocket 实时推送（60s 轮询足够）
- 字段台账虚拟滚动（100 行以下无需）
- 多语言/国际化
