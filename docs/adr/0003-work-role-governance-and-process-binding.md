# ADR-0003: 工作角色治理与流程绑定

## 状态

Accepted

## 背景

流程输入基线和文档结构化输出长期使用“执行角色”等自由文本，花名册提供的是人员当前所在部门和职务，MDM 的 `roles/person_roles` 则用于系统权限与项目治理。三者含义不同，不能继续用岗位名称或 RBAC 角色代替流程责任。

仓库需要一种稳定的业务责任分类，用来说明 L3 流程由哪类角色负责、A1 业务行为由哪类角色发起、执行、审核、批准、协同、提供或接收，并能由行政人事部映射到花名册岗位。

## 决策

1. 新增正式领域概念“工作角色”。工作角色不是人员、岗位、部门、原文角色称谓或 RBAC 角色。
2. 行政人事部在 `docs/organization/工作角色目录与岗位映射.md` 维护工作角色目录、生命周期、岗位映射和原文别名；流程责任部门确认工作角色与具体 L3/A1 的绑定。
3. 领域关系固定为：`原文角色称谓 -> 工作角色 -> 花名册岗位 -> 任岗人员`。工作角色与岗位多对多，不直接绑定人员。
4. 文档结构化输出 v2 以可选 `work_role_bindings[]` 表达候选和已确认关系，同时永久保留 `steps.actor_role` 等原文字段。自动抽取和字符串匹配最多生成 `proposed`，不能生成 `confirmed`。
5. `step_ref=null` 表示 L3 流程负责人，只允许 `owner`；非空表示 A1 参与关系，允许 `initiator/executor/reviewer/approver/collaborator/provider/receiver`。
6. 已确认关系必须有有效工作角色、参与部门的有效岗位映射、可定位且非 OCR 待复核的证据和业务确认依据。未确认结果只留在结构化草稿、`artifacts/` 和待确认清单，不自动写入流程输入基线。已停用角色只允许保留既有历史绑定，不能创建新的正式绑定。
7. 仓库组织文档和流程输入基线是正式发布真源。`docs/work-role-data.json`、公司流程快照和后续 MySQL 表都是派生数据，不反写真源。
8. 当前 MDM 暂不持久化工作角色绑定。顶层或结构块投影中的 `work_role_bindings` 任一非空，导入必须明确拒绝，不能静默丢弃。MySQL 承接在行政人事目录和受控试点稳定后实施。
9. 现有 RBAC 用户分组统一称为“项目治理角色”，底层 `role_group='project'` 和既有角色编码保持兼容；工作角色不会自动授予系统权限。

## 影响

- 制度原文、规范工作角色和花名册岗位形成可追溯的三层语义，不再用字符串相等代替行政人事确认。
- 3001 可以在正式目录为空时继续整理原文、生成角色证据和待确认问题；没有行政人事确认时不会虚构 `WR-*` 编码。
- parser 和公司快照只发布 `confirmed` 关系，历史自由文本继续保留，允许部门渐进迁移。
- 后续 MDM 需要独立的工作角色主数据、岗位映射、流程绑定、变更申请和权限点，不能复用 `roles/person_roles`。
