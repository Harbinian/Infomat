# Infomat 主线关系图

> 状态：执行规则  
> 生效日期：2026-06-07  
> 目的：说明 MDM 主线、PMO 主线、流程输入基线、组织真源和脚本工具之间的数据流关系，防止误把展示副本当维护入口。

## 1. 当前阶段主线

2026-09-11用户明确：所有`docs/`文件都不再是真源，不以旧制度、映射、组织、角色或人员Markdown作为治理基础。主线为：

```text
用户指定的外部原始材料 + 业务主体对实际做法的说明
  → 3001：单流程编制，用户主动下载未审核JSON
  → 用户手动上传3000
  → 3000：治理、部门核对、审核、正式版本及后续治理工作包
  → 依据经治理确认的版本生成程序文件
```

需要退回时，由编制人在3001修订后主动下载，再上传到3000原案例形成新修订。3001保持独立、无状态，不与3000自动互写或共享数据库；编制材料不等于正式版本，程序文件是治理后的输出。

人员事实回到用户指定的行政人事部发布Excel核对；`docs/organization/花名册.md`只是转换副本。具体流程职责、审核人员和系统权限分别依据明确业务确认及任命，不从旧文件、姓名或岗位推断。

下文区分当前技术边界和历史消费链。现有程序读取部分`docs/`资产只说明兼容现状，不恢复治理权威，也不表示已完成正式运行切换。历史资产的迁移或替换按授权、影响和恢复条件处理。

## 2. 当前单流程编制与治理

```text
指定外部原始材料 + 实际业务说明和确认
  → 3001（当前页面内存，兼容读取历史JSON）
  → 用户下载未审核JSON
  → 用户手动上传3000
  → 预览核对、受控提升、审核及不可变正式版本
  → 根据经治理确认的版本生成程序文件
```

本工作区3001默认 `process-governance-v8` 候选，支持V1至V7旧文件及既有多候选兼容输入，在页面内存迁移，不修改源文件。历史V7保持原摘要兼容。候选代码和测试不能证明正式3001实例已经升级；以应用README、健康响应及部署记录核对版本。

3001只读目录副本用于录入，不以其决定组织、任命或责任；任何可见输入不得静默丢失或应用。3001不调用3000、数据库或业务会话，不自动提交JSON。用户主动下载是唯一持久化动作。

3000保留原生V7/V8的预览、核对、提升和正式版本路径，V8不扩大后续工作包范围。原精确试点引用限制已取消；功能标志、正式身份权限、部门范围、修订号、内容摘要和阻断项仍生效。旧V1至V3编制、导入及旧跨部门承接入口已退役。按 `apps/mdm-platform/README.md` 核对实现与门槛，不以本图宣布数据库已准备、运行已开启或业务已验收。

## 3. 历史映射与组织消费链

`docs/norms/`、`docs/organization/`、`docs/company-sankey-data.json`及流程地图驾驶舱保留历史材料和兼容关系，均不作为当前治理依据。

旧展示链仅在获准维护时使用 `parse-sankey-data.mjs --legacy-display --domain-map <JSON> --out <JSON>`；无默认写入，仅显式 `--dashboard <HTML>` 才注入页面。历史部门域JSON不能从组织Markdown首个代码块猜取，缺少解析部门的映射时拒绝生成。隔离输入可选`--norms`、`--cross-report`、`--chain-report`及`--work-roles`；新兼容快照meta含`historicalDisplayOnly=true`及`domainMapSource`技术来源标注，保留旧快照不变。工作角色生成须显式兼容输入及输出，不自动造码、任命或正式绑定。

`sync-process-governance-mainline.mjs`不再自动生成资料快照或注入驾驶舱。显式选定历史快照时默认仅输出同步计划；真实MySQL写入另需 `--apply`、完整配置、目标和恢复条件授权，参数及副作用见 `scripts/README.md`。SQLite仅为明确命名的历史迁移或隔离测试，不作为正式运行替代。

字段台账的对象及黄金源线索不能直接认定主数据、权威系统或维护责任，仍需按字段由有权主体确认。历史草稿、文档结构化v2及旧MySQL映射仅作为技术兼容记录。

## 6. PMO 项目管理主线

```text
pmo/信息化项目_计划管控真源.md
pmo/信息化项目_WBS结构真源.md
pmo/信息化项目_执行标准真源.md
pmo/信息化项目_工作平衡.md
pmo/信息化项目_工作开展原则.md
pmo/信息化项目_协同工作规则.md
pmo/信息化项目_部门主备对接人名单.md
  ↓
pmo/build_pmo_task_data.py
  ↓
pmo/tasks.json
pmo/pmo-source-manifest.json
pmo/gantt-react/public/tasks.json
pmo/gantt-react/public/pmo-source-manifest.json
  ↓
pmo/gantt-react/
```

规则：

- PMO Markdown 是项目计划当前维护入口。
- 部门主备岗、会议和行动项协同规则以 `pmo/信息化项目_协同工作规则.md` 为准，当前主备岗人员以 `pmo/信息化项目_部门主备对接人名单.md` 为准。
- `pmo/信息化项目_协同工作规则_群通知.md` 只用于信息化工作群发布，不是真源。
- 历史 XLSX / MPP / CSV 任务导入文件已废弃，不作为当前输入、不再保留或读取。
- 两份`tasks.json`和两份`pmo-source-manifest.json`是React应用直接消费的受控派生文件，不是手工维护真源；修改七份PMO Markdown真源后必须运行固定生成命令和`npm run test:pmo-task-data`。

## 7. 信息表收集主线

```text
MySQL: person -> user_accounts
MySQL: departments
  ↓ 只读身份与部门
apps/information-collection-service/
  ├─ 4000 管理端：表单设计、任务发布、完成情况、答卷和导出
  └─ 4001 填报端：本人任务、草稿、提交、修改和附件
  ↓
MySQL: collection_*
COLLECTION_FILE_ROOT（仓库外受控附件目录）
```

规则：

- 4000 和 4001 由同一进程提供，但使用独立路由和独立会话 Cookie；任一端口启动失败时，进程关闭另一端口并退出。
- 服务只读复用 `person`、`user_accounts` 和 `departments`。信息收集权限写入 `collection_app_grants`，不得自动继承 3000 的 `admin`、MDM 工作角色或部门负责人权限。
- 表单、不可变发布版本、任务目标快照、当前答卷和历次正式提交均写入 `collection_*` 表。附件正文只写入仓库外 `COLLECTION_FILE_ROOT`，数据库只保存元数据和哈希。
- 服务不写入 MDM 治理业务表、`docs/norms/` 或 PMO 真源。数据库迁移先执行 dry-run，再 apply 和 schema 检查。

## 9. 禁止的跨线操作

| 禁止操作 | 原因 | 正确做法 |
|---|---|---|
| 改 MDM 时顺手改 `docs/norms/` | 平台代码和流程输入基线混线 | 先确认是否是资料变更任务 |
| 改 PMO 驾驶舱时手工重造流程数据 | 展示副本会偏离流程输入基线 | 获准维护历史展示链时显式指定parser输入和输出 |
| 跑SQLite遗留测试时写共享 `platform.db` | 会污染平台本地状态 | 只用`legacy-sqlite:`命令并通过`MDM_DB_PATH`指定隔离库；正式主线使用MySQL |
| 整理文档时移动 `apps/mdm-platform/` | 运行系统路径被脚本和说明引用 | 先写迁移计划和验证命令 |
| 把截图、zip、解包目录作为证据长期提交 | 检索噪音高，容易误导 AI | 放入 `artifacts/` 或精选到 `docs/samples/` |

## 10. 持续维护检查

1. 修改获准维护的历史消费资产时，显式选择输入、输出及影响范围，运行相称的兼容检查；历史摘要比较另行选择，不触发当前治理或数据库同步。
2. 修改七份PMO Markdown真源后，重新生成两份任务数据和两份清单，并核对全部真源摘要。
3. 当前3000运行及获准的数据库写入使用MySQL；旧资料同步默认仅输出计划，SQLite遗留实现仅用于显式隔离的历史迁移或测试。
4. 新增受控派生消费文件、目录级`AGENTS.md`或长期架构例外时，同步更新边界文件、责任矩阵、上下文说明和对应ADR状态。
5. 历史输出在责任、敏感性、直接消费关系和恢复路径确认前，只登记分类，不移动、不删除。
