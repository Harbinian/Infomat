# 工作角色目录与岗位映射

> 状态：行政人事真源
> 管理部门：行政人事部
> 生效日期：待行政人事部首次确认
> 当前口径：正式目录初始为空；文档结构化输出中的 `proposed` 关系不是正式工作角色。

## 1. 管理边界

工作角色用于说明某个 L3 流程由哪类角色负责，或某个 A1 业务行为由哪类角色参与。工作角色可以映射到花名册中的部门和岗位，但不直接授权到具体人员，也不等同于 MDM 的“项目治理角色”或基础权限角色。

行政人事部负责正式工作角色的命名、编码、启停，以及工作角色与岗位、原文角色别名的确认。流程治理可以提出候选关系，但候选关系只有在本文件登记后才成为正式口径。

维护规则：

1. 工作角色编码由行政人事部在确认时按 `WR-0001`、`WR-0002` 顺序分配；停用编码永久保留、不复用，表格不得跳号。本文件不预填示例编码，不从流程原文或岗位名称自动造码。
2. 工作角色与岗位是多对多关系。岗位按“部门 + 职务”精确核对 `花名册.md`；尚未匹配的行只能保持 `draft`，不得进入 `active` / `retired`。生成脚本只读核验花名册，不反向修改花名册。
3. 原文角色别名按部门维护，保留制度或表单中的原始措辞，用于把同义表达映射到正式工作角色。
4. 三张表的 `status` 只允许 `draft`、`active` 或 `retired`。退役记录保留用于历史追溯，不应删除后重建同义编码。
5. `proposed` / `confirmed` 是文档结构化输出中的关系确认态，不写入本目录三张正式表的 `status` 字段。
6. 生效日期使用 `YYYY-MM-DD`；`active` / `retired` 记录必须填写生效开始日期，`retired` 记录还必须填写生效结束日期，结束日期不得早于开始日期。
7. 工作角色定义和制定依据不能为空；岗位映射、原文角色别名进入 `active` / `retired` 前必须填写确认依据。
8. `draft` 是行政人事部内部草拟态，不能用于形成 `confirmed` 流程关系；`active` 才是当前可选正式口径，`retired` 只供历史追溯。

## 5. 生成与校验

从仓库根目录运行：

```powershell
npm run build:work-role-data
npm run test:work-role-contract
```

生成器读取本文件和 `花名册.md`，完整校验成功后原子替换 `docs/work-role-data.json`。任一角色引用、岗位、状态或重复键校验失败时，命令以非零状态退出，并保留已有快照不变。
