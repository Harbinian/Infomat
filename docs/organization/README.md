# docs/organization 说明

> 状态：组织与部门口径真源目录  
> 生效日期：2026-06-10  
> 范围：组织架构、部门职责、花名册和项目组架构材料。

本目录保存组织架构和部门职责口径。涉及部门清单、部门到域映射、组织编码、岗位和人员同步时，优先核对这里的真源文件。

## 1. 当前文件

| 文件 | 作用 | 口径 |
|---|---|---|
| `组织架构和部门职责.md` | 组织架构、部门职责、组织编码、岗位和人员同步口径 | 组织真源 |
| `花名册.md` | 人员、工号、OA账号、部门、职务、人员类别和来源核查状态 | 人员资料 |
| `花名册事实核查问题清单.md` | 合并外部花名册后的重复、冲突和待确认问题 | 人员资料待确认清单 |
| `工作角色目录与岗位映射.md` | 行政人事部维护的正式工作角色、角色到花名册岗位的映射及原文角色别名 | 工作角色真源；初始为空，不接收流程自动造码 |
| `信息化项目人员角色映射.md` | 花名册人员与信息化项目组、项目执行架构、PMO 运行材料之间的角色映射 | 组织人员真源映射层 |
| `项目组架构.svg` | 项目组架构图 | 图示材料 |
| `昌兴复材信息化项目组架构.svg` | 信息化项目组架构图 | 图示材料 |

## 2. 使用边界

1. 部门清单和部门到域映射以 `组织架构和部门职责.md` 为准。
2. `docs/norms/` 的部门映射、`docs/contracts/dcm-bbm-contract.json` 的校验部门表、PMO 驾驶舱和 MDM 组织同步都应与本目录口径保持一致。
3. 修改组织架构后，不要只改脚本常量或页面文案；应先改真源，再同步派生数据。
4. SVG 图示是展示材料，不能单独替代 Markdown 真源。
5. `信息化项目人员角色映射.md` 只记录已经进入信息化项目运行链条的人，不复制全量花名册；3002 等运行台账只能只读使用映射或派生快照，不能反向修改花名册、组织架构或 PMO Markdown 真源。
6. 合并外部花名册时按工号/胸卡号去重；不因花名册导入新增组织层级，班组不进入主表；同一人员出现部门、职务、人员类别等身份相关冲突时，主表保留当前确认口径，冲突写入 `花名册事实核查问题清单.md` 等待行政人事确认。
7. 工作角色与 MDM 的“项目治理角色”/基础权限角色是不同对象。流程治理只能提出 `proposed` 关系；行政人事部在 `工作角色目录与岗位映射.md` 登记定义、生效期、依据并确认后才形成正式角色及岗位映射。三张表的生命周期状态统一为 `draft|active|retired`。
8. `docs/work-role-data.json` 是从工作角色真源和花名册生成的只读快照，不是维护入口。生成器核对“部门 + 岗位”；不一致行只能保留为 `draft`，`active` / `retired` 会硬失败。生成过程不修改花名册，也不把岗位直接推断成工作角色。

## 3. 修改自检

- 修改部门名称、域归属或组织编码后，检查仓库中是否还有对应硬编码。
- 修改人员或岗位材料后，确认是否需要回归 MDM 组织同步测试。
- 修改工作角色、岗位映射、别名或花名册岗位后，运行 `npm run build:work-role-data` 和 `npm run test:work-role-contract`；生成失败时不得覆盖已有快照。
- 引用部门数据时，避免把历史别名写成当前正式部门名称。
