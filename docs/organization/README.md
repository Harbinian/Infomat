## 2. 使用边界

1. 部门清单和部门到域映射以 `组织架构和部门职责.md` 为准。
2. `docs/norms/` 的部门映射、`docs/contracts/dcm-bbm-contract.json` 的校验部门表、PMO 驾驶舱和 MDM 组织同步都应与本目录口径保持一致。
3. 修改组织架构后，不要只改脚本常量或页面文案；应先改真源，再同步派生数据。
4. SVG 图示是展示材料，不能单独替代 Markdown 真源。
5. `信息化项目人员角色映射.md` 只记录已经进入信息化项目运行链条的人，不复制全量花名册；3002 等运行台账只能只读使用映射或派生快照，不能反向修改花名册、组织架构或 PMO Markdown 真源。
6. 花名册按行政人事部发布版本维护，以员工编号（本文件列名“工号”）核对身份，不以姓名自动认领。新版未收录者保留历史记录，不据此判定离职或停用。人员按“公司领导层→部门→办公室或班组”三级管理；第三级缺项保留为空，已有办公室/班组原名保留，虚拟单位及归属待项目负责人按流程设置。岗位、合同类别及 OA 编号不自动转为 MySQL `person` 有效状态、账号或角色；正式导入前需另有准确目标、差异核对、备份恢复和变更授权，不预设人数相同。
7. 工作角色与 MDM 的“项目治理角色”/基础权限角色是不同对象。流程未固化时可先按“部门 + 花名册岗位”记录 `proposed` 岗位参与草稿，但不分配 `WR-*`、不进入正式投影；行政人事部在流程责任清楚后，于 `工作角色目录与岗位映射.md` 登记定义、生效期、依据并确认，才形成正式角色及岗位映射。岗位与流程角色按多对多关系归并，三张正式表的生命周期状态统一为 `draft|active|retired`。
8. `docs/work-role-data.json` 是从工作角色真源和花名册生成的只读快照，不是维护入口。生成器核对“部门 + 岗位”；不一致行只能保留为 `draft`，`active` / `retired` 会硬失败。生成过程不修改花名册，也不把岗位直接推断成工作角色。
9. 信息化项目部门主备岗的当前名单以 `pmo/信息化项目_部门主备对接人名单.md` 为准；项目决策组确认人员后，再同步更新 `信息化项目人员角色映射.md`。不得从既有工作组名单推断主备岗。
10. 旧 `sync:organization-structure` 使用脚本内固定组织和领导办公室/人员安排，只检查组织文档含名称及代码，不读取本版花名册或虚拟单位定义。它不是本次人员真源的导入入口；不得用它或 `init:mysql` 将本轮文档变更直接套入运行库。

## 3. 修改自检

- 修改部门名称、域归属或组织编码后，检查仓库中是否还有对应硬编码。
- 修改人员真源或岗位材料后，回归受影响的只读解析、项目人员映射和工作角色核验；不得把文档转换或测试通过写成 3000 员工数据已经发布。
- 修改工作角色、岗位映射、别名或花名册岗位后，运行 `npm run build:work-role-data` 和 `npm run test:work-role-contract`；生成失败时不得覆盖已有快照。
- 引用部门数据时，避免把历史别名写成当前正式部门名称。
