# 2026-07-02 文档结构化输出待确认问题识别与用户处理说明

> 状态：修订审核稿  
> 目的：按“文档结构化输出”的数据模型识别文档问题，并把问题交给业务用户处理。  
> 取代口径：本文不再以 MDM 问题池表结构为起点，而以制度/流程文档结构化输出字段为起点。MDM 问题池只作为后续承接页面和处理记录，不作为字段设计的主线。  
> 边界：本文只写识别口径和用户处理说明，不修改 `docs/norms/` 流程输入基线、不改 MDM 代码、不写数据库、不把待确认问题当作已确认流程映射。
> 标准 schema：`docs/contracts/document-structured-output.schema.json`。

## 1. 核心结论

“待确认问题”不是先问一张 MDM 问题卡有哪些字段，而是先问：

> 一份制度、表单或流程文档被结构化输出后，哪些字段还不能安全进入正式流程输入基线，需要业务用户确认？

因此，待确认问题的最小单位应是：

| 维度 | 含义 |
|---|---|
| 结构化对象 | 制度草稿、L3 流程、A1 业务行为、跨部门承接、表单、字段、证据、主数据需求 |
| 目标字段 | 这个对象上的哪个字段需要确认 |
| 当前值 | 当前抽取、录入或草案中的值 |
| 来源证据 | 能不能回到制度、表单、台账、流程图、条款、页码、表格或字段 |
| 待确认原因 | 缺来源、原文没写清、角色不明、系统落位不明、字段对象不明等 |
| 用户动作 | 补证据、修改源文件后重新导入、确认不是问题、转交其它部门或进入专项确认 |

MDM 问题池里的 `issue_id`、`display_status`、`point_status`、`selected_option` 等字段只负责承接处理流程，不能替代上面的业务判断。

## 2. 文档结构化输出的数据模型

当前“文档结构化输出”页面覆盖九类业务对象。字段标准以 `docs/contracts/document-structured-output.schema.json` 为准；本文负责说明识别口径和用户处理方式。

| 页面对象 | 页面字段 | 业务用途 |
|---|---|---|
| 制度草稿 | 制度草稿名称、依据类型、为什么新增、依据说明、是否涉及其他部门、涉及其他部门 | 说明为什么要新增或调整一份制度结构草稿 |
| 制度档案 | 制度名称、制度编号、目的、范围、承继关系 | 建立制度自身的管理信息 |
| 术语 | 术语、适用位置、术语定义 | 统一制度中的业务词、角色词、对象词 |
| L3 流程 | L1 能力域、L2 业务能力、L3 流程、流程类型、流程编号、流程说明 | 把制度内容落到流程骨架 |
| A1 业务行为 | 所属流程、业务行为、执行角色、输入材料、输出结果 | 把流程拆成谁做、做什么、用什么、形成什么 |
| 行为详情 | 是否需要审批、是否跨部门、前置条件、触发场景、执行标准、交付对象、审批要求 | 判断行为边界、完成标准、审批和交接要求 |
| 跨部门承接 | 跨部门行为、承接部门、承接标准 | 发起承接请求，承接流程编号和行为由承接部门回写 |
| 表单/字段 | 表单名称、表单说明、归档规则、附表类型、表名、字段名称、字段类型、是否必填、字段中文名、字段英文名、数据对象、字段证据说明 | 沉淀表单结构、字段口径和潜在主数据对象 |
| 证据/输出 | 证据类型、来源名称、确认人、记录时间、证据说明、来源位置、Markdown 草案 | 证明结构化结果来自哪里，并导出草案 |

这些页面字段最终应尽量沉淀到“流程治理结构块 v1”的五个结构块。

| 结构块 | 关键字段 | 作用 |
|---|---|---|
| `meta` | `dept_code`、`dept_name`、`domain`、`maintainer`、`version`、`status`、`parser_schema_version` | 部门、域、版本和 parser 兼容信息 |
| `l3_catalog` | `l1`、`l2`、`l3_key`、`l3_name`、`system`、`owner`、`evidence_refs` | L2/L3 流程骨架、流程建议落位系统、owner 和证据 |
| `a1_catalog` | `a1_code`、`l3_key`、`behavior`、`role`、`entry`、`system`、`evidence_refs` | A1 编号、所属 L3、业务行为、角色、入口、系统和证据 |
| `evidence_catalog` | `id`、`source_type`、`source_file`、`locator`、`locate_method`、`status` | 证据 ID、源文件、条款/页码/表格位置和核验状态 |
| `mdm_requirement_catalog` | `object`、`key_fields`、`owner_dept`、`requirement`、`evidence_refs` | 待确认主数据对象、关键字段、责任部门和治理要求 |

## 3. 什么情况算“文档问题”

只要某个结构化字段不能安全进入正式流程输入基线，就应生成待确认问题。

| 问题类型 | 识别条件 | 用户要判断什么 |
|---|---|---|
| 来源证据不足 | 没有源文件编号、制度/表单名称、条款、页码、表格位置或原文摘录 | 是卡片证据没给够，还是本来就没有来源 |
| 原文定义不足 | 已找到源文件，但原文没写清责任、动作、对象、交付物、审批或归档要求 | 是否需要修改制度或表单源文件后重新导入 |
| L3 结构待确认 | L1/L2/L3 归属、L3 粒度、L3 编号、流程类型或流程说明不稳 | 这个流程是否应该作为当前 L3 进入基线 |
| A1 行为待确认 | 行为缺执行角色、输入材料、输出结果、完成标准或归属 L3 | 这个 A1 是否成立，是否需要拆分、合并或补充 |
| 角色责任待确认 | 只写“相关部门”“负责人”，或历史部门称谓与现行组织口径不一致 | 谁是执行、审核、批准、协同或确认对象 |
| 跨部门承接待确认 | 行为标记为跨部门，但承接部门、承接标准或回写对象不清 | 是否需要对方部门承接，承接标准是什么 |
| 系统落位待确认 | `system` 为空、多系统并列、写入不允许的系统，或 A1 入口为“待确认” | 只是确认流程建议落位，不做系统选型评价 |
| 表单字段待确认 | 字段名、字段类型、必填性、数据对象、字段证据说明不清 | 是否形成表单字段或待确认主数据对象 |
| 主数据需求待确认 | 从字段或业务对象推导出主数据对象，但未经过字段台账或原文确认 | 是否可以进入 `mdm_requirement_catalog`，不能凭模型建议直接写入 |
| OCR/抽取待复核 | 证据来自 OCR、低质量文本或抽取结果与原文锚点不匹配 | 先核原图/PDF，不能直接进入正式基线 |

## 4. 按结构块识别问题

### 4.1 `meta`

| 字段 | 常见问题 | 处理口径 |
|---|---|---|
| `dept_code` | 部门代码不是既有口径，或与部门名称不一致 | 交信息化负责人和部门接口人确认 |
| `dept_name` | 部门名与组织真源不一致，出现历史称谓 | 回到组织真源和现行部门名称确认 |
| `domain` | 总经理直辖、经营副总、生产副总归属不一致 | 以组织架构真源为准 |
| `maintainer` | 维护人是“待确认” | 必须作为待确认问题交给部门确认 |
| `version`、`status` | 草案误写成正式状态 | 草案只能是 `draft` 或待审状态 |
| `parser_schema_version` | 缺失或不是当前版本 | 不能被 parser 当作结构块 v1 正式读取 |

### 4.2 `l3_catalog`

| 字段 | 常见问题 | 处理口径 |
|---|---|---|
| `l1`、`l2` | 不来自本部门已有能力域/业务能力 | 不开放模型自造 L1/L2，先回到已有映射确认 |
| `l3_key` | 编号新造、重复或与现有稳定编号冲突 | 交流程治理负责人确认编号口径 |
| `l3_name` | 粒度过大、过小，或改变现有 A1 挂接关系 | 作为 L3 粒度问题交业务确认 |
| `system` | 为空、多系统并列、写入 `MDM`、或不在 OA/MES/PLM/ERP 范围 | 确认单一流程落位；不得写系统评价性描述 |
| `owner` | 为空或“待确认” | 交部门确认 L3 owner |
| `evidence_refs` | 引用不存在的证据，或证据状态不是可用状态 | 先补证据或回源核验 |

### 4.3 `a1_catalog`

| 字段 | 常见问题 | 处理口径 |
|---|---|---|
| `a1_code` | 新造编号、重复编号或与现有编号冲突 | 交流程治理负责人确认编号口径 |
| `l3_key` | 找不到对应 L3 | 不能入库，先修正归属 |
| `behavior` | 不是“动词 + 对象 + 结果”口径，或把多个动作混在一起 | 交业务确认是否拆分或改写 |
| `role` | 角色不具体、历史部门称谓、只写相关部门 | 回到原文和组织口径确认 |
| `entry` | 为空或“待确认” | 交对应系统工作组/业务部门确认处理入口 |
| `system` | 为空、错误、或与 L3 流程落位关系冲突 | 只确认该 A1 的处理系统，不评价系统重要性 |
| `evidence_refs` | 缺引用、引用悬空、证据未核验 | 先补证据 |

### 4.4 `evidence_catalog`

| 字段 | 常见问题 | 处理口径 |
|---|---|---|
| `id` | 重复或无法被 L3/A1 引用 | 先修正证据编号 |
| `source_type` | 无法区分制度、表单、台账、流程图、访谈或 OCR | 补来源类型 |
| `source_file` | 只有中间 Markdown、JSON 或脚本产物路径 | 必须回到制度、表单或原始文件 |
| `locator` | 没有条款、页码、表格、字段或流程节点位置 | 先补来源位置 |
| `locate_method` | 定位方式不清 | 明确是条款、页码、表格、字段、流程图节点还是人工定位 |
| `status` | 写成 `verified` 但没有回源核验记录 | 降为 `pending_review`，直到人工核验 |

### 4.5 `mdm_requirement_catalog`

| 字段 | 常见问题 | 处理口径 |
|---|---|---|
| `object` | 模型从字段名直接推导主数据对象 | 不能直接写入，先经过字段台账或原文确认 |
| `key_fields` | 关键字段来自表单字段猜测 | 交数据治理/业务部门确认 |
| `owner_dept` | 维护部门由角色或系统推断 | 必须由业务确认，不能从标题推断 |
| `requirement` | 治理要求没有制度或字段证据 | 先补证据 |
| `evidence_refs` | 没有可核验证据 | 保持待确认，不能入库 |

## 5. 交给用户的处理路径

页面或待办不应让用户理解 `selected_option`、`handling_method`、`point_status` 这类内部字段。用户只需要按下面顺序处理。

### 第一步：看来源是否够

| 看到的情况 | 用户选择 | 后续动作 |
|---|---|---|
| 没有源文件编号、制度/表单名称、条款、页码、表格位置或原文摘录 | 证据不足，先补来源 | 不判断制度有问题，先补证据 |
| 只有流程输入基线或中间 Markdown 位置 | 证据不足，尚未定位到原文 | 回到制度或表单源文件定位 |
| 有源文件和位置，但原文摘录对不上 | 证据对不上 | 先核原文或重新抽取 |
| 来源是 OCR 或图片识别 | OCR 待复核 | 先核原图/PDF |

### 第二步：回到原文判断字段是否写清

| 原文情况 | 用户选择 | 后续动作 |
|---|---|---|
| 原文确实没写清角色、动作、对象、输出、审批、交付或归档 | 问题成立，需要修改制度或表单源文件后重新导入 | 进入部门审核和源文件修订 |
| 原文已经写清，系统或模型没有识别出来 | 这条不是问题，原文已经写清楚 | 在说明中写明制度、条款、页码或字段 |
| 事项不属于本部门 | 这条不是问题，不属于本部门处理范围 | 写明建议主责部门 |
| 已有其它问题或来源覆盖 | 这条不是问题，已被其他问题或来源覆盖 | 写明对应问题或来源 |
| 需要其它部门承接 | 需要跨部门承接 | 写明承接部门和承接标准 |

### 第三步：按问题对象补说明

| 问题对象 | 用户说明必须包含 |
|---|---|
| L3 流程 | 是否保留该 L3、所属 L1/L2、流程边界、主责 owner |
| A1 业务行为 | 谁执行、做什么、对象是什么、输入是什么、输出是什么、完成标准是什么 |
| 角色责任 | 执行、审核、批准、协同或确认对象分别是谁 |
| 跨部门承接 | 发起部门、承接部门、交付物、承接标准、回写对象 |
| 系统落位 | 该流程或行为建议落位到哪类应用，只说落位关系，不评价系统 |
| 表单字段 | 字段名称、字段类型、是否必填、数据对象、证据来源 |
| 主数据需求 | 对象、关键字段、维护部门、治理要求、证据来源 |
| 证据 | 源文件编号、制度/表单名称、条款/页码/表格/字段位置、摘录或核验说明 |

## 6. 建议的待确认问题字段

为了让系统承接时不偏离文档模型，建议每条待确认问题至少包含以下字段。

| 字段 | 展示名 | 用途 |
|---|---|---|
| `stable_key` | 稳定键 | 去重和重复生成识别 |
| `department` | 部门 | 谁处理 |
| `document_name` | 来源文档 | 哪份制度、表单或台账 |
| `structured_object_type` | 结构化对象类型 | meta、L3、A1、证据、表单字段、主数据需求等 |
| `structured_object_key` | 结构化对象编号 | 如 L3 key、A1 code、evidence id、字段编号 |
| `target_block` | 目标结构块 | `meta`、`l3_catalog`、`a1_catalog`、`evidence_catalog`、`mdm_requirement_catalog` |
| `target_field` | 待确认字段 | 如 `owner`、`system`、`entry`、`role`、`locator` |
| `current_value` | 当前值 | 当前草案值，如“待确认”“MES”“质量安环部检验员” |
| `source_file` | 源文件 | 后台追溯；页面展示应转成业务来源名 |
| `source_anchor` | 来源位置 | 条款、页码、表格、字段、流程图节点 |
| `source_excerpt` | 原文摘录 | 用户核验依据 |
| `evidence_status` | 证据状态 | verified、pending_review、source_missing、ocr_extracted_not_confirmed、review_only |
| `issue_type` | 问题类型 | 见第 3 节 |
| `question_for_user` | 请用户确认的问题 | 用业务语言写成一句话 |
| `suggested_handler` | 建议确认人 | 部门接口人、体系文件管理员、系统工作组、数据治理人员等 |
| `allowed_actions` | 允许动作 | 补来源、修改源文件后重新导入、不是问题、转交、专项确认 |
| `user_decision` | 用户判断 | 用户最终选择 |
| `user_reason` | 用户原因 | 原文已写清、不属本部门、证据不足等 |
| `user_note` | 用户说明 | 必须写清依据 |
| `next_step` | 下一步 | 回源修订、部门审核、跨部门承接、数据治理确认、关闭 |

如果短期不改数据库，这些字段可以先进入问题点的结构化证据 JSON 中；`where_text` 只做兜底展示，不再承担解析主责。

## 7. 首批可交给用户处理的问题清单

以下清单来自当前质量管理部结构块试点草案的待确认项，适合作为首批用户处理入口。

| 类型 | 对象 | 需要用户确认的问题 | 建议确认人 | 处理动作 |
|---|---|---|---|---|
| 编码口径 | `dept_code=QMS`、L3 编号、A1 编号 | 是否接受部门代码用 QMS，同时流程/A1 沿用现有 ZL 编号 | 信息化负责人 / 质量管理部接口人 | 确认编码口径或给出替代口径 |
| L3 粒度 | `ZL-02-01` 至 `ZL-02-07` | 是否以现有 7 条稳定 L3 作为首轮试点，而不是合并成 3 条新 L3 | 流程治理负责人 / 质量管理部 | 确认保留、合并或拆分 |
| L3 owner | 全部 7 条 L3 | 现有映射表没有 L3 owner 字段，是否由质量管理部确认 owner | 质量管理部 | 补每条 L3 owner |
| L3 系统落位 | 全部 7 条 L3 | 当前已按单一流程落位收敛为 MES 或 PLM，是否认可该落位口径 | MES/PLM 工作组 / 质量管理部 | 确认流程落位系统或说明调整 |
| A1 入口 | 全部 27 条 A1 | `entry` 当前为“待确认”，需要确认业务处理入口或应用模块 | MES/PLM 工作组 / 质量管理部 | 补 A1 入口 |
| 角色称谓 | A1 执行角色 | 源表仍出现历史称谓，是否要统一到现行组织口径 | 质量管理部 / 体系文件管理员 | 确认保留原文称谓或改为现行称谓 |
| 证据状态 | 全部 evidence | 本轮只读映射表，未回到制度/表单原文核验，不能标记 verified | 质量体系文件管理员 | 回源核验后更新证据状态 |
| 主数据需求 | `mdm_requirement_catalog` | 当前保持空数组；检验项目、测量设备等对象不能凭模型建议直接写入 | 数据治理人员 / 质量管理部 | 经过字段台账或原文确认后再补 |

## 8. 与 MDM 问题池的关系

MDM 问题池可以承接这些待确认问题，但页面和接口应遵守以下关系：

| 文档结构化模型 | MDM 问题池承接 |
|---|---|
| 结构化对象和字段决定问题来源 | 问题卡标题、问题类型和详情 |
| 来源证据决定能否提交判断 | 证据门禁和来源卡片 |
| 用户业务判断决定下一步 | 问题点处理结论和事件历史 |
| 回源修订或确认不是问题决定是否关闭 | 状态流转和关闭条件 |

也就是说：

- 先有文档结构化字段问题，再有 MDM 问题卡。
- 先看源文件和结构块字段，再看状态流转。
- 用户处理的是制度、流程、行为、表单、字段和证据，不是数据库字段。

## 9. 审核时重点看什么

交给其它模型或人员审核时，请重点判断：

1. 是否所有待确认问题都能回到文档结构化输出字段。
2. 是否区分了“问题卡缺证据”和“源文件原文本身没写清”。
3. 是否避免把中间 Markdown、JSON、脚本产物暴露给业务用户。
4. 是否避免把 MDM 或具体应用系统写成业务真源。
5. 是否没有把模型建议直接写入 L3、A1、系统落位或主数据需求。
6. 用户是否能按“看来源、核原文、选判断、写依据、进入下一步”的路径完成处理。

## 10. 下一步落地建议

短期建议先做三件事：

1. 在待确认问题生成时补齐 `target_block`、`target_field`、`current_value`、`question_for_user` 和 `source_excerpt`。
2. 页面优先展示“结构化字段要不要进入正式结构块”的业务问题，而不是内部处理字段。
3. 对质量管理部试点清单逐条回源核验，核验前 `evidence_catalog.status` 保持 `pending_review`，`mdm_requirement_catalog` 保持空数组。

完成这些之后，再考虑是否把结构化字段正式接入 MDM 问题池数据库列、事件 payload 或 `evidence_json`。
