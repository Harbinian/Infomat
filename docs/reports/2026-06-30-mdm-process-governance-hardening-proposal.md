# 2026-06-30 MDM 流程治理建设建议与收口方案

> 状态：推进建议
> 范围：流程治理输入基线、`scripts/parse-sankey-data.mjs`、`apps/mdm-platform/` 流程治理读模型与闭环能力
> 边界：本文件只定义建设方向、执行标准与收口边界；不直接修改 `docs/norms/` 流程输入基线，不实施代码或数据迁移

## 1. 目标

本提案用于把 MDM 流程治理从“可运行承接原型”收口为“可进入单域试点准备”的状态。

本轮收口只围绕两个硬约束展开：

1. **parser 改善前，先提供可落地的兜底推进方案。**
2. **流程治理不再继续使用 SQLite，统一收口为 MySQL-only。**

对应的总体目标是：

- 让各部门先把各自的流程治理输入真源“代码化”。
- 让 parser 从“依赖文档格式猜测”转向“读取受控结构块”。
- 让平台侧的流程治理读模型、权限、审计和闭环能力统一建立在 MySQL 上。

## 2. 建设原则

### 2.1 输入基线边界不变

- `docs/norms/` 仍是流程输入基线。
- `scripts/parse-sankey-data.mjs` 仍是流程快照生成入口。
- `apps/mdm-platform/` 仍是流程治理承接与验证平台。
- 平台不反向覆盖 `docs/norms/`。

### 2.2 先收口输入，再收口平台

当前 parser 的脆弱点，本质上是输入真源的结构化程度不够。因此不建议只在平台侧做兜底，而应先把输入真源做成稳定契约。

推进顺序建议固定为：

1. 文档代码化标准
2. 结构校验与词表校验
3. parser 改为只吃结构块
4. 平台 `MySQL-only` 收口
5. 单域试点

### 2.3 第一阶段只覆盖流程骨架与证据定位

为降低部门负担，文档代码化第一阶段只要求：

- L2/L3/A1 流程骨架
- 应用系统落位
- 角色与处理入口
- 证据定位
- MDM 建设要求

不要求各部门直接维护：

- 问题卡状态机
- 映射待办流转
- 质量问题关闭/重开逻辑
- 平台内部派生统计字段

## 3. 兜底推进方案

### 3.1 采用双轨制

建议采用 `Markdown 正文 + 固定结构块` 的双轨制。

短期：

- 各部门继续维护原有 Markdown 文档，保证可阅读。
- 同一文档内增加固定结构块，作为 parser 的结构化输入。

中期：

- 等结构块稳定后，再逐步迁到独立 YAML/JSON 真源。
- Markdown 退为阅读说明文档，不再承担结构化真源职责。

### 3.2 为什么选择双轨制

相较于“立即改成独立 YAML/JSON 输入基线”，双轨制更适合当前阶段：

- 不会一下子把部门维护门槛拉太高。
- 可以延续现有 `docs/norms/{部门}部门-能力-流程-系统映射关系.md` 输入基线路径。
- 更容易和当前 parser 演进路径衔接。
- 更适合作为 parser 改善前的兜底推进方案。

### 3.3 部门侧最小交付物

每个部门应先交付一份满足以下条件的真源文档：

- 文件路径保持不变：`docs/norms/{部门}部门-能力-流程-系统映射关系.md`
- 文档同时包含正文和结构块
- 结构块至少覆盖：
  - `meta`
  - `l3_catalog`
  - `a1_catalog`
  - `evidence_catalog`
  - `mdm_requirement_catalog`

只有通过结构校验的文档，才允许进入 parser 生成快照。

## 4. 文档代码化执行标准建议

### 4.1 标准定位

建议定义一版 `v0.1 试点标准`，目标不是一次性解决所有问题，而是确保输入真源达到四个条件：

- 可读
- 可解析
- 可校验
- 可追责

### 4.2 文件级标准

- 文件命名保持现有规则，不新增部门自定义命名。
- 同一部门只维护一份当前有效的流程输入基线文档。
- 文档必须带版本号、状态、维护责任人。
- 废弃版本不覆盖原有编码语义，需显式标记状态。

### 4.3 结构块标准

每类结构块在同一份文档中只能出现一次，起止标记必须固定，不允许部门自由变体。

推荐形式如下：

~~~markdown
<!-- STRUCTURED:meta:start -->
```yaml
...
```
<!-- STRUCTURED:meta:end -->
~~~

建议固定五类结构块：

- `meta`
- `l3_catalog`
- `a1_catalog`
- `evidence_catalog`
- `mdm_requirement_catalog`

parser 在后续整改中应只读取这些结构块，不再依赖正文表头和标题猜测。

### 4.4 元数据标准

`meta` 至少包含：

- `dept`
- `domain`
- `owner_role`
- `maintainer`
- `version`
- `status`
- `parser_schema_version`

说明：

- `dept` 和 `domain` 必须与组织真源保持一致。
- `status` 建议受控为 `active`、`deprecated`、`draft`。
- `parser_schema_version` 用于后续 parser 升级时做兼容控制。

### 4.5 L3 目录标准

每条 L3 至少包含：

- `l2_code`
- `l2_name`
- `l3_code`
- `l3_name`
- `systems`
- `owner_dept`
- `evidence_ref_ids`

规则：

- L3 编码长期稳定，改名不改码。
- `systems` 必须是数组，不再用中文顿号分隔。
- 每条 L3 至少关联一条证据。

### 4.6 A1 目录标准

每条 A1 至少包含：

- `a1_code`
- `l3_code`
- `a1_name`
- `roles`
- `entry_type`
- `entry_target`
- `systems`
- `evidence_ref_ids`

规则：

- A1 编号应遵循全域规则，不得由部门临时自造。
- 角色名必须使用受控词表。
- `entry_type` 建议先收敛为有限枚举，例如：`page`、`form`、`manual`、`report`。
- A1 若无独立证据，可暂时继承 L3 证据，但必须显式标注继承关系。

### 4.7 证据目录标准

每条证据至少包含：

- `evidence_id`
- `source_type`
- `source_file`
- `citation`
- `locator_type`
- `status`

建议枚举：

- `source_type`：`制度`、`表单`、`台账`、`记录`、`报告`
- `locator_type`：`page_section`、`page_paragraph`、`table_cell`、`form_field`、`appendix_item`
- `status`：`verified`、`pending_review`、`source_missing`

要求：

- 不允许只写“见原文”“制度有写”“业务确认”。
- 必须能定位到页码、段落、表格位置或字段位置。
- 证据应优先引用制度或表单原文，不依赖中间提取文件名给业务用户做口径展示。

### 4.8 MDM 建设要求标准

`mdm_requirement_catalog` 至少包含：

- `master_data_object`
- `source_l2`
- `key_fields`
- `responsible_dept`
- `system_boundary`
- `governance_requirement`
- `evidence_ref_ids`

目的：

- 让主数据对象识别和流程骨架、证据链保持在同一份部门真源中。
- 为后续 MySQL 读模型导入建立稳定结构。

## 5. 校验标准建议

### 5.1 结构校验

进入 parser 之前，先做结构校验：

- YAML 语法合法
- 结构块齐全
- 必填字段齐全
- 数组字段确实为数组
- 引用 ID 不悬空

### 5.2 词表校验

进入 parser 之前，先做词表和口径校验：

- 部门名称必须来自组织真源
- 域映射必须来自组织真源
- 系统名称必须来自受控词表
- 角色名称必须来自平台受控角色口径
- 过时部门名不得再出现

### 5.3 语义校验

进入 parser 之前，先做引用关系校验：

- `l3_code` 唯一
- `a1_code` 全域唯一
- `a1` 必须指向已存在的 `l3`
- 每个 L3 和 A1 至少有一条证据引用
- 废弃项不得被活动项继续引用

### 5.4 阻断级问题

以下问题应直接阻断导入：

- 结构块缺失
- YAML 非法
- A1 编码重复
- A1 指向不存在的 L3
- 证据 ID 悬空
- 使用未登记系统名
- 引用不存在部门

以下问题可进入“待复核”，但必须出现在问题清单中：

- 证据状态为 `pending_review`
- A1 暂时继承 L3 证据
- 入口说明不完整但结构字段齐备

## 6. parser 收口建议

### 6.1 目标

把 `scripts/parse-sankey-data.mjs` 从“兼容多种人工写法的解析器”，收口为“读取固定结构块的快照构建器”。

### 6.2 收口原则

- 不再新增新的正文模糊匹配规则。
- 不再继续放大表头别名和标题层级猜测。
- 新能力优先加在结构块 schema 和校验器中，不加在正文猜测上。

### 6.3 过渡方式

建议分两步：

1. 保留现有逻辑，但新增结构块优先读取。
2. 当试点部门全部采用结构块后，逐步下线正文猜测逻辑。

这样做可以避免一次性切换带来的风险，同时防止 parser 继续向“超大兼容器”演化。

## 7. MySQL-only 收口建议

### 7.1 核心决策

流程治理后续统一采用 **MySQL-only**，不再使用 SQLite。

### 7.2 收口范围

以下能力全部应统一到 MySQL：

- 流程治理读模型
- 问题池
- 输入基线问题复核
- 质量问题闭环
- 映射待办闭环
- 角色工作台中的流程治理聚合
- 活动与审计事件

### 7.3 明确禁止

后续整改中，应禁止以下做法：

- 保留 SQLite 与 MySQL 双读模型并行作为长期状态
- 在流程治理接口中继续增加 SQLite fallback
- 因导入或结构问题而回退到 SQLite 旧快照
- 让测试继续默认依赖 SQLite 路径来证明“流程治理可用”

### 7.4 配套工作

- 统一环境变量语义，移除“流程治理读模型可切 SQLite/MySQL”的长期口径。
- 导入脚本只保留 MySQL 主路径。
- 路由与仓储围绕 MySQL adapter 收口。
- 测试口径只保留 MySQL 契约、API 和 smoke。

## 8. 平台侧模块收口建议

### 8.1 路由层

建议把 `processGovernance.js` 拆成更清晰的子域 module：

- 流程快照查询
- 质量问题闭环
- 映射待办闭环
- 输入基线问题复核
- 问题池

短期即使不拆成独立路由文件，也应先拆出内部子模块，降低聚合复杂度。

### 8.2 权限层

建议统一形成“动作-权限-角色”矩阵：

- 查看
- 评论
- 分派
- 提交
- 关闭
- 重开
- 生成问题池

规则应以 permission code 为主，role code 只做兼容映射，不再作为长期主判断入口。

### 8.3 审计层

建议把流程治理关键动作统一写入 MySQL 事件面：

- 质量问题动作事件
- 映射待办动作事件
- 输入基线复核动作事件
- 问题池动作事件

平台应支持按单条事项查看事件历史，而不只是全域活动汇总。

## 9. 推荐推进顺序

### 9.1 第一阶段：定义标准

- 输出文档代码化模板
- 输出字段字典与受控词表
- 输出阻断级校验规则

### 9.2 第二阶段：选一个部门试点

- 选择一个最配合的部门试填
- 用试点文档验证结构块、词表、校验器是否可执行
- 不建议一开始全量铺开

### 9.3 第三阶段：parser 收口

- 先实现结构块优先读取
- 再逐步下线正文猜测

### 9.4 第四阶段：平台 MySQL-only 收口

- 移除 SQLite 路径
- 收口流程治理读模型
- 收口权限和事件记录

### 9.5 第五阶段：单域试点

只有以下条件同时满足，才建议进入单域试点：

- 试点部门文档已代码化
- parser 已按结构块稳定输出
- 平台流程治理已 MySQL-only
- 权限矩阵已明确
- 关键动作审计事件已可查询

## 10. 建议给 Codex 的实施范围

若后续把本文件交给 Codex，建议把工作分成三个独立包，不要一次性混做：

1. `文档代码化模板与校验器`
2. `parser 结构块优先读取改造`
3. `流程治理 MySQL-only 收口`

不要把“模板规范、parser 重写、平台路由拆分、问题池新功能”放在同一个实施包里，否则很容易失焦并扩大回归风险。

## 11. 本提案结论

本轮建议不是继续给流程治理加更多功能，而是先收口：

- 输入真源先代码化
- parser 先从猜测型解析转向结构型读取
- 平台先停止 SQLite，统一到 MySQL

只有这样，流程治理才适合从“当前原型状态”进入“可控试点准备状态”。
