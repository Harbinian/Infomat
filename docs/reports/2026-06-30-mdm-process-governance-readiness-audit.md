# 2026-06-30 MDM 流程治理上线准备度审查

> 状态：只读审查结论
> 范围：`apps/mdm-platform/` 流程治理相关前后端、导入脚本、测试入口；`docs/norms/` 流程治理输入基线；`scripts/parse-sankey-data.mjs`
> 边界：不修改 `docs/norms/` 流程输入基线，不修改 PMO 驾驶舱，不实施代码调整；本文件只整理审查结论，供后续 Codex 制定和实施整改方案

## 1. 审查背景

当前仓库主线仍处于“流程地图与数据地图的梳理与沉淀”阶段。`docs/norms/` 承载流程输入基线，PMO 驾驶舱是当前展示入口，`apps/mdm-platform/` 仅承担后续平台承接与验证，不反向覆盖资料入口。

本轮审查聚焦一个问题：`apps/mdm-platform/` 中的流程治理能力，距离“单域试点上线”还有多远。

审查结论是：**距离单域试点上线仍有明显差距，但问题不在于完全没有能力，而在于上线所需的稳定性、口径一致性、权限与审计闭环，以及输入基线收口都还没有达到试点门槛。**

## 2. 结论摘要

### 2.1 总体判断

- 现状更接近“流程治理承接能力原型”，不是“可稳定运维的单域试点能力”。
- 平台已经具备流程快照、问题池、输入基线复核、映射待办、治理闭环、角色工作台汇总等雏形能力。
- 阻碍上线的主要矛盾不是“页面少几个按钮”，而是四类系统性风险尚未收口：
  1. 读模型和导入链路存在双栈与回退逻辑，容易导致口径不一致。
  2. 流程治理路由和仓储过度聚合，改动成本高，局部修正容易牵连全域。
  3. 权限与审计虽有基础能力，但分散在多处实现，缺少统一、可证明的试点口径。
  4. parser 对 Markdown 结构和文案格式敏感，当前流程输入基线还不够“代码化”。

### 2.2 试点结论

- 若以“全员正式上线”为标准，当前阶段不具备上线条件。
- 若以“单域试点”为标准，只有在输入基线、读模型、权限与审计三类问题同步收口后，才适合进入试点。
- 继续保留 SQLite 作为流程治理兼容路径，会扩大排障和口径风险，不建议继续保留。

## 3. 审查范围与证据入口

本轮审查主要覆盖以下资产：

- 平台主入口与路由注册：`apps/mdm-platform/server/index.js`
- 流程治理聚合路由：`apps/mdm-platform/server/routes/processGovernance.js`
- 流程设计与发布投影：`apps/mdm-platform/server/routes/processDesign.js`
- 角色工作台聚合：`apps/mdm-platform/server/routes/roleWorkbench.js`
- 流程治理 MySQL 读模型仓储：`apps/mdm-platform/server/processGovernanceMysqlRepository.js`
- 输入基线问题复核仓储：`apps/mdm-platform/server/processInputBaselineReviewRepository.js`
- 流程治理问题池仓储：`apps/mdm-platform/server/processGovernanceIssuePoolRepository.js`
- 审计与活动聚合：`apps/mdm-platform/server/auditMysqlRepository.js`、`apps/mdm-platform/server/routes/activity.js`
- 流程治理导入与 smoke/test 入口：`apps/mdm-platform/scripts/`
- 流程输入 parser：`scripts/parse-sankey-data.mjs`

## 4. 主要发现

### 4.1 发现一：流程治理模块过度聚合

`apps/mdm-platform/server/routes/processGovernance.js` 同时承担以下职责：

- 读模型选择与可用性兜底
- 快照与 Sankey 查询
- A1、证据、MDM 建设要求查询
- 质量问题闭环
- 映射待办闭环
- 输入基线问题复核
- 问题池生成与操作
- 权限判断与部门隔离

这说明流程治理当前缺少清晰 seam，形成了一个体量过大、职责混杂的 module。任何对问题池、输入基线复核或权限逻辑的小改动，都可能波及其他子域。

影响：

- 认知成本高，新人或自动化代理难以快速定位真正要改的部分。
- 变更范围难以收敛，容易引入旁路回归。
- 测试虽然多，但很大程度是在兜底一个过度聚合的实现，而不是验证一个清晰接口。

### 4.2 发现二：流程治理存在双栈与回退风险

现有实现中，流程治理读模型、问题池与输入基线复核存在不同程度的模式切换或回退逻辑：

- 流程治理读模型受 `PROCESS_GOVERNANCE_READ_MODEL` 影响。
- 输入基线复核受 `PROCESS_CANDIDATE_REVIEW_STORE` 影响，并带有 artifact fallback 语义。
- 问题池仓储存在 SQLite 与 MySQL 两套实现入口。

这类设计在“过渡期”可以理解，但对试点上线不友好。用户会认为自己看到的是同一套流程治理事实，而系统内部却可能来自不同存储、不同快照、不同回退来源。

影响：

- 同一事项在不同页面出现口径差异的风险升高。
- 环境问题排查难度高，容易出现“本地可见、线上不可见”或“接口正常但数据并非同源”的现象。
- 权限、审计、事件历史难以在一套读模型上闭环。

### 4.3 发现三：权限判断已有基础，但试点口径不够统一

流程治理并非完全没有权限控制。当前权限体系已经覆盖：

- `auth.js` 中的 RBAC 权限与字段约束能力
- `processGovernance.js` 中的查看、处理、关闭等动作判定
- `activity.js` 与审计仓储中的活动聚合能力

问题在于：

- 流程治理内既使用 permission code，也混合使用 role code 白名单。
- 关闭、重开、评论、提交等关键动作的能力边界散落在多个 helper 中。
- 对试点管理者而言，缺少一份可被解释的“动作-角色-权限矩阵”。

影响：

- 业务侧难以确认“谁能看、谁能改、谁能关”。
- 上线前难以形成可审计、可复核的权限基线。
- 一旦流程治理进一步扩展，权限逻辑会继续向聚合路由堆积。

### 4.4 发现四：审计能力已有雏形，但还没有形成流程治理域的统一事件面

现有审计仓储已经可汇总以下来源：

- 流程映射待办事件
- 流程治理质量问题事件
- 映射提交/审核
- 版本记录
- 术语创建/审核
- 冲突处理
- 通用待办完成

这说明“活动热力图”类能力不是空白，但对流程治理试点来说仍不够：

- 需要能按单条质量问题、单条映射待办、单个输入基线问题查看完整事件历史。
- 需要明确哪些动作是强制记审计、哪些只是前端展示变化。
- 需要确保流程治理关键写操作统一落在 MySQL 事件表，而不是散落在不同路径。

### 4.5 发现五：parser 已有较强能力，但输入真源仍然过度依赖文档格式纪律

`scripts/parse-sankey-data.mjs` 已支持：

- 组织真源解析
- 部门映射文档自动发现
- Markdown 表格解析
- A1 段落和表格识别
- 证据引用、MDM 建设要求、跨部门报告整合
- 输出到 `docs/company-sankey-data.json` 与 PMO 驾驶舱内嵌数据

问题在于：

- parser 仍大量依赖表头关键词、标题层级、列名变体和文本结构猜测。
- 一旦各部门文档格式稍有漂移，解析稳定性就会下降。
- 当前输入基线更像“人写给人看、机器顺便读一下”，而不是“先定义结构，再表达语义”。

影响：

- 流程治理输入基线的稳定性依赖文档编写习惯。
- parser 提升速度会被部门文档格式漂移拖慢。
- 平台承接端无法建立更严格的结构契约。

## 5. 上线阻断项

若以单域试点作为目标，以下项应视为阻断项：

### 5.1 阻断项一：不应继续保留 SQLite 作为流程治理承接路径

理由：

- SQLite 会继续扩大双栈风险。
- 流程治理事件、权限、读模型和闭环状态难以统一。
- 任何“回退到 SQLite 旧数据”的做法，都会掩盖真源和 MySQL 导入链路的问题。

结论：

- 流程治理应收口为 **MySQL-only**。

### 5.2 阻断项二：输入基线未代码化前，parser 难以成为稳定上线入口

理由：

- 当前 parser 更像“有较强容错能力的解析器”，不是“严格消费结构化真源的编译器”。
- 部门文档若继续自由书写，平台承接层就无法建立稳定契约。

结论：

- parser 改善前，必须先推进部门文档代码化，至少覆盖流程骨架与证据定位。

### 5.3 阻断项三：权限与审计口径尚未达到试点可解释标准

理由：

- 试点不是“能操作就行”，而是要回答“为什么这个人能看到、处理、关闭这个事项”。
- 没有统一权限矩阵和统一事件面，试点阶段容易引发争议。

结论：

- 权限判断与审计记录必须统一到一套 MySQL 读写口径上，并形成明确试点规则。

### 5.4 阻断项四：流程治理 module 结构需要收口

理由：

- 聚合路由过大，会让后续所有修正都带有高风险。
- 即使短期不做大规模重构，也应先按子域拆开内部职责。

结论：

- 在试点前，至少要形成更清晰的内部 seam，而不是继续把子能力堆在一个文件里。

## 6. 适合保留的现有基础

当前实现中，以下能力值得保留并在整改中继续利用：

- `docs/norms/` 作为流程输入基线的边界没有问题。
- `scripts/parse-sankey-data.mjs` 已具备一定的结构化抽取与证据整合基础。
- MySQL 读模型、输入基线复核、问题池、活动汇总已经具备可继续深化的 adapter 和测试入口。
- `apps/mdm-platform/scripts/` 下已有较完整的测试与 smoke 入口，可作为整改后的试点门槛基础。

## 7. 审查结论

本轮审查不建议把 MDM 流程治理理解为“再补几个页面细节就能上线”的状态，而应理解为：

- 现有能力已经足以支撑下一轮收口和试点准备。
- 但在 **输入基线代码化、MySQL-only 收口、权限与审计统一、流程治理 module 拆分** 完成前，不建议进入单域试点。

建议后续以两条主线推进：

1. 先做输入真源的“文档代码化”标准化，把 parser 的输入变稳定。
2. 再做平台侧的 `MySQL-only` 和流程治理模块收口，把承接端变稳定。
