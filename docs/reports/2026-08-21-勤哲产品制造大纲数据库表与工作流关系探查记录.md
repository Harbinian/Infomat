## 3. 结论摘要

1. 截图中的 16 个对象均为 `CXSYSYS.dbo` 下的物理表。
2. 16 张业务表均存在同名 `_wi` 表。每对表的字段数量相同，按字段名比较的数据类型也相同；但 11 对表的字段顺序不同，原表的非空约束和主键没有复制到 `_wi` 表，只有部分 `_wi` 表保留 `ExcelServerRCID + ExcelServerWIID` 索引。因此，不能再笼统地称为“表结构完全一致”。
3. 所有 `_wi` 表均包含 `ExcelServerWIID`。数据库同时存在 `ES_WorkItem.WiId`，两者类型均为 `nvarchar(20)`。结合用户确认口径，可以确认 `_wi` 表属于 WorkItem 配套数据层；其具体保存时点和生命周期仍需实时数据抽样确认。
4. `ES_WorkItem` 表示工作项，`ES_WiTodo` 表示工作项到用户的待办分派，`ES_User` 提供用户身份。
5. `ES_v_Todo` 视图已经直接证明 `ES_WorkItem`、`ES_WiTodo`、`ES_User`、`ES_WfTask`、`ES_Tmp` 和 `ES_RepCase` 的待办查询关系。
6. 产品制造大纲业务表之间未发现数据库外键。勤哲系统主要通过 `ExcelServerRCID`、`ExcelServerWIID`、`WiId`、`RcId`、`TId`、`PiId`、`RtId`、`表编号`和`制造大纲表编号`维持应用逻辑关系。
7. 名称包含“大纲”或“大钢”的对象共 128 个，其中物理表 122 张、视图 6 个。只有部分对象与原始 16 张表存在直接 SQL 引用关系，其余对象只能按名称和字段结构列为相关候选。
8. 当前结构证据可以识别两层业务流：一层是“流程实例—工作项—待办分派—办理人—前后节点—表单数据”的系统执行流；另一层是“制造大纲内容—审批完成—最新批准版本—车间可选版本或流转卡关联”的业务内容生命周期。系统执行流的表间关系证据较强；具体审批节点、办理角色、退回路线和流转卡使用时点仍需实时实例和勤哲页面确认。
9. A 档候选范围的字段级附录已经覆盖 78 张物理表的 1037 个字段定义，以及 20 个直接相关视图的 367 个输出字段。该统计来自本地缓存，不代表实时数据库当前记录情况。

## 6. `_wi` 表与 WorkItem

### 6.1 已确认事实

- 每张原始业务表均存在一个同名 `_wi` 表，共 16 张。
- 每对表的字段数量相同，字段名称集合相同，按字段名比较的数据类型相同，共各 243 个字段定义。
- 11 对表的字段顺序不同；原表上的非空约束和主键没有出现在对应 `_wi` 表中。
- 5 张 `_wi` 表保留了 `ExcelServerRCID + ExcelServerWIID` 索引，其余 11 张 `_wi` 表在缓存中没有索引。
- 原表和 `_wi` 表均包含 `ExcelServerRCID`、`ExcelServerWIID`、`ExcelServerRTID`、`ExcelServerRN` 等勤哲系统字段。
- `ES_WorkItem` 包含 `WiId`、`RcId`、`TId`、`PiId`、`WiType`、`State`、创建人、完成人和完成时间等字段。
- `ES_WorkItem.WiId` 与业务 `_wi` 表的 `ExcelServerWIID` 类型均为 `nvarchar(20)`。

## 7. 工作流与待办关系

### 7.1 核心对象

```text
ES_WfCase（流程实例，PiId）
  ↓
ES_WorkItem（工作项，WiId）
  ├─ ES_WiTodo（WiId + UserId，待办分派）
  │    └─ ES_User（办理人）
  ├─ ES_WfTask（任务节点，TId）
  │    └─ ES_Tmp（表单模板，RtId）
  ├─ ES_WiLink（前后工作项关系）
  ├─ ES_RepCase（表单实例，RcId）
  └─ 业务表_wi（工作项对应的表单数据）
```

### 7.2 `ES_v_Todo` 已确认的连接规则

| 发起对象 | 接收对象 | 连接条件 | 作用 |
|---|---|---|---|
| `ES_WorkItem` | `ES_WiTodo` | `ES_WorkItem.WiId = ES_WiTodo.WiId` | 找到工作项的待办分派 |
| `ES_WiTodo` | `ES_User` | `ES_WiTodo.UserId = ES_User.UserId` | 找到待办办理人 |
| `ES_WorkItem` | `ES_WfTask` | `ES_WorkItem.TId = ES_WfTask.TId` | 找到任务节点定义 |
| `ES_WfTask` | `ES_Tmp` | `ES_WfTask.RtId = ES_Tmp.RtId` | 找到表单模板 |
| `ES_WorkItem` | `ES_RepCase` | `ES_WorkItem.RcId = ES_RepCase.RcId` | 确认对应表单实例存在 |
| `ES_WorkItem` | `ES_WiLink` | `ES_WorkItem.WiId = ES_WiLink.WiId` | 找到前序工作项 |

`ES_v_Todo` 还包含以下筛选条件：

- `ES_WorkItem.State = 0`；
- `ES_WfTask.TType <= 2`；
- `ES_WfTask.DelFlag = 0`；
- `ES_User.AccState = 0`；
- 对应的 `ES_RepCase` 必须存在。

因此，查询“某名用户当前有哪些产品制造大纲待办”时，应先使用 `ES_v_Todo` 或按该视图规则查询工作项和待办分派，再通过 `RcId`、`WiId`连接产品制造大纲业务数据。查询人员不能只依赖 `_wi` 表判断待办状态。

### 7.3 状态口径

缓存视图定义给出以下状态解释：

| 字段 | 值 | 视图解释 | 证据来源 |
|---|---:|---|---|
| `ES_WorkItem.State` | 0 | 待办 | `ES_v_WorkItems` |
| `ES_WorkItem.State` | 1 | 被打开 | `ES_v_WorkItems` |

### 7.4 业务流识别结论

当前证据足以识别业务流的结构和候选阶段，但不足以直接发布一套正式的“产品制造大纲审批流程”。原因是数据库缓存能够说明对象如何连接，却没有提供一个完整实时实例来证明具体节点名称、办理顺序、条件分支和责任岗位。

可以理解为：`ES_WfCase`表示一件业务的完整流转记录，`ES_WorkItem`表示这件业务当前或历史上的一个办理步骤，`ES_WiTodo`表示系统把某个步骤交给哪名用户办理。这个例子只帮助理解三类对象的关系，不代表产品制造大纲的实际节点名称或审批规则。

#### 7.4.1 可以确认的系统执行流

```text
ES_WfCase（一次流程运行，PiId）
  ↓ 同一 PiId 下包含多个工作项
ES_WorkItem（一个办理步骤，WiId）
  ├─ TId → ES_WfTask：这个步骤对应哪个任务节点
  ├─ WiId → ES_WiTodo → ES_User：这个步骤交给谁办理
  ├─ State / State1：这个步骤当前处于待办、打开、完成、暂存或退回等状态
  ├─ RcId → ES_RepCase：这个步骤对应哪次表单填报
  ├─ WiId / RcId → 业务表_wi：这个步骤对应的表单数据候选
  └─ ES_WorkItem（前序）.WiId = ES_WiLink.PrevWiId；ES_WiLink.WiId = ES_WorkItem（当前）.WiId：前后步骤的连接候选
```

根据这条关系链，只要取得一个实时 `PiId` 或 `RcId`，就可以把同一流程实例中的工作项、前后节点、办理人、状态和时间串起来。节点顺序应以 `ES_WiLink` 为主，创建时间只能用于辅助核对，不能代替前后节点关系。

#### 7.4.2 产品制造大纲业务内容生命周期候选

| 候选阶段 | 数据对象或判断条件 | 当前可以确认的内容 | 仍需确认的内容 |
|---|---|---|---|
| 制造大纲内容形成 | `产品制造大纲_主表`及各页主表、明细表 | 数据库保存制造大纲编号、版次和各页内容 | 谁创建、谁修改，以及原表与`_wi`表分别在什么时点写入 |
| 进入流程办理 | `ES_RepCase`、`ES_WfCase`、`ES_WorkItem`、业务`_wi`表 | 数据库具备表单实例、流程实例和工作项的连接结构 | 产品制造大纲实际使用的流程模板、首个节点和发起岗位 |
| 工作项分派和办理 | `ES_WiTodo`、`ES_User`、`ES_WfTask`、`ES_WiLink` | 可以追踪工作项交给谁、对应哪个任务节点以及前后步骤 | 节点业务名称、审核或批准含义、会签、并行和条件分支规则 |
| 审批完成 | `已走完审批流程大纲`视图要求`批准日期`和`批准`非空 | 视图将满足条件的制造大纲认定为已经走完审批流程 | 页面上的最终状态、批准人和流程实例终态是否完全一致 |
| 形成最新批准版本 | `最新版本大纲`按`制造大纲编号`取最大`批准日期` | 可以找到批准日期等于该编号最大批准日期的全部记录 | 同一最大批准日期出现多条记录时，视图不会再按版次或表编号选出唯一一条 |
| 旧版特殊选用 | `特殊可供车间选用旧版大纲_明细`通过`UNION ALL`并入 | 视图将特殊旧版加入可选记录集合 | 旧版选用的申请、批准、适用范围和失效条件 |
| 与流转卡关联 | `表编号 = 制造大纲表编号` | 制造大纲主表和产品制造大纲流转卡存在直接数据连接 | 流转卡在审批完成前还是完成后创建，以及由谁使用 |

因此，当前可以形成以下业务流候选：

```text
编制产品制造大纲及各页内容
  ↓ 具体发起条件和岗位待确认
进入勤哲流程并生成工作项
  ↓ 系统把当前工作项分派给办理人
办理人处理、完成或退回工作项
  ↓ ES_WiLink 连接前后工作项；是否属于正常后续或退回待确认
满足“批准日期和批准均非空”的审批完成条件
  ↓ 按制造大纲编号选择最大批准日期
形成最新批准版本
  ├─ 特殊旧版按独立规则加入车间可选集合
  └─ 按表编号与产品制造大纲流转卡关联
```

上述流程中，“生成工作项”“待办分派”“批准完成条件”和“最新版本选择”有数据库结构或视图定义支持；“编制岗位”“实际审核节点”“退回到哪里”“旧版如何批准”和“流转卡何时使用”仍是待确认事项。

#### 7.4.3 实时数据可还原的完整业务流

后续获得只读实时查询条件后，可以按以下顺序还原一个实际流程实例：

1. 查询人员按`制造大纲编号 + 制造大纲版次`定位一条制造大纲记录，并取得`ExcelServerRCID`。
2. 查询人员通过`RcId`定位`ES_RepCase`和`ES_WorkItem`，取得对应`PiId`和`WiId`。
3. 查询人员按`PiId`提取全部工作项，并通过`ES_WiLink`恢复前后节点关系。
4. 查询人员通过`TId`取得节点定义，通过`ES_WiTodo.UserId`和`ES_User`取得每个节点的办理人。
5. 查询人员结合`State`、`State1`、创建时间、完成时间和完成人，区分待办、完成、暂存和退回记录。
6. 查询人员再把每个`WiId/RcId`连接业务`_wi`表和原始业务表，核对不同节点对应的数据变化。
7. 业务人员在勤哲页面核对节点名称、操作按钮、退回方向和最终状态后，才能把数据库还原结果确认为正式业务流。

### 8.2 主键和索引

- `产品制造大纲_主表`的主键为`制造大纲编号 + 制造大纲版次`。
- 多数明细表以`明细主键`作为主键。
- `产品制造大纲流转卡_主表`的主键为`制造大纲编号 + 类别质量编号`。
- 16 张原始业务表均有`ExcelServerRCID + ExcelServerWIID`索引。
- 本次探查未发现上述业务表之间的数据库外键。

### 8.3 待实时验证关系

除工序页外，其他页主表和明细表均包含 `ExcelServerRCID`，字段和索引结构与工序页一致。该结构支持“各页主表和对应明细表也通过 `ExcelServerRCID` 连接”的判断，但仍需通过实时记录核对连接命中率和重复情况。
