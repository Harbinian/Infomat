## 3. API Key处理规则

1. 用户登录后必须在前端输入本人API Key。服务端通过DeepSeek余额接口验证成功后，才允许填报对话和独立结构预审调用模型。
2. 输入框使用密码掩码。绑定成功后，页面只显示服务端生成的SHA-256前12位指纹、绑定时间和登录会话到期时间，不提供完整Key查看功能。
3. Key只保存在当前服务进程内存中，并绑定登录令牌的会话`nonce`。同一账号的不同登录会话相互隔离；共享同一登录Cookie的多个标签页共享Key。
4. 退出、会话到期、上游返回`MODEL_AUTH_FAILED`或服务重启时，系统清除对应Key。余额不足、模型繁忙、超时和网络中断不清除Key。
5. Key不得写入仓库、本机环境文件、数据库、Cookie、浏览器存储、日志、错误详情或业务文件。
6. 余额不足或低于20元时允许绑定并提示，不自动充值。

未配置Key时，用户仍可读取模板、导入JSON、编辑、执行结构校验和下载当前文件；填报发送、独立结构预审和本人余额查询关闭。

## 4. 模型与管理员边界

- 填报：`deepseek-v4-pro`，关闭思考模式。
- 独立结构预审：`deepseek-v4-pro`，启用`reasoning_effort=high`。
- “0813”保留为试点模型版本记录。实际调用使用供应商正式模型标识`deepseek-v4-pro`；只有供应商模型接口明确返回专用标识时，才另行变更固定配置。
- 管理员只能查看每个账号是否存在有效Key会话、有效会话数和非内容用量，不得查看其他账号余额、指纹或完整Key。

AI仍只追问和整理流程、业务行为、数据对象、表单、字段及其关系。AI不确认流程事实、部门责任、主数据分类或系统选型。

## 5. 验收口径

业务验收共7个案例：

- 4个统一基准案例：丁硕、工程技术部研发、工程技术部批产和行政人事部各完成1个。
- 3个真实案例：工程技术部研发、工程技术部批产和行政人事部各完成1个。一份流程JSON在同一时间只有一名编制人，三者不得并行修改同一文件。

正式发布后，5名用户还须分别使用合成材料完成一次Key绑定、一次填报和一次独立结构预审，以验证各账号模型调用链路。该验证产生实际费用，执行前必须显式确认；管理员不得集中收集其他账号Key。

自动验收至少覆盖五账号唯一性、无服务端Key配置、会话隔离、绑定和清除、刷新保留、退出和到期清除、重启清除、无Key时零模型调用、完整Key不进入响应和日志、管理员无跨账号余额权限，以及两类模型调用参数。
