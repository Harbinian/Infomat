### 1.2 抽象口径

本次不把“程序文件名称”机械等同于“业务能力”，但 L2 业务能力的命名必须与制度标题、条款标题或正文中的业务用词对齐；只有引用条款能够证明扩展含义时，才在能力名中增加更宽的抽象词。建议采用以下分层：

| 层级 | 含义 | 本部门示例 |
|---|---|---|
| L0 部门域 | 经营发展部整体职责域 | 经营发展管理 |
| L1 能力域 | 部门长期稳定承担的大类治理主题 | 市场开发与客户合同治理、采购与供应商资源治理 |
| L2 业务能力 | 可复用、可归责、可配置数据对象的管理能力 | 供应商审核批准与物料清册管理、产品交付与结算回款管理 |
| L3 业务流程 | 制度中可执行的工作序列 | 合同起草、供应商再评价、外协结算付款 |
| L4 应用/数据承载 | 员工侧流程系统与后台主数据治理 | OA、MES、PLM、ERP；MDM单独治理 |

## 2. 能力层建议

建议将经营发展部抽象为1个部门域、8个一级能力域。该划分既覆盖经营规划、绩效、市场、合同、订单、采购、外包、技改、体系、合规等职责，又避免把每份制度直接铺成能力节点。

本轮已对 L2 业务能力补做命名校验：例如 `月度绩效考核管理` 采用 GLTX-JY-05-D《公司月度绩效考核管理规定（暂行）》及 §5.1-§5.4 的原文口径，不再使用未充分证明的泛化写法；`年度部门绩效考核管理`、`年度经营指标制定分解管理`、`项目合同评审执行管理` 等也按制度标题或条款对象校正。

```text
经营发展管理
  ├─ 战略规划与经营指标治理
  ├─ 市场开发与客户合同治理
  ├─ 订单交付与项目履约治理
  ├─ 采购与供应商资源治理
  ├─ 外包外协与委外检测治理
  ├─ 基建技改与设备验收治理
  ├─ 管理体系、流程与文化创新治理
  └─ 合规、风险与外部申报治理
```

## 3. 与既有映射口径的差异

现有 `docs/部门-能力-流程-系统的映射关系汇总.md` 尚未单独展开经营发展部，只在项目管理、生产执行、工程技术等视角中间接出现订单、工时定额、外协计划等条目。本文件采用经营发展部全域职责视角，补齐市场开发、合同订单、采购供应商、外包外协、基建技改、绩效、体系文件、风险合规和海关申报等能力。

| 差异点 | 既有汇总口径 | 本文件口径 |
|---|---|---|
| 部门覆盖 | 未单列经营发展部 | 以经营发展部职责和制度为主线独立建模 |
| 能力范围 | 分散在订单、工时、外协等制造执行链路 | 覆盖战略、市场、合同、采购、供应商、外包、绩效、合规等全域经营治理 |
| 系统承载 | 多从生产执行角度落ERP/MES/PLM | 仅在OA、MES、PLM、ERP四类员工侧系统中选择，并说明设计依据 |
| 主数据表达 | 未独立列出经营侧MDM对象 | 单独识别客户、合同订单、供应商、定额、风险、证照、海关要素等MDM对象 |

## 4. MDM建设总体要求

1. MDM不作为员工侧流程系统，不出现在应用系统字段中。
2. 表单记录不是都进MDM。MDM管稳定对象、编码、分类、关系、状态、版本、责任人和有效期；申请单、审批单、会议纪要、评价报告、结算单等作为业务记录，由OA、MES、PLM、ERP承载并引用主数据。
3. 经营发展部涉及大量跨系统对象，尤其是客户、合同、销售订单、供应商、采购类别、外包任务包、工时定额、技改项目、风险事项和证照资质，必须建立统一ID和状态生命周期。
4. 与供应商、合同、订单、外包、海关、证照有关的数据，应补充权限、保密等级、有效期、停用规则和审计追溯要求。
5. 对PDF扫描件、缺正文、重复目录和待分配编号材料，应先补齐文件号/条款，再作为正式导入依据。
