## 一、目标和责任原则

本计划不以培训人数作为完成标准。首轮必须跑通以下可重复执行链路：

> 业务资料确认 → 3001 四轮单流程编制和评审准备检查 → 部门业务核对 → Codex 线下预审 → 部门整改 → 3000 预览 → 部门 MDM 审核员受控导入 → 留存审核和导入记录

首轮完成标准是两条样板流程均在 3000 审核导入成功。该结果只通过“首轮工具链门槛”，允许受控启动下一批3001编制，不代表EA/BPM治理评价已经具备全面推广条件。正式发布、数据地图发布和跨部门待办全部关闭不属于两周完成条件，但 MDM 工作组必须核对 3000 是否按 JSON 内容生成预期跨部门待办。

3001标准评审准备功能只执行规则检查和整改定位，不记录正式评审结论。根据2026年8月13日用户关于次日部门现场评审的明确指示，3001前端已增加“流程评审”，使用`process-review-readiness-v1`按四方面逐项走查。G-01至G-06仍约束3000正式治理评价、批量导入、数据流和生命周期治理开发，不因本次前端升级自动解除。

本计划执行 [Infomat 数据治理工作规则](../architecture/data-governance-operating-rules.md)。统一责任口径为：

> 业务讲事实，MDM 做结构，PMO 管过程，有权主体作决定，3000 保存治理结果。

MDM-AI 助手不是标准推广路径。后续如按已批准范围开展 AI 试点，用户仍须将结果手工导入 3001，并执行本计划规定的业务核对、线下预审和 3000 受控导入链。

## 二、样板范围

| 部门 | 样板流程 | 核对重点 | 两周输出 |
|---|---|---|---|
| 工程技术部 | ERP 系统物料主数据维护 | 程序、业务对象、六张业务视图表单、字段归属、产生行为和使用行为 | 1 份 v3 单流程 JSON、四轮交接记录、业务核对记录、预审问题清单、3000 审核和导入记录 |
| 行政人事部 | 岗位变动申请、审批、工作交接与考核期管理 | 条件分支、跨部门承接、人员数据、三张表单和审批责任 | 1 份 v3 单流程 JSON、四轮交接记录、业务核对记录、预审问题清单、3000 审核和导入记录 |

工程技术部不得为赶进度合并六张业务视图。行政人事部不得删除部门内部调动、跨部门调动等场景之间的条件和审批差异。

当前应用支撑关系不作为3001结构化编制内容。流程导入3000后，本部门人员再按A1业务行为补充产生、保存、使用、传递、人工辅助，或者明确记录“人工办理”“不使用应用”。应用名称只作为事实线索，不用于评价供应商系统优劣。

首轮不追求正式流程发布、数据地图发布或生命周期治理。两周冲刺不得通过减少表单、合并明细、删减流程分支或降低审核要求实现。

## 三、参与角色和权限

每个样板部门在 2026 年 8 月 14 日前确认：

- 1 名编制人：唯一维护当前 3001 JSON；
- 1 名业务核对人：逐项核对流程事实、表单和现行做法；
- 1 名部门 MDM 审核员：在 3000 核对预览和审核依据并执行受控导入；
- 必要的专业核对人员：只提供核对意见，不并行编辑 JSON。

编制人与部门 MDM 审核员不得由同一角色代替。`pmo/信息化项目_部门主备对接人名单.md` 当前仍处于待项目决策组确认状态，名单中的主对接人不得直接视为本次编制人、业务核对人或部门 MDM 审核员。

| 主体 | 本轮责任 | 完成证据 |
|---|---|---|
| 部门负责人 | 确认本部门三类人员和材料授权范围 | 具名确认记录 |
| 编制人 | 顺序维护唯一当前 JSON，执行导出、重新导入和整改 | 文件交接记录、当前 JSON |
| 业务核对人 | 核对流程事实、表单、字段、条件、责任和来源 | 部门业务核对表 |
| 部门 MDM 审核员 | 使用真实身份核对预览和审核依据，执行受控导入 | 3000 审核和导入记录 |
| MDM 工作组 | 维护结构基准，组织培训和陪跑，处理结构问题，核对导入结果 | 版本基线、问题处理记录、复盘记录 |
| PMO | 登记行动项，跟踪期限、阻塞、证据和关闭条件 | 行动项台账 |
| Codex | 只做线下结构预审，不写审核状态，不修改业务事实 | 与 JSON 分开的预审问题清单 |
| `admin` | 创建账号并分配固定角色 | 身份与角色审计记录 |
| `mdm_lead` | 处理结构卡口，确认第三条试点的场景覆盖，组织后续治理审核 | 结构处理记录、场景覆盖确认和门槛审核记录 |

`mdm_lead`不得替业务部门确认流程事实，也不得替有权主体决定责任边界或业务做法。

## 七、状态、待定和升级

行动项事项状态统一为：

> 未启动 → 进行中 → 待确认 → 已完成 → 已关闭

流程阶段单独记录为：

> 未启动 → 编制中 → 部门核对 → Codex 预审 → 待整改 → 3000 待预览 → 待审核导入 → 已导入

不适用于具体流程的启动和管理事项，流程阶段填写“—”。“阻塞”是附加标记，不替代事项状态或流程阶段。待定事项本身不自动升级。只有跨部门无法形成一致意见、影响已发布流程版本、影响责任边界或超过已批准处理期限时，PMO 才按现行协同规则发起升级。

## 八、记录分层

所有样板材料分别保存：

1. 流程事实：记录当前实际怎么做，以及制度、表单或具名确认来源；
2. 治理结论：记录有权主体确认后的统一定义、责任和管理规则；
3. 改进建议：记录未来可能调整的流程、系统或数据管理方式。

编制人不得为满足治理目标修改当前流程事实，也不得把未来方案写回现状描述。

## 九、首轮验收

两条样板流程必须同时满足：

- 编制人完成四轮编制，每轮均留存当前JSON和交接记录，最后一轮文件与待审文件一致；
- JSON 符合 v3 结构，一份文件只有一个流程，无损坏引用；
- 3001 导出后重新导入，除合法导出时间外，业务内容和稳定引用不丢失；
- 所有业务提示已整改，或形成明确待定事项、确认主体和后续动作；
- 部门业务核对、Codex 预审和 3000 审核材料相互分离且可追溯；
- 3000 预览摘要与审核导入使用的摘要一致；
- 导入记录包含真实审核人员、部门、审核依据和时间；
- 3000 统一保存 v3 完整 JSON，行为、关系、数据对象、表单和字段数量一致；
- 跨部门承接生成预期待办；首轮不要求全部关闭；
- 编制人不能代替审核员导入，其他部门不能越权审核，`admin` 业务写入继续被拒绝；
- 相同文件重复导入不产生重复流程、修订或审核记录；
- 原始制度、表单、3001 源文件和流程输入基线未被修改。

验收记录必须区分自动化检查、人工业务核对和真实导入结果。自动化测试通过不能替代部门业务核对；页面可访问不能替代真实审核导入。

## 十、两级扩面门槛

### 1. 首轮工具链门槛

2026 年 8 月 28 日召开样板评审。两条流程均通过硬性验收，且不存在数据丢失、越权、审核绕过、幂等失败或无法恢复的问题后，只允许受控启动下一批3001编制。该门槛不授权全面推广EA/BPM治理评价。

后续每批仍按两周、每部门一条完整流程执行，最多两个部门并行：

1. 第 1 批：质量管理部、物资保障部；
2. 第 2 批：项目管理部、复材车间；
3. 第 3 批：运维安环部、财务部；
4. 第 4 批：经营发展部，同时处理前批遗留并复核推广材料。

每批开始前，MDM工作组提出流程建议，归口部门确认真实边界、材料和三类人员，PMO登记计划，`mdm_lead`确认场景覆盖。每批结束执行一次门槛评审。上一批存在阻断问题时，下一批不启动。九个部门各完成一条 3000 审核导入流程后，再制定部门内批量扩展和 3001 JSON 批量导入计划。

### 2. EA/BPM治理评价全面推广门槛

全面推广前必须由三条不同的真实流程分别覆盖：

1. 普通顺序流程；
2. 含审批、退回或并行的流程；
3. 跨部门且包含数据和表单的流程。

当前两部门样板只提供其中部分场景证据。两部门样板评审后，MDM工作组提出第三条流程建议；归口部门确认真实边界、人员和材料；PMO跟踪计划；`mdm_lead`确认三类场景均已覆盖。不得为凑场景虚构流程。

三条流程必须完成四轮编制、部门业务核对、3000审核导入、发布前评价和部门确认；发布阻断事项为零；发布后整改项具备责任人、期限和复核方式；跨部门流程完成双方确认；相同输入幂等复跑无重复数据。上述证据完整后，MDM工作组和`mdm_lead`才能记录EA/BPM治理评价全面推广结论。

设计态业务数据流和生命周期治理继续等待批量导入、数量核对、幂等复跑、首轮完整测试和 MDM 工作组门槛审核，不因本计划建立而提前编码。

## 十一、推广事实指标

PMO只记录能够回到具体流程和证据的事实指标，不计算综合分，不进行部门排名：

- 已启动、完成四轮编制、通过部门核对、导入3000和正式发布的流程数量；
- 首次导入成功率和重复导入幂等通过率；
- 每条流程的阻断发布、待确认和发布后整改事项数量；
- 从开始编制到部门确认、从部门确认到发布的实际用时；
- 跨部门承接完成双方确认和逾期的数量；

上述指标只用于发现培训、规则和协作问题，不用于评价部门绩效或证明流程先进。
