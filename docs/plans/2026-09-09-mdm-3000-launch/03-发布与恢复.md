## 2. 配置与访问边界

`scripts/infomat-services.config.json`继续是监听地址、3000端口、MySQL非敏感连接和两种读模型的唯一固定配置。`service:*`只提取其中MDM、MySQL及readModels字段，不读取admin或PMO配置，不自动启动MySQL容器，也不读取私有env文件。运维人员必须在执行前通过已批准的安全注入方式向进程提供Secret；不得把Secret写进命令参数、任务描述、日志或本文件。

直接`npm start`使用显式环境变量。专用`service:*`把固定配置中的对应字段映射为下表变量；会话、HTTPS和超时参数使用进程环境，不读取旧`allowInsecureDevSecret`作为正式设置。

| 环境变量 | 作用及默认值 | 约束 |
|---|---|---|
| `MYSQL_HOST`、`MYSQL_PORT`、`MYSQL_USER`、`MYSQL_DATABASE` | MySQL目标；专用命令来自固定配置 | 缺失拒绝；维护脚本另要求精确`--target` |
| `MYSQL_PASSWORD` | 由安全方式注入 | 必填；不读取或输出真实值 |
| `MYSQL_CONNECTION_LIMIT` | 既有业务仓储连接池上限；固定配置当前为16 | 是各池上限，不是全进程合计或容量结论 |
| `MDM_IDENTITY_READ_MODEL`、`PROCESS_GOVERNANCE_READ_MODEL` | 均为`mysql` | 错误或缺失时在监听前退出 |
| `NODE_ENV` | 专用命令未指定时为`production` | 正式使用`production`；隔离本地开发可显式使用`development` |
| `HOST`、`PORT` | 直接入口默认`127.0.0.1`和3000；专用命令来自固定配置 | 专用命令只接受固定配置端口3000；绑定IP必须显式有效 |
| `SESSION_SECRET` | Cookie签名密钥，安全注入 | HTTPS至少32字节；运维应提供随机高熵值。重启保留同一值，轮换会使旧Cookie失效 |
| `MDM_SESSION_STORE` | 默认`mysql` | `memory`只允许显式测试环境；既有遗留隔离标志仍可使用内存测试会话，production禁止 |
| `MDM_ACCESS_MODE` | 正式必须为`https-proxy` | production不得使用HTTP模式；没有TLS配置则启动失败 |
| `MDM_PUBLIC_ORIGIN` | 完整HTTPS origin，包括实际外部端口（如有） | 不含用户名、密码、路径、查询或片段；正式值待定 |
| `MDM_TRUST_PROXY` | 用逗号分隔的可信代理IP或CIDR | 必须明确来源，不接受布尔值、跳数、别名或`/0`；正式列表待定 |
| `MDM_SESSION_TTL_SECONDS` | 默认86400，范围60至604800 | 滑动空闲有效期；访问时续期，过期服务端拒绝 |
| `MDM_SESSION_CONNECTION_LIMIT` | 会话专用池默认2，范围1至10 | 与业务池分开；第05阶段允许最多32个等待请求，超过上限或整体超时则失败，不无限排队 |
| `MDM_SESSION_TIMEOUT_MS` | 默认2000，范围100至10000 | 包括取得连接及会话SQL操作；超时销毁连接 |
| `MDM_READY_TIMEOUT_MS` | 默认2000，范围100至10000 | 就绪探测整体时限；专用探测池最多1连接，无等待队列 |
| `MDM_READY_CACHE_MS` | 成功缓存默认3000，范围1000至30000 | 失败缓存至多1000毫秒；并发请求共享同一探测 |
| `ALLOW_INSECURE_SESSION_SECRET` | 仅保留历史本地开发兼容 | production设置为`1`时直接拒绝，不自动采用开发密钥 |

`http-local`仅用于非production且绑定回环地址的本地环境，不信任任何代理头。正式模式保持Secure，业务和页面入口要求可信代理提供HTTPS及匹配的公开主机名。代理必须覆盖客户端传入的`X-Forwarded-For`、`X-Forwarded-Host`、`X-Forwarded-Proto`，并通过网络访问控制阻止绕过代理直连后端。精确来源、网络隔离及证书信任仍须在正式拓扑验证；本阶段不配置真实代理。

这与[Express可信代理说明](https://expressjs.com/en/guide/behind-proxies/)及[express-session Cookie说明](https://expressjs.com/en/resources/middleware/session/)一致。当前实现复用已安装的Express 4.22.1、express-session 1.19.0及mysql2 3.22.5，没有新增或升级依赖，没有执行audit fix。

## 3. 会话、迁移与兼容

### 3.1 会话行为

正式HTTPS Cookie名称固定为`__Host-infomat.mdm.sid`，具有`Secure`、`HttpOnly`、`SameSite=Lax`及`Path=/`，不设置Domain。回环开发使用`infomat.mdm.sid`。名称与旧`connect.sid`不同，不接受旧Cookie，不读取或清除其他应用的Cookie。

新表`mdm_http_sessions`只保存`sid_hash`（SHA-256摘要主键）、`session_json`及毫秒时间戳`expires_at`，并为过期时间建索引。JSON格式版本为1，只包含身份标识`personId/accountId/authVersion`以及Cookie和CSRF必要元数据，不包含显示身份、角色权限、业务正文或原始会话ID。运行账号需要该表的SELECT、INSERT、UPDATE、DELETE；不需要DDL权限。会话及其摘要仍属于受保护运行数据，不导出到日志或Git。

登录先重新生成会话，再等待MySQL保存成功，保存失败返回503。活动会话按配置滑动续期；应用重启后，只要MySQL记录未过期且签名密钥不变，会话继续可用。退出删除对应服务端记录并清除本应用Cookie；删除失败返回503，运维不得将其写成退出成功。过期记录即时失效，物理清理由显式维护命令完成，运行时不建表或批量清理。

每次正式受保护请求必须具有完整身份字段，并实时复核账号、人员状态及`auth_version`；停用、撤权或授权变化后的旧会话返回401。首次改密会话可取得CSRF令牌、读取本人状态、修改本人密码和退出，业务入口仍返回403。第03阶段没有改变真实人员或角色授权。

旧MemoryStore会话不能可靠迁出，且原来本就会在重启后丢失；首次切换新Cookie时要求重新登录，不迁移旧`connect.sid`，不影响业务表和V3/V7历史记录。若回退程序不理解新会话格式，应保留新表并按经验证的兼容版本处理，不能自动降回旧不安全入口。密钥轮换和未知会话格式均要求重新登录。

### 3.2 显式维护命令

执行前必须获得对应目标库的具体授权，核对备份、维护窗口及运行账号/迁移账号边界。本阶段只对自建隔离容器执行下列迁移逻辑；没有在固定配置指向的真实库执行命令。

在已安全注入所需变量、明确目标后，可构造精确目标字符串，不在命令中拼入口令：

```powershell
Set-Location 'E:\CA001\Infomat\apps\mdm-platform'
$sessionTarget = "$($env:MYSQL_HOST):$($env:MYSQL_PORT)/$($env:MYSQL_DATABASE)"
npm.cmd run migrate:sessions:inspect -- --target $sessionTarget
npm.cmd run migrate:sessions:apply -- --target $sessionTarget
npm.cmd run migrate:sessions:inspect -- --target $sessionTarget
```

`inspect`只读`information_schema`、`SHOW CREATE TABLE`和既有`schema_migrations`。`apply`只准备会话表及迁移记录`2026-09-10-mdm-http-sessions-v1`，不调用`init:mysql`，不初始化身份和角色，不写业务数据。既有迁移登记表缺失时停止，不能借此初始化整库。

| 检查结果 | 操作 |
|---|---|
| 表和记录都不存在 | 经授权apply创建新表和记录 |
| 结构匹配且已登记 | 重复apply返回已应用，不重建 |
| 表存在且结构完全匹配、无登记、表为空 | 允许显式apply续接建表后中断的迁移登记 |
| 无登记但表中已有记录 | 停止并追溯来源，不自动认领或清除 |
| 列、索引、约束、引擎或字符集等不匹配，或登记存在但表缺失 | 停止检查；不自动修表或补造记录 |

MySQL DDL不能与迁移登记保证同一事务。遇中断先重新inspect；若回退在删表后、删登记前中断，应由维护人员核对准确恢复点并处理残余记录，本入口保持拒绝，不猜测恢复历史会话。

例行过期清理仅操作过期会话，默认每批最多1000条：

```powershell
npm.cmd run cleanup:sessions:inspect -- --target $sessionTarget
npm.cmd run cleanup:sessions:apply -- --target $sessionTarget --limit 1000
```

每日执行频率、执行账号和失败处理人须由正式运维安排；本阶段未创建清理定时任务。单次apply最多删除指定批量，若返回满批可在同一已授权范围继续分批；不得以清理名义删除有效会话。

只有3000已经受控停止、确认会话表为空且确需撤销会话结构时，才使用`npm.cmd run migrate:sessions:rollback -- --target $sessionTarget`。非空表拒绝回退，包括尚未物理清理的过期记录。通常程序恢复保留该表即可，不需要删表；业务库不做整库覆盖或回滚。

## 4. 存活与就绪合同

| 接口 | 成功及失败 | 作用 |
|---|---|---|
| `GET /api/health` | 进程可响应时200、`status=ok`，保留原身份与模型字段 | 兼容存活接口；不访问会话表或业务库，不代表业务就绪 |
| `GET /api/ready` | 就绪为200、`ready=true/status=ready`；否则503、`ready=false/status=not_ready` | 只读核对配置、MySQL连接、现有正式路由基础依赖表列和会话迁移结构；不执行维护 |

两个接口都使用`Cache-Control: no-store`。响应只包含状态、固定故障类别、模型、检查时间和运行版本摘要，不返回SQL、口令、连接目标、账号清单或业务正文。源码摘要`version.sourceDigest`来自启动时的`server/`、`public/`和应用package/lock文件；`checkoutHead`仅用于追溯，不代表该HEAD已经部署。专用check同时核对运行摘要与本地文件摘要，工作区文件变化后旧进程不能继续冒充当前源码。

就绪检查以已有schema和迁移定义为来源，基础依赖共60条表列探测；另检查会话表的列、索引、引擎、字符集与迁移登记。V7或工作包未开启时，其专用结构不成为全站就绪前提；开启时必须有精确范围配置、对应专用表列及迁移记录。不会自动开启功能。本检查不证明所有业务表的字段类型、外键、迁移历史、业务数据、事务或实际人员权限均正确，这些仍由相应迁移与验收工作取证。

成功结果最多滞后`MDM_READY_CACHE_MS`，默认3秒；失败结果最多缓存1秒。探测有整体超时及单一并发检查，超时销毁连接，不留下无限SQL等待队列。停止期间返回`STOPPING`，随后关闭HTTP监听。探测只读，不用写业务数据来判断可用；实际读写授权还须由功能验证证明。

## 5. 仅3000的运维入口

所有入口在应用内`package.json`维护，根共同启动脚本保持原样。专用入口不会执行DDL、账号初始化、同步、PMO、3001或Docker操作。

```powershell
npm.cmd run service:start
npm.cmd run service:check
npm.cmd run service:stop
npm.cmd run service:restart
```

启动与重启前校验必要配置。启动记录监督进程及子进程的PID、创建时间、Node可执行路径及绝对应用入口，只对匹配本工作目录的进程进行管理。停止不能仅凭3000端口杀进程；状态文件缺失、PID被复用、入口不符或孤立子进程均停止自动处理。遇端口占用时拒绝启动，不结束占用者。重复监督进程也会拒绝，不覆盖现有归属记录。

启动成功必须同时满足：受管理的进程拥有监听、存活和就绪通过、源码摘要匹配，以及应用首页含MDM内容。HTTPS模式由Node从已配置公开origin验证首页，并使用该Node进程有效的CA信任；不能仅凭Windows或Edge已信任就认定检查可用。内部CA按C07在Node启动前注入`NODE_EXTRA_CA_CERTS`公开根证书路径，不禁用证书校验。超时或未就绪以非零退出码报告，已启动的监督进程可能仍在运行，先check及检查状态，不反复启动或自动迁移。

运行文件固定为被忽略的`artifacts/mdm-3000-runtime/`，包括`state.json`、`supervisor.lock`、短期`operation.lock`、`stop.request`及`service.log`。部署时应将该目录访问权限限制为对应运维身份；本阶段没有调整真实ACL。工作目录移动后不得沿用原状态文件冒认进程。

停止先发送本地停止请求，监督进程通过IPC要求应用停止接收新请求，允许已有请求最多15秒结束。超时会关闭连接并退出；监督进程17秒后仍未退出才结束它自己持有的子进程。控制命令最多等待约22秒，失败后保留现场，不按端口扩大终止范围。应用失去监督进程IPC连接时也进入受控停止，避免继续作为无归属进程运行。

监督进程在子进程异常退出后按1、2、3秒退避最多恢复3次；仍失败则停止并以失败码退出。不会因数据库暂时不可用反复重启应用；此时进程可存活但ready失败，数据库恢复后重新探测。服务日志仅记录进程生命周期事件、PID和固定状态，丢弃任意应用stdout/stderr，避免把驱动SQL或请求内容带入日志。日志达到1MiB后轮转，保留当前文件和3份历史；这一入口不是完整应用审计日志平台。

### Windows开机恢复准备

当前已验证的是Windows本地监督方式。可由任务计划程序以已批准的运维身份运行下面的前台监督命令，不应把会立即返回的`service:start`作为需要持续跟踪的任务动作：

```powershell
node.exe E:\CA001\Infomat\apps\mdm-platform\scripts\mdm-service.js --supervise
```

实际任务应固定经过验证的Node绝对路径，工作目录为应用目录，启动触发器为系统启动，允许错过启动后补跑，禁止同一任务重复实例，执行时间不设自动截止，并按维护安排设置有限次数失败重试。Secret及HTTPS配置必须由该任务身份下的已批准启动环境安全注入，不能填在任务参数里。交互终端中的临时环境不会自动传给开机任务；缺少注入方式时，不得注册一个无法登录的开机任务。

本阶段未创建、注册或开启真实任务，也未证明重启主机后的行为。正式主机、任务身份、密钥注入和TLS拓扑核定后，再把上述参数落实为该环境的任务配置并验证开机恢复。恢复不得自动pull、自动迁移、重置账号或开启试点。

## 6. 故障处理与版本恢复

| 故障 | 处理及停止条件 |
|---|---|
| `MDM_CONFIG_INVALID`或`MDM_RUNTIME_CONFIG_INVALID` | 核对变量名称、非敏感目标及安全注入是否完成；不打印变量全量，不放宽Secure |
| `HTTPS_PROXY_REQUIRED` | 核对正式origin、代理IP、转发头覆盖和后端网络边界；不设trust proxy=true |
| `MDM_NOT_READY`、`MYSQL_OR_SCHEMA_UNAVAILABLE` | 核对目标连通、运行账号授权及对应只读结构检查；不执行init:mysql或自动补表；恢复后等失败缓存失效再check |
| `SESSION_STORE_UNAVAILABLE` | 登录保存、会话读取或登出未完成；核对会话表和运行权限；恢复后重试，不能报成功 |
| `SESSION_AUTHORIZATION_CHANGED`或`SESSION_IDENTITY_INVALID` | 要求重新登录；若有授权疑问由账号维护主体核对，不恢复旧Cookie或绕过auth_version |
| 端口、归属或PID创建时间不符 | 保留其他进程；核查路径与归属后再决定具体动作，不按端口清场 |

**C1：以后获准的正式只读检查。** 工作目录为获准发布布局内的`apps/mdm-platform`；以下占位值必须来自独立批准记录，不能由当前env自证目标正确。先由维护身份安全注入连接变量，再执行：

```powershell
$approvedTarget = '<批准的host:port/database>'
$approvedReportDir = '<批准的新受控报告绝对路径>'
if ($approvedTarget.Contains('<') -or $approvedReportDir.Contains('<')) { throw 'APPROVED_TARGET_REQUIRED' }
```

**C2：以后获准的正式备份与独立恢复。** 具体工具绝对路径、版本、源/恢复连接配置、输出位置及新实例归属尚待10.5落实。采用与第06阶段相同的“先逻辑备份、恢复独立实例、再逐对象核对”路线。以下为MySQL工具命令形态，凭据由数据库维护人员放在获准、限制ACL的选项文件中，本文不生成或读取该文件：

```text
mysqldump.exe --defaults-extra-file=<获准源连接选项文件> --single-transaction --routines --events --triggers --hex-blob --no-tablespaces --set-gtid-purged=OFF --databases <获准库名> --result-file=<新的受控备份.sql>
mysql.exe --defaults-extra-file=<获准独立恢复连接选项文件> --execute="SOURCE <受控备份的正斜杠绝对路径>"
```

以上不是可直接粘贴的正式命令；占位值必须经10.5批准后逐项具体化。`--databases`会携带原库名，恢复端必须是明确自有、无同名既有数据的独立实例，不能只切换正式库中的database参数充当隔离。`--single-transaction`不能证明非事务表或DDL期间一致；正式元数据如有非InnoDB表、视图、触发器、事件、存储程序或DEFINER权限问题，由维护人员补足相应一致性和恢复处理，禁止静默省略对象。备份与恢复均检查退出码；用`Get-FileHash -LiteralPath <获准SQL绝对路径> -Algorithm SHA256`登记摘要。行数、稳定ID、正文、审核/版本链和引用均须比较，不能仅以文件存在、字节大小或表数相等放行。R3成功前不得执行正式迁移。
