### 1.1 历史自由提交与本轮主链交付的区别

用户补充确认：此前流程治理和主数据识别由各部门自由提交流程与数据，绝大多数材料与主价值链无关，因此不需要将这些历史成果强行拼成流程地图。当前已经向各部门提出围绕主链配套流程的要求，本轮成果应按该要求检查覆盖和承接。

据此，后续分析以用户已下达的主链要求及其确认材料为覆盖基线，逐项对照部门JSON。不能只根据已经收到的文件倒推“主链需要哪些流程”，从而漏掉尚未提交的必要环节。每项要求记录对应流程、输入输出和支撑数据的覆盖情况；具体环节和责任以已下达要求及业务确认内容为准，不由Codex补造。

历史自由提交材料按原有边界保留。仅在与本轮主链存在明确关系且进入本批分析范围时引用；历史材料数量、历史字段数量和JSON结构校验通过，都不能替代本轮主链交付完成度。

本轮要检验的是：部门是否交付了所要求的流程，流程之间能否交付和接收，数据是否支撑相应业务环节，以及缺口能否形成可执行待办。直接承接流程和必要保障流程分别说明其作用，不要求所有保障流程都处于同一条顺序路径。

## 3. 整合与问题分析方法

### 3.1 结构化问题

优先复用当前3001结构规则、共享V7校验器和受支持历史导入规则，记录代码提交、规则版本及结构规则摘要。检查解析、类型、必填字段、枚举、重复标识、失效引用和关系两端。

结构硬错误与业务内容待核对分开记录。结构失败的文件保留在输入清单和问题清单中，不悄悄丢弃；其未验证内容不得作为可靠连接依据。原文缺少说明只形成待补事实问题，不由Codex补造业务动作、部门或处理条件。

### 3.2 流程地图

分别表示流程内业务行为关系和流程间承接关系。流程节点可展开到文件中实际存在的业务行为、表单和数据对象；跨流程连接保留两端位置、交付物、接收条件及来源依据。

关系的证据和确认状态分别表达：

- 原文明确：保留原始描述和位置，业务确认状态按实际证据记录。
- 待定匹配建议：有可解释线索，但尚无充分证据确定连接。
- 待补输入或存在分歧：明确缺少哪一侧材料，或两侧描述具体在哪里不一致。

不能为了画成一条连续路径而虚构连接。覆盖检查应区分“已按要求覆盖”“部分覆盖”“已要求但未提交”“已提交但与要求不符”和“范围外或经确认不适用”。前四类对照实际要求记录证据，不能把已要求但未提交的环节一律解释为本批范围外。

地图可以标明已下达要求中尚未覆盖的位置，但必须显示为交付缺口，不能当作JSON中实际存在的流程。对已要求但缺失的环节、无法承接的交付物或不匹配的数据，生成相应模拟待办，并保留任务要求和已有材料的两侧依据。

真正处于约定范围外的流程、合法开始或结束节点、并行分支、条件分支和返工回路不自动判为错误。断点分析分别记录交付缺口、关系不明确和双方明确冲突。

线下节点使用本批输入身份与文件内稳定引用定位，不伪造正式`process_version_id`。后续3000实现仍按不可变正式流程版本建立受控关系；原始文件不成为正式运行时真源。

### 3.3 数据关系

检查业务行为对数据的创建、修改、使用和传递，表单字段对对象字段的引用，以及文件声明的来源和生命周期线索。

跨文件匹配同时比较业务含义、标识、字段定义、用途、责任和上下文。名称相同或字段相似只形成待定匹配建议。不能自动认定主数据、黄金源或维护部门；也不因单流程没有描述完整生命周期而判定其编制错误。

现有`buildGovernanceCandidates`只提供部分待核对线索，不能替代跨流程分析或有权主体确认。运行现有规则与本轮分析产生的待办要分别注明规则或分析依据。

## 4. 模拟待办

待办与源JSON分开保存，全部标记为线下模拟。三类来源都必须可追溯：结构化问题、流程关系问题、数据关系问题。同一根因影响多处时可合并为一项并列出全部证据；需要不同主体回答的具体问题分别记录，避免一张卡包含无法共同关闭的事项。

每条待办至少包含：

| 内容 | 要求 |
|---|---|
| 标识和来源类别 | 同一批次重复分析可识别同一问题；保留规则版本或分析依据 |
| 发现位置 | 已有材料问题记录输入摘要、流程引用和JSON字段路径，跨文件问题列出两侧；缺交问题记录已下达要求的原始位置，不伪造不存在的JSON路径 |
| 已知事实和问题 | 写清目前材料写了什么，缺什么或冲突在哪里 |
| 影响 | 指明阻碍哪项结构校验、地图连接、数据判断或后续功能 |
| 处理动作 | 写成业务人员能够回答的问题或编制人员能够执行的修正 |
| 建议承接角色及依据 | 技术或结构问题由MDM工作组组织处理；流程事实由相应业务主体确认；不凭姓名、岗位推测正式责任 |
| 关联与前置事项 | 记录依赖的材料、问题或双方确认；信息不足不自动升级决策组 |
| 关闭条件 | 明确需要哪些修订、证据或确认；重新校验不再出现不等于业务已确认 |
| 模拟状态与实际确认 | 场景操作标为模拟；真实答复、正式指派和确认记录分别保留 |

实际负责人、期限和批准结果在未确认时留空。模拟角色不等于真实账号授权。演练不发送通知，不写正式待办、不改PMO台账或审核状态。

## 7. 完成与上线判断

只有实际样本已整合、三类模拟待办已核对、适用基本功能全部在线下执行并取得通过证据，才可报告本轮线下验收完成。未实现、执行失败、缺证据或未验证都不能写成通过。

业务内容存在待定事项时，可以验证系统是否正确生成、阻断和流转对应待办；不得据此宣称该业务关系已确认。技术缺陷与业务待定事项分别报告。

本轮线下验收是3000上线的必要前提。部署目标、正式数据库迁移、备份恢复、运行开关、正式人员权限、业务验收和启用决定仍按既有规则分别取得证据。当前接收目录已经明确，但实际JSON数量为0，不能生成真实地图、统计实际问题数量或给出上线通过结论。
