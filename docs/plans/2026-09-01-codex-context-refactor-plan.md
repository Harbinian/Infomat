## 二、计划结论

本计划只调整 `E:\CA001\Infomat` 仓库内的 Codex 上下文架构，解决以下问题：

- 项目指令链超过默认预算，3001 局部规则在中文句子中间被截断。
- 根入口混入大量应用专项规则，普通任务也要承担无关上下文。
- 相同规则散落在多份文档中，维护者需要同时修改多个位置。
- `AGENTS.md`、`CODEX.md`、`MEMORY.md`、边界文档和架构文档之间的职责重叠。
- 提高模型推理强度也无法弥补未进入模型输入的规则。

当前已确认的直接故障是：

- 根 `AGENTS.md`：18,721 字节。
- 3001 局部 `AGENTS.md`：37,108 字节。
- 根到 3001 的项目指令链：55,829 字节。
- Codex 默认项目指令预算：32 KiB。
- 3001 局部规则当前在中文内容中间被截断，后半部分的图形、校验、运行和验证规则没有进入模型。

该行为符合 [Codex 官方的 AGENTS.md 发现与预算说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md#how-codex-discovers-guidance)：Codex 从项目根目录向当前工作目录合并项目级指令，并受 `project_doc_max_bytes` 限制。用户级 `AGENTS.md` 单独注入，不与项目链共用这 32 KiB 预算，但仍会占用模型上下文。

改造采用“小入口、按需读取、单一规则所有者”的结构：

- 把自动加载的 `AGENTS.md` 作为小型 Module Interface，即只负责入口、硬规则和任务路由。
- 把执行纪律、业务细节和技术规则留在按需读取的 Implementation 文档中。
- 通过明确的 Seam，把每类任务路由到唯一真源，提高 Depth、Leverage 和 Locality。
- 不通过提高上下文上限掩盖职责重复。
- 不用减少验证、删除安全规则或模糊业务边界来换取文件变短。

完成标准：

- 根 `AGENTS.md` 不超过 6,144 字节。
- 3001 局部 `AGENTS.md` 不超过 8,192 字节。
- 任意已登记的“项目根 → 当前目录”指令链不超过 16,384 字节，为默认 32 KiB 上限保留至少一半余量。
- `codex debug prompt-input` 能完整看到 3001 局部规则，不出现中途截断或 Unicode 替换字符 `�`。
- 现有硬性规则全部有明确归属，不因压缩而删除。
- 同一规则只保留一个权威正文，其他位置只做链接或简短路由。
- 代表性任务评测不得出现真源选择、操作范围、无状态边界、MySQL 主线或状态表述方面的回退。

## 三、Implementation 变更

### 1. 建立改造前基线和规则迁移矩阵

开始实施时，Codex 重新检查 Git 状态。计划编制时工作区为干净状态，但实施时不得直接沿用该结论。

Codex 在任何改写前，将以下基线保存到被 Git 忽略的 `artifacts/codex-context-eval/`：

- 当前所有项目级 `AGENTS.md` 的路径、UTF-8 字节数和 SHA-256。
- 根到各个目录的实际项目指令链及累计字节数。
- 根目录和 3001 目录的 `codex debug prompt-input` 输出。
- 六个固定代表任务的只读执行结果。
- 根 `AGENTS.md` 和 3001 局部 `AGENTS.md` 的逐条规则迁移矩阵。

迁移矩阵中的每条现有规则必须标记为以下一种状态：

- 保留在当前入口；
- 迁移到明确的唯一真源；
- 已由现有真源完整覆盖，只删除重复文本；
- 属于历史规则，保留在历史文档但不再作为当前执行指令；
- 存在冲突，停止迁移并提交人工确认。

Codex 不得仅凭相似用词判定规则重复。只有责任主体、适用条件、处理对象、时序、输入输出、异常处理和验证要求均一致时，才能删除重复正文。

### 2. 重构根目录上下文 Module

各文档固定为以下唯一职责：

| Module | 改造后唯一职责 | 不再承担的内容 |
|---|---|---|
| 根 `AGENTS.md` | 当前阶段、全仓硬性边界、主责资产判断、任务类型路由、状态与验收表述底线 | PMO 页面细节、MDM 角色规则、3001 交互细节、端口配置、静态资源路径、账号和模型配置 |
| `CODEX.md` | 仓库变更任务的按需执行手册，包括基线检查、脏工作区保护、验证选择、文档同步和交付要求 | 普通只读问答的强制前置读取、应用业务规格、完整目录清单 |
| `DIRECTORY_OWNERSHIP.md` | 目录责任和全部局部 `AGENTS.md` 的唯一注册清单 | Codex 启动顺序、应用实现细节 |

| `MAINLINE_MAP.md` | 真源、生成器、受控派生文件和消费方之间的数据流 | 页面控件、交互步骤、AI 协作说明 |

| `docs/architecture/context-management.md` | 上下文分层、预算、路由设计、维护原则和检查方法 | 每次任务都要读取的执行规则、重复的完整目录清单 |
| `CONTEXT.md` | 稳定的领域语言、仓库结构概念和当前业务主线 | 易变化的命令、版本和运行状态 |

根 `AGENTS.md` 使用短路由表指导按需读取：

- 普通只读问答：读取任务直接相关的真源，不强制读取 `CODEX.md`。

- 判断目录责任或局部入口：读取 `DIRECTORY_OWNERSHIP.md`。
- 判断真源、派生文件和数据流：读取 `MAINLINE_MAP.md`。

- 运行状态、版本、服务、Git 状态和数据库状态：实时检查，不以 `MEMORY.md` 代替。
- 应用专项任务：先进入相应目录，再按局部 `AGENTS.md` 路由。

`CODEX.md` 按用户确认结果保留为按需执行手册，不并入根 `AGENTS.md`，也不在本轮退役。

## 六、推理强度

本计划实施时固定使用：

```text
model = "gpt-5.6-sol"
model_reasoning_effort = "xhigh"
```

选择 `xhigh` 的原因：

- 本轮需要逐条判断规则是否真正重复，而不是只比较文字。
- 删除重复规则前必须保留责任主体、适用条件、时序、异常处理和验证边界。
- 多份根文档和 3001 文档之间存在职责交叉，需要较强的跨文件一致性判断。
- 当前用户配置已经是 `xhigh`，保持配置不变有利于前后 A/B 对比。

本轮不推荐 `max` 或 `ultra`：

- 当前核心问题是项目指令被截断，不是模型思考时间不足。
- 更高推理强度不能恢复模型没有收到的局部规则。
- 提高强度会增加延迟和资源消耗，并给 A/B 对比引入新变量。

本轮保持仓库配置不变：

```text
model_verbosity = "medium"
model_reasoning_summary = "auto"
```

上下文架构完成并通过 A/B 验证后，日常单模块任务可以单独评估是否降为 `high`；这不属于本计划的实施范围。
