# 3000 EA/BPM 治理评价产品需求

> 状态：3001五方面前端已实现；3000治理评价等待开发门槛
> 版本：V1.1
> 日期：2026-08-13

## 1. 需要解决的问题

3001已经能够编制单个流程的目的、范围、业务行为、执行主体、行为关系、数据、表单和跨部门承接，但其输出属于未审核流程事实。3000需要在真实身份、部门权限和不可变流程版本基础上，完成流程设计评价、问题整改、部门确认、跨流程一致性审核和正式发布。

本期不以增加评价表、综合分或流程数量为目标。系统必须让责任人看到具体问题、处理对象、处理动作、复核主体和发布影响，并保留可追溯记录。

## 2. 产品目标

1. 在流程发布前，对草稿修订执行BPM设计评价，阻止不可执行、责任不清、跨部门未确认、越权或重大合规风险进入正式流程版本。
2. 在流程生效后，以不可变的 `process_version_id` 开展EA关系和数据治理评价，不读取原始3001文件。
3. 使用版本化固定规则库执行自动检查和人工确认，不允许任何角色直接填写流程总分或总评。
4. 将需要判断、补证据或整改的事项生成可定位问题卡，3000保存治理问题和结论，PMO只跟踪推进。
5. 通过3001四轮编制、渐进展开和页面内评审准备检查降低业务人员使用门槛；检查结果不写入JSON，不代替3000正式评审。

## 3. 用户和责任

| 主体 | 主要责任 | 不得执行 |
|---|---|---|
| `department_contact` | 编制和整改本部门流程事实，补充当前应用支撑关系 | 部门确认、关闭本人问题、发布 |
| `department_mdm_reviewer` | 确认本部门事实、审核依据和可发布的整改安排 | 替其他部门确认、全局发布 |
| `data_conflict_handler` | 整理已分派的跨部门分歧和处理方案 | 单方面裁决、处理未分派事项 |
| `data_quality_auditor` | 检查数据关系、证据质量和一致性 | 改写业务事实、替部门确认 |
| `mdm_lead` | 维护并发布规则版本、组织结构审核、审核发布后整改安排、发布治理版本 | 单方面裁决仍有异议的业务事实 |
| `decision_group` | 决定满足升级条件的重大未决事项 | 日常填写、部门审核和发布 |
| `admin` | 管理账号、固定角色和访问审计；全局只读治理材料 | 评价、整改、确认、复核或发布等业务写操作 |

问题处理人与复核人必须分离。跨部门问题由相关部门分别确认，一方确认不能替代另一方。

## 4. 范围

### 4.1 第一阶段包含

- 业务能力、L3流程、A1业务行为、组织和责任关系；
- 设计态数据对象、产生和使用关系、表单字段、关键字段、来源和生命周期待办；
- 按A1业务行为记录的当前应用支撑关系；
- 规则版本、评价批次、逐项结果、问题卡、证据、整改、复核、例外和审计；
- 流程版本、数据地图和业务能力地图分别发布、分别保留历史；
- 历史流程按风险、变更和治理需要分批回评。

### 4.2 第一阶段不包含

- 应用系统优劣、重要程度、替换顺序或供应商排名；
- 目标应用架构、接口技术血缘、数据库血缘、服务器和网络技术架构；
- 流程运行效率、成本、处理量、及时率、自动化率或成熟度；
- 3001账号、数据库、自动保存、证据上传、审核状态或3000通信；
- 3001保存正式评价结论、确认记录、问题卡、整改状态或发布决定；
- 可视化自由配置规则、公式或脚本执行平台。

### 4.3 3001评审准备边界

3001使用固定版本 `process-review-readiness-v4` 对当前页面内存中的单流程内容执行五方面评审准备检查。第三方面检查每个业务行为的“具体做什么”是否按实际顺序写清每个动作、处理对象和结果，并提示明显抽象定性表述；节点组合、嵌套循环、嵌套并行和并行中止图例只在“流程评审”显示。页面显示“可下载并提交部门核对”“有业务提示，可以下载”或“存在结构错误”等操作状态，并逐项定位到需要补充或核对的位置。图例与跨职能流程图预览使用同一图形规则，并支持平移、缩放、适应画布、重置视图和展开查看。

评审准备检查不创建评价批次，不采集审核意见，不保存部门确认，不生成正式问题卡，也不决定流程能否发布。需要业务判断的项目只能提示“需要部门核对”；文件进入3000后，3000依据真实身份、部门权限、规则版本和草稿修订执行正式评价。

3001现有学习评分继续作为折叠的辅助说明。评分不参与三种操作状态计算，不进入JSON、3000、治理门禁、部门排名或绩效评价。

## 5. 两段评价机制

### 5.1 流程发布前

3000对 `draft_id + revision_no` 执行BPM设计评价。草稿内容变化后，旧评价自动失效。流程发布时，3000将当次规则版本、逐项结果、证据和确认记录与新生成的不可变流程版本关联。

### 5.2 流程生效后

3000以 `process_version_id` 建立EA和数据治理工作。流程可以先发布；未完成的数据治理事项继续办理，但相关内容不得进入正式数据地图。新流程版本产生后，3000创建差异复核任务，不静默沿用旧结论。

## 6. 评价结果

每条适用规则分别产生以下用户可见结果：

| 结果 | 含义 | 发布影响 |
|---|---|---|
| 通过 | 当前对象满足规则，且需要的确认和依据已经取得 | 不阻断 |
| 待确认 | 缺少业务事实或依据，暂时无法判断 | 到达发布节点前必须转为其他明确结果 |
| 需整改 | 问题已经确认，需要修改或补充 | 按影响决定发布前完成或形成发布后整改项 |
| 阻断发布 | 问题影响流程身份、可执行性、责任、关键控制、权限安全或重大合规 | 必须解决，不得例外放行 |
| 不适用 | 规则不适用于当前对象 | 必须记录理由、确认人和依据 |

3000按照最严重的未关闭结果实时汇总流程当前状态。任何角色都不能直接修改总状态。

## 7. 第一阶段规则集

### 7.1 六项通用规则

1. 流程名称、目的、范围和归口部门明确。
2. 流程开始条件和结束结果明确。
3. 每个A1业务行为有明确名称、执行主体和完成标准。
4. 业务行为之间存在可解释、可到达的关系。
5. 判断、退回和并行关系具备必要条件，且不存在损坏引用。
6. 流程事实已由归口部门确认，并具备规定的审核依据。

### 7.2 五类条件规则

| 触发场景 | 检查内容 |
|---|---|
| 跨部门办理 | 办理事项、双方责任、触发条件、完成标准、返回要求和双方确认 |
| 数据产生与使用 | 产生行为、使用行为、稳定引用和数据时序 |
| 表单或记录 | 绑定行为、主表字段、每张明细表字段和字段归属 |
| 审批或会签 | 处理主体、触发条件、处理结果和未通过路径 |
| 异常、退回或作废 | 触发条件、返回位置和后续处理 |

### 7.3 四类生效后治理规则

1. 流程版本与业务能力的关系已经确认，或者明确保持待定。
2. 待治理数据对象未因名称相同而自动合并。
3. 当前应用支撑关系已按A1业务行为确认，或者明确记录“人工办理”或“不使用应用”。
4. 数据对象责任、来源、关键字段和生命周期规则按风险进入后续工作包，未完成内容不得显示为通过。

实施期间不得临时扩项。新增或修改规则必须发布新的规则版本。

## 8. 发布门禁和发布后整改项

以下问题阻断流程发布：

- JSON无法解析、稳定标识重复或引用损坏；
- 无法确定流程身份、归口部门或当前修订版本；
- 关键A1业务行为没有执行主体；
- 流程没有可识别的开始条件或结束结果；
- 跨部门办理缺少承接部门、办理事项或必要的双方确认；
- 审批、会签或退回存在无法继续执行的断点；
- 归口部门尚未确认流程事实；
- 存在未解决的越权、数据泄露或重大合规风险。

发布后整改项必须同时满足：不影响当前版本正确执行，不改变责任边界，不影响关键控制，不产生权限安全或重大合规风险，并且已经明确责任人、期限和复核方式。归口部门审核员确认业务影响，`mdm_lead`审核本次发布安排。阻断发布项和事实未确认事项不得例外放行。

## 9. 问题卡

系统只把需要人工判断、补证据或整改的事项生成问题卡。问题卡必须写清：

- 稳定问题编号；
- 所属规则版本和规则编号；
- 流程版本或草稿修订；
- 发现位置和当前情况；
- 业务或发布影响；
- 责任主体和处理动作；
- 完成条件、期限和复核主体；
- 处理前后内容、依据和历史事件。

责任人不能自行关闭问题。复核未通过时，3000退回责任人并保留此前记录。PMO行动项只引用稳定问题编号，不复制结论、证据或审核状态。

## 10. 版本和地图发布

- 流程版本、数据地图和业务能力地图分别审核、分别发布、分别记录生效状态。
- 业务能力地图工作视图可以包含“未归类、待确认”关系，并显示“治理中，不代表正式结论”。
- 正式能力地图只包含已发布流程版本和已确认能力关系，并保留历史版本。
- 新流程版本可以复用旧证据作为评价输入，但必须重新执行规则并形成新的确认记录。
- 已发布历史流程不因新规则上线自动失效；管理视图区分“已按当前规则评价、仅按历史规则评价、尚未回评”。

## 11. 验收标准

1. 用户不能填写综合分或直接修改流程总状态。
2. 系统根据流程内容启用通用规则和条件规则，只生成适用问题卡。
3. 自动检查通过不被显示为业务事实已确认。
4. 草稿修订变化后，旧评价失效；流程新版本不继承旧通过状态。
5. 阻断发布事项存在时，发布接口拒绝执行且返回具体问题编号。
6. 发布后整改项具备双重确认、责任人、期限和复核方式。
7. `admin`可以读取，但所有评价、整改、确认、复核和发布写操作返回403。
8. 部门角色不能处理其他部门事项，跨部门确认不能由单方替代。
9. 流程、数据地图和能力地图的版本状态互不覆盖。
10. 3001保持无状态，`process-governance-v4`格式不增加评审准备字段，历史文件继续在当前页面内存中兼容导入。
11. 3001评审准备检查只产生页面临时结果；关闭页面后不保留，也不能显示为部门已确认或正式评审已通过。
12. 3001五方面前端按2026年8月13日和15日用户明确指示实施；G-01至G-06继续约束3000正式评价、批量导入、数据流和生命周期治理开发。
