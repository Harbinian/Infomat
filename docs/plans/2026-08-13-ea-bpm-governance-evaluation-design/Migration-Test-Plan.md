# 3000 EA/BPM 治理评价迁移与测试计划

> 状态：3001四方面前端已实现；3000治理评价和迁移仍等待开发门槛
> 版本：V1.1
> 日期：2026-08-13

## 1. 启动前提

只有以下门槛全部取得证据后，才能编写3000迁移并修改3000正式治理功能：

1. 3001 JSON批量导入输入范围和摘要冻结；
2. 每个文件有导入成功、返回既有记录或明确拒绝结果；
3. 导入前后数量、结构版本、稳定引用、修订号和内容摘要核对通过；
4. 相同输入幂等复跑不产生重复流程、修订或审核记录；
5. 第一轮完整自动化测试和真实导入核对通过，阻断缺陷为零；
6. MDM工作组完成门槛审核，`mdm_lead`记录开发启动结论。

## 2. 迁移前盘点

dry-run必须盘点：

- 草稿及各状态数量、最大修订号、缺失内容摘要和无法解析内容；
- 当前和历史流程版本数量，以及版本是否不可变；
- `process_ref`、`behavior_ref`、数据、表单和承接稳定引用完整性；
- 已有问题卡、问题点、参与人、事件和重复当前问题；
- 现有证据表能够覆盖的对象类型和缺失范围；
- 已有业务能力、应用、数据地图关系及同名对象；
- 固定角色、人员、部门范围和部门最终负责人是否完整；
- 已发布、已替代、已撤销和尚未生效的流程版本。

固定流程版本仍可原地修改、稳定引用无法跨版本保持，或问题池存在无法确定的重复当前事实时，迁移必须停止。

## 3. 迁移策略

### 3.1 数据库结构

1. 先创建评价批次、逐项结果、证据、评价问题关联、发布后整改、应用支撑、能力关系和地图版本表。
2. 不修改3001文件，不给历史JSON添加评价字段。
3. 不批量生成“通过”结果。历史流程初始状态为“尚未回评”。
4. 只在明确关联时连接现有问题卡；无法唯一关联的项目进入迁移报告，不自动合并。
5. 当前应用名称相同只生成待定匹配建议，不自动建立统一应用身份。
6. 历史能力归类如果没有具名确认记录，只进入工作视图，不进入正式能力地图。

### 3.2 历史流程回评

历史流程按以下优先级建立独立批次：

1. 涉及跨部门、审批、敏感数据、关键判断或重大合规要求；
2. 即将发生实质变更；
3. 已出现治理问题；
4. 即将进入数据地图和生命周期治理；
5. 其余流程按批准批次逐步处理。

新规则上线不自动使历史流程失效。回评发现阻断问题时创建整改任务并标记风险，不自动撤销历史版本；是否暂停使用由有权主体依据实际影响决定。

### 3.3 备份、回滚和补偿

- apply前备份受影响表结构、记录和预计回填清单；
- 迁移批次使用稳定批次键，重复执行不重复写入；
- 尚未发生迁移后业务写入时，可以按批次回滚新增表和关联；
- 已发生确认、整改或发布写入后，只允许补偿状态，不删除历史事件；
- 任一对象不能安全处理时，迁移在写入前停止并列出对象标识和原因。

## 4. 自动化测试

### 4.1 规则和评价

- 六项通用规则、五类条件规则和四类生效后规则；
- 不适用条件、理由和确认人；
- 自动检查不得直接确认业务事实；
- 总状态按最严重未关闭结果计算；
- 规则版本变化生成新批次且不覆盖历史；
- 草稿修订变化使旧批次失效；
- 新流程版本复用证据但重新执行规则。

### 4.2 问题处理

- 规则结果只生成一个当前问题卡；
- 相同输入和幂等键返回既有对象；
- 责任人提交处理后不能自行关闭；
- 复核退回保留所有处理记录；
- 跨部门双方分别确认；
- 发布后整改项具有双重确认、责任人、期限和复核方式；
- 阻断发布和事实未确认事项不能创建放行记录。

### 4.3 发布和版本

- 当前草稿摘要与评价批次不一致时拒绝发布；
- 存在阻断发布事项时返回问题编号；
- 待确认事项到达发布节点时不能绕过；
- 流程、能力地图和数据地图分别发布；
- 地图发布原子完成，失败无部分生效；
- 纠正版本保留错误版本和恢复依据；
- 新流程版本创建差异复核任务，不静默沿用旧确认。

### 4.4 权限和安全

- `admin`全部业务写入403；
- 部门越权读取和写入被拒绝；
- 处理人与复核人为同一人员时拒绝关闭；
- 跨部门一方不能代另一方确认；
- 未分派冲突处理被拒绝；
- `decision_group`日常写入被拒绝；
- 日志和错误不泄露流程正文、证据内容、SQL或凭据。

### 4.5 并发和幂等

- 草稿和问题 `expected_revision`冲突返回409并不丢失用户输入；
- 同一流程、修订、规则版本重复执行评价返回既有批次；
- 同一问题重复提交不生成重复事件；
- 同一地图发布请求重复执行返回既有版本；
- 10个代表性并发用户下，登录、工作台、评价列表和问题处理保持可用。

## 5. 迁移验证

至少执行：

1. schema dry-run；
2. 数据dry-run；
3. apply；
4. 重复apply；
5. 表、列、索引、外键和约束检查；
6. 草稿、流程版本、问题、评价和事件数量核对；
7. 随机样本的稳定引用和内容摘要核对；
8. 无业务写入场景的回滚；
9. 已发生业务写入场景的补偿演练；
10. 迁移失败后恢复服务和继续处理。

## 6. 3001评审准备与回归

3000正式评价不修改3001数据结构，也不把评价结果写回JSON。根据2026年8月13日用户关于次日部门现场评审的明确指示，3001已按[流程标准评审准备规则规格](3001-Review-Readiness-Spec.md)增加四方面走查、操作状态和问题定位；接口、v3结构和无状态边界保持不变。G-01至G-06仍约束3000治理评价、批量导入、数据流和生命周期治理开发。3001前端发布前必须证明：

- 上一受支持版本可以导入当前版本；
- 当前版本导出后可以重新导入；
- 历史高级内容和未收录值不丢失；
- 每轮不完整草稿可以下载，损坏引用不能下载；
- 学习评分不写入JSON、不进入3000；
- `process-review-readiness-v4`五方面逐项结果只存在当前页面内存，不写入JSON、不形成正式评审结论；v1、v2、v3和旧v4文件继续使用既有字段，无需新增迁移字段；
- 业务行为未填写“具体做什么”、使用明显抽象定性表述、没有具体动作时分别生成可定位提示；判断节点、并行开始和并行汇合不误报；
- 多个具有完成标准的合法末端不被误报为“流程只能有一个出口”；
- 规则只根据明确结构判断审批、会签、异常和跨部门场景，不根据名称推测；
- 没有数据或表单时按不适用处理，不要求用户虚构对象；
- 技术错误阻止下载，业务提示不阻止下载，人工确认提醒不被自动显示为通过；
- 每个可修复问题能够定位实际输入控件，定位和重新检查不修改流程内容；
- 页面没有账号、数据库、自动保存、浏览器持久化或3000通信；
- 现有3001自动化测试和真实浏览器流程全部通过。

规则实现使用[测试数据定义](../../samples/3001-process-review-readiness-test-cases-v1.md)及其三个基础样例。技术样例通过不能替代三条真实流程试点。

## 7. 浏览器验收

使用真实部门范围账号完成：

1. `department_contact`从工作台进入本部门流程，查看系统自动检查和问题卡；
2. 责任人修改流程或提交整改，不能自行关闭；
3. 部门审核员复核本部门事项，不能处理其他部门；
4. 跨部门双方分别确认，一方不能替代另一方；
5. `data_quality_auditor`检查数据和证据，但不能改写业务事实；
6. `mdm_lead`查看门禁、审核发布后整改安排并发布规则或地图版本；
7. 存在阻断事项时发布失败并定位问题；
8. 无阻断事项且发布后整改安排完整时发布成功；
9. 新流程版本触发重新评价和差异任务；
10. 历史流程显示当前规则、历史规则或尚未回评的准确状态。

## 8. 试点和完成标准

实施完成后，使用普通顺序流程、含审批退回或并行流程、跨部门且包含数据和表单的流程分别完成端到端试点。只有同时满足以下条件才能宣布完成：

- 三条流程均完成3001编制、部门核对、3000导入、发布前评价和对应确认；
- 阻断发布事项为零；
- 发布后整改项具备责任人、期限和复核方式；
- 相同输入幂等复跑无重复数据；
- 迁移、权限、并发、发布、历史和恢复测试通过；
- 根服务烟测和真实浏览器验收通过；
- PRD、技术方案、接口约定、数据库结构、权限、推广说明、迁移测试说明、README、角色手册和术语表同步完成。

自动化检查通过不能替代部门业务确认，文档检查通过不能替代真实导入和发布结果。
