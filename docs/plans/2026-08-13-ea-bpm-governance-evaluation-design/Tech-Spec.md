# 3000 EA/BPM 治理评价技术方案

> 状态：3001五方面前端已实现；3000治理评价等待开发门槛
> 版本：V1.1
> 日期：2026-08-13

## 1. 总体设计

3000在现有流程草稿、不可变流程版本、固定身份、跨部门承接和问题池之上增加治理评价能力。系统不得复制第二份流程事实，也不得把评价结果写回 `process-governance-v3`。

```text
3001未审核单流程JSON
  → 3000预览和部门审核导入
  → process_design_drafts.process_content_json
  → 发布前BPM评价（draft_id + revision_no）
  → 流程发布
  → process_design_versions.id（process_version_id）
  → 生效后EA与数据治理评价
  → 分别发布能力地图和数据地图版本
```

## 2. 模块边界

| 模块 | 职责 | 不负责 |
|---|---|---|
| 固定规则库 | 保存版本化规则定义、适用条件、严重程度和处理说明 | 自由脚本、用户自定义公式 |
| 评价编排器 | 创建评价批次、加载流程快照、执行规则、保存结果 | 修改流程内容、替业务确认 |
| 自动检查器 | 执行结构、引用、可达性、数据时序和版本检查 | 判断业务合理性和责任正确性 |
| 人工确认工作台 | 收集确认结果、依据和不适用理由 | 批量勾选全部通过 |
| 问题卡适配器 | 把需处理结果关联到3000现有问题池 | 在PMO建立第二份治理问题 |
| 状态汇总器 | 按最严重未关闭结果计算当前总状态 | 保存可人工编辑的总评 |
| 发布门禁 | 检查阻断事项、待确认事项和发布后整改安排 | 绕过权限和规则结果 |
| 版本差异器 | 按稳定引用识别新增、变化、删除和未变化对象 | 按名称推测对象身份 |
| 地图投影器 | 从已确认关系生成能力地图和数据地图版本 | 反向改写流程版本 |
| 审计记录器 | 追加规则、评价、处理、复核、例外和发布事件 | 更新或删除历史事件 |
| 3001评审准备检查 | 在浏览器当前页面内按固定规则生成操作状态、逐项提示和字段定位 | 保存结果、调用3000、形成正式评价或修改JSON |

## 3. 规则定义

第一阶段规则使用已提交的固定配置或代码常量，不建设可视化编辑器。每条规则至少包含：

```json
{
  "rule_code": "BPM-COMMON-001",
  "rule_set_version": "ea-bpm-governance-v1",
  "stage": "pre_publish",
  "object_type": "process",
  "applicability": "always",
  "evaluation_mode": "automatic_and_human",
  "default_result_on_failure": "release_blocked",
  "title": "流程基本边界明确",
  "remediation_guidance": "补充流程名称、目的、范围和归口部门，并由归口部门审核员确认。"
}
```

规则版本发布前必须通过静态校验、规则样例测试和MDM工作组评审。`mdm_lead`只发布已经确认的规则版本，不能在运行页面直接修改规则内容。

## 4. 评价批次

### 4.1 发布前批次

- 输入：`draft_id`、`revision_no`、`content_hash`和当前规则版本。
- 幂等键：`stage + draft_id + revision_no + rule_set_version`。
- 草稿修订发生变化后，旧批次状态变为“已失效”，但历史结果继续只读保留。
- 发布时必须重新确认当前 `revision_no` 和 `content_hash` 与评价批次一致。

### 4.2 生效后批次

- 输入：不可变 `process_version_id`、版本内容摘要和当前规则版本。
- 幂等键：`stage + process_version_id + rule_set_version + evaluation_scope`。
- 数据治理和地图发布只引用 `process_version_id`，不得保存或读取原始3001文件路径、文件名或上传摘要。

### 4.3 历史回评批次

历史流程按风险清单创建独立批次。批次必须记录选择依据、范围、规则版本和完成情况。未进入批次的历史流程显示“尚未回评”，不得显示为通过。

## 5. 适用条件和逐项结果

评价编排器先根据流程内容判断规则是否适用：

- `cross_department_handoffs[]`非空时启用跨部门规则；
- 存在数据对象及产生、使用关系时启用数据规则；
- `forms[]`非空时启用表单规则；
- 会签标记、审批节点或受控审批关系存在时启用审批、会签规则；
- 存在 `loop`、退回、作废或异常路径时启用异常规则。

系统对每个“规则＋对象”保存一条逐项结果。自动检查只能直接产生自动通过、待确认、需整改或阻断发布建议；凡涉及业务事实、责任、证据或不适用判断，必须由相应角色确认后才能成为最终结果。

## 6. 总状态计算

总状态不落为可编辑字段，由查询服务实时计算：

```text
存在未关闭 release_blocked → 阻断发布
否则存在未关闭 needs_remediation → 需整改
否则存在未关闭 pending_confirmation → 待确认
否则所有适用结果均为 passed 或 not_applicable → 通过
```

“发布后整改项”仍属于未关闭的 `needs_remediation`。流程发布接口只有在该事项具备部门审核员确认、`mdm_lead`审核、责任人、期限和复核方式后，才允许本次发布。

## 7. 问题卡复用

3000继续以现有 `process_governance_issues`、`process_governance_issue_points`、参与人和事件表作为用户问题池。评价能力通过关联表把评价结果绑定到现有问题卡，不创建第二套问题事实。

一个评价结果最多关联一个当前未关闭问题卡。相同幂等键重复评价时返回既有问题卡；规则结果变化时追加事件或创建后继问题，不覆盖旧处理历史。

## 8. 证据和确认

证据记录只保存可追溯元数据和确认记录：来源类型、来源名称、页码或条款位置、确认主体、确认时间、缺失原因、预期提供人和关闭条件。第一阶段不在3001增加附件上传，也不把自动检查日志当作业务证据。

评价结果可以复用旧版本证据作为输入，但必须生成新的确认记录。涉及责任、条件、完成标准、数据关系、表单字段或跨部门承接变化时，旧人工确认自动失效。

## 9. 当前应用支撑关系

应用支撑关系在流程导入3000后，由本部门人员按A1业务行为补充。关系类型固定为产生、保存、使用、传递和人工辅助。没有应用时明确记录“人工办理”或“不使用应用”。

应用名称只作为发现线索。系统可以生成待定匹配建议，但不得按名称自动合并应用身份。该关系只描述当前事实，不代表未来系统归属或系统优劣评价。

## 10. 能力地图和数据地图

- 能力地图工作视图读取已发布流程和待确认能力关系，显示治理中标记。
- 正式能力地图只收录已发布流程版本和已确认能力关系，并形成不可变地图版本。
- 数据地图继续执行现有生命周期治理计划，只有完成部门确认、跨部门确认、MDM工作组审核和发布门禁的内容才能进入正式版本。
- 两类地图发布均采用原子事务；失败时不得出现部分关系生效。

## 11. 安全和并发

- 所有写接口使用当前 `person -> user_accounts -> person_roles` 身份链和服务端权限检查。
- 部门角色的查询和写入必须带部门范围约束；前端隐藏按钮不能替代服务端校验。
- 草稿评价、处理和发布继续使用 `expected_revision` 或等价版本条件，冲突返回409并保留用户输入。
- 自动评价不得把流程正文、证据内容或敏感字段写入普通运行日志。
- `admin`业务写操作返回403；跨部门事项必须分别校验参与部门身份。

## 12. 工作包和实施顺序

### 12.1 3001评审准备实现边界

`process-review-readiness-v4`由3001前端根据当前内存中的 `process-governance-v4` 内容计算。实现复用现有结构校验、业务提示、图关系和字段定位能力，并在“流程评审”增加业务行为逐动作可执行性、循环逐层退出、最近共同并行汇合和并行提前结束检查；不增加服务端接口、数据库、浏览器持久化、JSON字段或3000运行依赖。

规则结果对象只在当前页面使用，固定为 `pass`、`prompt`、`confirmation_required`、`not_applicable` 和 `blocker`。其中 `confirmation_required` 表示文件下载后仍需部门核对，不阻止下载，也不得转换为“正式通过”。页面总状态只按结构阻断和业务提示汇总；学习评分不参与总状态计算。

前端实现、旧文件兼容和字段定位的固定输入见 `3001-Review-Readiness-Spec.md`，回归数据见 `../../samples/3001-process-review-readiness-test-cases-v1.md`。根据2026年8月13日和15日用户关于部门现场评审的明确指示，本节对应的3001无状态前端已经实施；接口、结构规则和3000运行边界保持不变。

### 工作包A：流程设计评价与3001推广

1. 固化规则定义和样例；
2. 建立评价批次、逐项结果和问题关联；
3. 建立处理、复核、发布后整改和发布门禁；
4. 完成三类真实流程试点；
5. 按部门推广。

### 工作包B：数据流与生命周期治理

继续执行现有 `WP-00` 至 `WP-08`，并复用工作包A建立的规则版本、问题、证据、权限、审计和版本能力。工作包B不得重新建设第二套评价或问题平台。

## 13. 暂停条件

出现以下任一情况时停止实施：

- 既定批量导入和首轮测试门槛未通过；
- `process_design_versions`仍允许原地修改；
- 稳定引用无法跨版本比较；
- 方案要求修改七个固定角色或允许 `admin` 业务写入；
- 方案要求3001保存状态、连接3000或承担正式证据和评价；
- 3000正式评价启动前，G-01至G-06尚未形成可复核证据；
- 迁移演练出现数据丢失、重复问题、越权或无法补偿。
