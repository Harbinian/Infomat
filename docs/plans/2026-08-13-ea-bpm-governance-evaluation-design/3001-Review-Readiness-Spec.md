# 3001 流程标准评审准备规则规格

> 状态：3001前端已实现，供部门现场走查
> 规则版本：`process-review-readiness-v4`
> 日期：2026-08-15
> 适用对象：3001 编制人、业务核对人、MDM 工作组、开发人员和测试人员

## 1. 目标和边界

3001 根据当前页面中的 `process-governance-v4` 内容执行流程标准评审准备检查。检查结果帮助编制人发现缺项、返回对应输入位置并补充流程事实。

3001 不执行正式评审，不记录审核意见、部门确认、证据、问题处理结论或发布决定。正式业务流程管理（BPM）设计评价、身份审核、部门确认、问题卡和发布门禁仍由 3000 负责。

本规则不得：

- 增加或修改 JSON 字段；
- 把检查结果、学习评分或页面状态写入 JSON；
- 根据名称推测业务事实、责任部门、审批性质、数据对象身份或跨部门关系；
- 把自动检查通过显示为业务事实已确认；
- 阻止用户下载只有业务提示的未审核草稿。

## 2. 页面操作状态

3001 每次进入“核对下载”或用户点击重新检查时，使用当前页面内存中的流程副本重新计算结果。页面只显示以下三种操作状态：

| 状态 | 判定条件 | 用户动作 |
|---|---|---|
| 可下载并提交部门核对 | 没有技术错误，也没有自动识别的内容缺项 | 下载未审核 JSON，交业务核对人逐项确认事实 |
| 有业务提示，可以下载 | 没有技术错误，但存在内容缺项、待确认或场景核对提示 | 按定位逐项补充；暂时不能确认时保留事实并交给有权主体确认 |
| 存在结构错误 | JSON 解析、版本、结构规则、技术引用、导出回读或内容保持检查失败 | 修复技术错误后重新检查；修复前禁止下载 |

“需部门或 3000 确认”属于人工确认提醒，不等同自动检查不通过。该提醒必须始终显示，但不单独改变“可下载并提交部门核对”状态。

## 3. 逐项结果模型

每个规则对一个明确对象返回一项结果：

| 字段 | 说明 |
|---|---|
| `rule_set_version` | 固定为 `process-review-readiness-v4` |
| `rule_id` | 本文件定义的稳定规则编号 |
| `result` | `pass`、`prompt`、`confirmation_required`、`not_applicable` 或 `blocker` |
| `object_type`、`object_ref` | 流程、行为、关系、数据、承接或表单的稳定对象位置 |
| `message` | 只陈述当前页面能够确认的事实 |
| `suggestions[]` | 至少一条可执行建议 |
| `editorSection`、`processSection` | 目标编制阶段和子分区 |
| `focusKind`、`focusRef` | 需要先选中的对象 |
| `focusPath`、`focusPaths` | 需要聚焦和高亮的实际输入控件 |

上述结果只存在当前页面内存。重新检查不得修改流程对象、稳定引用、当前选择或未导出状态。

## 4. 九项通用规则

| 规则编号 | 自动检查内容 | 结果和定位 |
|---|---|---|
| PRR-COM-01 | 流程名称、目的、范围和归口部门均有明确内容 | 缺少一项生成一条 `prompt`，分别定位到实际字段 |
| PRR-COM-02 | 流程存在一个可识别入口；入口行为写明“流程如何开始”；每个无后续非回路关系的末端业务行为写明完成标准 | 多个合法末端不报错；末端缺少完成标准时定位该行为，不再要求整个流程只能有一个出口 |
| PRR-COM-03 | 每个业务行为具有节点类型、名称、执行主体和完成标准；并行控制节点不要求填写业务完成标准 | 动态责任部门同时检查前序数据和办理人员确定规则 |
| PRR-COM-04 | 除显式回路外，每个已登记节点都能从入口到达；每条关系起点、终点和类型有效 | 断开节点、缺失端点和非回路闭环逐项提示，不自动补线或改写关系类型 |
| PRR-COM-05 | 判断分支、流程内部回路、并行开始和并行汇合符合现有结构规则 | 一条无条件顺序关系可以作为判断默认继续路径；判断分支和回路必须有条件；并行开始至少两条不同目标路线，并行汇合至少两个有效来源 |
| PRR-COM-06 | 流程事实需要归口部门确认，审核依据需要在 3000 由真实身份审核员填写 | 固定返回 `confirmation_required`，不得自动返回 `pass`，不写入 JSON，不改变下载状态 |
| PRR-COM-07 | 每条显式回路都有从本层检查节点通向本层循环外的退出路线 | 嵌套循环逐层检查；内层退出可以进入外层循环，最外层必须退出到循环外后续行为 |
| PRR-COM-08 | 每个并行开始的全部路线共同到达最近的并行汇合 | 任一路线在共同汇合前形成流程结束位置时，不得按并行通过评审；实际只执行一条结果路线时使用判断分支 |
| PRR-COM-09 | 每个业务行为的“具体做什么”按实际顺序写明具体动作、处理对象和结果 | 未填写、使用“确保……可以完成”“保证……真实性、合理性”等抽象定性表述、没有出现具体业务动作时分别提示并定位`behavior_description`；控制节点不适用 |

## 5. 五类条件规则

### 5.1 跨部门办理

存在固定外部门行为或 `cross_department_handoffs[]` 时启用：

| 规则编号 | 检查内容 |
|---|---|
| PRR-XD-01 | 每个固定跨部门行为只有一条对应交接关系，不再用普通流程关系重复表达同一次交接 |
| PRR-XD-02 | 交接方向、关联本流程行为和承接部门明确；承接部门不能确认时使用“待明确责任部门” |
| PRR-XD-03 | 交接事项或传递数据、触发条件和外部门完成标准明确 |
| PRR-XD-04 | 设置“需要返回”时，返回数据和本流程恢复位置均明确 |
| PRR-XD-05 | 对方流程和对方行为暂缺时只提示进入 3000 后继续治理，不阻止下载 |
| PRR-XD-06 | 双方确认只能在 3000 完成；3001 固定返回 `confirmation_required` |

### 5.2 数据产生与使用

存在 `data_objects[]` 时启用：

| 规则编号 | 检查内容 |
|---|---|
| PRR-DATA-01 | 数据名称、产生行为和使用行为引用有效 |
| PRR-DATA-02 | 数据只能被产生位置之后、沿非回路关系明确可达的行为使用 |
| PRR-DATA-03 | 同一行为自身、明确前序行为和无先后关系的并行兄弟路线不得使用尚未形成的数据 |
| PRR-DATA-04 | 跨部门前置输入从锚点起可用；返回数据从恢复位置起可用 |

没有数据对象时返回 `not_applicable`，并提示不得为满足检查虚构数据。

### 5.3 表单或记录

存在 `forms[]` 时启用：

| 规则编号 | 检查内容 |
|---|---|
| PRR-FORM-01 | 表单名称和现状／拟设计状态明确；关联行为存在时引用有效 |
| PRR-FORM-02 | 每张表单正常情况下只有一个主表；缺少主表、多个主表或未分类结构逐项提示，不自动迁移 |
| PRR-FORM-03 | 多张明细表分别保存；存在多张明细表时，每张明细表具有可区分的标题 |
| PRR-FORM-04 | 每个填写项具有名称、标准类型、字段归属和是否必填信息 |

没有表单或记录时返回 `not_applicable`，并提示不得为满足检查虚构表单。

### 5.4 审批或会签

只有当前 JSON 中存在以下明确结构之一时启用：合法历史 `work_role.role_duty` 为“审核”“批准”或“会签”，或者行为设置了会签目标。不得根据行为名称中的“审批”“审核”等文字自动判定适用。

| 规则编号 | 检查内容 |
|---|---|
| PRR-APP-01 | 处理行为具有明确执行主体和完成标准 |
| PRR-APP-02 | 存在未通过、退回或不同意场景时，触发条件和后续位置明确 |
| PRR-APP-03 | 会签目标部门完整；会签只表示确认知悉，不替代审核或批准 |

当前 JSON 无法证明是否存在审批或会签时，本类规则返回 `not_applicable`，同时在部门核对清单中提醒业务核对人确认场景，不把名称匹配当作证据。

### 5.5 异常、退回或作废

存在 `loop`、明确异常分支或业务人员已经登记的相关结构时启用。第一版不得根据行为名称推测异常或作废场景。

| 规则编号 | 检查内容 |
|---|---|
| PRR-EX-01 | 每条退回关系具有明确触发条件和返回位置 |
| PRR-EX-02 | 异常或作废分支具有触发条件、处理行为和末端完成标准 |
| PRR-EX-03 | 显式回路不参与主线入口、末端数量和数据先后计算 |

## 6. 页面结构和学习评分

“流程评审”首先按以下五方面顺序展示现场走查卡：

1. 流程目的、范围和结束边界；
2. A1业务行为和责任角色；
3. 业务行为逐动作可执行性；
4. 条件分支、退回和跨部门承接；
5. 表单、业务对象和数据输入输出。

五方面是部门现场评审的展示结构，九项通用规则和五类条件规则仍是自动检查真源。页面根据问题定位把规则结果归入对应方面，不复制第二套判断规则。页面自动检查未发现缺项时，每方面仍显示“待部门确认”。第三方面的自动检查只发现说明缺失、明显抽象定性表述和没有具体动作三类问题；每个动作、处理对象和结果是否完整仍由业务部门确认。

第四方面下方固定展示节点组合关系表和九类图形化图例：基础顺序、判断分支、单层循环、会签接并行汇合、并行内判断、并行内循环、嵌套循环、嵌套并行和并行提前中止。图例复用跨职能流程图的泳道、节点、关系线和布局组件，用户可以平移、缩放、适应画布、重置视图和展开查看。图例不在其他编制标签显示，不增加业务编辑控件，不写入 JSON。

3001 保留一个编辑器，编制导航调整为：

1. 基本情况：基本信息、目的与范围、术语定义；
2. 实际步骤：业务行为、执行主体、完成标准和流程关系；
3. 输出与承接：数据、表单和跨部门承接；
4. 核对下载：流程标准评审准备、导出检查、学习评分和下载。

页面在四个阶段上方显示“流程骨架、完成与异常、数据与表单、跨部门核对”四轮操作说明。轮次仅用于指导操作，不保存完成状态。每轮仍由用户主动下载 JSON；再次工作时手工导入。

现有结构化学习评分折叠为次要学习提示。评分不参与 `process-review-readiness-v4` 状态汇总，不作为下载、导入、审核或发布门槛。

## 7. 实施和停止条件

2026年8月13日，用户明确要求为跨部门现场评审启用3001前端检查。2026年8月15日，用户将现场走查重点增加为五方面，并明确要求业务行为可执行。上述指示替代本文件原“G-01至G-06通过后才修改3001页面”的时间门槛，但不解除3000正式评价、批量导入、数据流和生命周期治理的开发门槛。

本次前端实现复用现有技术结构、并行、可达性、数据时序和字段定位能力。`businessWarnings()`保持普通导出范围；业务行为逐动作可执行性、循环逐层退出、共同并行汇合和并行提前结束只在“流程评审”生成专用提示。页面不增加接口、数据库、浏览器持久化、JSON字段或3000通信。

出现以下任一情况时停止实施并重新评审：

- 现有 v4 不能承载已经确认的流程事实；
- 规则要求增加审核状态、评审意见、正式证据或部门确认字段；
- 检查需要连接 3000、账号系统或数据库；
- 新规则与现有选择器、导出检查或结构评分出现两套不同判断；
- 历史 JSON 内容、未知值或稳定引用不能无损保留。

## 8. 完成标准

本规则进入3001实现后，必须同时满足：

- 所有规则具有稳定编号、代表性样例和自动化断言；
- 三种操作状态与技术阻断、业务提示和人工确认边界一致；
- 每个可修复问题能够定位到实际输入控件；
- 检查、重新检查和问题定位不修改流程内容；
- v1、v2、v3和旧v4导入后无损导出当前v4；
- 现有3001自动化测试和真实浏览器回归全部通过；
- 三类真实流程完成部门核对和3000正式治理闭环后，才允许全面推广EA/BPM治理评价。
