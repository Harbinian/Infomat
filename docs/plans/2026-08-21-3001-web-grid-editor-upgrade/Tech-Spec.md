# 技术方案：3001双模式网页表格编辑器与字段复用减负

## 一、事实来源与状态边界

当前候选的`process-governance-v7` JSON是步骤5唯一业务数据。业务式编辑通过页面编辑会话提交修改；表格编辑从当前JSON生成完整文档工作副本。对象字段批量选择、编辑定位、表格筛选和问题浏览状态都只属于当前页面上下文，不进入业务JSON或下载文件。工作副本和页面上下文均不写入浏览器存储；刷新、新建、清空、重新导入或服务重启后按各自规则清除。

```text
当前v7 JSON
  ├─ 业务式编辑会话
  │    ├─ 对象和对象字段唯一正式写入口
  │    └─ FormFieldReuse批量规划器：在文档克隆上规划并一次提交
  └─ ProcessV7GridAdapter.read
       → WebGridCore工作副本
       → NativeWebGrid单面板与常驻原生输入控件
       → 引用检查与技术完整性检查
       → POST /api/validate
       → 一次替换当前v7 JSON
       → 一条整体撤销记录

页面内存中的界面状态
  ├─ AuthoringSelectionContext：候选、模式、工作区、表格、稳定引用和焦点
  └─ GovernanceReviewQueue：检查快照、过期状态和浏览顺序
```

## 二、模块边界

### 1. WebGridCore

`public/web-grid-core.js`只管理表格定义、工作副本、稳定行标识、显式删除、顺序、差异、来源版本检查、应用和放弃。它不认识v7字段，不调用业务接口。

通过JSDoc固定三个复用接口：

- `GridTableDefinition`：表格标识、列、编辑器、引用选择器和父级过滤规则。
- `GridIssue`：表格、行、列、严重程度、错误码、用户提示和JSON定位路径。
- `GridCommitDriver`：取得当前文档及版本指纹、校验完整候选文档、提交完整候选文档。

### 2. ProcessV7GridAdapter

`public/process-v7-grid-adapter.js`负责v7 JSON与九类表之间的双向映射、稳定技术标识、枚举、父子引用、跨上级移动保护、显式删除保护、对象字段派生列、候选文档和差异摘要。

适配层保留不属于表格范围的字段，包括生命周期、迁移归档、流程基本信息、业务行为、流程关系和术语。它不推断主数据、权威来源或业务事实。

适配层按以下规则建立新增工作行：

- 数据行为关系和表单行为关系的`behavior_ref`为空。
- 字段来源的`source_type`和`source_role`为空，`source_data_ref`为`null`。
- 表单的`form_design_state`为`unspecified`。
- 主表或明细区域的`area_type`为空。
- 表单字段的`required`为空，只允许存在于工作副本；应用时必须明确为布尔值。

表单字段的`data_field_ref`选择器跨全部数据对象分组显示。用户选择有效对象字段后，`business_data_ref`和`item_type`成为派生只读列。直接输入、粘贴、批量输入和复制行都不能绕过只读约束。用户清除字段引用后，适配层保留已填写的`item_name`、`item_type`、`value_usage_mode`和`value_origin_mode`，并把对象归属留在可明确调整的兼容状态。

用户把字段来源切换为“本流程数据”后，页面仍要求用户明确选择数据对象。用户切换为“外部系统”后，页面只清理不适用的本流程数据引用，不生成系统名称、数据名称或来源作用。数据操作可以继续使用v7已有的`pending_confirmation`；表单操作可以保持空数组，等待用户明确选择。

适配器生成候选前还执行来源类型的条件必填和互斥清理：`process_data`必须包含`source_data_ref`和`source_role`，同时清空外部系统名称及来源数据名称；`external_system`必须包含`source_system_name`、`source_data_name`和`source_role`，同时把`source_data_ref`置为`null`。缺失项分别返回可定位错误，失败候选不得进入当前JSON。

### 3. 页面提交驱动

3001提交驱动取得当前JSON及指纹，调用现有技术引用检查和`/api/validate`，再通过现有撤销管理器一次替换完整候选文档。表格打开后如果当前JSON指纹变化，应用返回来源冲突，要求重新生成工作副本。

异步表格应用在校验前记录候选标识、当前JSON指纹、表格会话对象、会话修订号和来源键。应用期间锁定重复提交、放弃、候选／步骤／视图切换及统一三分支按钮；校验返回后再次逐项核对，任一项变化时拒绝旧结果并保留最新工作副本。批量字段应用使用独立会话令牌，并同时比较会话指纹、批量补丁指纹和当前JSON指纹，避免校验返回后把旧选择写入新会话。

未来3000可以实现独立提交驱动，携带`expected_revision`保存MySQL草稿，并继续执行权限、并发和审计检查。本次不实现该驱动，也不让3000依赖3001服务。

### 4. NativeWebGrid

`public/native-web-grid.js`只处理输入法组合事件、剪贴板二维数据、粘贴值转换、区域边界和复制文本。页面直接渲染常驻的原生`input`、`textarea`和`select`，并通过事件委托更新`WebGridCore`工作副本。普通输入不调用整页`render()`，选择上级记录只刷新下级表格。

### 5. FormFieldReuse纯逻辑

`public/form-field-reuse.js`不持有页面状态，并采用浏览器与Node双环境导出方式。它提供以下接口：

- `indexDataFields(document)`：按稳定`field_ref`建立对象字段索引，并按数据对象生成分组目录。
- `buildReferencePatch(item, fieldRef, index)`：只生成`data_field_ref`、`business_data_ref`、`item_type`和必要的`item_name`补丁。只有`item_name`为空时，补丁才使用对象字段名称。
- `planBatchReference(document, input, refFactory)`：在文档克隆上规划整批新增，不修改传入文档。输入包含当前候选标识、打开草稿时的文档指纹、`formRef`、去重后的`fieldRefs[]`、每个字段明确选择的`required`和目标区域信息。

规划成功时，函数返回完整候选文档、新增摘要和成功状态；规划失败时，函数返回可定位错误，不返回部分写入后的文档。该模块不得修改既有表单显示名称、填写说明、必填属性、来源关系、`value_usage_mode`或`value_origin_mode`，也不得按引用次数推断字段值的使用方式和取值方式。

### 6. 页面编排与批量对象字段复用

`public/index.html`负责业务式编辑和表格编辑的页面编排。“数据对象与行为关系”是业务式数据对象和对象字段的唯一正式写入口。表单、主表、明细表和表单字段只显示引用摘要；“修改对象定义”使用`data_ref`和`field_ref`跳转并聚焦正式编辑控件。

业务式“引用对象字段”使用批量弹窗。页面按数据对象分组显示字段，显示字段类型、引用次数和已有位置，并用集合防止同一批次重复选择同一个`field_ref`。页面不预选目标区域或必填属性。用户选择新建明细表时必须填写名称；选择归属待确认区域时不生成未经确认的明细名称。每个字段的`required`必须由用户明确选择；“统一设为必填／统一设为非必填”只批量填写当前页面选项，用户可以逐项覆盖。

批量应用按以下顺序执行：

1. 页面根据稳定引用重新解析表单、对象字段和目标区域，不使用打开弹窗时的数组下标。
2. 页面校验表单、全部字段和目标区域仍存在且归属一致，并确认每个字段已有布尔型`required`。
3. 规划器在克隆文档上生成全部独立`item_ref`；新建明细表时，一批只创建一个区域。
4. 规划器写入确定性派生字段。新字段的`value_usage_mode`和`value_origin_mode`使用结构已有的`pending_confirmation`，表示尚待业务人员确认，不表示系统推断了取值规则。
5. 页面冻结批量字段、目标区域、必填设置、批量快捷按钮和确认／取消操作，再对完整候选执行现有v7结构和引用完整性校验。
6. 校验返回后，页面再次比较候选标识、批量会话令牌、会话指纹、批量补丁指纹和当前JSON指纹；任一项变化时拒绝旧结果。
7. 全部检查通过后，页面通过现有整文档命令提交一次；成功后清理批量草稿并定位第一条新增字段。成功、失败或超时后均解除操作锁。

任何一步失败时，当前JSON、目标区域和撤销栈均不改变。页面保留用户已经选择的字段、目标区域和必填设置，并指出失效字段、失效区域或版本冲突。应用期间确认按钮处于禁用状态，避免双击产生重复批次。

表格编辑执行相同的确定性补齐规则时，只更新`WebGridCore`工作副本。`ProcessV7GridAdapter`在生成候选文档时只为本次新建且名称仍为空的表单字段补齐名称；既有空名称记录继续报告必填错误，不进行静默修复。`WebGridCore`和`NativeWebGrid`不认识对象字段、表单字段或默认值规则。

### 7. AuthoringSelectionContext页面上下文

页面按候选隔离以下状态：当前编辑方式、数据或表单工作区、当前表格、`dataRef`、`dataFieldRef`、`formRef`、`areaRef`、`formItemRef`，以及各表筛选、排序、选中行、滚动位置和焦点列。

上下文只保存稳定引用，不使用名称或数组位置。父级被删除后，页面清除子级选择；引用失效后，页面回到最近仍存在的父级或明确空状态，不自动选择另一条记录。新建、清空和重新导入会重置上下文。上下文不得写入业务JSON、下载文件、`localStorage`、`sessionStorage`、IndexedDB、Cookie或服务端。

### 8. GovernanceReviewQueue连续整改队列

问题队列复用步骤1至5现有问题来源，不增加第二套校验规则。步骤6和步骤7继续只读，修改操作返回步骤1至5的正式入口。每个问题的唯一标识由规则编码、目标稳定引用和必要的字段或路径组成，不使用问题文案或数组序号。技术阻断项优先，其余问题按治理步骤和现有稳定顺序排列；相同文案发生在不同对象上时保留为不同问题。

用户首次执行“检查本轮”后，页面保存当前检查快照。用户继续编辑时，快照继续显示但标记为“结果已过期，重新检查后才能判断是否仍成立”。页面不在每次输入时自动重算或跳转。“重新检查并定位下一项”重新计算全部问题；只有重新计算后消失的问题才算解决。“暂时跳过”只改变当前页面的浏览顺序，不写入JSON，也不表示接受或解决问题。

表格工作副本存在未应用修改时，全局队列仍以已应用JSON为准，并显示“表格修改尚未应用”。表格工作副本错误继续显示在表格页签和对应单元格中。

### 9. 单面板表格编排

页面任一时刻只渲染当前页签的一张主表格。数据工作区和表单工作区分别显示四个、五个表格页签；每个页签显示当前范围行数、未应用修改、错误数量和缺少上级选择状态。当前表格上方固定显示由稳定引用解析的父级路径。

新增按钮从表定义的业务名称生成，页面只显示当前表格的一个新增按钮。子表没有有效父级或父级已在工作副本中标记删除时，页面禁用新增，不选择第一条父级记录。`addGridRow()`新增记录后只清除会隐藏新行的本表筛选条件，再聚焦新行第一个未确认或必填控件。切换表格不应用或丢弃工作副本，并分别保留筛选、排序、选中行和滚动位置。隐藏表的错误页签显示数量；问题定位按稳定引用切换到对应工作区、表格、父级、行和单元格。

### 10. 双模式稳定引用定位

业务式实体和表格式行按以下稳定引用对应：

| 业务式实体 | 表格式目标 | 稳定引用 |
|---|---|---|
| 数据对象 | 数据对象表 | `data_ref` |
| 对象字段 | 对象字段表 | `field_ref` |
| 数据行为关系 | 数据行为关系表 | `link_ref` |
| 数据来源关系 | 跨流程数据来源表 | `source_ref` |
| 表单 | 表单或记录表 | `form_ref` |
| 表单行为关系 | 表单行为关系表 | `link_ref` |
| 主表或明细表 | 主表与明细表 | `area_ref` |
| 表单字段 | 表单字段表 | `item_ref` |
| 字段来源 | 字段取值来源表 | `source_link_ref` |

从业务式切换到表格式时，页面根据稳定引用选择工作区、表格、父级和行。从表格式切换到业务式时，未应用的新行不能直接显示；存在未应用修改时，页面先显示统一三分支弹窗。应用成功后，页面定位到新实体；放弃后，页面清除临时引用并回到仍有效的父级。中文输入法组合输入尚未结束时，页面不执行模式或表格切换。

### 11. 模态焦点管理

页面从所有可见模态框和治理抽屉中，按计算后的`z-index`及DOM顺序确定最上层`role="dialog"`。全局键盘处理先处理`Tab`：正向和反向焦点只在顶层对话框内可见且未禁用的按钮、输入框、下拉框、文本框、链接和可聚焦元素之间循环。顶层没有可用控件时，页面阻止浏览器默认跳转，为对话框容器设置程序化焦点并停留其中。

弹窗状态保存发起操作所对应的候选、稳定对象引用、表格行与列或批量入口模式。关闭、取消、放弃、继续编辑或确认后发生重绘时，页面从新DOM重新查询目标并恢复焦点，不直接复用重绘前的元素对象。多层弹窗只允许最上层接收键盘，底层批量字段弹窗和背景工作区不得获得焦点。

## 三、原生表格边界与Tabulator退役决定

- 2026-08-24确认原Tabulator实现不适合3001。Tabulator的临时单元格编辑器与3001按上级记录刷新下级表格的机制冲突；鼠标按下后建立的编辑器会在行选择触发重绘时被销毁，表现为用户只有持续按住鼠标才能输入。临时编辑器的建立和销毁也无法稳定承接Windows中文输入法事件顺序。
- 3001已删除`tabulator-tables`依赖、JS/CSS静态路由、旧编辑器封装和对应许可文件，不保留备用入口。
- 单击输入控件同时确定当前行和当前区域起点；普通输入只修改工作副本。按住Shift再单击可以扩展区域，粘贴多行多列时一次更新工作副本。
- 输入法切换按键不拦截。组合输入期间和组合结束后紧随的选词回车保持当前单元格；随后明确按下的普通回车进入下一行同列，没有下一行时保持当前焦点。
- 技术标识默认隐藏或只读；发生重名时，引用选择器显示技术标识用于区分。
- 显示排序不修改`_order`；只有上移、下移等显式顺序动作修改业务数组顺序。

交互依据包括飞书官方帮助中“选择单元格”与“双击进入编辑状态”的区分，以及本仓库`apps/information-collection-service/public/respondent/app.js`中4001明细表常驻原生输入控件的实现。飞书参考：[设置单元格局部内容样式](https://www.feishu.cn/hc/zh-CN/articles/947298221311-%E4%B8%BA%E5%8D%95%E5%85%83%E6%A0%BC%E5%86%85%E7%9A%84%E5%B1%80%E9%83%A8%E5%86%85%E5%AE%B9%E8%AE%BE%E7%BD%AE%E6%A0%B7%E5%BC%8F/)、[插入或删除行列和单元格](https://www.feishu.cn/hc/zh-CN/articles/360049067459-%E5%9C%A8%E8%A1%A8%E6%A0%BC%E4%B8%AD%E6%8F%92%E5%85%A5%E6%88%96%E5%88%A0%E9%99%A4%E8%A1%8C-%E5%88%97%E5%92%8C%E5%8D%95%E5%85%83%E6%A0%BC)。3001没有照搬双击模式，而是采用常驻输入控件，因为其业务表格更接近表单填报，不是通用电子表格。

## 四、校验与失败恢复

表格工作副本的应用顺序固定为：

1. 捕获候选标识、当前JSON指纹、表格会话对象、会话修订号和来源键，并确认来源指纹仍与表格打开时一致。
2. 锁定重复应用、放弃及会隐藏工作副本的切换操作。
3. 检查必填值、枚举、技术标识、父子关系、字段归属、关系冲突和删除引用。
4. 生成完整v7候选文档并执行现有技术完整性检查。
5. 调用`POST /api/validate`执行完整结构校验；前端等待上限为20秒，超时后通过`AbortController`中止本次等待。
6. 校验返回后重新比较候选、JSON指纹、会话对象、修订号和来源键；只有全部仍一致时才提交。
7. 一次替换当前JSON并写入一条撤销记录；无论成功、失败或超时，最后都解除操作锁。

任一步失败或超时时，当前JSON、撤销栈和源文件保持不变；表格工作副本、批量字段选择和问题定位继续保留。迟到响应不得在超时或上下文变化后写入。用户可以修正后再次应用，或明确放弃。

业务式新增数据行为关系、表单行为关系和字段来源同样先建立统一编辑会话草稿，不立即修改当前JSON。用户没有明确选择业务行为、来源类型、来源对象或来源作用时，应用必须失败并保留输入。取消、切换或放弃草稿时，当前JSON保持不变。

## 五、旧数据影响

本次不改变v7结构、结构摘要、发布状态、HTTP API或导入导出字段，因此不新增旧数据迁移脚本。`item_name`、`item_type`、`business_data_ref`、`data_field_ref`、布尔型`required`、`value_usage_mode`、`value_origin_mode`和`source_links`继续使用现有字段。

v1至v6和历史结构化文件仍按既有迁移模块在页面内存中转换为v7，再由适配层读取。旧v7中只有对象归属而没有字段引用的表单字段、自定义表单显示名称、已确认的使用方式和取值方式、已有字段来源、失效字段以及对象归属错配均原样保留。页面可以显示错误和兼容入口，但不得在导入、首次渲染或模式切换时静默修复。表格应用不得重写生命周期、迁移归档或不在九类表范围内的内容。
