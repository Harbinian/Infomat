# MDM 治理落地计划

> 日期：2026-06-29  
> 适用阶段：流程地图与数据地图的梳理与沉淀  
> 输入口径：`docs/norms` 是流程输入基线，不是天然正确的最终结论。  
> 平台口径：MDM 承接治理闭环，不反向替代流程输入基线。

## 1. 外部文章要点转化

知乎回答链接：<https://www.zhihu.com/question/487566537/answer/2018005987362120819?share_code=1ophQPZ7KR2tx&utm_psn=2054845726425985083>

文章主题是项目管理工具，不是 MDM 专文。可转化到本项目的要点如下：

1. WBS 的价值是把任务拆到“谁做、做什么、何时交付、交付物是什么”。
2. 甘特图不只是排计划，更要持续看计划和实际的偏差。
3. RACI 要让每件事只有一个最终拍板人，同时区分执行、协同和知情。
4. 风险分解要在启动时做，提前列出人、事、系统、时间和外部依赖风险。
5. 四象限和 PDCA 适合做每周节奏：先处理关键且紧急的问题，再持续校正。
6. 问题清单、变更管理、周报和复盘，是让项目不靠口头推动的闭环工具。

对 MDM 治理的落地含义：不要先追求“大平台”，先把输入、责任、问题、变更、发布和复盘固定成可执行工作流。

## 2. 治理判断

MDM 在本阶段不是“替业务定义规则”的系统，而是治理工作台：

- 记录流程输入基线中的待确认问题。
- 组织字段台账、数据对象、黄金源、维护部门、审批部门和消费系统的确认。
- 保存证据、确认意见、变更记录和关闭原因。
- 推动问题回到责任人，而不是让问题沉在文档或会议纪要里。
- 只有回源核验和人工确认完成后，才进入已确认流程映射、PMO 展示或后续接口设计。

因此，MDM 治理工作要围绕“输入基线问题池 + 字段台账 + 黄金源确认 + 数据质量闭环”建设，不以模块堆叠作为第一目标。

## 3. 落地路径

| 阶段 | 时间盒 | 主要动作 | 产出 |
|---|---:|---|---|
| 0. 术语收口 | 已完成 | 统一“流程输入基线”“输入基线问题复核”“待确认主数据对象”等口径；建立禁词守卫 | 术语守卫、脚本和文档命名一致 |
| 1. 输入基线盘点 | 1 周 | 按部门检查 L3/A1、证据、输入输出、审批链、数据对象 | 输入基线问题池、责任人初分配 |
| 2. 字段台账成型 | 2 周 | 从流程和 A1 抽字段、对象、维护动作、消费场景 | 字段台账 V0.1、待确认主数据对象清单 |
| 3. 黄金源确认 | 2 周 | 按字段确认黄金源、维护部门、审批部门、只读消费系统 | 黄金源矩阵、确认记录、冲突项 |
| 4. 质量闭环 | 持续 | 对重复、缺失、冲突、过期、跨系统不一致建立问题单 | 数据质量看板、整改记录、周报 |
| 5. 发布与复盘 | 每两周 | 已确认项进入已确认流程映射和 PMO 快照，未确认项继续留在问题池 | 发布记录、复盘结论、下轮 WBS |

## 4. WBS 工作包

| 工作包 | 可执行任务 | 完成标准 |
|---|---|---|
| 输入基线问题池 | 对每个部门生成问题清单，问题必须带来源位置、类型、建议动作和确认对象 | 每条问题能定位到源文件或映射行 |
| 责任矩阵 | 为问题、字段、对象分别标记执行人、最终确认人、协同方和知情方 | 无“多人都负责但无人拍板”的项 |
| 字段台账 | 以 L3/A1 为入口登记字段、对象、系统消费和维护动作 | 字段能追溯到流程和业务动作 |
| 黄金源矩阵 | 按字段确认黄金源、维护部门、审批部门和消费系统 | 每个字段至少有一个明确处理状态 |
| 变更记录 | 已确认项变更必须记录原因、影响范围、审批人和发布时间 | 能解释为什么改、谁确认、改到哪里 |
| 周报与复盘 | 每周输出进度、风险、阻塞、下周动作；每两周复盘 | 管理层看到同一版状态 |

## 5. RACI 口径

| 对象 | R 执行 | A 最终确认 | C 协同 | I 知情 |
|---|---|---|---|---|
| 流程输入基线问题 | 业务对接人 / 数据质量员 | 部门负责人或授权确认人 | MDM 工作组、PMO | 项目管理工作室 |
| 字段台账 | MDM 工作组 | 字段维护部门负责人 | 业务部门、系统实施方 | 数据质量工作组 |
| 黄金源 | 字段维护部门 | MDM 工作组牵头确认 | 消费系统负责人、业务部门 | 项目决策组 |
| 已确认流程映射发布 | 流程治理负责人 | 项目管理工作室 | 相关部门、PMO | 全项目组 |
| 数据质量问题关闭 | 数据质量员 | 数据质量工作组负责人 | 业务责任人、系统负责人 | MDM 工作组 |

## 6. 度量指标

| 指标 | 口径 |
|---|---|
| 输入基线覆盖率 | 已盘点部门数 / 应盘点部门数 |
| 问题闭环率 | 已关闭问题数 / 本周期新增问题数 |
| 超期问题数 | 超过确认时限仍无处理结论的问题 |
| 字段台账完整率 | 已登记维护部门、审批部门、消费系统的字段占比 |
| 黄金源确认率 | 已确认黄金源字段数 / 字段总数 |
| 证据完整率 | 有来源位置、原文摘录、确认记录的问题占比 |
| 返工率 | 发布后因证据或责任不清回退的问题占比 |

## 7. 近期执行清单

1. 将 `输入基线问题待办.md` 和 MDM `input-baseline-review` MySQL 表作为同一工作流的人工处理面板与结构化存储。
2. 用 `npm run test:process-input-baseline-review` 固定输入基线问题识别、待办生成和 MySQL 复核链路。
3. 在 MDM 工作台中把“我现在该做什么”优先指向：待确认问题、字段台账补全、黄金源确认、数据质量整改。
4. 每周输出一版 MDM 治理周报：新增问题、关闭问题、超期问题、黄金源确认进度、需要决策的问题。
5. 每两周做一次发布复盘：哪些进入已确认流程映射，哪些继续留在问题池，哪些需要回到部门补证。
