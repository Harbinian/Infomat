## 2. 业务目标

业务人员在一个流程内确认数据对象后，3001根据现有业务行为、流程关系、表单字段、触发条件、前提条件、完成标准和异常说明，自动整理数据行为关系和生命周期建议。业务人员按数据对象集中核对结果，不需要为每一个业务行为重复定义数据。

v7仍只形成单流程、未审核的结构化事实。3001负责结构检查、确定性分析和编制提示；业务部门负责确认本流程事实；3000负责生命周期规则、审核证据、跨流程一致性、统一对象认定和版本发布。3001的分析结果不得写成正式治理结论。

### 2.1 数据对象与主数据的定义

**数据对象**是流程中具有完整业务含义、能够与字段和具体实例区分，并会被创建、更新、使用、传递或保管的一组业务信息。供应商、采购订单、发票、付款申请和会计凭证都可以作为数据对象；供应商名称、统一社会信用代码和银行账号属于字段；某一家具体供应商属于数据对象的实例。

**主数据**是经过有权治理主体认定，用于稳定识别企业核心业务实体，并需要在多个业务行为、流程、部门或系统之间保持统一的数据对象。主数据通常具有稳定身份、可重复引用、变化相对缓慢、错误会影响多个业务环节等特点，并需要明确责任部门、权威来源、关键识别字段、质量规则、变更规则和生命周期规则。

两者关系固定如下：

- 数据对象是流程编制和数据分析的基础单位；主数据是对部分数据对象作出的治理分类和管理结论。
- 所有主数据都是数据对象，但不是所有数据对象都是主数据。
- 3001只能记录“流程中出现了什么数据对象、怎样被使用以及发生了什么生命周期事实”，不能直接把数据对象标记为已确认主数据。
- 数据对象是否属于主数据，必须由业务责任部门补充事实，MDM工作组结合跨流程复用、稳定身份、责任边界和权威来源完成认定。
- 数据重要、存在唯一编号、出现在多个系统或跨部门传递，都只能作为识别线索，不能单独证明它是主数据。

表单通常不是主数据，必须区分三层：

- 空白表单模板或表单定义描述“按什么格式收集信息”，通常属于受控模板、制度附件或参考数据；只有经过专门治理认定时，才可能作为需要统一管理的模板类数据对象。
- 填写完成的表单描述“一次具体业务发生了什么”，例如某一张付款申请单，属于交易记录或业务证据，不是主数据。
- 表单字段可以引用主数据，例如付款申请单中的供应商、申请部门和经办人员；这些字段引用主数据，不代表整张付款申请单成为主数据。

如果一张“供应商新增申请表”用于申请建立供应商，申请表本身仍是业务记录；审核通过后形成的统一供应商记录，才可能成为经认定的主数据。

### 2.2 跨部门判断原则

跨部门场景需要同时回答“是否为同一个对象”和“各部门分别确认什么”，不能因为名称相同就自动合并，也不能让每个部门分别维护一份互不关联的数据。

1. 各部门先在本部门流程中如实记录数据对象、业务行为、字段和来源。
2. 3001只保留当前单流程事实，可以提示存在跨部门使用或下游流程线索，但不绑定另一份流程文件。
3. 3000根据稳定编码、业务定义、关键识别字段、责任边界和使用场景形成待定匹配建议。
4. 各参与部门分别确认本部门产生、维护、核对或使用的事实；任何一个部门都不能代替其他部门确认。
5. MDM工作组在部门事实一致后认定是否为同一个统一数据对象、是否属于主数据，以及哪些字段由哪个权威来源提供。
6. 身份、字段或责任存在分歧时保持“待定”，不得按名称、系统表或模型分数自动合并。

跨部门复用通常会提高一个数据对象成为主数据的可能性，但不是充分条件。发票、付款申请等交易记录会跨部门流转，也不能因此认定为主数据。

### 2.3 供应商付款示例

以下用供应商付款这一实际业务场景说明判断方法。部门动作是示例口径，正式责任仍以公司制度、流程和责任部门确认结果为准。

| 业务阶段 | 部门动作 | 主要数据对象 | 主数据判断 |
|---|---|---|---|
| 采购准备 | 物资保障部选择供应商并形成采购订单 | 供应商、采购订单 | 供应商具有跨采购、付款和后续结算复用的稳定身份，属于待认定主数据；采购订单记录一次采购交易，不是主数据 |
| 付款申请 | 物资保障部提交付款申请、合同或验收依据和发票 | 付款申请、合同、验收记录、发票、供应商 | 付款申请、合同、验收记录和发票是本次业务记录；跨部门传给财务部也不会变成主数据 |
| 财务审核 | 财务部核对收款方、统一社会信用代码、银行账户、发票和付款条件 | 供应商、供应商银行账户、发票、付款申请 | 财务部使用并核对供应商身份。银行账户可以是供应商主数据的受控组成，也可以是独立敏感数据对象，须由MDM工作组结合责任和变更规则认定 |
| 记账与支付 | 财务部形成会计凭证并执行受控付款 | 会计凭证、支付记录、供应商 | 会计凭证和支付记录描述一次财务事件，不是主数据；它们引用供应商，不应另建一个“财务供应商”副本 |

在该场景中，物资保障部流程和财务部流程可能都出现名为“供应商”的数据对象。3001分别记录两个流程中的使用事实，不能自动宣布它们是同一个主数据。进入3000后，系统可以根据供应商编码、统一社会信用代码、法定名称、责任边界和使用场景形成待定匹配建议；物资保障部确认采购侧事实，财务部确认付款和结算侧事实，MDM工作组再认定是否属于同一个统一供应商主数据及各字段的权威来源。

如果名称相同但统一社会信用代码不同，必须视为不同对象或保持待定；如果统一社会信用代码相同但银行账户不同，需要先判断是正常的多账户、账户变更还是错误记录。系统不得直接合并或覆盖。主数据变更生效后，历史采购订单、发票和会计凭证仍保留当时使用的数据快照，不反向改写已经发生的交易记录。

## 3. 已冻结的范围

### 3.1 继续保留的边界

- 3001保持无状态：不增加数据库、账号草稿、自动保存、浏览器持久化或服务端业务会话。
- 用户主动下载JSON仍是唯一持久化动作；刷新、关闭页面或服务重启后草稿清空。
- 一份JSON只记录一个流程，不绑定另一份JSON、外部文件或3000中的流程版本。
- 3001不调用3000、AI模型或网络分析服务；分析器使用本地确定性规则。
- v7不保存真实业务数据值、真实业务日期、计时器运行结果、正式证据附件或生产处置结果。
- v7不执行停用、归档、销毁或匿名化等生产业务动作。
- v7不认定正式主数据，也不管理数据访问权限生命周期。

### 3.2 数据行为与生命周期分层

`data_objects[].behavior_links[]`继续作为数据对象与业务行为关系的唯一活动事实位置，只表达：

- `create`：该行为首次形成当前数据对象或当前版本；
- `update`：该行为修改既有数据对象；
- `use`：该行为读取、核对、判断或引用数据对象但不改变它；
- `pending_confirmation`：现有材料不能确定以上三种关系。

传输、接收、复制、同步、导入和导出属于数据流，不单独作为生命周期动作。只有这些动作实际创建或更新了数据对象时，才同时形成`create`或`update`关系。

生命周期事件独立记录下列动作：

| 稳定枚举 | 用户用语 | 固定含义 |
|---|---|---|
| `activate` | 生效 | 数据对象首次从未生效进入有效状态 |
| `deactivate` | 停用 | 暂停业务使用，后续允许重新启用 |
| `reactivate` | 重新启用 | 仅把已停用对象恢复为有效，不等同首次生效 |
| `void` | 作废 | 因错误或受控决定取消其业务效力，不允许直接重新启用 |
| `expire` | 失效 | 因期限届满或条件满足而结束业务效力，不等同作废 |
| `archive` | 归档 | 从在用保管转为归档保管，不改变业务效力结论 |
| `restore_active_custody` | 恢复在用保管 | 从归档保管恢复为在用保管，不等同重新启用 |
| `destroy` | 销毁 | 受控结束载体保管，属于不可逆高风险动作 |
| `irreversible_anonymize` | 不可逆匿名化 | 永久消除可识别性，不等同删除或销毁 |

系统删除、数据库物理删除和页面删除不是业务生命周期动作，不得映射为`destroy`或`void`。

### 3.3 三个状态维度

每个数据对象记录入口状态；每条分支、并行路径或循环路径记录自己的出口状态。v7不另建一套可自由绘制的状态机，路径仍由现有`flow_relations[]`决定。

| 维度 | 状态 |
|---|---|
| 业务效力 | 未生效、有效、停用、作废、失效 |
| 保管状态 | 在用保管、归档、销毁 |
| 可识别性 | 可识别、不可逆匿名化 |

可识别性维度只在当前对象确实适用时启用；不适用和待确认必须显式区分，不能要求所有数据对象填写匿名化状态。

### 3.4 生命周期事件最小内容

每个生命周期事件至少记录：

- 关联的数据对象和所在路径；
- 生命周期动作；
- 触发方式和触发条件；
- 动作完成后的三个状态维度结果；
- 作用范围；
- 责任主体；
- 异常或例外处理；
- 形成该事实或建议的来源位置与分析依据；
- 自动生成、待确认、已确认、不适用或已否决状态。

触发方式固定覆盖：业务行为、时间或期限、数据或业务条件、外部流程或通知、待确认。简单组合只支持`AND`和`OR`；复杂条件保留原文并标记待确认，不自动改写成确定规则。

作用范围固定覆盖：单条记录或实例、版本、批次、全部记录、待确认。归档、恢复在用保管和销毁还要记录载体范围：纸质原件、电子原件、业务副本、两者、待确认。位置变化只作为线索，不直接认定权威保管位置。

事件关联业务行为时，责任主体继承该行为的执行主体。仅由期限、条件或外部通知触发的事件不得伪造业务行为或执行人，必须单独记录责任部门和岗位；无法确认时保持待确认。

### 3.5 自动分析与人工核对

用户确认一个数据对象后，系统对该对象关联的全部业务行为、表单字段、流程关系和异常说明执行增量分析。页面同时提供“重新分析当前对象”和“重新分析全部对象”，不要求用户逐行为配置分析规则。

分析规则固定如下：

1. 来源优先级为“用户已确认事实 > 明确结构关系 > 业务行为逐动作说明 > 弱关键词”。
2. 来源唯一、含义明确且不与已确认内容冲突时，系统可以自动写入结构化事实，并记录分析器版本、来源位置和依据。
3. 需要解释文本、存在多个候选或来源冲突时，系统只能生成待确认建议。
4. 已确认内容不得被重新分析静默覆盖。来源变化时，系统把受影响内容标记为“需要重新核对”，并保留原确认值。
5. 用户选择“不适用”或否决建议时，必须选择固定原因并可补充说明；该决定随v7文件下载和重新导入，防止同一输入反复出现相同建议。
6. 相同输入、相同分析器版本和相同规则配置必须产生相同结果。分析器版本与`process-governance-v7`结构版本分开记录。
7. 待确认建议可以随文件下载，但必须同时保存推导依据，且不得伪装成已确认事实。

销毁、不可逆匿名化、全部记录处置、备份或副本处置，以及仅由条件触发的不可逆动作，统一视为高风险事件。系统不得自动确认；业务人员必须在数据对象层面逐项核对。

## 4. 页面调整

v7复用当前七步导航，不增加新的一级步骤，也不恢复旧标签页导航。

- 步骤5“数据与表单”中的数据关系工作区增加“数据流”和“生命周期”两个互斥视图。
- 两个视图共用当前数据对象、对象列表和属性面板，不分别维护两套对象事实。
- 生命周期图沿用现有流程分支、并行和循环关系；文字清单与图形读取同一份结构化内容并保持同步。
- 页面先展示按对象汇总的自动结果，再让用户处理冲突、待确认和高风险项；不得新增“逐行为定义数据”的必填流程。
- 步骤6“跨部门核对”显示下游流程或外部通知线索，但不绑定另一流程文件或版本。
- 步骤7“评审与交接”增加第六个方面“数据生命周期与异常处理”。
- 生命周期缺口属于业务提示，不阻止草稿下载；结构错误、断裂引用和非法状态转换继续阻止下载。
- 结构化学习评分纳入生命周期完整性并提升评分规则版本，但不得因当前流程未覆盖对象的全部生命周期阶段而扣分。

### 4.1 主数据判断提示

步骤5的数据对象属性面板增加“主数据认定提示”。该提示由前端根据当前数据对象的既有事实确定性生成，不调用AI，不新增“已确认主数据”字段，也不把提示结果保存为正式治理结论。

| 提示类型 | 判断线索 | 前端提示 |
|---|---|---|
| 建议后续认定 | 对象描述供应商、人员、组织、物料等稳定业务实体；具有稳定标识；被多个行为、流程或部门重复引用；错误会影响多个业务环节 | “该数据对象可能需要后续主数据认定。请核对业务定义、稳定标识、责任部门和权威来源，并交由MDM工作组认定。” |
| 当前更像业务记录 | 对象描述一次申请、订单、发票、付款、凭证、审批、检验或其他具体业务事件 | “该数据对象当前更像交易记录或业务证据。即使跨部门流转，也不会因此自动成为主数据。” |
| 表单关系说明 | 当前对象是空白模板、填写完成的表单，或主要依据仅是表单名称 | “表单通常不是主数据。请继续判断表单字段是否引用供应商、人员、部门等主数据。” |
| 信息不足 | 缺少业务定义、稳定标识、使用范围、责任部门或来源依据，无法支持以上判断 | “现有信息不足，暂不能判断是否需要主数据认定。请补充对象事实，或将其列入交接待定事项。” |
| 存在冲突 | 名称相同但稳定标识、业务含义、责任边界或使用场景不一致 | “发现可能不是同一对象的证据。请保持待定，不要自动合并。” |

判断顺序固定为：

1. 先判断对象描述的是稳定业务实体，还是一次业务事件或记录。
2. 再检查是否存在稳定标识、跨行为或跨流程复用、明确责任和权威来源线索。
3. 跨部门传递只作为复用线索，不单独提高为主数据结论。
4. 存在反向证据或信息不足时，优先显示“信息不足”或“存在冲突”，不得显示确定性结论。

提示卡只提供“查看判断依据”“补充对象事实”和“列入交接待定事项”三个处理入口，不提供“确认是主数据”或“确认不是主数据”。提示属于业务提示，不阻止阶段草稿或最终待核对文件下载，也不计入结构错误。进入3000后，责任部门和MDM工作组仍须重新核对事实并作出正式认定。

## 5. v7结构与兼容迁移

### 5.1 结构规则门槛

开始编码前，维护人员必须在独立计划包中收口并评审以下文件：

- `PRD.md`：用户路径、对象级核对、高风险人工确认和非目标；
- `Tech-Spec.md`：字段路径、状态转换、分析器边界、前端状态和失败恢复；
- `API-Contract.md`：模板、结构规则、版本历史、校验和健康检查的v7返回约定；
- `Migration-Mapping.md`：v1至v6到v7的字段映射、无法自动确认项和禁止猜测项；
- `Migration-Test-Plan.md`：往返、幂等、失败恢复、分支、并行、循环和大流程样本；
- `docs/contracts/process-governance-v7.schema.json`：v7唯一结构真源。

精确字段名和JSON路径以上述结构规则与接口约定为准。本计划冻结业务语义，不授权在`index.html`中临时增加未入结构规则的隐藏字段。

### 5.2 迁移规则

- v1至v6和历史多候选结构化JSON继续只作为导入输入；新建和下载统一使用v7。
- v7先在`data_objects[].fields[]`定义当前单流程的对象字段，再由表单主表或明细表通过`data_field_ref`引用；表单保留位置、必填、填写说明、顺序和值使用方式。
- 同一对象内同名同类型旧表单字段自动归为同一个对象字段；同名不同类型、多个权威录入位置或没有建立位置的引用保留并提示，不自动选择或覆盖。
- 对象字段引用只减少当前流程内重复维护，不形成企业级字段身份、黄金源结论或运行时自动带入能力。
- 旧文件没有生命周期事实时，迁移只能生成待确认状态或可解释建议，不能默认补成“已完成”“不适用”或“有效”。
- 迁移不修改用户选择的源文件，不记录当前时间，不改变能够保留的稳定引用和首次来源。
- v7文件重新导入时保留业务内容、已确认内容、待确认建议、否决决定、来源依据和分析器版本。
- 重复迁移同一输入必须语义一致，不重复创建事件或建议。
- 任一候选迁移或v7校验失败时，页面不得替换当前草稿、选择、撤销记录、下载基线或源文件。
- v7不提供向v6降级导出。回退服务版本时，用户保留已下载的v7文件，待v7恢复后重新导入。

## 6. 与3000及其他服务的边界

- 3000当前结构规则与3001 v7分开演进。v7发布不代表3000已经能够导入v7。
- 在3000完成独立的v7兼容、服务端重新校验、受控审核和迁移测试前，3001页面必须明确提示“v7文件暂不能直接导入3000”。
- MDM-AI助手继续固定使用其现有v5边界，不纳入本次升级，也不得自动接收v7字段。
- DSH、3003、3004和独立试点启动脚本不随本计划改变。
- 3000后续接收v7时，只接收用户选择并通过服务端校验的固定内容，不依赖3001运行，也不把3001自动建议当作正式审核依据。

## 8. 验收与发布门槛

### 8.1 自动化测试

至少覆盖：

- v1至v6导入v7、v7下载后重新导入、重复迁移和迁移失败恢复；
- 九类生命周期动作的正向、非法前态、非法后态和不适用场景；
- 三个状态维度相互独立，不把归档写成失效，不把销毁写成作废；
- 行为、期限、条件、外部通知和待确认五类触发；
- 简单`AND`、`OR`与复杂条件保留原文；
- 记录、版本、批次、全部记录和待确认作用范围；
- 分支、并行、循环、跨流程线索和版本替代；
- 增量分析、重新分析当前对象、重新分析全部对象和分析器版本变化；
- 明确事实自动写入、歧义进入待确认、冲突不自动裁决；
- 人工确认不被覆盖，来源变化进入重新核对；
- 不适用和否决决定重新导入后仍有效；
- 高风险事件始终需要对象级人工确认；
- 3001不产生数据库、业务日志、浏览器持久化、AI调用或3000运行依赖；
- 当前流程编辑、图形、表单、下载、撤销重做和候选隔离回归通过。

固定回归入口继续包括：

```powershell
node scripts/test-service-contract.js
npm.cmd test
git diff --check
```

新增测试必须纳入`npm.cmd test`，不能依赖测试人员手工逐个运行。

### 8.2 浏览器验收

测试人员使用真实浏览器覆盖1920×1080、1536×864和1280×720内容可视区，并核对：

- 页面无横向溢出、文字遮挡、属性面板重叠和控制台错误；
- 数据流与生命周期视图切换不丢失当前对象和未下载内容；
- 一对多、多对一、并行和循环关系不穿过节点，图与文字清单一致；
- 用户按数据对象完成核对，不需要进入每个业务行为重复定义数据；
- 用户先定义对象字段，再让两张以上表单引用同一字段，不需要重复维护名称、类型和业务定义；
- 首次建立值和后续引用值能够区分；多个建立位置、没有建立位置和同名不同类型只提示，不替用户作业务决定；
- 结构错误阻止下载，生命周期业务提示允许下载并保留提示；
- 刷新、关闭页面和重启服务后不存在业务草稿残留。

### 8.3 真实流程门槛

MDM工作组选择若干个真实、已脱敏且结构不同的流程，至少覆盖普通顺序、分支、并行、循环、跨部门和期限触发场景。真实编制人和真实核对人必须确认：

- 自动分析结果能够定位来源，错误建议可以集中处理；
- 停用、作废、失效、生效、重新启用、归档、恢复在用保管、销毁和不可逆匿名化没有混用；
- 系统没有要求用户逐行为定义数据；
- 待确认内容没有被写成已确认事实；
- 3001结果仍是未审核文件，不会被误认为3000正式治理结论。

### 8.4 发布与回滚

- v7在隔离工作区实施，当前v6服务继续使用已验证提交。
- 不使用功能开关在v6文件中预埋v7字段。
- 全部门槛通过后，负责人记录v6和v7提交、结构摘要、测试结果、浏览器证据和人工核对结论，只重启3001。
- `/api/health`必须返回`ok`、`process-governance-v7`和正确Git提交。
- 严重缺陷回滚到记录的v6提交；不得改写、删除或自动降级用户已经下载的v7文件。

## 9. 暂停条件

出现以下任一情况时，负责人暂停受影响工作：

- 当前在途前端改动尚未形成可复现基线，v7改动会与其混写；
- v7结构规则、迁移映射或状态转换尚未评审；
- 自动分析需要AI、网络、3000或用户逐行为配置才能运行；
- 迁移需要猜测业务效力、保管状态、责任主体或正式来源依据；
- 重新分析会覆盖人工确认，或否决决定无法随文件保留；
- 分支、并行或循环被简化成单一出口状态；
- 方案把停用、作废、失效、归档、销毁、重新启用或恢复在用保管合并；
- 测试发现数据丢失、重复事件、断裂引用、持久化残留或无法恢复；
- 方案要求同步修改3000、MDM-AI助手、DSH、PMO或`docs/norms/`。

阻塞原因消除后，从最近一个已经通过验证的阶段继续，并重新运行全部受影响检查。
