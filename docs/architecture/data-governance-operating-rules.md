# Infomat 数据治理工作规则

> 状态：项目级执行规则  
> 生效日期：2026-08-12  
> 适用范围：PMO、MDM 工作组、业务部门使用 3001 开展流程结构化编制，以及 3000 受控承接后的流程地图与数据地图治理工作。  
> 口径优先级：用户当前确认事实和仓库根规则高于本文；本文高于历史方案、历史提示词和展示副本。

## 一、责任边界原则

> 业务讲事实，MDM 做结构，PMO 管过程，有权主体作决定，3000 保存治理结果。

各主体按以下边界工作：

| 主体 | 负责 | 不负责 |
|---|---|---|
| 业务部门 | 说明并确认流程做法、岗位、表单字段、数据用途、来源、异常处理和本部门责任 | 独立完成主数据分类、全局去重、跨系统权威来源判定或跨部门裁决 |
| MDM 工作组 | 推广 3001、维护结构基准、组织编制和复核、处理结构问题、识别待治理对象和承接关系 | 替业务部门确认事实；仅凭名称、字段或评分合并对象 |
| PMO | 建立行动项，跟踪责任人、期限、阻塞、证据和关闭条件，整理可决策事项 | 替业务部门定义事实；替 MDM 工作组审核结构；决定系统或部门业务口径 |
| MDM-AI助手 | 在五账号试点范围内依据3001当前结构规则追问并整理用户提供的信息，执行独立结构预审，输出未审核JSON和单独的问题处理记录 | 确认流程事实、部门职责、业务做法、主数据分类、权威来源或系统选型；把预审意见写入JSON |
| Codex | 依据当前结构规则执行线下结构预审，问题清单与 JSON 分开保存 | 修改审核状态；替业务部门补造事实；替有权主体作决定 |
| `admin` | 创建账号、分配固定角色、维护身份与访问审计 | 执行填写、确认、业务审核、分歧处理、导入或发布等治理写操作 |
| `department_mdm_reviewer` | 在本部门权限范围内核对 3000 预览、填写审核依据并执行受控导入 | 代替编制人编制；审核其他部门流程 |
| `mdm_lead` | 组织结构核验、处理结构卡口、记录工作组审核结果并按授权发布 | 单方面裁决仍有异议的业务事实 |
| `decision_group` | 对满足升级条件的重大跨部门分歧作出决定 | 接收所有尚未知晓或尚未补证据的普通待定事项 |

编制人与部门 MDM 审核员不得由同一角色代替。责任主体必须来自组织真源、正式角色配置或明确确认记录，不得按姓名、岗位、职务或历史常量推测。

## 二、当前工作主线

当前分析对象是业务流程，不是应用系统，也不是脱离流程的数据库字段。默认分析顺序为：

> 部门与业务能力 → 业务流程（L3）→ 业务行为（A1，含跨部门行为）→ 普通流程关系 → 业务对象和数据 → 表单字段 → 责任、来源和系统使用关系

应用系统只用于记录数据当前在哪里产生、保存、使用或传递。系统现状不能单独证明业务责任、权威来源或未来系统归属。不得评价具体应用系统“最忙”“承载最多”或“最重要”。

用户询问“该用哪个系统”但没有说明业务场景时，先确认需要办理的业务、责任主体、输入输出、现有做法和限制，再讨论系统承载；不得脱离流程直接给出系统选型结论。

普通业务人员先说明实际流程、表单和数据用途。MDM 工作组再识别待治理数据对象、待定关键字段、待定关系和待定匹配建议。不得把“请申报本部门主数据”作为第一轮工作入口。

流程评审必须把“业务行为是否可以直接执行”作为独立重点。每个业务行为的“具体做什么”应按实际顺序写清每个动作、处理对象和结果，使执行人员不需要根据抽象描述猜测操作。不得用“确保……可以完成”“保证……真实性、合理性”等抽象、定性表述代替实际动作；责任主体、业务条件或处理对象变化时，应分开描述相应动作。

## 三、3001 与 3000 的边界

### 1. 3001

3001 是 MDM 工作组推广使用的独立、无状态、单流程编制工具：

1. 一份 JSON 只包含一个流程。当前输出为 `process-governance-v7`，并按当前支持范围兼容导入历史文件。
2. 工作内容只存在于当前页面内存；用户主动下载 JSON 是唯一持久化方式。3001 不增加账号、数据库、服务端草稿、自动保存、浏览器持久化或 3000 运行依赖。
3. 旧交接、工作角色、参考材料和内部流程调用只按兼容规则在页面内存中转换或只读保留。迁移不得修改用户选择的源文件，也不得猜测无法无损转换的业务事实。
4. 3001 不保存审核状态、批准标记或 MDM 审核意见，不通过 API、数据库、队列、回调、共享会话或轮询向 3000 传递业务内容。
5. 纸质表单按整张表单及其主表、明细表如实编制。对象字段引用只表示当前单流程内的设计复用，不形成企业级字段身份、黄金源或跨流程合并结论。
6. 业务提示和结构评分帮助编制人发现缺口，不代表业务正确、部门确认或审核结论。损坏引用等硬性结构错误必须修正后才能下载。
7. 页面必须区分未应用修改、未下载修改和下载基线。任何可见输入不得在切换、重绘、下载、替换或离页时静默丢失或静默应用。
8. 3001 输出是未审核的单流程成果，不是正式流程、正式数据地图或已确认主数据。

3001 的七步或候选四项任务、编辑会话、图形、表格、生命周期、错误码、浏览器矩阵和性能要求由 `apps/structured-output-service/AGENTS.md` 路由到当前 README、PRD、Tech-Spec 和结构规则。本文件只规定治理责任和 3000/3001 边界，不复制控件级 Implementation。

### 2. 结构预审

五账号试点人员可以在MDM-AI助手中对同一份`process-governance-v5` JSON执行独立结构预审；其他受控场景仍可由Codex依据当前结构规则执行线下结构预审。两种方式都只检查硬性结构错误、字段归位和对象拆分，不确认业务事实。助手不得通过受限Patch修改迁移记录。结构预审问题处理记录、业务核对记录、PMO行动项和3000审核依据分别保存，不得写入JSON，也不得相互替代。

### 3. 3000

3000 是流程结果的受控预览、导入、保存、审核和发布边界：

1. 部门 MDM 审核员使用真实身份，在本部门权限范围内执行预览和审核导入。
2. 审核员必须核对预览摘要，填写审核依据，并使用预览返回的内容摘要执行导入。
3. 3000 的现有正式编制路径在服务端重新校验输入，统一保存 v3 完整流程 JSON，并生成治理投影和审核记录。原生V7使用独立的预览核对、提升和正式版本路径，正文不转换为v3。
4. 3001 源文件是历史输入，不是 3000 后续治理的运行时真源。
5. 3000 中固定版本的完整流程 JSON 是流程进入平台后的治理事实来源。
6. 3000、3001 与 `docs/norms/` 不得自动相互覆盖。
7. 重复输入、内容变化、无法无损转换、权限不足或写入失败时，必须明确返回结果，不得静默覆盖或留下部分数据。

3000当前继续承接v1、v2和v3文件，并统一保存v3完整流程JSON。原生V7预览、跨部门核对、提升、提交、审核、发布和按不可变`process_version_id`读回的技术路径已经实现；M1、M2数据库结构已经准备，但运行时默认关闭。只有预览和正式开关、一个精确`PROCESS_V7_TRIAL_PROCESS_REF`、正式身份权限、部门范围、当前修订号、内容摘要和未解决阻断项全部通过时，3000才允许对该单一试点流程执行V7写操作。V7新修订必须回到3001修改并重新进入预览核对，3000通用下一版草稿和旧结构化导入入口不得把V7降级为V3。管理员对治理材料保持全局只读。MDM-AI助手输出的`process-governance-v5`仍须先由用户手工导入3001迁移为v7，不能直接进入3000。

原生V7承接按以下四个状态分别记录：

| 状态层 | 记录要求 |
|---|---|
| 已实现 | 记录代码路径、接口、提交和技术测试结果 |
| 数据库已准备 | 记录M1/M2一致性和当时的V7行数，不改写首次迁移前证据缺口 |
| 运行时已开启 | 记录开关、运行提交、唯一试点`process_ref`、时间窗口和批准人 |
| 业务已验收 | 只记录实际通过的流程、日期、归口部门、承接部门和确认主体 |

“已实现”或“数据库已准备”不能代替“运行时已开启”；前三项也不能代替业务人员对真实试点的验收。扩大到第二个流程或全量范围必须另行批准。

## 四、事实、结论和建议分层

Codex 和治理材料必须区分三类信息：

| 信息层 | 含义 | 保存要求 |
|---|---|---|
| 流程事实 | 描述业务当前如何执行，包括当前表单、台账、岗位、系统现状和异常处理 | 保留当前事实及来源，不因治理目标或未来方案而改写 |
| 治理结论 | 描述经有权主体确认后，业务对象、字段、责任、来源和管理规则应如何统一 | 记录确认主体、依据、生效范围和版本，不反向覆盖历史事实 |
| 改进建议 | 描述未来可能调整的流程、系统或数据管理办法 | 明确为建议，未经批准不得写成现状或正式规则 |

例如，当前三个 Excel 分别维护供应商属于流程事实；统一供应商定义属于治理结论；由 MDM 统一维护后同步 ERP 属于改进建议。三类信息可以并存，不得互相覆盖。

## 五、待定状态和升级条件

信息不足时必须保持“待定”，并记录：

- 缺少什么事实或证据；
- 由哪个角色或部门确认；
- 确认后影响哪些流程、数据、责任或系统关系；
- 期望完成时间和关闭条件。

待定状态本身不得触发自动升级。Codex 和系统只能按既定治理规则指出下一确认主体。满足明确条件后才进入升级流程，例如：

- 跨部门在规定范围内无法形成一致意见；
- 事项影响已发布流程版本；
- 事项影响部门责任边界；
- 事项超过已批准的处理期限。

“当前不知道”不得直接等同于“需要 `decision_group` 决策”。

面向业务人员和管理人员统一使用“待定数据对象、待定关系、待定关键字段、待定匹配建议、待业务确认、待补证据、待跨部门确认、待决策”。既有机器可读字段中的 `candidate` 等稳定名称不因页面文案要求直接改名。

## 六、业务对象识别和同名判断

名称只能作为发现线索，不能作为对象身份依据。判断两条记录是否属于同一业务对象时，应优先比较：

- 业务含义；
- 生命周期；
- 唯一标识；
- 责任边界；
- 使用场景；
- 所在流程和上下文。

上述内容不足时，只能形成待定匹配建议。不得仅凭名称相同、字段相似或模型评分自动合并、覆盖或建立正式关系。

3001 中的数据对象属于待治理数据对象。数据对象是流程中具有完整业务含义、能够与字段和实例区分，并会被创建、更新、使用、传递或保管的一组业务信息。对象字段描述该数据对象在当前流程中使用的属性；表单字段通过对象字段引用复用其名称、类型和业务定义。主数据是经有权治理主体认定、需要跨行为、流程、部门或系统保持统一的核心实体数据对象；所有主数据都是数据对象，但不是所有数据对象都是主数据。表单通常不是主数据，填写完成的表单通常属于交易记录或业务证据；表单字段可以引用主数据，但该引用不使整张表单成为主数据。

3001 v7只记录当前单流程内的对象字段、表单引用、值使用方式、对象入口状态、路径事件、出口状态和推导来源。停用、作废、失效、归档、销毁和不可逆匿名化必须按各自含义记录，系统删除不是业务生命周期动作。同一对象内同名同类型旧字段可以确定性归并；同名不同类型、多个权威录入位置或没有建立位置的引用必须保留冲突并提示。是否属于主数据或参考数据、是否与其他流程对象相同、唯一标识、责任部门、正式权威来源、质量规则、共享范围和跨流程生命周期规则，均留到后续有权确认。跨部门使用只能作为主数据识别线索，不能直接形成认定或自动合并。

数据对象是流程中被创建、更新、使用、传递或保管的完整业务信息单位。主数据是经有权治理主体认定，用于稳定识别企业核心业务实体，并需要在多个业务行为、流程、部门或系统之间保持统一的部分数据对象。所有主数据都是数据对象，但不是所有数据对象都是主数据。跨部门传递、业务重要、存在唯一编号或出现在多个系统，只能作为识别线索，不能单独形成主数据结论。

表单通常不是主数据。空白表单模板通常属于受控模板、制度附件或参考数据；填写完成的表单属于交易记录或业务证据。表单字段可以引用供应商、人员、部门等主数据，但不会使整张表单自动成为主数据。例如，“供应商新增申请表”是申请和审核记录，审核通过后形成的统一供应商记录才可能成为经认定的主数据。

3001前端可以根据稳定实体、稳定标识、复用范围、责任和来源线索显示“主数据认定提示”，也可以提示对象更像交易记录、表单记录或存在身份冲突。提示必须显示判断依据，只允许用户返回数据流编辑当前对象的名称、说明和信息类型，不得提供“确认是主数据”或“列入交接待定事项”的操作，不得阻断草稿下载，也不得替代3000中的责任部门确认和MDM工作组认定。

例如，供应商付款会跨物资保障部和财务部使用供应商、采购订单、发票、付款申请和会计凭证。供应商具有跨流程复用和稳定身份，属于待认定主数据；采购订单、发票、付款申请和会计凭证记录具体业务事件，即使跨部门流转也不因此成为主数据。物资保障部和财务部分别确认本部门事实，MDM工作组再依据供应商编码、统一社会信用代码、业务定义、责任边界和使用场景认定是否为同一个统一供应商主数据。名称或部分字段不一致时保持待定，不得自动合并。

## 七、来源、证据和推断

每项治理结论应记录制度、规程、表单、台账、会议决定、业务确认记录或系统现状证据。输出必须区分：

- 已确认事实：有明确原文、数据、系统现状或具名确认记录支持；
- 分析判断：依据已有事实形成，但尚未完成业务确认或治理审核；
- 待定事项：材料不足，无法可靠判断。

数据库表、SQL、接口和系统页面只能证明系统当前如何实现，不能单独替代制度、流程和业务责任主体对业务规则的确认。

## 八、PROV-O 边界

当前不采用 W3C PROV-O 作为强制业务模型、结构规则或实施要求。Codex 可以借用来源追踪思路持续询问“是什么、怎么形成、谁参与、依据什么、为什么改变”，但不得据此新增 `prov_entity`、`prov_activity`、`prov_agent` 等字段、接口、数据库表、本体或知识图谱。

## 九、争议处理

当部门定义、责任或系统口径不一致时，Codex 应整理：

1. 各方当前口径；
2. 各自依据和使用场景；
3. 涉及的流程、业务行为、数据对象和系统；
4. 不统一或统一后的业务、责任和系统影响；
5. 可执行的处理方案；
6. 各方需要分别确认的事项；
7. 是否满足升级条件；
8. 决定生效后需要修改的资料、平台记录和验证项。

PMO 跟踪事项和证据。MDM 工作组组织结构核验。业务部门确认本部门事实。只有满足升级条件且无法形成一致意见时，`decision_group` 才作出决定。

## 十、推进顺序

1. 核对部门和业务能力边界。
2. 选择一个真实流程，明确唯一编制人和业务核对人。
3. 编制人可以直接进入3001，也可以在五账号试点范围内先通过受限DSH治理工作区填报并取得v5未审核JSON和独立问题处理记录。其他受控场景可以由Codex执行线下结构预审。
4. 使用助手形成v5文件时，编制人手工导入3001；3001只在当前页面内存中迁移为v7，不修改源文件。3001下载的v7不得反向导入助手。
5. 编制人按七步治理路径维护L3、A1、参与岗位、流程关系、动作和异常、数据对象、表单字段与跨部门位置，并分别下载四轮阶段草稿。
6. 业务部门核对流程事实、来源证据和跨部门衔接。页面“未识别到跨部门位置”不构成“不涉及跨部门”的业务结论。
7. MDM工作组检查结构并记录待定事项；编制人按问题清单整改，业务部门再次确认受影响的业务事实。
8. 编制人在“评审与交接”处理技术阻断并确认业务提示，下载“最终待核对”v7文件，再重新导入核对业务内容和稳定引用。
9. 业务部门完成事实核对后，编制人把最终v7 JSON、结构预审问题处理记录和业务核对记录分别交给MDM工作组，并核对文件SHA-256。
10. MDM工作组只有在3000的V7代码、M1/M2一致性、隔离验证、运行提交和回退条件均通过后，才可申请一个精确`process_ref`的真实试点。试点必须使用正式身份链路，由归口部门和承接部门分别核对，按当前修订号和内容摘要完成提升、提交、审核、发布和`process_version_id`读回。试点结束后关闭两个V7开关并清空试点引用；未完成业务确认前不得扩大范围或宣布V7全量承接。

每完成一个有证据、有人确认、可以复核的真实流程，才增加一部分可信的企业数据知识。不得为追求数量批量生成没有业务依据的流程、对象、字段、责任或系统关系。

## 十一、数据流与生命周期治理开发门槛

3000 的设计态业务数据流与生命周期治理目前只有正式开发计划。启动开发前必须同时取得：

1. 3001 JSON 批量导入输入范围和文件摘要已经冻结；
2. 每个文件都有导入成功、返回既有记录或明确拒绝的结果；
3. 导入前后数量、结构版本、稳定引用、修订号和内容摘要核对通过；
4. 相同输入幂等复跑不产生重复流程、修订或审核记录；
5. 第一轮完整自动化测试和真实导入核对通过，阻断缺陷为零；
6. MDM 工作组完成门槛审核，`mdm_lead` 记录开发启动结论。

门槛通过后仍只管理设计态业务数据流，不建设运行态技术血缘。生命周期工作包只绑定 3000 的不可变 `process_version_id`，不得读取、引用或依赖原始 3001 JSON、文件名、文件路径或上传摘要。

## 十二、默认交付要求

每次数据治理任务至少输出：

1. 处理对象和资料边界；
2. 已确认事实及来源；
3. 当前流程、业务行为、数据对象和字段关系；
4. 待定事项、缺少的证据、确认主体和关闭条件；
5. 各责任主体的具体动作；
6. 应进入 3001、3000、流程输入基线或 PMO 台账的内容边界；
7. 异常、争议和升级路径；
8. 完成标准和验证方法。

不得把建议写成已安排动作，不得把计划写成已完成，不得把自动化检查替代人工业务核对或真实导入结果。

## 十三、DSH治理入口边界

1. DSH只承担页面外壳、当前登录会话内的治理工作区和受限插件运行，不是3001或3000的替代品。
2. 一个治理工作区对应一个治理案例。工作区名称由用户填写，不得据此推断流程名称、责任部门、主数据分类或系统选型。
3. DSH中的AI答复、结构评分和自动校验只用于发现信息缺口与结构问题，不能确认流程事实、部门责任、业务做法、权威来源或治理结论。
4. 用户必须主动下载未经独立预审的JSON、预审后的JSON、独立问题处理记录和部门业务核对记录。退出、会话到期、实例终止、子进程故障或服务重启后，服务器不负责恢复业务内容。
5. 原页面`/classic`只作为管理员可切换的应急入口。入口切换不得复制、迁移或合并两个入口中的业务内容。
