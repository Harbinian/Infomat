# 3000 启用前四架构设计

> 文档状态：启用前设计评审稿，尚未生效
> 编制日期：2026-08-26
> 适用范围：3000 的企业架构、业务架构、数据架构和数字化治理技术架构
> 不适用范围：3001 单流程结构化编制、具体业务系统选型、企业通用信息技术架构
> 启用结论：当前不满足启用条件。完成本文件的关键决策、迁移、验证和试点门槛后，才能重新作出启用决定。

## 1. 目的和结论

本文件回答四个问题：

1. 3000 当前已经具备什么，哪些能力只是技术基础，哪些能力尚未实现。
2. 公司从“部门直接管理成员”过渡到“部门下设办公室”后，3000 如何保持组织、责任和权限边界稳定。
3. 3000 如何以待办事项驱动流程治理、数据治理、组织和员工主数据治理，并支持纬理（Facilitator）的跨部门业务协同。
4. 3000 如何从当前实现逐步升级为可迁移、可审计、可回退、可运行的数字化治理平台。

结论如下：

- 当前 3000 是以 Express.js、MySQL 和单页前端为主体的模块化单体。系统已经具备人员账号、固定七角色、流程草稿与版本、跨部门承接、部分冲突处理、角色工作台、审计记录和 V7 技术基础。
- 当前正式组织模型仍以“人员直属部门”为核心。办公室、岗位任职、正式工作角色、场景化纬理和行政人事审核发布尚未进入正式 MySQL 主线。
- 当前待办分散在多个表和领域状态中。角色工作台负责临时聚合，但“可以查看”和“可以办理”没有完全分开，管理员不能通过一张全局队列看到从导入结束开始的全部治理工作。
- 当前数据地图能够记录对象、字段、场景和字段责任，但会在缺少对象编号时按对象名称生成稳定键。名称只能作为匹配线索，不能作为跨 JSON 自动合并的依据。系统尚未建立“局部数据出现项—企业数据身份—数据关系—数据模型版本”的完整链路。
- 当前流程前后对比只覆盖部分删除项，普通数据冲突也缺少完整两侧上下文，不能满足管理员、PMO 和决策组查看精确冲突项及冻结前后差异的要求。
- 当前技术基础适合继续采用模块化单体，不需要先拆微服务。启用前应优先完成正式 MySQL 真源收口、显式迁移、统一连接池、持久会话、统一工作项、稳定数据身份、语义差异、权限边界、健康检查和恢复演练。

## 2. 事实、设计和决定的表达规则

本文件使用以下状态，避免把建议写成已经实现的能力：

| 状态 | 含义 |
|---|---|
| 当前已实现 | 当前代码中已经存在，并能从正式路径找到对应实现 |
| 当前受限 | 已有部分技术能力，但范围、数据或权限不足以满足目标 |
| 目标设计 | 本轮建议采用的目标结构，尚未实施 |
| 待确认 | 会改变责任、权限、数据真源或发布方式，必须由有权主体确认 |
| 启用门槛 | 必须取得实现、迁移、验证或业务试点证据后才能通过 |

“纬理”已经于 2026-08-26 确认为 Facilitator 的正式中文名称。英文名称继续使用 Facilitator，稳定机器语义键和场景任命类型使用 `facilitator`。“业务协同促进角色”只用于解释职责，不作为并列正式名称。名称确认不等于行政人事部已经发布正式工作角色目录，也不表示 3000 已经建立场景任命、接口或系统权限。

“业务行为”指流程中的具体业务动作。“治理工作项”指为了规划、核对、纠正、协调、验收或改进而安排的工作。治理工作项可以关联业务行为，但不能替代业务行为，也不能把任务编排写回正式流程关系。

## 3. 设计边界

### 3.1 3000 的职责

目标 3000 承担以下职责：

- 组织、员工、岗位、任职和正式工作角色的受控维护、审核、发布和历史追溯；
- 流程治理的导入、核对、跨部门承接、审核、冲突、发布和版本追溯；
- 数据对象、字段、数据关系、责任、来源、使用场景和企业数据模型的治理；
- 从导入结束开始的治理工作项、任务推进、问题分析、结果验收和持续改善；
- 冲突事实冻结、精确变更对比、协调、升级和决定记录；
- 账号、3000 RBAC 角色、访问控制和访问审计。

### 3.2 3000 不承担的职责

- 不在 3000 中重新实现 3001。3001 继续负责单流程、无状态、当前页面内存中的结构化编制。
- 不运行时读取用户原始 3001 JSON 作为正式治理真源。正式对象必须绑定 3000 内不可变的 process_version_id 或对应版本身份。
- 除本文件明确纳入的员工基本信息主数据外，不保存各业务系统的业务记录值，不把 3000 建成业务数据仓库。
- 不根据名称自动决定两个数据对象或字段是同一个企业数据。
- 不让管理员、PMO、纬理或技术人员代替业务责任部门确认业务事实。
- 不因为建立待办而复制第二份流程、数据、组织或冲突结论。
- 不在本轮设计中评价或选择 OA、MES、ERP、PLM 等具体应用系统。

## 4. 当前架构

### 4.1 当前技术形态

当前主链可以概括为：

    浏览器
      |
      v
    public/index.html 单页前端
      |
      v
    Express 路由、鉴权和 CSRF
      |
      +--> 领域路由和大型仓储模块
      |       |
      |       +--> 正式 MySQL
      |       |
      |       +--> 少量遗留 SQLite 路由
      |
      +--> 静态文件和运行健康接口

| 层次 | 当前实现 | 已确认优点 | 当前限制 |
|---|---|---|---|
| 浏览器端 | public/index.html 单文件，约 13,000 行 | 无复杂构建链，部署直接 | 页面、状态、接口调用和渲染高度集中，变更碰撞和回归风险高 |
| HTTP 服务 | Express.js 路由、Session、CSRF、安全头 | 已有基本鉴权和请求保护 | 会话使用默认内存存储；重启丢失且不适合多实例 |
| 业务实现 | 按流程、数据地图、冲突、待办、身份等文件划分 | 已形成领域边界雏形 | processDesignMysql.js 等文件过大，路由、规则、事务和查询交织 |
| 正式数据 | MySQL | 身份、流程版本、审核任务、冲突和数据地图已有表结构 | 运行期初始化结构、连接池分散；组织主数据结构不完整 |
| 遗留数据 | SQLite | 保存了早期组织、岗位和人员任职模型 | 不是正式运行真源，但部分路由和工作台查询仍然使用 |
| 版本保护 | expected_revision、内容摘要、行锁、幂等约束、只追加事件 | V7 技术链路已经具备较好的并发保护基础 | V7 功能标志默认关闭，真实业务试点和正式发布证据不足 |
| 运行检查 | /api/health | 可确认 HTTP 进程返回 | 只返回静态状态和模型版本，不能证明 MySQL、迁移或关键依赖可用 |

截至 2026-08-26 本轮检查时，3000 端口未监听。本文件的运行状态结论来自端口检查，功能和数据架构结论来自代码、结构规则及当前 MySQL 只读快照；本轮没有完成 3000 服务级或端到端运行验收。

### 4.2 当前企业和身份模型

正式身份链路是：

    person
      |
      +--> user_accounts
      |
      +--> person_roles --> roles
      |
      +--> current_department_id --> departments

当前固定治理模型为 rbac-raci-v3-2026-07-31，包括：

- admin：账号、授权和访问审计；治理材料全局只读；
- mdm_lead：全局分派、结构卡口和治理版本发布；
- department_contact：本部门起草、修改、提交和整改；
- department_mdm_reviewer：本部门审核，并记录有权主体已经作出的决定；
- data_conflict_handler：处理本人被分派的冲突；
- data_quality_auditor：全局读取并形成质量审计发现；
- decision_group：决定已经升级的重大争议。

当前限制：

- 正式 MySQL 的 person 只记录当前部门、基本联系方式和状态，没有办公室、岗位任职、任职历史和员工信息发布版本；
- 正式 MySQL 没有完整的 org_unit、position、person_position_assignment 和正式工作角色目录；
- 组织接口在正式身份模式下只读，新增、修改和删除返回 ORGANIZATION_TRUTH_READ_ONLY；
- 管理员开户时可以在人员不存在的情况下创建 active 人员，人员主档与账号生命周期尚未分离；
- PMO 不是固定治理角色，当前代码只在部分入口借用 mdm_lead 承接 PMO 评审含义；
- 纬理尚无正式工作角色、场景任命或系统权限模型。

当前组织和角色真源还包括：

| 当前受控真源 | 当前作用 | 迁入 3000 前的处理 |
|---|---|---|
| docs/organization/组织架构和部门职责.md | 公司、部门、三个公司级经理办公室、部门职责和部门到域映射 | 作为组织迁移输入；逐项核对 MySQL departments 和办公室缺口 |
| docs/organization/花名册.md | 人员、工号、部门和岗位参考资料，当前共 240 人 | 只作为行政人事查阅和首版编制参考；不是员工主数据真源，不要求与 MySQL person 强制统一对账，也不能自动发布 |
| docs/organization/工作角色目录与岗位映射.md | 正式工作角色及其与花名册岗位的多对多映射 | 已确认切换为 3000 发布真源；正式切换前继续保持当前单一受控真源，花名册岗位只作参考核验 |
| docs/organization/信息化项目人员角色映射.md | 已进入信息化项目运行链的成员和项目治理角色关系 | 作为项目治理组织成员任命的迁移输入，不自动产生 3000 RBAC 权限 |
| MySQL person、user_accounts、person_roles | 当前正式运行身份和访问授权 | 保留 person_id 和账号关系；现有 person 只能作为员工首版编制参考，不自动成为行政人事已发布事实 |

切换目标不是让文档和 3000 同时人工维护。每类真源都必须明确迁移预览、差异处理、批准切换、受控导出和旧写入口退役条件。

### 4.3 当前业务治理模型

当前已经具备：

- 流程草稿、审核任务、退回、批准、不可变版本和发布；
- 跨部门承接、部门核对、冲突升级和故事链；
- V7 预览案例、修订、核对项和事件基础；
- 数据对象、场景、字段、字段责任和字段系统关系；
- 普通数据冲突和术语冲突；
- 通用待办、流程映射待办、质量问题、输入基线问题以及从领域状态派生的承接待办；
- 角色工作台对多个待办来源的聚合。

当前限制：

- 待办来源分散，没有统一治理案例、统一工作项编号和统一事件链；
- 角色工作台会再次按照 can_act 过滤工作项。管理员虽然具有全局读取权限，但因为没有业务办理权限，反而无法从一张队列看到多数治理事项；
- 工作台中的通用待办仍有遗留 SQLite 查询，而正式待办接口已经使用 MySQL；
- 多类工作项设置了固定数量上限，当前摘要不能证明“全部待办”；
- 当前流程对比主要识别消失的流程、步骤和表单名称，不能展示字段级和关系级前后差异；
- 普通数据冲突虽然保存 A/B 值，但完整两侧对象、来源版本、上下文、责任和证据没有形成冻结决策包；
- 当前只有人员身份和账号管理，没有行政人事部主责的“起草—复核—批准—发布”员工主数据链。

### 4.4 当前数据模型

当前数据地图主要包括：

- data_map_objects：数据对象；
- data_map_contexts：部门、流程和业务行为等使用场景；
- data_map_fields：场景中的字段；
- data_map_field_system_links：字段与系统的关系；
- data_map_field_identities：字段责任、权威来源主张和确认状态；
- mdm_field_conflicts、mdm_term_conflicts：字段和术语冲突。

当前最重要的结构缺口如下：

1. 数据对象缺少明确 object_key 时，代码会基于对象名称生成稳定键。名称相同不代表企业身份相同，因此不能用这个键自动连接不同 JSON。
2. 当前字段身份主要附着于场景字段，没有把“每个流程版本中的数据出现项”和“企业级数据身份”分开。
3. 当前对象写入使用重复键更新，可能把同名对象的来源、责任和说明覆盖为后来一次导入的值。
4. 当前删除路径存在物理删除字段的实现，不能满足正式治理历史、合并回退和错误关联恢复。
5. 当前没有跨 JSON 的数据关系建议、部门核对、纠正、合并、关联、拆分和数据模型版本发布工作流。

当前稳定键使用 SHA-1 摘要的前十六个十六进制字符。对象键主要来自对象名称，字段键还包含当前数据库的上下文数字 ID。它们可以辅助定位和变化检测，但会受改名、同名和环境数据编号影响，不能作为公开企业身份。

### 4.6 当前数据完整性和审计风险

代码只读核查还发现以下启用前风险：

- 字段更新会先写审计记录，再执行正式更新。正式更新失败时，可能留下“已经修改”的虚假审计；
- 字段和系统关系采用先删除再插入，当前没有与字段修改保持同一事务；
- 字段存在硬删除路径，级联后可能失去身份、关系、冲突和质量问题；
- 待办删除前先写 deleted 事件，随后硬删除待办；事件外键级联可能把删除事件一并删除；
- Excel 导入逐行写入，没有完整批次事务和批次幂等，中途失败可能留下部分数据；
- 版本查询接口目前只有登录校验，尚未证明按部门、事项和敏感级别实施服务端数据范围判断；
- 产品、分类、属性和值等旧主数据仍由 SQLite 路由承载，与正式 MySQL 数据地图没有统一身份和版本关系；

目标架构继续采用模块化单体。模块共享同一个正式 MySQL 实例，但每个模块必须明确表结构所有权、应用服务入口和事务边界。

    组织与人员主数据 --------+
                              |
    流程治理 ----------------+--> 治理案例与统一工作项 --> 我的待办
                              |                          --> 全局治理队列
    数据治理与数据模型 -------+                          --> PMO 跟踪
                              |                          --> 决策队列
    冲突与变更决策 -----------+

### 5.1 必须保持的四条边界

1. 领域对象保存业务事实，统一工作项保存协同状态，二者通过稳定引用连接，不相互复制结论。
2. 企业数据身份和每次导入的数据出现项分开保存，任何自动匹配都只能形成待核对建议。
3. RBAC 角色、正式工作角色、岗位和场景任命分开保存，任何一层都不能自动推导另一层权限。
4. 已发布版本不可原地改写。纠正、合并、关系调整和组织变化通过新修订、新版本或受控重定向生效。

## 6. 企业架构设计

### 6.1 组织层级

目标组织层级至少支持：

    公司
      |
      +--> 部门
      |      |
      |      +--> 办公室
      |             |
      |             +--> 岗位
      |
      +--> 公司级办公室
             |
             +--> 岗位

目标规则：

- 部门继续作为行政责任、部门治理权限和业务归口的根边界。
- 办公室可以挂在公司或部门下。部门下的办公室可以沿祖先关系得到所属部门；公司级办公室没有部门祖先，不能套用这一推导规则。
- 人员可以有多条办公室和岗位任职，但每名有效员工必须有且只能有一条主要行政归属。主要行政归属必须指向部门，可以同时指向该部门下的办公室；办公室可以为空，以兼容当前部门直接管理人员的状态。岗位可以有多条，同一时点最多一条主岗；暂时未定岗时允许主岗为空并记录原因，不创建“未定岗”虚假岗位。兼岗、次要办公室、借调和纬理场景任命都不得自动扩大部门数据范围。
- 部门范围 RBAC 必须保存明确 scope_department_id。公司级办公室任职默认不授予全公司业务权限；只有明确的 global 授权或指定 scope_department_id 才能获得对应数据范围。
- 不把办公室直接塞入 departments 并让 person.current_department_id 指向办公室。现有权限代码把该字段解释为部门，这样修改会破坏部门数据范围。
- 组织单元、岗位、任职关系和负责人均使用稳定标识、生效日期和历史记录。
- 历史流程版本、待办和决定保存当时的组织名称、责任人和组织版本快照，不因后来更名或调动而改变。
- 部门负责人、办公室负责人、岗位任职人和被委托决定人分别记录，不按名称、岗位或职务推测最终责任。

办公室长期分管具体业务不能只靠组织父子关系或临时工作项表达。目标模型增加 org_unit_business_responsibility，至少保存：

- 稳定责任关系标识和组织版本；
- 责任组织单元及其授权范围；
- 分管对象类型和稳定标识，包括能力域、L3 流程、A1 业务行为、数据域或治理事项；
- 责任类型，包括部门最终负责、办公室日常分管和正式委托；
- 生效期、确认主体、依据、变更原因和历史版本。

责任解析顺序建议为：已经发布的部门最终责任 → 已经发布的办公室日常分管 → 有效正式委托 → 当前工作项分派。后一级只能说明“当前由谁办理”，不能静默取代前一级的最终责任，也不能自动改变 RBAC。

行政人事部维护并发布责任记录，但不替业务主体决定分管内容。部门下办公室的长期分管范围由部门最终负责人确认；公司级办公室的长期分管范围由相应公司级责任主体确认。责任关系涉及多个部门时，每个受影响部门分别确认；无法达成一致时提交 decision_group。PMO 和纬理可以提出建议、推进确认和记录风险，但不能批准业务分管范围。

### 6.2 人员、岗位、工作角色、场景任命和权限

目标模型分为七层：

| 层次 | 回答的问题 | 是否直接授予 3000 权限 |
|---|---|---|
| 人员 | 谁在公司任职 | 否 |
| 行政归属 | 人员属于哪个部门和办公室 | 否，用于范围判断 |
| 岗位任职 | 人员在组织单元中承担什么职位 | 否 |
| 正式工作角色 | 人员在业务流程、业务行为或受控业务场景中承担哪类责任 | 否 |
| 项目治理组织成员 | 人员是否属于 PMO、MDM 工作组或决策组，以及任期和任命依据 | 否 |
| 场景任命 | 人员在某个具体场景中承担什么临时或专项责任 | 否，必须同时具备系统权限 |
| 3000 RBAC 角色 | 人员在 3000 中最多可以查看和办理什么 | 是 |

本文件固定使用以下术语：

- 岗位：人员在组织单元中的任职位置；
- 正式工作角色：行政人事部维护的业务责任类型，以 WR-* 编码，不直接授权系统；目标设计区分流程或业务行为型 `behavior` 与场景型 `scenario`；
- 项目治理组织成员：PMO、MDM 工作组和决策组等项目组织中的任命关系；
- 场景任命：纬理等只适用于特定场景的责任；
- 3000 RBAC 角色：admin、mdm_lead 等系统权限角色。

项目治理组织成员身份、岗位、正式工作角色和场景任命都不得自动生成 3000 RBAC 授权。目标设计建议由外部有权主体完成项目组织任命，3000 保存成员、任期、任命依据、退出记录和 RBAC 映射证据。

当前受控工作角色目录、`work_role_bindings` 和对应校验规则只承接流程或业务行为型工作角色。纬理属于 3000 目标设计中的场景型工作角色，不占用具体业务行为的一对一工作角色绑定。行政人事部首次发布纬理目录记录前，必须先扩展当前目录的角色类型、字段说明、生成器和校验规则；完成扩展前，“纬理”只能作为已经确认的目标名称，不能写入当前正式目录或形成有效场景任命。

### 6.3 行政人事部的主数据职责

目标设计建议由行政人事部在 3000 内维护并发布以下首批主数据：

- 公司、部门、办公室；
- 岗位；
- 员工基本信息；
- 主岗、兼岗和任职历史；
- 部门和办公室负责人；
- 正式工作角色目录；
- 岗位与正式工作角色的关系；
- 后续经过单独结构设计和责任确认的行政人事目录。

D-01A、D-01B 和 D-18 已确认 3000 是组织、员工主数据和正式工作角色的目标正式真源。组织和正式工作角色完成迁移及切换前，对应受控组织资料继续保持当前真源地位，3000 组织写接口继续只读。花名册从本轮确认起只作为参考材料；3000 发布首个员工主数据版本前，不得把现有 person 或花名册称为已发布员工主数据。

不建议先提供任意 JSON 的“其他内容”编辑器。每种新增目录必须先明确稳定标识、字段结构、维护人、审核人、发布人、有效期、敏感级别和历史保留方式。

员工基本信息是“3000 不保存普通业务记录值”边界中的明确例外：3000 可以保存经行政人事部审核发布的员工主数据值，但必须与数据地图中的“员工数据对象和字段定义”分开。前者是受字段级权限保护的员工记录，后者是元数据、责任和关系，不得混成同一张通用数据表。

行政人事部使用表格工作区维护员工主数据，不直接编辑 JSON 或数据库。表格工作区至少支持筛选、排序、按行编辑、连续单元格粘贴、批量设置、结构检查、差异预览和整批撤销。每次保存形成新的草稿修订；每次发布固定修订号、内容摘要、生效时间、发布人和前序版本。单元格变化保存字段路径、旧值、新值、修改人、修改时间和修改依据。历史版本只读，纠正历史错误必须形成新修订和新版本，不能原地覆盖或物理删除。

    起草

      |
      v
    行政人事复核
      |

### 6.4 纬理（Facilitator）设计

纬理的核心不是管理具体流程，而是在已经授权的业务场景中推进业务行为和治理工作。

首次出现时使用以下受控定义：**纬理（Facilitator）是在已经授权的业务场景内，承担前期规划、计划编排、业务动作推进、问题分析、任务派发、结果验收记录和持续改善的跨组织协同角色；纬理不因角色名称或任职关系取得部门管理权、业务决定权、治理发布权或全局数据访问权。**

纬理属于场景型正式工作角色。纬理任命可以把一个或多个稳定 `behavior_ref`、治理对象或改进事项纳入协同范围，但不得把纬理写入这些业务行为的一对一 `work_role_bindings`，也不得替换业务行为原有的责任人、执行人、审核人或批准人。

纬理应采用“正式工作角色 + 场景任命 + 受限系统权限”的组合：

- 行政人事部维护正式工作角色定义；
- 有权业务主体针对业务场景、治理案例、能力域或改进事项任命具体人员；
- 场景任命记录范围、起止时间、允许动作、可见对象、可派发对象、验收准备、验收记录和受托验收状态变更的能力上限及退出条件；具体工作项的验收标准、验收责任槽位和 `acceptance_effect_mode` 由业务结果责任主体在不可变验收方案中另行确认；
- 用户只有同时具备有效场景任命和对应系统权限时，服务端才允许其操作；
- 任职部门或办公室不限制其参与跨部门场景，但其可见和可办理范围只来自具体场景任命；
- 场景任命失效后，用户保留历史记录的最小只读权限，不再产生新的办理权限。

| 纬理动作 | 允许的结果 | 不允许的结果 |
|---|---|---|
| 前期规划 | 记录目标、范围、参与方、依赖、风险和验收条件 | 把建议写成已确认业务事实 |
| 计划编排 | 安排治理工作项和业务行为的推进顺序 | 改写正式流程关系 |
| 业务行为推进 | 围绕稳定 behavior_ref 跟踪准备、执行和阻塞 | 代替业务责任人完成业务动作 |
| 问题分析 | 保存现象、证据、原因假设、影响和建议 | 把分析判断写成部门决定 |
| 任务派发 | 在场景授权范围内分派责任人、协作人和期限 | 向无授权主体派发部门业务责任 |
| 结果验收 | 按事先确认的标准记录通过、退回和缺口 | 取得部门最终决定权或治理发布权 |
| 持续改善 | 创建改进事项、复盘和下一轮工作项 | 覆盖已经发布的流程或数据版本 |

“记录验收结果”和“对业务结果承担最终责任”必须分开。只有场景任命明确包含验收记录权时，纬理才能提交验收记录；纬理只有同时取得受托验收状态变更能力上限和工作项精确委托时，才可能作出改变工作项状态的验收决定。最终责任仍属于业务行为或工作包的责任主体。

这里的“验收记录权”不能解释为“纬理可以自行作出通过或退回决定”。D-06A 已确认把验收核对、验收记录和工作项状态变更分开授权；在 D-06B 至 D-06D 及相应实现、迁移和权限验证完成前，3000 不启用纬理受托验收状态变更。

### 6.5 PMO、管理员和决策组

目标权限建议：

| 主体 | 查看范围 | 办理范围 |
|---|---|---|
| admin | 全部治理工作项、状态、冲突、变更和活动记录；员工敏感字段按最小必要原则脱敏 | 账号、授权和访问审计；治理业务始终只读 |
| PMO | 全部治理进度、期限、阻塞、冲突和变更影响 | 写跟踪说明、风险和升级建议，记录已经批准的期限；不改变业务责任、正式期限、领域状态或发布结果 |
| mdm_lead | 全局治理事项和必要详情 | 分派、结构卡口和按授权发布 |
| decision_group | 已升级事项及其完整冻结决策包 | 记录升级决定、依据和适用范围 |
| 纬理 | 有效场景任命范围内的计划、任务、证据和影响信息 | 执行场景任命明确列出的促进动作 |

PMO 当前不是固定系统角色。若确认 PMO 需要在 3000 中写入跟踪说明、风险、升级建议或记录已批准期限，应在下一版固定治理模型中增加受限角色，例如 pmo_coordinator。该角色不能修改工作项的业务责任、领域状态和验收结论，也不能借用 mdm_lead 的治理权限。

纬理不应增加为一个不受场景限制的全局角色。实现时可以提供最小权限包，但每次写操作仍必须校验有效场景任命。

### 6.6 纬理的名称、稳定编码和历史显示

中文显示名称、正式工作角色身份、场景任命类型和系统权限编码必须分开。已经确认的名称与稳定身份关系如下：

| 用途 | 建议值或规则 | 变更规则 |
|---|---|---|
| 中文显示名称 | 纬理 | 进入 `work_role_revision`，随正式工作角色目录版本发布 |
| 英文名称 | Facilitator | 作为跨语言说明，不用于判断权限 |
| 正式工作角色编码 | 由行政人事部在首次确认时按 `WR-0001`、`WR-0002` 顺序分配 | 遵守当前受控目录规则，不按名称预造编码；编码一经发布永久保留且不可复用 |
| 正式工作角色类型 | `scenario` | 与流程或业务行为型 `behavior` 分开；不得进入具体业务行为的一对一工作角色绑定 |
| 稳定机器语义键 | `facilitator` | 与顺序工作角色编码分开；全局只能对应一个稳定 `work_role_id`，发布后不可修改，角色退休后不得复用；不作为页面名称，也不直接授予权限 |
| 场景任命类型 | `facilitator` | API 和数据结构使用的稳定枚举，必须与正式工作角色的机器语义键一致，不按中文或英文名称关联 |
| 系统权限 | 按规划、派发、推进、验收记录等动作分别编码 | 权限模型版本化发布，不建立无限范围的 `facilitator` 全局权限角色 |

名称确认和后续变更遵守以下规则：

- 业务页面首次出现时显示“纬理（Facilitator）”和职责解释，后续统一显示“纬理”；
- “业务协同促进角色”只是解释语，不作为第二个正式中文名称；
- 现有 `data_conflict_handler` 的“冲突处理人”或界面中的“协调人”是另一项职责，不得批量改名为“纬理”；
- `work_role.machine_key` 为空时不参与机器语义匹配；非空时必须满足全局唯一约束。`facilitator` 只能绑定一个稳定 `work_role_id`，不得因中文名称变化、角色退休或重新启用而改绑其他身份；
- 正式工作角色目录使用独立的不可变 `work_role_catalog_version`。`work_role_revision` 必须保存 `work_role_revision_id`、`work_role_catalog_version_id`、`work_role_id` 和内容摘要，并对 `(work_role_catalog_version_id, work_role_id)` 建立唯一约束；组织版本和流程绑定发布时必须固定引用所用目录版本；
- 每次场景任命或任命范围变化都生成新的 `scenario_assignment_revision_id`，并冻结 `assignment_type=facilitator`、`work_role_id`、`work_role_revision_id`、`assignee_person_id`、适用对象、允许动作、可派发对象、验收准备、验收记录和受托验收状态变更的能力上限、有效期、`appointing_authority_ref`、`appointment_decided_by_person_id`、`recorded_by_person_id`、任命依据和内容摘要；替换修订还必须冻结 `replaces_assignment_id`、`planned_cutover_at`、被替换任命的活动修订和授权版本基线、被替换范围摘要；这些字段进入 D-05B 的确认内容摘要，改变切换时间或任一替换基线时必须建立新修订并重新收集全部确认；旧修订不得覆盖；
- `assignment_type=facilitator` 只能引用 `role_kind=scenario`、机器语义键为 `facilitator` 且在所用目录版本中有效的 `work_role_id`，不能按“纬理”、Facilitator 或其他文本匹配；
- 每个写操作的审计事件保存 `work_role_revision_id`、`scenario_assignment_revision_id`、治理模型版本和本次实际通过服务端校验的权限码；审计回放不读取当前名称、当前任命或当前权限代替历史依据；
- 场景任命和审计事件可以保存当时的名称快照用于直接显示，但名称快照不能替代上述不可变身份；调整显示名称不得覆盖历史快照；
- D-04 确认后同步更新 `docs/glossary.md`，但名称确认本身不创建角色、授权、账号或场景任命；
- 正式工作角色名称发布与 3000 RBAC 权限模型发布分别控制。名称确认本身不等于系统权限已经可用。
- 名称、任命范围或权限变化只追加新目录版本、场景任命修订或治理模型版本。回退时恢复上一有效指针和写入门槛，不删除新修订；历史事件始终按其冻结身份解析。

### 6.7 纬理任命权拆分

D-05 需要分别确认任命权解析、跨组织接受和任命退出，不能用“场景业务责任主体”一个模糊字段代替。任命决定主体、实际录入人和被任命人必须分别保存；PMO 代为录入或跟踪不产生任命权。

D-05A 已确认采用以下任命权解析规则：

| 任命范围 | 任命决定主体 | 不能据此取得任命权的主体 |
|---|---|---|
| 单一部门业务场景 | 已发布责任记录中的部门最终负责人，或该负责人作出的有效正式委托所指向的主体 | 场景发起人、PMO、管理员 |
| 部门下办公室负责的业务场景 | 已发布责任记录明确赋予任命权时，由办公室业务责任主体决定；记录未明确时回到部门最终负责人 | 仅因在办公室任职的人员 |
| 公司级办公室或全公司场景 | 已发布公司级责任记录中的公司级责任主体，或其有效正式委托所指向的主体 | 公司级办公室成员、管理员、PMO |
| 跨部门场景 | 已发布牵头责任记录中的牵头业务责任主体提出任命决定；任命何时生效及各部门确认范围由 D-05B 另行确认 | 任一参与部门单方面代表其他部门确认范围 |
| 治理案例 | `governance_case.accountable_subject_ref` 指向的有权主体；只有领域规则明确指定时才由 `mdm_lead` 决定 | 导入者、冲突处理人、管理员 |
| 能力域 | 已发布能力责任记录中的能力责任主体 | 根据能力名称、岗位或历史常量推测的人员 |
| 改进事项 | 该事项所绑定父场景、治理案例或能力域的有权主体 | 事项创建人、PMO |

任一范围无法解析出唯一、有效且可追溯的任命决定主体时，3000 只能保存任命草稿，不能激活场景任命。存在多个互相冲突的责任记录时，相关主体先处理责任冲突；`decision_group` 只处理满足升级条件的争议，不作为默认任命人。

D-05B 已确认把任命决定与任命生效分开。任命决定形成后，3000 针对同一个 `scenario_assignment_revision_id` 收集以下三类确认：

| 确认类型 | 确认主体 | 确认对象 | 拒绝或缺失时的结果 |
|---|---|---|---|
| 本人接受 | 被任命人本人 | 职责、业务场景、允许动作、有效期和退出条件 | 任命保持待接受，不产生查看或办理权限 |
| 资源投入确认 | 根据被任命人的主要行政归属解析出的日常管理责任主体；办公室责任记录未明确时回到部门最终负责人 | 投入时间、工作冲突、任期和必要交接 | 任命保持待资源确认，不产生查看或办理权限 |
| 组织范围确认 | 每个受影响责任组织根据已发布责任记录解析出的有权主体 | 仅限本组织的数据对象、可见范围、允许动作和可派发对象 | 该任命不得在未确认范围内生效；需要缩小范围时建立新修订后重新确认 |

任命生效遵守以下已确认规则：

- `scenario_assignment_revision` 冻结全部受影响组织，不使用会随组织变化自动扩大的“当前全部部门”或名称通配范围；
- 被任命人、主要行政管理责任主体和全部受影响责任组织完成所需确认后，任命状态才从 `pending_confirmation` 进入 `active`；无人答复时保持待确认，系统不得自动同意；
- 同一人员同时承担任命决定、资源投入确认或组织范围确认职责时，页面可以合并操作，但系统分别保存确认类型、授权身份和依据；
- 每个组织只确认本组织范围，不能代表其他组织确认，也不能借范围确认改写任命人；
- 每个任命修订先生成非空、稳定且不可修改的必需确认槽位：本人接受槽位绑定被任命人，资源投入槽位绑定冻结的主要行政管理责任记录，组织范围槽位分别绑定每个冻结的 `affected_org_unit_id`；
- `confirmation_slot_key` 根据确认类型和对应稳定身份生成，不使用人员姓名或组织名称。确认记录按照 `(scenario_assignment_revision_id, confirmation_type, confirmation_slot_key)` 建立唯一约束；`required_confirmation_subject_ref` 只用于校验当前谁有权完成该槽位，不能代替槽位身份；
- 确认请求必须提交待确认任命修订、任命内容摘要、确认集合 `expected_revision` 和幂等键。相同幂等请求返回原确认记录；同一唯一键出现不同决定、不同摘要或旧确认集合修订时拒绝写入，不能以后提交覆盖先提交；
- 确认记录一经提交即不可修改。被任命人改变时关闭原任命并建立新任命；职责、动作、有效期或组织范围改变时生成新修订，并重新收集该新修订的全部必需确认；
- 只有精确绑定当前待激活 `scenario_assignment_revision_id`、任命内容摘要和冻结确认主体的 `accepted` 记录可以计入完成集。旧确认只读保留，永不复制、重挂或重新解释为新修订的确认；
- 最后一项确认写入后，3000 在同一数据库事务内锁定稳定任命、待激活修订、当前有效修订和必需确认集合，重新核对人员、工作角色、责任记录、有效期、全部确认及摘要，再按任命类型决定下一状态；并发请求不能绕过完成集核对。普通首次任命或处于 `active` 的任命内容修订只有在激活条件全部满足时才进入 `active`；D-05C 所述替换候选先进入 `ready_for_cutover`，不得沿普通路径单独激活；用于恢复 `suspended` 任命的新候选取得全部确认后先进入 `ready_for_activation`，必须由当前任命控制主体另行发起精确激活；
- 每个稳定任命同一时点只允许一个状态为 `draft`、`pending_confirmation`、`ready_for_activation` 或 `ready_for_cutover` 的未结束候选修订。3000 创建候选时在同一事务内锁定 `scenario_assignment`，确认 `open_candidate_revision_id` 为空，插入候选并设置该指针；存储层使用生成的 `open_candidate_guard` 建立唯一约束：上述开放候选保存 `scenario_assignment_id`，终态修订保存空值。候选修订保存不可变 `base_active_revision_id` 和 `base_authorization_epoch`；没有活动修订时明确保存空基线；
- 激活候选修订时，3000 必须同时比较并交换当前有效修订指针和任命授权版本：当前指针仍等于候选的 `base_active_revision_id`、当前 `authorization_epoch` 仍等于 `base_authorization_epoch`、任命业务有效性状态允许激活、全部权威依赖版本仍有效且激活事务结束时不存在开放停止条件，候选才能激活。基线、内容摘要、权威依赖版本或终态不匹配时，候选修订进入 `stale`，其确认只读保留；基线仍匹配但存在可以按 D-05C 解除的开放停止条件时，确认齐全的候选保持 `ready_for_activation`，不产生权限。任命决定主体必须在条件解除后重新发起精确激活，系统不得把最后一个停止条件关闭解释为自动增权；
- 新修订处于 `pending_confirmation`、`ready_for_activation` 或 `ready_for_cutover` 时，原 `active` 修订只在原范围、原有效期和稳定任命仍为 `active` 的条件下继续授权，新修订不产生任何新增权限。普通首次激活或普通新修订激活时，3000 在同一事务内递增 `authorization_epoch`；存在原活动修订时先把它改为 `superseded`，再切换 `active_revision_id`、清空 `open_candidate_revision_id` 并写入审计事件。替换修订只按 D-05C 的新旧任命原子切换规则激活；候选进入 `stale`、`rejected` 或 `cancelled` 终态时也在同一事务内清空开放候选指针并保留全部历史；
- 任命修订激活或因人员失效、正式工作角色退役、任命到期、授权依据被正式撤销而安全失效时，3000 同一事务写入权限失效事件，并使相关权限缓存和高风险写会话在下一次写操作前重新校验；
- 任一确认被拒绝时，3000 在同一事务内把候选修订标为 `rejected`、清空开放候选指针并停止收集其余确认；任命不产生部分权限。任命决定主体可以缩小范围后建立新候选，或者不再继续任命；
- PMO 和管理员可以查看确认进度，PMO 可以催办和记录风险，但二者都不能代替本人、日常管理责任主体或受影响组织确认；
- D-05C 已确认设计方向，但在状态机、确认撤回、替换、交接、迁移和权限验证通过前，3000 仍不开放活动任命的人工暂停、恢复、撤销或人员替换入口；安全失效条件仍按上述规则自动停止新写入。

D-05C 已确认采用“先停止新增权限，再处理恢复或交接；业务任命决定与技术访问控制分开；替换人员不改写历史”的规则。下列内容是已确认设计方向；接口、数据库、状态机、迁移和权限验证证据仍待形成，不能据此认定 3000 已经发布相应权限规则。

场景任命的业务有效性状态与 `scenario_assignment_revision` 的内容修订状态必须分开。`active_revision_id` 只指向当前选用的任命内容，不能单独证明该任命仍可授权。稳定任命建议使用以下业务有效性状态：

| 状态 | 业务含义 | 是否可以恢复 |
|---|---|---|
| `pending_activation` | 尚无已经生效的任命修订，不产生场景权限 | 取得 D-05A 任命决定和 D-05B 全部确认后进入 `active` |
| `active` | 当前任命修订、有效期和全部必需条件均有效，可以进入后续权限交集判断 | 不适用 |
| `suspended` | 任命暂时停止生效；场景任命不再提供新增查看范围或任何业务写权限，但保留历史、影响清单和交接记录 | 只允许按下述恢复规则恢复 |
| `revoked` | 当前有效任命控制主体正式撤销任命 | 否；需要再次任命时建立新任命 |
| `expired` | 达到任命有效期的排他上限 | 否；需要续任时建立新任命，或在到期前以新修订完成续期 |
| `invalidated` | 人员身份、正式工作角色或任命依据发生明确的永久失效，系统按权威事件终止任命 | 否 |
| `closed` | 任命对象产生预先定义的权威终止事件 | 否 |
| `replaced` | 新人员的替换任命已经受控切换生效 | 否 |
| `cancelled` | 任命从未生效，任命决定主体终止继续收集确认 | 否 |

`revoked`、`expired`、`invalidated`、`closed`、`replaced` 和 `cancelled` 是终态。系统不得通过修改原记录恢复终态，也不得把账号停用、会话失效或系统权限撤回写成业务任命已经撤销。

暂停、恢复和撤销权按以下规则解析：

| 触发主体或条件 | 允许动作 | 系统结果 |
|---|---|---|
| 任命修订中 `appointing_authority_ref` 代表的当前有效责任主体 | 人工暂停、符合条件时恢复、正式撤销 | 系统重新解析操作时唯一有权办理人，保存决定、依据和实际录入人 |
| 被任命人本人 | 撤回本人接受 `withdraw_acceptance` | 系统追加本人确认撤回事件，并立即暂停整个任命 |
| 被任命人本人 | 申请受控退出或替换 `request_exit` | 系统建立退出和交接工作项；本人未撤回接受且不存在安全风险时，原任命继续到受控切换或其他正式停止条件发生 |
| 被任命人当前主要行政管理责任主体 | 撤回资源投入确认 | 系统追加资源确认撤回事件，并立即暂停整个任命 |
| 任一受影响组织的当前有权主体 | 只撤回本组织的范围确认 | 系统追加该组织确认撤回事件，并立即暂停整个任命；不能只让其他组织范围继续授权 |
| 客观安全失效条件 | 自动停止 | 系统打开对应停止条件并停止全部新写入，不等待人工通知或事后确认 |
| PMO | 查看、催办、记录风险、提出升级建议和代录已经形成的决定 | 不取得业务暂停、恢复、撤销或转派决定权 |
| 管理员 | 停用账号、撤回系统 RBAC、失效会话和执行已经形成的安全处置 | 不修改业务任命、组织确认或工作项责任，不取得业务暂停、恢复、撤销或转派决定权 |

“当前有效任命控制主体”不能按人员姓名、岗位名称、办公室成员身份或管理员角色推测。3000 每次使用任命中冻结的 `appointing_authority_ref`，结合操作时有效的已发布责任记录和正式委托，解析唯一有权办理人。原 `appointment_decided_by_person_id` 只有在操作时仍代表该责任主体时才可以办理。稳定责任主体正常更换负责人时，当前经发布记录确定的承接主体取得后续控制权；原决定人不保留个人控制权。任命依据被明确撤销且撤销范围包含从属任命、责任主体被撤销且没有合法承接主体，或存在多个冲突承接主体时，系统安全暂停任命并建立责任解析工作项；PMO、管理员和任一办公室成员均不能代为指定承接主体。正常负责人换届不追溯否定当时有权形成的任命，也不自动撤回组织已经形成的确认。

D-05B 的确认记录仍保持不可修改。被任命人、主要行政管理责任主体或受影响组织撤回确认时，3000 追加 `scenario_assignment_confirmation_withdrawal` 或等价只追加事件。事件必须绑定原 `confirmation_id`、`scenario_assignment_revision_id`、`confirmation_slot_key`、撤回主体、撤回主体当时的授权身份、原因、依据、发生时间、实际录入人、`expected_revision`、`expected_authorization_epoch` 和幂等键。每个主体只能撤回自己所代表确认槽位的确认；撤回事件不得覆盖原确认，也不得改变其他组织的确认记录。页面必须让被任命人明确选择“立即撤回本人接受”或“申请安排替换后退出”，不能把普通退出申请自动解释为确认撤回。

确认撤回事务锁定稳定任命、原确认和对应必需确认槽位，并核对原确认状态为 `accepted`、确认槽位仍属于该修订当前必需集、撤回主体仍有权代表该槽位以及 `expected_authorization_epoch` 未被用于恢复或切换。每个 `confirmation_id` 最多只能存在一条有效撤回记录，数据库对 `confirmation_id` 建立唯一约束；相同幂等请求返回原撤回记录，不同请求不得重复撤回同一确认。

确认撤回必须绑定当前稳定任命的精确修订。撤回当前 `active_revision_id` 的必需确认时，系统立即暂停整个稳定任命并使开放的后续候选进入 `stale`；撤回当前开放候选中的确认时，系统只把该候选改为 `rejected`、清空 `open_candidate_revision_id`，原活动修订仍按原确认和范围继续有效；`superseded`、`stale`、`rejected` 或其他历史修订中的确认保持只读，撤回接口拒绝处理。撤回替换候选中的确认时，系统还要清空原任命的 `open_replacement_assignment_id`，新稳定任命进入 `cancelled`，不能遗留待切换指针。

任一必需确认被撤回后，原确认集合立即失效。即使后续恢复相同内容，任命决定主体也必须建立新的候选修订，并重新收集该修订的全部 D-05B 确认。需要减少受影响组织、职责、动作、数据范围、可派发对象、验收准备、验收记录或受托验收状态变更能力上限、有效期时，同样建立新修订并重新确认；系统不得通过“只删掉撤回组织”形成部分继续授权。

只有停止条件矩阵明确标为“不要求新修订”的情形，才允许恢复同一修订。首期包括 `manual_control_suspension`，以及任命依据和范围均未变化的 `control_subject_unresolved`；任命内容和责任依据必须未变化，被任命人、正式工作角色和全部 D-05B 确认仍有效，并且没有其他开放停止条件且未到期。当前任命控制主体追加精确恢复决定后，恢复事务把 `lifecycle_status` 从 `suspended` 改为 `active` 并递增 `authorization_epoch`。每个停止条件只能由该条件预先定义的解除依据关闭；关闭事件必须引用对应打开事件。关闭一个条件后仍有其他开放条件时，任命继续保持 `suspended`，此次关闭不增加有效权限，也不能让其他主体用一次恢复操作覆盖剩余条件。

确认撤回、人员变化、主要行政归属变化、责任依据实质变化、范围变化或任命内容变化均不能复用原确认。任命决定主体为同一被任命人建立新候选并重新取得全部 D-05B 确认后，激活事务只能关闭由该新确认集合明确替代的旧确认撤回条件；事务随后重新核对全部停止条件、权威依赖、`base_active_revision_id` 和 `base_authorization_epoch`。只有不存在其他开放条件时，系统才在同一事务内激活新修订、恢复稳定任命并递增 `authorization_epoch`；否则候选保持 `ready_for_activation` 且不产生权限。`revoked` 等终态不能恢复。

自动停止条件至少包括：

- 行政人事发布的员工主数据进入不允许继续任职的状态；
- 当前正式工作角色修订退役或失效；
- 纬理任命必须填写非空 `effective_to`；服务端数据库时间达到该排他上限时，有效期判断统一采用 `effective_from <= now < effective_to`；
- 任命依据被正式撤销，且撤销事件明确包含该任命或其从属任命；
- 主要行政归属、资源投入责任、受影响组织或授权范围发生实质变化，原确认不能继续代表当前范围；
- `appointing_authority_ref` 无法解析唯一、有效的当前责任主体；
- 任命对象产生该 `assignment_scope_type` 预先登记的权威终止事件。

停止条件的打开和关闭来源建议固定如下。页面操作、管理员判断、PMO 跟踪记录和后台投影均不能代替表中的权威来源。

| 停止条件类型 | 打开依据和立即结果 | 唯一关闭或终止依据 | 是否必须建立新修订并执行全部 D-05B 确认 |
|---|---|---|---|
| `manual_control_suspension` | 当前任命控制主体的暂停决定；进入 `suspended` | 当前任命控制主体作出精确绑定原修订和授权版本的恢复决定，且其他条件均有效 | 否；任命内容、确认和依据任一变化时改为“是” |
| `assignee_acceptance_withdrawn` | 被任命人撤回当前有效本人确认；进入 `suspended` | 新候选包含新的本人接受、资源和全部组织范围确认，当前任命控制主体再发起激活 | 是 |
| `resource_confirmation_withdrawn` | 当前主要行政管理责任主体撤回资源确认；进入 `suspended` | 新候选取得全部 D-05B 确认，当前任命控制主体再发起激活 | 是 |
| `organization_scope_withdrawn` | 任一受影响组织撤回本组织范围确认；整个任命进入 `suspended` | 新候选取得全部 D-05B 确认，当前任命控制主体再发起激活 | 是 |
| `employee_ineligible` | 行政人事发布员工不再具备履职条件；进入 `suspended` | 行政人事发布新的有效员工状态，新候选取得全部 D-05B 确认，当前任命控制主体再发起激活 | 是 |
| `control_subject_unresolved` | 当前责任记录无法解析唯一控制主体；进入 `suspended` | 已发布责任记录或正式委托恢复唯一控制主体；该主体显式恢复，且任命依据和范围未变化 | 否；任命依据或范围变化时改为“是” |
| `assignment_scope_materially_changed` | 主要行政归属、资源责任、受影响组织或授权范围发生实质变化；进入 `suspended` | 新的已发布组织或责任记录生效，新候选取得全部 D-05B 确认，当前任命控制主体再发起激活 | 是 |
| `work_role_retired` | 行政人事发布正式工作角色退役；进入 `invalidated` | 无；原稳定任命终止 | 不适用；需要重新任命时使用届时有效的正式工作角色建立新任命 |
| `appointment_basis_revoked` | 权威撤销事件明确撤销该任命依据及从属任命；进入 `invalidated` | 无；原稳定任命终止 | 不适用；需要重新任命时重新执行 D-05A 和 D-05B |
| `assignment_expired` | 数据库时间达到非空 `effective_to`；进入 `expired` | 无 | 不适用 |
| `scope_object_terminated` | 精确任命对象产生已登记的权威终止事件；进入 `closed` | 无 | 不适用 |

同一组织只更换实际负责人，但稳定责任身份、责任范围和有效依据均未变化时，原组织确认继续作为组织决定保留；继任主体取得后续撤回权，不自动打开停止条件。表中可关闭条件的权威来源事件只负责证明条件已经解决，不自动恢复权限。最后一个可关闭条件解决后，任命仍保持 `suspended` 或候选保持 `ready_for_activation`，直到当前任命控制主体发起精确激活事务。终止条件发生时，系统把任何开放候选改为 `stale` 并清理开放指针，不允许恢复原稳定任命。

“场景结束”当前没有统一真源，不能直接作为通用自动状态。每种 `assignment_scope_type` 必须先声明可接受的终止事件。终止事件至少保存稳定对象标识、对象版本、事件时间、有权决定主体、依据和 `source_event_id`。治理案例只能使用治理案例正式关闭或取消事件；改进事项只能使用其领域定义的正式终止事件；能力域或长期业务场景没有天然终止事件时，只能通过任命到期或有权主体撤销结束。单个工作项关闭、PMO 台账标记完成、会议结束或页面显示状态变化均不能证明场景结束。相应对象类型未定义权威终止事件前，3000 不启用该对象类型的自动 `closed` 转换。

为防止多个停止原因互相覆盖，建议增加以下逻辑记录：

| 逻辑记录 | 关键内容 |
|---|---|
| `scenario_assignment_lifecycle_event` | 暂停、恢复、撤销、到期、关闭、替换和取消的只追加事件；保存前后状态、当前活动修订、操作责任身份、实际办理人、原因、依据、服务端时间、幂等键和当时的 `authorization_epoch` |
| `scenario_assignment_stop_condition` | 每个开放停止条件的稳定键、类型、来源对象和来源事件；同一任命、条件类型和来源只能存在一个开放条件，关闭条件必须引用对应打开事件 |
| `scenario_assignment_confirmation_withdrawal` | 对原不可变确认的只追加撤回事件，不修改或删除 `scenario_assignment_confirmation` |
| `scenario_assignment_replacement` | 稳定 `replacement_id`、源任命和冻结的修订、授权版本、内容及范围摘要，目标任命和 `ready_for_cutover` 目标修订及摘要，`planned_cutover_at`、替换状态、双方 `expected_revision`、幂等键、请求摘要和最终切换事件 |
| `scenario_assignment_work_item_impact` | 任命停止时冻结的未完成工作项清单、影响类型、旧责任和验收快照、处置状态及后续转派事件引用 |
| `work_item_authorization_hold` | 工作项因当前任命停止而暂时不可办理的独立限制；保存工作项、所需办理或验收能力、任命生命周期事件、打开和关闭依据，不覆盖工作项原业务状态 |

`scenario_assignment` 建议增加 `lifecycle_status`、单调递增的 `authorization_epoch`、`open_replacement_assignment_id`、终止时间和终止原因。任何使有效授权增加、减少或换代的事务都必须递增 `authorization_epoch`，包括首次激活、同一修订恢复、活动修订切换、暂停、撤销、到期、关闭和替换；创建候选和收集确认本身不改变有效授权，因此不递增。候选修订除 `base_active_revision_id` 外还要冻结 `base_authorization_epoch`。任命暂停、撤销、确认撤回或安全失效的最小原子事务只承担安全停权：3000 锁定稳定任命、当前活动修订和开放候选，打开对应停止条件，追加生命周期或确认撤回事件，更新业务有效性状态并递增 `authorization_epoch`，把开放候选转为 `stale`，清空 `open_candidate_revision_id`，并写入一条最小、必达的后续处理 outbox。上述任一步失败时，安全停权事务整体回滚。替换候选取得全部确认但尚未切换时使用 `ready_for_cutover` 修订状态；该状态仍属于开放候选，不产生任何权限，也不能清空候选唯一保护。

工作项影响清单、通知、跟踪工作项和管理投影在安全停权提交后，由 outbox 消费者按生命周期事件幂等生成；这些后续处理失败时，系统告警并使 readiness 失败，但不得恢复已经停止的权限。生命周期事件保存 `impact_snapshot_at` 和稳定事件序号；影响生成器根据 `work_item_event` 重建该时点的未完成事项，再把后续已经发生的合法工作项事件作为单独变化保留，不能读取一张后来已经变化的当前表冒充停权时快照。

人员状态、正式工作角色、责任依据和组织范围等上游真源发布时，3000 必须在同一 MySQL 事务中同步停止受影响任命并递增 `authorization_epoch`。每次纬理权限判定还要直接核对所冻结上游版本仍然有效，不能只等待停止条件、缓存或投影异步生成。将来只有在保持等价的同步停权或提交前权威版本校验后，才允许把相关模块拆到不同事务边界。

最后一项确认激活、候选修订切换、暂停、撤销、确认撤回和替换切换必须使用同一稳定任命锁和固定锁顺序串行化。固定顺序先按 `scenario_assignment_id` 升序锁定全部涉及的稳定任命，再依次锁定任命修订、确认槽位和确认记录、停止条件、工作项，最后写生命周期事件和 outbox；任何路径不得交换顺序。每次纬理业务写入必须在同一业务事务内先锁定稳定任命，再校验 `scenario_assignment_revision_id`、`authorization_epoch`、`lifecycle_status=active`、有效期、开放停止条件、对象和动作范围、工作项 `expected_revision` 及幂等键，然后才写领域对象和工作项事件。写请求先取得任命锁并提交时，其业务事件发生在停止事件之前；停止事务先提交时，旧请求必须因任命状态或授权版本变化而失败。这样可以保证停止事务提交后，不再有使用旧任命的新业务写入提交。暂停和安全失效属于只减权限的操作，服务端在取得锁后以最新活动修订执行停止；旧页面不能阻止安全停权。恢复、撤销、内容变更和替换切换则必须绑定精确当前修订、内容摘要和授权版本，旧页面提交时拒绝写入。

到期停权不依赖定时任务、缓存失效或管理投影。每次权限判定直接使用服务端数据库时间；后台任务只负责补写到期事件、工作项和通知。任命状态改变后，3000 同一事务写入权限失效事件，并使授权缓存和高风险写会话在下一次写操作前重新校验。管理员可以停用账号和会话以立即阻断技术访问，但账号恢复不能绕过仍未恢复的业务任命。

人员替换采用以下规则：

1. 3000 为新人员建立新的稳定 `scenario_assignment_id`，并建立不可变身份为 `replacement_id` 的 `scenario_assignment_replacement`。替换记录保存 `source_assignment_id`、`source_active_revision_id`、`source_authorization_epoch`、源内容和被替换范围摘要、`target_assignment_id`、`target_candidate_revision_id`、目标内容摘要、`planned_cutover_at`、双方 `expected_revision`、幂等键、请求摘要和替换状态。系统不得修改原任命的 `assignee_person_id`。
2. 新任命完整执行 D-05A 任命决定和 D-05B 全部确认。一个原任命同一时点只允许一个开放替换候选，数据库使用稳定指针或等价唯一约束防止并发建立多个替换链。最后一项确认完成后，新修订先进入 `ready_for_cutover`，不能按普通新任命路径单独激活。
3. 计划替换且不存在安全风险时，旧任命只在原范围和原有效期内继续生效。到达已经确认的 `planned_cutover_at` 后，系统或当前任命控制主体发起切换事务并重新核对双方状态；后台调度只负责发起事务，不能绕过核对。切换请求必须提交 `replacement_id`、新旧任命的 `expected_revision`、目标 `target_candidate_revision_id`、幂等键和请求摘要。只有旧任命的当前活动修订、`authorization_epoch`、内容摘要和被替换范围摘要仍等于冻结基线，且新任命的开放候选仍等于目标修订、目标修订仍为 `ready_for_cutover`、内容摘要和全部确认未变化时，才允许切换；任一条件不成立时替换候选和替换记录进入 `stale` 并重新任命、重新确认。
4. 成功切换时，3000 在同一事务内把旧任命自己的开放内容候选改为 `stale` 并清空其 `open_candidate_revision_id`，把旧稳定任命改为 `replaced`，把目标修订改为 `active`，把新稳定任命的 `lifecycle_status` 从 `pending_activation` 改为 `active` 并设置其 `active_revision_id`，清空新任命的 `open_candidate_revision_id` 和旧任命的 `open_replacement_assignment_id`，递增双方 `authorization_epoch`，把替换记录改为 `cutover_complete`，再在同一 `replacement_id` 下分别写入新旧两侧生命周期事件、权限失效事件和 outbox。事件冻结全部预期值、实际前后值、两侧内容和范围摘要；事务按稳定任命标识排序锁定新旧任命，不能因两个页面先后提交而形成替换范围重叠。
5. 原人员失效、拒绝交接、失联、停职、离职或存在安全风险时，系统先停止旧任命，不等待交接或新任命生效。新人员在 D-05A 和 D-05B 全部完成前不取得预授权限。
6. 替换链只处理被明确替换的一条任命，不据此决定同一场景是否允许多人共同担任纬理。确需共同任命时，应另行明确人数、责任槽位、重叠动作和冲突处理规则，不能把替换过程当成共同任命。
7. 替换候选进入 `rejected`、`stale` 或 `cancelled` 时，3000 在同一事务内清空原任命的 `open_replacement_assignment_id`；原任命在其他有效条件未变化时继续按原范围授权。原任命在切换前已经进入任一终态时，系统保留原终态，把替换候选和替换记录改为 `stale` 并清理开放指针；替换候选不能脱离原替换决定自动变成普通任命。

任命暂停、撤销、到期、安全失效或替换时，3000 生成不可变的未完成工作项影响清单，但不自动删除、关闭、取消、延期或改写工作项，也不回滚已经完成的历史动作：

- 原纬理只是规划、派发或跟踪工作项，而另有具备独立业务责任和有效权限的办理人时，办理人可以继续处理；系统不自动改派该工作项；
- 原纬理是当前责任人、唯一办理人或预先指定验收人时，工作项保留原业务状态，系统打开 `work_item_authorization_hold` 并追加 `assignment_suspended` 事件；页面显示当前不能办理的原因。当前业务责任主体按现有 `reassigned` 规则重新分派办理责任；业务结果责任主体按 `acceptance_reassigned` 规则指定新的验收主体；
- 已经提交并等待原纬理验收的工作项不得自动通过、退回或关闭；业务结果责任主体指定新的有效验收主体，或等待替换任命生效后再转派；
- 新纬理不会因新任命自动继承旧工作项。办理责任使用 `reassigned` 事件，验收责任使用 `acceptance_reassigned` 事件；历史事件继续指向原责任槽位和任命，不能重挂；
- 转派事务先区分目标责任依据。目标办理或验收责任依赖场景任命时，事务按“新旧稳定任命按标识排序、任命修订和停止条件、工作项和对应责任槽位按标识排序、hold、事件和 outbox”的固定顺序加锁；3000 必须确认目标任命 `lifecycle_status=active`，目标 `active_revision_id` 和 `authorization_epoch` 与请求值精确一致，数据库时间仍在有效期内，没有开放停止条件，目标人员、正式工作角色和全部权威依赖仍有效，且任命的对象范围和允许动作覆盖该工作项及本次办理或验收能力；
- 目标责任不依赖场景任命时，对应责任槽位的 `current_scenario_assignment_*` 必须全部为空。3000 锁定并校验当前已发布的领域责任记录、目标人员有效状态、固定 RBAC 最大权限、组织和数据范围、工作项状态及直接业务动作权限；页面选择的姓名、岗位或办公室任职不能代替这些依据。两条分支任一条件不满足时，系统均不得更新工作项真源；
- `reassigned` 或 `acceptance_reassigned` 事务在通过上述校验后，连同工作项和责任槽位各自的 `expected_revision` 一起更新对应责任主体及该槽位的当前授权引用。事件保存授权来源类型；使用场景任命时冻结原任命、原修订和原 `authorization_epoch`，新任命、新修订和新 `authorization_epoch`；使用直接业务责任时冻结对应领域责任记录和权限依据。两条分支均保存工作项及槽位修订、转派决定主体及其授权身份、实际录入人、依据、实际通过的动作和对象范围、已解决的 hold 标识、幂等键和请求摘要；
- 转派事务只关闭已经由新责任依据解决的 `work_item_authorization_hold`；仍有其他开放限制时，工作项继续不可办理，系统不能用一次转派清除全部限制；
- 原期限保持不变。需要延期时，原分派主体或领域有权主体另行决定并记录依据；PMO 只能记录已经批准的期限；
- 原被任命人只能按单独的最小只读规则查看本人历史操作和交接清单，场景任命停止后不再提供当前场景新增内容的查看范围或任何写权限。

停止新写入不以原被任命人完成交接、受影响组织收到通知或事后确认作为生效条件。3000 在停止事务提交后向全部受影响组织生成通知或跟踪工作项；这些事项用于处理业务连续性和争议，不恢复已经停止的权限。

### 6.8 纬理验收权拆分

D-06 不能继续用“有验收记录权”一个字段同时表示整理验收材料、记录核对结果和作出通过或退回决定。当前设计一方面要求纬理只记录验收且不承担最终业务责任，另一方面又允许获得验收记录权的纬理直接把工作项从 `submitted_for_acceptance` 改为 `accepted`。这两种含义会产生不同的业务授权和系统状态效果，必须分开确认。

D-06 建议拆成四个连续决定：

| 编号 | 需要确认的边界 | 本项未确认前的限制 |
|---|---|---|
| D-06A | 纬理可以记录什么，何时可以自行作出受托验收决定并改变工作项状态 | 纬理不能仅凭“验收记录权”使工作项通过或退回 |
| D-06B | 自验禁止、利益冲突和不得受托验收的事项范围 | 不启用纬理受托验收决定权 |
| D-06C | 验收标准、提交成果、证据、逐项结果、总体结果和并发写入规则 | 不形成正式验收结果或状态变化 |
| D-06D | 跨组织验收、验收转派、纠错重开、旧数据迁移和验证门槛 | 不启用跨组织或历史验收承接 |

D-06A 已确认把纬理相关能力分成以下三层：

| 能力层 | 纬理可以执行的动作 | 对工作项正式状态的影响 |
|---|---|---|
| 验收准备 `acceptance_prepare` | 查看已经冻结的验收标准和当前提交，整理成果、证据和缺口，起草逐项核对记录 | 不改变 `submitted_for_acceptance` |
| 验收记录 `acceptance_record` | 提交完整的逐项核对结果和依据，或代录具名业务验收主体已经形成的决定；系统分别保存声明的决定主体、声明的实际决定人和实际录入人 | 默认采用 `record_only`；纬理不能仅凭该权限自行产生 `accepted` 或正式退回状态。初次启用时，业务结果责任主体或其有效直接验收主体必须确认采用该记录，或者具名决定人本人登录并精确确认冻结内容；纬理代录请求本身不触发状态变化 |
| 受托验收状态变更 `acceptance_apply_state` | 在业务结果责任主体已经对精确工作项、标准版本、对象范围、允许结果和有效期作出明确委托时，纬理按不可变标准决定通过或退回 | 只有验收方案明确使用 `delegated_state_transition`，且 D-06B 至 D-06D 的全部门槛通过后，纬理的正式验收结果才能在同一事务内改变工作项状态 |

D-06A 的已确认规则如下：

- 验收方案保存 `acceptance_effect_mode`。缺省值只能是 `record_only`，空值、页面按钮、岗位、RBAC 角色或历史任命不能被解释为已经取得受托验收决定权；
- 业务结果责任主体可以直接作出验收决定；D-06C 进一步要求该人员先成为当前验收责任槽位中的具名验收人，不能在槽位仍由他人承担时直接覆盖决定。业务结果责任主体也可以在后续低风险白名单内，针对精确工作项、验收标准修订、验收责任槽位、对象范围、允许结果和有效期，明确授予 `delegated_state_transition`；
- 纬理获得 `delegated_state_transition` 后，只能按业务结果责任主体已经确认的标准判断结果。纬理不能修改标准以适配成果，不能把失败项改成例外，不能自行更换验收主体，也不能把受托验收扩大到其他工作项；
- 验收事件分别冻结 `business_accountable_subject_ref`、`decided_by_person_id`、`recorded_by_person_id` 和 `decision_authority_ref`。实际录入人不能替代决定主体，受托决定人也不能因此取得最终业务责任；
- `accepted` 只表示治理工作项满足其已确认验收门槛，不表示部门事实已经确认，也不自动产生审核、批准、发布、数据合并、权限变更或正式版本生效；这些领域动作仍由各自有权主体执行；
- 初次启用不提供通配验收授权、全场景验收决定权或自定义 `full_acceptance_authority`。旧记录缺少精确委托证据时，只能迁移为 `record_only` 或只读的 `legacy_unproven`，不得补造成受托验收决定权。

D-06A 只决定“普通验收记录是否等于业务决定权”。该项已经确认普通验收记录不等于业务决定权，并允许业务结果责任主体按精确范围另行授予受托验收状态变更权。低风险白名单、自验禁令、固定排除事项、跨组织确认、标准和证据冻结、状态汇总、并发、转派及纠错规则继续分别由 D-06B 至 D-06D 收口；接口、数据库、迁移和权限验证证据仍待形成。

#### D-06B 已确认：职责分离和禁止范围

D-06B 已确认采用“正式验收不设自验例外；系统按稳定人员身份和当前成果的贡献记录判断冲突；低风险工作类型和全部低风险条件必须同时满足；固定禁止事项优先于白名单”的规则。

正式验收中的“同一人员”必须按正式身份链中的稳定 `person_id` 判断。该人员名下的不同账号、岗位、RBAC 角色、正式工作角色、场景任命、委托、代理身份和会话仍代表同一个人。正式委托只能证明该人员是否有权验收，不能消除该人员已经参与成果形成的事实。

3000 应针对当前提交修订保存完整的成果参与记录。每次工作项首次进入办理、正式退回后重新办理或受控重开时，系统建立稳定 `participation_cycle_id`；办理、提交、代理提交、共同编制、成果修改、证据处理、标准起草和标准修改等动作写入该办理参与周期的只追加参与事件。正式提交时，系统才建立绑定 `submission_revision_id` 的 `acceptance_round_id`，并为当前提交冻结不可修改的参与者快照、`participant_revision` 和 `participant_set_digest`。重新办理时，新参与周期必须引用上一提交，并把当前成果仍然采用的历史贡献人纳入传递贡献闭包；不能只统计本次修改人员。责任槽位转派、人员退出、修改被回退或成果再次修改，都不得删除先前参与记录。以下人员不得对同一提交修订执行 `delegated_state_transition`，也不得作出正式通过或正式退回决定：

- 当前提交及其仍被采用历史成果的现任或历史办理人；
- 实际提交人，以及代理提交所代表的具名成果主体；
- 成果编制人、共同编制人和成果实质修改人；
- 对验收证据作出实质增加、删除、替换或内容修改的人；仅按已经固定的证据清单执行机械上传且没有选择或改变证据内容时，不据此自动认定为成果参与人；
- 决定把缺失证据、不符合项或未知结果作为例外、豁免、风险接受或需要裁量的“不适用”处理的人；服务端按工作开始前已经冻结的客观适用条件自动计算不适用时，不把仅提交适用性事实和证据的人视为不适用决定人；
- 工作开始后修改验收标准、阈值、通过条件、证据要求、汇总规则或适用性的人；
- 形成、实质修改或选择了父工作项当前修订引用、汇总或采用的任何子成果或证据的人；该人员不能通过把共同成果拆成子工作项、改名为附件或跟踪记录，或者只验收父工作项规避回避要求；
- 当前提交的参与人员、代理关系或成果来源无法可靠识别的人员。此时系统把验收资格标为 `eligibility_unproven`，只允许 `record_only`。

以下动作本身不构成成果参与，但不能单独产生验收决定权：

| 动作 | 可以继续承担的验收工作 | 转为利益冲突的条件 |
|---|---|---|
| 本人自检 | 办理人随提交保存自检结论和证据 | 自检不能产生正式 `accepted` 或正式退回结果 |
| 规划、计划编排和派发 | 纬理在精确委托下验收他人完成的低风险成果 | 纬理亲自形成、修改或选择了提交成果，或者父工作项实际引用、汇总或采用的子成果或证据 |
| 催办、提醒、会议组织和进度记录 | 纬理继续准备或记录验收 | 跟踪记录被写入成果并构成实质结论 |
| 问题分析和原因假设 | 纬理记录现象、证据、假设和建议 | 纬理形成的解决方案被直接采用为当前提交成果 |
| 起草客观验收标准 | 业务结果责任主体在工作开始前独立确认并冻结标准后，纬理仍可在其他条件满足时受托验收 | 纬理自行确认标准，或者在工作开始后修改标准、决定例外或调整通过口径 |
| 代录具名决定 | 纬理按 `record_only` 记录独立业务主体已经形成且可追溯的决定 | 纬理把本人意见写成他人决定，或者缺少决定主体和依据 |

“起草客观验收标准”不构成冲突的条件必须可以由记录直接核对：`criteria_drafted_by_person_id` 与 `criteria_confirmed_by_person_id` 不是同一稳定人员；业务结果责任主体的确认由该人员实际登录并作出，不能只填写姓名或由起草人代理；确认绑定精确 `criteria_revision_id` 和内容摘要；确认事件早于不可变的工作开始事件。后续任何人实质修改标准都会建立新修订，并使引用原确认和原标准的受托验收资格失效。

纬理执行 `delegated_state_transition` 时，实际登录人、实际决定人和实际录入人必须是同一个稳定人员，即 `session.person_id = decided_by_person_id = recorded_by_person_id`。他人代录具名决定只能使用独立的 `record_only` 请求，并保存决定主体、实际决定人、实际录入人和可核对依据；页面选择姓名、上传签名图片或切换代理身份不能证明该人员已经完成正式验收。

同一人员同时具有业务结果责任主体和纬理身份时，3000 必须记录该人员本次使用的真实授权来源。该人员没有参与成果形成时，可以按直接业务责任身份验收；该人员已经办理、提交或实质修改成果时，切换为业务负责人或纬理身份仍不能自验。领域规则要求独立复核和批准分离时，直接业务责任身份也不能降低该要求。

纬理受托改变验收状态时，低风险资格必须同时通过“工作类型白名单”和“工作项属性”两层检查：

1. `work_type`、目标对象类型和动作必须命中不可变、版本化、已经发布的封闭白名单；页面名称、自由文本、管理员选择和纬理自行标记都不能建立白名单资格；
2. 当前工作项只有一个明确的业务责任范围和验收范围，不需要多个组织分别确认；跨组织结果在 D-06D 确认和实现前只能使用 `record_only`；
3. 业务结果责任主体已经在工作开始前独立确认并冻结客观、可逐项判断的验收标准；标准不包含“总体可接受”“基本合理”等主观裁量，也不允许纬理决定例外、风险接受或证据豁免；
4. 成果、证据、代理关系和参与人员完整且可追溯；任何必需信息缺失、未知或无法验证时均不满足低风险条件；
5. 验收结果可以受控重开或纠正，并且不会直接或通过父子、汇总、依赖、门槛和自动动作链，被任何高影响事项用于形成关闭、通过、发布、生效、例外、对外承诺或不可逆动作；依赖链不完整或无法确认时不满足低风险条件；
6. 当前事项不确认或改变部门业务事实、责任边界、正式版本、发布状态、数据身份、组织人员关系、权限或任命；
7. 当前事项不存在开放冲突、升级、授权暂停、证据不足、风险接受、例外或责任主体不明；
8. 当前验收人不在本轮办理人、提交人、被代理提交主体、成果贡献人、冲突标准修改人或传递贡献人集合中；传递贡献人根据当前修订实际引用、汇总或采用的全部子成果和证据自动计算，不接受人工填写“非决定性”标签；
9. D-06A 的精确委托、场景任命、人员身份、验收责任槽位、固定 RBAC 上限、对象范围和有效期均有效。

初次启用的白名单建议只包含不改变领域事实的客观工作，例如检查既定附件是否到位、既定格式或结构是否已经修正、既定模板是否完整、普通跟踪动作是否已经完成。正式机器代码必须在后续受控策略目录中发布，不能把本段示例直接当成已经发布的枚举。

受托验收策略应保存不可变策略版本和内容摘要，并把规则分成 `mandatory_deny` 与 `low_risk_allow` 两层。验收方案、验收资格判断和正式验收决定必须精确绑定同一个 `policy_revision_id` 及策略摘要。3000 命中任一 `mandatory_deny` 时立即拒绝；未命中固定禁止规则后，只有命中明确的 `low_risk_allow` 且该规则的全部条件均为真时，验收资格才是 `eligible`。未命中允许规则、条件缺失或判断结果未知时，系统均拒绝 `delegated_state_transition`。失败的状态变更请求必须整笔无写入；如需保存 `record_only`，用户另行发起明确请求，系统不得自动降级，也不得复用状态变更请求的幂等键。管理员、PMO、纬理和页面配置均不能覆盖固定禁止规则。

`mandatory_deny` 必须沿当前不可变父子关系、汇总关系、依赖关系、关闭门槛和自动动作链反向传播。只要本工作项的正式验收状态会被高影响事项用于关闭、通过、批准、发布、生效、例外或不可逆动作，本工作项就不能使用 `delegated_state_transition`。3000 不能因为本工作项显示为“附件到位”“格式检查”或“跟踪完成”而忽略真实下游效果；依赖和下游动作无法完整解析时，验收资格为 `eligibility_unproven`。

以下决定或正式状态变化不得通过纬理受托验收产生：

- 部门业务事实、部门责任边界、跨部门立场或跨部门总体结果的确认；
- 流程的审核、批准、发布、版本生效或失效；
- 数据对象身份、主数据分类、归口、权威来源、共享范围、纠正、关联、解除关联、合并、拆分、重定向、退役或数据模型发布的决定；
- 员工基本信息、组织、部门、办公室、岗位、任职和正式工作角色的审核、批准、发布或生效；
- 账号、固定 RBAC 角色、数据范围、权限、正式委托和纬理任命的授予、变更或撤回；
- 跨部门冲突裁决、`decision_group` 决定、风险接受、规则例外、证据豁免、缺证放行，以及未在冻结方案中预先定义、需要主观裁量、例外、风险接受或证据豁免的“不适用”决定；
- 领域规则要求指定验收人、独立复核人、批准人或法定签字人的法律、财务、质量、安全、客户和对外承诺事项；
- 不可逆动作、仍有开放争议或升级的事项、证据不足的事项、责任主体不明的事项，以及领域规则确定的其他高影响事项。

上述禁止清单限制的是纬理作出正式业务决定。业务有权主体已经完成相应决定或发布后，纬理可以在另一条低风险工作项中核对既定材料是否到位或既定执行动作是否完成；该核对不得反向建立、改变或替代原业务决定。

高影响事项中，纬理只可以执行 `acceptance_prepare`、`acceptance_record` 和 `record_only`：整理标准、成果和证据，记录缺口和客观不符合项，协调补证和独立验收，并代录具名有权主体已经形成的决定。纬理不能使用 `delegated_state_transition` 作出正式通过或退回决定，也不能据此关闭业务事项、批准例外或触发发布。

人员不足、紧急处理和自动检查均不构成自验例外：

- 小部门或单人场景没有独立验收人时，业务结果责任主体把验收责任上收到上一级稳定责任主体，或者精确委托同领域且未参与成果的人员；暂时无法安排时，工作项保持待验收；
- 紧急事项确需先使用结果时，有权业务主体可以另行作出有期限、可撤销并保留风险的临时使用决定。该决定不能写成 `accepted`，到期前仍须完成独立验收；
- 自动检查默认只生成结构、完整性、测试或数量核对证据，不能自动产生正式验收结果。全自动状态变化需要另行确认不可变规则、适用白名单、失败处理和停用条件，不属于 D-06B 的初次启用范围；
- 管理员、PMO 和 `decision_group` 不能因人员不足或紧急情况代替业务验收主体。只有事项已经满足现行升级条件时，`decision_group` 才处理相应争议。

D-06B 的验收请求至少提交工作项、验收责任槽位、验收方案、当前提交、验收标准、策略、参与者集合、场景任命、精确验收委托及两类授权版本的预期修订与摘要。服务端沿用 D-05C 的固定锁前缀：先按标识锁定场景任命、精确验收委托、相应修订和开放停止条件，再锁定工作项、办理和验收责任槽位、当前提交、验收标准、策略修订及参与者快照。服务端随后按 `decided_by_person_id` 重新执行人员冲突反查。全部校验通过后，系统才在同一事务中写入验收决定、工作项状态、只追加事件和 outbox。任一修订、摘要、参与人员、策略状态、责任槽位、场景任命 `authorization_epoch` 或精确委托授权版本变化时，系统返回 `409 ACCEPTANCE_CONTEXT_CHANGED`，整笔事务不写验收结果、状态效果或自动降级记录。

D-06B 的服务端验证至少覆盖：同一人员使用多个账号、多个角色或多个场景任命；办理后先转派再验收；共同编制后退出责任槽位；代理提交和代录；成果或证据修改后回退；工作开始后改变标准、阈值、例外或“不适用”规则；把共同成果拆成子工作项、附件或跟踪记录后验收父工作项；把低风险子项状态用于高影响父项关闭、发布或生效门槛；白名单与固定禁止清单同时命中；类型、参与记录、传递贡献血缘或下游依赖未知；管理员、PMO 或决策组越权；小部门和紧急理由绕过；参与事件与验收决定并发；策略安全失效与验收决定并发；精确验收委托撤回、范围变化或授权版本变化与验收决定并发；旧页面在参与人员、策略、责任槽位、提交、标准、场景任命或精确委托授权版本变化后提交。任何失败路径均不得产生 `accepted`、正式退回或下游状态效果。

上述内容是 D-06B 已确认设计方向。当前 3000 尚无统一工作项的人员贡献记录、版本化验收职责分离策略或相应服务端校验；D-06C 和 D-06D 也尚未确认。因此，D-06B 确认不等于已经可以启用受托验收。

#### D-06C 待确认：验收冻结包、逐项结果和原子状态变更

D-06C 建议采用“验收只针对一个完整、不可变且可核对的冻结包；验收人逐项判断，系统计算总体结果；有效结果、状态效果、事件和 outbox 原子提交”的规则。当前 V7 代码已经使用修订号、以 64 个十六进制字符保存的 SHA-256 内容摘要、数据库行锁和冲突返回保护流程内容；D-06C 复用这种技术模式，但不把现有流程审核记录当成统一工作项验收已经实现。

| `work_item_acceptance_state_effect` | 有效结果如何改变工作项状态、状态效果的有权依据和状态前后修订 | 每个有效结果必须在同一事务中建立一个状态效果；`record_only` 候选记录不能直接建立状态效果 |
| `work_item_acceptance_event` | 方案确认、提交、开始核对、记录结果、采用结果、退回、失效和状态变化的只追加事件 | 历史事件只读取当时冻结身份和摘要，不读取当前指针重新解释 |

所有摘要建议使用 SHA-256，并同时保存 `canonicalization_version`，即计算摘要时所用的固定规范化规则版本。标准摘要至少覆盖顺序、必需性、判定类型、参数、容差、单位、适用条件、证据要求、汇总规则和 `acceptance_effect_mode`；提交摘要至少覆盖结果正文、结构化结果、目标对象稳定标识、当前版本、当前指针修订、生命周期修订及状态、允许验收守卫、证据清单和参与者集合；有效结果摘要还必须覆盖实际采用的证据检查修订和 `check_epoch`。稳定标识、修订号和摘要必须同时保存，不能只用摘要代替对象身份。

##### 验收方案和标准冻结

需要正式验收的工作项在进入 `assigned` 前，业务结果责任主体必须确认一个非空的验收方案修订。纬理可以按 D-06B 已确认边界起草候选标准，但不能自行确认标准或通过修改标准适配已形成的成果。

业务结果责任主体可以本人占用验收责任槽位并承担直接验收，也可以在已确认验收方案中预先指定一名初始直接验收主体。当前直接验收主体必须绑定稳定验收责任槽位的当前修订、具名 `person_id`、允许结果、有效期和明确 `decision_authority_ref`；只填岗位、角色、姓名文本或当前负责人不足以建立决定权。有效直接验收主体可以逐项核对后形成 `pass` 或 `return`，也可以精确采用 `record_only` 候选记录；所有正式路径都执行 D-06B 职责分离并冻结实际决定人和授权依据。业务结果责任主体需要从现任直接验收主体接管时，也必须先按 D-06D 形成新的槽位修订，不能绕过当前槽位直接覆盖决定。

直接验收主体不取得最终业务责任，也不能把决定权再次转委托给纬理或其他人员；变更直接验收主体按 D-06D 的受控转派规则处理，验收内容未变化时不改验收方案和提交修订，但必须终结旧验收轮次并针对新槽位修订建立新轮次。同一人员同时具有直接业务验收身份和纬理身份时，系统按本次实际 `decision_authority_ref` 判断：如果决定权来源只是纬理场景任命，该人员仍必须走 `delegated_state_transition`，不能用“直接验收主体”标签绕过 D-06A 和 D-06B。

`acceptance_required` 不能由创建人、纬理、管理员或页面按单个工作项自由关闭。版本化工作类型策略必须把所有会形成或改变业务事实、组织与人员信息、数据模型、流程版本、权限、冲突决定、发布结果、父项关闭门槛或其他下游状态效果的工作项固定为 `acceptance_required=true`。只有不形成业务决定、不改变领域对象、也不作为其他事项通过或关闭依据的通知和客观确认事项，才能由策略固定为 `false`；此类事项通过可机器核对的完成事件直接关闭，不经过 `accepted`，也不能借此绕过 D-06B。类型未知、策略缺失或影响范围无法证明时一律要求正式验收。

工作类型策略不能单独证明当前事项仍为低风险。3000 必须根据版本化父子关系、汇总关系、依赖关系、关闭门槛和自动动作链，为每个工作项维护 `work_item_downstream_context` 当前头和不可变传递闭包。方案确认、正式提交、D-06B 职责分离判断、候选记录、有效结果以及 `acceptance_required=false` 的客观直接关闭，都必须冻结并比较同一个下游影响上下文修订和摘要；不能只保存一次计算出的风险标签。

增删或改变任何会影响状态效果的关系，或者改变闭包中任一工作项的类型、目标动作、风险策略或状态效果定义时，服务端必须先用只读查询解析受影响工作项和领域动作集合，再按标识锁定这些工作项，重新核对集合没有变化，随后按标识锁定对应下游影响上下文当前头、领域动作门槛当前头和关系当前修订。服务端拒绝会形成状态效果循环的关系，新增不可变关系修订，重算全部受影响的传递闭包和领域动作门槛，再原子递增两类当前头修订；集合已变化时释放事务并按新集合重试，不能边锁边扩大集合。关系事务、工作项类型事务、验收事务和领域动作事务必须使用同一锁序或对相同当前头执行等价比较并交换。任何闭包未知、关系解析失败或修订不一致都使低风险资格成为 `eligibility_unproven`。纯说明性引用不能产生状态效果，必须与上述状态效果关系分开保存。

下游影响上下文在尚无有效结果时变化，系统使开放验收轮次进入 `stale`，记录 `acceptance_context_invalidated` 并要求按新上下文重新提交；客观直接关闭请求则整笔拒绝。工作项已经 `accepted` 或 `closed` 后新增下游门槛，或者现有下游工作项的类型、动作、风险策略或状态效果变化而扩大旧结果的用途或风险时，原结果继续作为历史，但新关系修订或原关系的替换修订只能先进入 `pending_revalidation`；该状态立即进入目标领域动作门槛当前头并阻塞对应动作，不能因关系尚未 `active` 而被查询忽略。旧结果和旧关系修订不能满足新的关闭、发布、合并或生效门槛。有权主体必须按 D-06D 建立重开或独立重新核验事项，完成后才能激活新修订。关系当前状态和激活依据均只追加保存，不能通过覆盖关系行把待核验状态改成生效。

验收方案确认事务至少执行以下动作：

1. 锁定工作项、验收方案身份、开放方案候选、业务结果责任依据和验收责任槽位；
2. 核对候选修订、内容摘要、`base_confirmed_revision_id` 和当前已确认方案指针没有变化；首次确认还必须核对工作项尚未进入 `assigned`，变更确认则必须记录原因和影响；
3. 核对每条必需标准具有可判断的条件和证据要求；
4. 冻结 `acceptance_effect_mode`、职责分离策略修订、下游影响上下文身份、当前修订和摘要，以及允许结果；
5. 保存决定主体、实际确认人、实际录入人、确认依据和数据库时间；
6. 变更确认时，在同一事务中使引用旧方案的开放验收轮次失效，并按下文规则处理工作项状态和重新提交待办；
7. 通过比较并交换原子切换当前已确认方案指针，终结开放候选，并把旧方案保留为历史；并发确认导致基线或当前指针变化时返回冲突，不覆盖另一确认结果。

工作项处于 `assigned`、`in_progress`、`blocked` 或 `submitted_for_acceptance` 时，如果需要改变任何标准正文、参数、阈值、适用性、证据要求、汇总规则或生效方式，业务结果责任主体必须建立并确认新方案修订。系统保留旧提交、旧核对和旧证据，把引用旧方案的开放验收轮次标为 `stale`；工作项已经提交且尚无有效结果时，系统在同一事务中把它退回 `in_progress`，记录 `acceptance_context_invalidated` 事件并建立重新提交待办，不生成 `returned` 事件或有效验收结果。系统不得用新标准追认旧成果，也不得自动改变原期限；期限调整由有权分派主体另行决定并记录依据。工作项已经 `accepted` 或 `closed` 时，新标准不能改写原验收历史；有权主体必须按 D-06D 的受控纠错和重开规则处理，或者针对后续责任建立新工作项。

验收方案可以由业务结果责任主体逐项确认，也可以从其已经批准并处于有效期内的工作类型模板实例化。模板实例化必须冻结模板修订、适用范围和全部结构化参数；参数缺失、超出模板范围或需要临时补写自由文本标准时，仍需业务结果责任主体确认本工作项方案。管理员、PMO、纬理和客户端不能把未批准模板、旧模板或默认文字解释为已经确认的验收标准。

单纯说明错别字但不改变正式标准时，系统应通过独立说明事件处理；只要页面正文、结构化参数或适用范围发生正式变化，就必须建立新修订，不能由客户端声称“没有语义变化”而绕过摘要更新。

##### 成果提交和证据冻结

办理人从 `in_progress` 正式提交时，3000 在同一事务内建立 `work_item_submission_revision` 和对应 `work_item_acceptance_round`，并把工作项改为 `submitted_for_acceptance`。提交修订至少冻结：

- 工作项和办理责任槽位的修订；
- 实际提交人、代理提交主体和本轮参与者集合；
- 当前确认的验收方案修订和标准摘要；
- 当前下游影响上下文身份、修订和传递闭包摘要；
- 结果正文或结构化结果摘要；
- 目标领域对象的稳定标识、提交时的当前版本标识和内容摘要、当前版本指针修订、生命周期修订和状态，以及“当前状态允许验收”的守卫摘要；
- 证据清单、每项证据的稳定标识和内容摘要；
- 自检结论；自检只作提交证据，不产生正式验收效力；
- 提交时的场景任命、授权版本、幂等键和请求摘要。

有效验收的目标必须是 3000 能够控制当前版本指针和生命周期守卫的领域对象，或者已经导入 3000 并形成稳定对象身份的不可变快照。任意外部系统的“当前页面”或可变记录不能直接作为目标当前性依据；如领域规则要求外部对象在验收时仍为当前版本，启用前必须接入可核对的外部版本标识和变化事件，否则只能验收导入快照，不能声称验收了外部对象的当前状态。

提交后，办理人不能在原修订上补写成果或证据。尚无有效结果时，办理人发现成果、证据或参与信息需要修改，必须发起“撤回提交”；服务端锁定工作项和验收轮次，确认当前办理责任和冻结上下文未变后，原子把轮次标为 `stale`、把工作项退回 `in_progress`、记录 `submission_withdrawn` 事件并建立新的办理参与周期。办理人随后才能修改，并在再次提交时建立新的提交修订和验收轮次。验收方案、下游影响上下文、证据检查结果或目标对象当前版本等外部于办理人的冻结上下文变化时，由相应有权事务记录 `acceptance_context_invalidated`：目标仍允许继续办理时执行同样的非决定型失效并回到 `in_progress`，目标已经取消、终止或禁止继续时进入 `blocked` 或受控取消路径。上述路径均不生成 `returned` 事件或有效验收结果。旧证据、旧提交和旧参与周期继续只读保留。

证据可以保存在 3000 的受控存储中，也可以引用能够提供不可变版本、内容摘要和满足审计期限的可用性保证的受控外部来源。普通网址、共享盘当前路径、文件名、聊天记录位置或会变化的在线页面不能单独作为冻结证据；如确需使用，提交人必须保存当时的受控快照、来源版本或内容摘要。证据完整性检查、文件安全检查或外部版本核对尚未完成时，3000 不允许形成有效验收结果。检查结果必须通过 `work_item_acceptance_evidence_check` 只追加保存；后续发现新的安全或完整性风险时，系统建立风险和重开处置事项，不反向改写历史检查记录或既有验收结果。

证据的技术完整性只证明“验收时看到的内容没有被替换”，不证明证据中的业务事实正确。3000 按字段敏感级别和最小必要原则控制证据内容，管理员和 PMO 的全局进度查看权不自动包含证据正文查看权。日志、错误响应和普通审计摘要不得保存完整业务材料或员工敏感字段。

##### 逐项结果和总体结果

验收人必须针对冻结方案中的每条标准记录结果。建议使用以下稳定结果：

| 逐项结果 | 含义 | 对总体结果的影响 |
|---|---|---|
| `passed` | 该项满足冻结标准，且该项要求的证据完整有效 | 可以计入通过集合 |
| `failed` | 该项不满足冻结标准；记录实际事实、缺口和依据 | 任一必需项失败时，总体结果为 `return` |
| `not_applicable` | 服务端根据工作开始前已经冻结的结构化客观适用条件和当前冻结证据计算该项不适用 | 验收人只提交适用性事实和证据，不能手工选择不适用；只有服务端可机器核验为真时才排除 |
| `not_reviewed` | 尚未核对或无法判断 | 不能计入通过集合，也不能形成总体 `pass` |

验收人只提交逐项结果、事实说明和证据引用。3000 根据冻结汇总规则计算总体结果，不允许验收人手工选择一个与逐项结果不一致的总体结论：

- 所有必需项均为 `passed`，允许不适用的项目均满足预先条件，全部必需证据有效且没有开放限制时，总体结果为 `pass`；
- 任一必需项为 `failed`，或者必需证据缺失、无效或无法冻结时，总体结果为 `return`；
- 没有失败项但仍有必需项 `not_reviewed` 时，验收轮次状态为 `in_review`，不能形成有效验收结果；
- 适用条件需要主观裁量、条件表达无法由服务端执行、证据不足或计算结果未知时，该项保持 `not_reviewed`；纬理可以保存 `record_only` 候选记录，但不能以受托验收方式形成状态效果；
- 标准、提交、证据、目标对象、人员集合、策略、责任槽位或授权上下文不再匹配时，验收轮次状态为 `stale`，不能形成有效验收结果；
- 验收人发现首个明确失败项后可以提前退回，但未核对项目继续标为 `not_reviewed`，系统和页面必须说明这是提前退回，不得显示为已经完成全面验收；
- 初次启用不支持“部分通过”“有条件通过”或由纬理临时批准例外。业务确需分批验收时，应在工作开始前拆成具有独立标准、提交和责任的子工作项；父工作项不能因部分子项通过而进入 `accepted`。

`pass` 和 `return` 是可以进入有效验收结果的总体结论；`in_review` 和 `stale` 只是验收轮次状态，不能保存为有效验收结果，也不能产生状态效果。

每次保存部分或完整核对都必须携带 `base_review_revision_id` 和 `expected_round_revision`。服务端锁定验收轮次后，只有基线仍等于 `current_review_revision_id` 时，才新增核对修订、原子切换当前核对指针并递增轮次修订；基线不匹配时返回 `409 ACCEPTANCE_REVIEW_CHANGED`，不能形成第二条并行“当前”分支。候选记录和有效结果只能引用锁内仍为当前的完整核对修订。初次启用不支持多人并行修改同一核对分支；D-06D 如需跨组织并行复核，必须使用彼此独立的复核单元和显式汇总修订，不能按最后保存时间选择任一分支。

##### 有效结果和工作项状态

| 情形 | 只追加记录 | 工作项状态效果 |
|---|---|---|
| 纬理保存部分核对 | 新增不可变 `work_item_acceptance_review_revision` | 保持 `submitted_for_acceptance` |
| 纬理在 `record_only` 下提交完整核对 | 新增 `work_item_acceptance_record` 和 `acceptance_recorded` 事件；不建立 `work_item_acceptance_result` | 保持 `submitted_for_acceptance`；业务结果责任主体产生采用或独立核对待办 |
| 当前占用验收槽位的业务结果责任主体或有效直接验收主体精确采用候选 `pass` 记录 | 采用处置、有效结果、状态效果、`acceptance_record_adopted` 事件和 outbox 同事务提交 | 原子进入 `accepted` |
| 当前占用验收槽位的业务结果责任主体或有效直接验收主体精确采用候选 `return` 记录 | 采用处置、有效结果、状态效果、`acceptance_record_adopted`、`returned` 事件和 outbox 同事务提交 | 原子回到 `in_progress`；期限不自动改变 |
| 当前占用验收槽位的业务结果责任主体或有效直接验收主体直接形成 `pass` 或 `return` | 直接核对修订、有效结果、状态效果、工作项事件和 outbox 同事务提交 | 按系统计算结果原子进入 `accepted` 或回到 `in_progress`；期限不自动改变 |
| 获得有效 `delegated_state_transition` 的纬理提交 `pass` | 有效结果、状态效果、工作项事件和 outbox 同事务提交 | 原子进入 `accepted` |
| 获得有效 `delegated_state_transition` 的纬理提交 `return` | 有效结果、状态效果、`returned` 事件和 outbox 同事务提交 | 原子回到 `in_progress`；期限不自动改变 |
| 纬理代录具名业务主体已经形成的决定 | 新增类型为 `named_decision_transcription` 的候选记录，分别保存声明的决定人和实际录入人；不建立有效结果 | 保持 `submitted_for_acceptance`；具名决定人本人必须登录并精确确认冻结内容，或者业务结果责任主体另行采用；纬理代录请求本身不得改变状态 |
| 业务结果责任主体不采用候选记录 | 新增不采用处置和 `acceptance_record_not_adopted` 事件并保存依据；候选记录保持不变 | 保持 `submitted_for_acceptance`；业务结果责任主体继续独立核对或另行作出受控退回决定 |
| 办理人撤回提交 | 当前轮次进入 `stale`，记录 `submission_withdrawn` 和前后摘要；不建立有效结果 | 尚无有效结果且服务端权限、工作项修订和轮次修订校验通过时，原子回到 `in_progress` 并建立新办理参与周期；期限不自动改变 |
| 成果或影响基线被有权事务判定失效 | 当前轮次进入 `stale`，记录 `acceptance_context_invalidated`、触发来源和前后摘要；不建立有效结果 | 方案、下游影响上下文、证据检查结果或仍允许继续办理的目标对象当前版本发生变化时，尚无有效结果的工作项原子回到 `in_progress` 并要求新提交；期限不自动改变 |
| 验收授权变化 | 当前轮次进入 `stale`，保存变化原因和前后摘要 | 仅验收责任槽位、策略或授权变化且成果基线未变时，保持 `submitted_for_acceptance` 并打开转派或授权处置待办；不得沿用旧轮次 |
| 目标对象已取消或不再允许继续 | 当前轮次进入 `stale`，保存领域状态和依据 | 不产生通过或退回决定；按领域规则进入 `blocked` 或受控取消路径 |

当前占用验收槽位的业务结果责任主体或有效直接验收主体采用 `record_only` 候选记录时只能精确采用该记录，不能在采用事务中手工改变逐项结论。需要改变逐项结论时，该有权主体必须先形成新的直接验收核对修订，再以该修订建立本轮唯一有效结果；原候选记录仍保留，并追加不采用处置。具名决定人本人登录确认时，确认请求必须精确绑定工作项、验收轮次、提交修订及摘要、方案和标准摘要、逐项结果集、总体结果、决定时间和授权依据，并针对本人重新执行 D-06B 职责分离判断。初次启用不把签名图片、姓名选择、普通邮件、聊天记录或纬理代录当作可靠身份认证；未来如需核验离线决定，必须另行设计可靠身份认证和独立核验事务，不得复用代录请求直接产生状态效果。

任一有效验收结果建立后，验收轮次立即进入终结状态；本轮尚未处置的其他候选记录在查询投影中显示为“因轮次已决定而失效”，但原记录不修改。任何人不得再采用这些候选记录；后续请求统一返回 `409 ACCEPTANCE_ALREADY_DECIDED`。

`accepted` 只表示当前工作项验收门槛已经满足。工作项只有在关联领域动作成功、对应领域动作门槛在锁内核对通过，并保存不可变领域结果引用后，才能按现有 `accepted → closed` 规则关闭。验收通过不得自动解释为流程、数据模型、组织、员工、权限或任命已经审核、批准、发布或生效。

关闭、发布、合并、生效和其他会消费验收结果的领域动作请求，必须携带目标工作项或领域对象修订、`action_gate_context_id`、`expected_action_gate_revision`、门槛摘要，以及全部 `active` 和 `pending_revalidation` 关系当前修订。服务端按本节固定顺序锁定目标及所引用来源工作项、下游影响上下文、领域动作门槛当前头和关系修订，并在锁内重算门槛。只要存在 `pending_revalidation`、未知关系、未满足的 `active` 门槛、来源结果不再匹配或上下文修订变化，领域动作和 `accepted → closed` 都整笔拒绝，工作项保持 `accepted`。`pending_revalidation → active`、`pending_revalidation → retired` 与对应领域动作使用同一门槛当前头锁序或等价比较并交换；验收 outbox 只能通知执行方重新核对，不能作为跳过门槛检查的授权凭据。

##### 并发、幂等和失败处理

正式验收或采用结果的请求至少携带以下冻结上下文：

- `work_item_id` 和 `expected_work_item_revision`；
- `acceptance_slot_id`、`expected_slot_revision`、预期具名验收人、`decision_authority_ref`、允许结果和有效期；
- `acceptance_plan_revision_id` 和 `criteria_digest`；
- `downstream_context_id`、`expected_downstream_context_revision` 和当前传递闭包摘要；
- `submission_revision_id`、`submission_digest`、`evidence_manifest_digest`、各证据预期 `check_epoch` 和当前通过检查集合摘要；
- `target_object_id`、`expected_current_version_id`、目标版本摘要、预期当前指针修订、预期生命周期修订和状态、允许验收守卫摘要；
- `acceptance_round_id`、`expected_round_revision`、`base_review_revision_id`、预期当前核对修订和逐项结果集摘要；采用候选记录时还包括 `acceptance_record_id` 和候选记录摘要；
- `participant_revision`、`participant_set_digest`、`policy_revision_id` 和策略摘要；
- 适用时的场景任命修订、场景任命 `expected_authorization_epoch`、精确验收委托修订和委托 `expected_delegation_epoch`；
- `idempotency_key` 和 `request_digest`。

服务端不接受客户端把旧请求中的版本号替换为当前值后继续提交。服务端必须重新读取全部冻结对象，并按以下固定顺序加锁：

1. 按标识排序的全部场景任命、精确验收委托、相应修订和开放停止条件；
2. 非场景任命验收主体使用的直接业务责任依据；
3. 按标识排序的全部受影响 `governance_work_item`；正式验收通常只有当前工作项，关系或类型变化事务使用上文重新核对后的完整受影响集合；
4. 按工作项和槽位标识排序的 `handling` 和 `acceptance` 责任槽位；
5. 目标对象稳定身份、当前版本指针、当前版本和生命周期守卫；
6. 按标识排序的下游影响上下文当前头、领域动作门槛当前头和状态效果关系当前修订；
7. 当前提交修订、验收方案修订和标准集合；
8. 证据清单及检查记录、参与者快照和职责分离策略；
9. 验收轮次、当前核对修订、候选记录、候选记录处置、有效结果和状态效果；
10. 工作项事件和 outbox。

服务端在锁内重新核对当前状态、决定主体、对象和动作范围、D-06B 职责分离结果，重算当前父子、汇总、依赖、关闭门槛和自动动作的传递闭包，再核对下游影响上下文当前修订及摘要、目标对象当前版本指针、生命周期状态和允许验收守卫、全部其他修订和摘要、证据可用状态、场景任命、场景任命授权版本、精确验收委托及其授权版本、幂等键和请求摘要。`record_only` 请求只写候选记录；有权采用、直接决定或有效受托决定全部通过后，系统才写有效结果和状态效果。

`acceptance_required=false` 的客观直接关闭请求也必须携带并锁定工作类型策略修订、下游影响上下文当前修订及摘要和工作项修订。服务端在锁内重算传递闭包；只要出现任何下游状态效果、关系未知或修订变化，就拒绝直接关闭，不得把旧的 `false` 投影继续当作有效依据。

普通 `accepted → closed` 请求必须执行上文领域动作门槛核对，不能因为工作项已经通过验收而跳过 `pending_revalidation`、未知关系和活动门槛。关系激活或退役与关闭并发时，门槛当前头比较只允许一个事务基于同一修订成功；另一事务重新读取后再决定，不能按旧关系列表继续关闭。

改变目标对象当前版本指针、发布新版本、替换、取消、终止或改变“允许验收”状态的事务，必须使用相同的目标对象锁顺序，或者对同一当前指针修订和生命周期修订执行等价的比较并交换。目标变化事务先提交时，验收请求返回 `409 ACCEPTANCE_CONTEXT_CHANGED`，使轮次进入 `stale`，再按目标是否允许继续办理进入 `in_progress`、`blocked` 或受控取消路径；验收事务先提交时，本次结果按当时冻结状态有效，后续目标变化通过新事件和相应处置事项处理，不反向改写历史验收。

并发和重复请求按以下规则处理：

- 相同幂等键和相同请求摘要返回原结果，不重复生成核对修订、候选记录、有效结果、状态效果或 outbox；
- 相同幂等键但请求摘要不同，返回 `409 IDEMPOTENCY_KEY_REUSED`；
- 不同幂等键再次决定已经终结的验收轮次，返回 `409 ACCEPTANCE_ALREADY_DECIDED`；
- 任一修订、摘要、人员、策略、下游影响上下文、证据、目标对象、责任槽位或授权版本变化，返回 `409 ACCEPTANCE_CONTEXT_CHANGED`；
- 核对保存请求的 `base_review_revision_id` 不再是当前指针，返回 `409 ACCEPTANCE_REVIEW_CHANGED`；旧核对分支不能建立候选记录或有效结果；
- 两个相反验收决定并发时，每轮唯一有效结果和工作项修订比较只允许一个成功，另一个返回冲突；候选记录之间不能自行争夺状态效果；
- 任命停止事务先提交时，旧验收请求因任命状态或授权版本变化失败；验收事务先按完整冻结上下文提交时，历史结果保持有效，后续任命停止不追溯改写已经有权形成的结果；
- 数据库事务中不得等待文件上传、安全扫描或外部系统响应。正式验收只能引用已经完成完整性和安全检查的不可变证据；
- 任何失败事务均不写部分逐项结果、候选记录、有效结果、状态效果、工作项事件或 outbox。验收草稿只能通过独立的草稿保存请求形成不可变核对修订。

D-06C 的启用前验证至少覆盖：尝试把结果型或影响下游的事项改成 `acceptance_required=false`；客观直接关闭与新增下游门槛并发；提交后新增父项、汇总、依赖、关闭门槛或自动发布动作；关系闭包未知；新增循环状态依赖；已经通过后新增下游门槛，或者提高既有下游工作项类型、动作或风险等级，并尝试直接消费旧结果；父项或领域对象关闭与 `pending_revalidation` 关系激活、退役或并发新增；关闭请求漏传待重新核验关系；工作开始前无验收方案；并发建立或确认方案候选；模板参数缺失或越界；空标准和主观标准；工作开始后改标准；`accepted` 或 `closed` 后试图改写标准；提交后改成果、证据、参与者或目标对象；可变链接和安全检查未完成证据；缺少必需证据；非法 `not_applicable`；部分核对和提前退回；部分通过或有条件通过；多个候选记录；采用与不采用并发；直接决定与采用候选记录并发；具名决定人与录入人不一致、具名决定人没有本人登录确认，以及签名图片、普通邮件或聊天记录冒充正式确认；缺少精确委托、委托范围不匹配、委托撤回或委托授权版本变化；受托通过和退回；`accepted` 与领域关闭分离；同一幂等键重试及异载荷复用；双人相反并发；任命停止、策略失效、责任槽位转派、证据变化和目标版本变化与验收并发；旧页面提交。所有禁止、陈旧或失败路径均不得形成 `accepted`、有效退回、关闭、发布或其他下游状态效果。

上述内容目前是 D-06C 待确认设计。当前仓库尚无这些统一验收实体、接口或自动化测试；现有 V7 修订号和内容摘要机制只能作为实现模式证据，不能替代 D-06C 的实现、迁移和业务验收。

| 组织与员工治理 | 组织、岗位、人员、任职和工作角色的起草、审核、发布 | 行政人事部和有权批准主体 |

| 发布与追溯 | 不可变版本、发布门槛、影响确认、审计和恢复 | 各发布主体、管理员只读监督 |

### 7.2 从导入结束开始的治理主线

建议把“正式治理起点”定义为受控导入事务成功提交，而不是用户只完成本地选择或预览。

要求：

- 导入阶段以 import_revision_id 标记数据出现项。流程发布后，再通过不可变 promotion 记录把该导入修订绑定到 process_version_id；
- 正式数据模型只能使用已经绑定有效 process_version_id 的出现项。流程发布前的出现项、匹配建议和核对记录不能冒充正式数据模型事实；
- 相同来源版本和内容摘要使用幂等键返回原治理案例和导入修订，只增加受控导入尝试记录，不重复创建出现项或派发工作项；

- 管理员从 import_committed 起能在全局治理队列中看到全部开放、完成、退回、取消、升级和重新打开的工作项；
- 管理员的 can_act 始终为 false，不因为全局可见而取得业务办理权。

### 7.3 统一治理案例和工作项

建议增加统一治理案例和工作项层，但不复制领域事实。

| 逻辑实体 | 保存内容 | 不保存内容 |
|---|---|---|
| governance_case | 治理案例编号、来源、领域、归口、当前阶段和整体状态 | 具体流程、字段或组织事实 |
| governance_work_item | 谁在何时针对哪个对象完成什么协同动作、状态、期限和验收条件 | 领域对象的审核结论或冲突决定原文副本 |
| work_item_responsibility_slot | 工作项当前办理或验收责任槽位；`slot_type` 取 `handling` 或 `acceptance`，并保存具名责任人员、责任角色、组织范围、当前场景任命及修订、授权版本和槽位修订；验收槽位另存 `decision_authority_ref`、允许结果和有效期 | 不复制任命内容、领域审核结论或历史事件；岗位、角色或姓名文本不能替代具名当前责任人员 |
| work_item_dependency | 稳定关系身份、不可变关系修订、`pending_revalidation`、`active`、`retired` 等受控状态、前后顺序、阻塞、父子、汇总、关闭门槛和自动动作关系，以及当前修订指针和激活依据 | 未经版本化的自由文本关系；正式业务流程关系仍由领域流程真源保存 |
| work_item_downstream_context | 工作项当前下游影响修订、传递闭包摘要和风险投影 | 第二份关系真源或可由页面直接修改的风险标签 |
| work_item_action_gate_context | 关闭、发布、合并、生效等领域动作的当前门槛修订、活动关系、待重新核验关系和摘要 | 第二份领域结果真源或可以忽略待重新核验关系的页面投影 |
| work_item_event | 分派、开始、提交、退回、验收、关闭、重开等只追加事件 | 可被覆盖的当前历史 |
| governance_activity_read_model | 管理员和 PMO 的跨领域只读查询投影 | 新的业务真源 |

统一工作项至少包含：

- work_item_id、governance_case_id 和 source_event_id；
- domain 和 work_type；
- 目标对象类型、目标对象稳定标识和目标版本；
- import_revision_id，以及发布后绑定的 process_version_id；业务行为相关事项同时保存 behavior_ref；
- data_object_id、data_field_id 或数据出现项标识，适用于数据事项；
- 办理和验收责任分别进入 `work_item_responsibility_slot`；主记录中的责任人、责任角色、责任部门和责任办公室只作当前查询投影，不作为第二份可独立修改的责任真源；
- 创建或首次分派时冻结且不可修改的 `origin_scenario_assignment_id` 和 `origin_scenario_assignment_revision_id`，适用于纬理场景；
- `handling` 槽位和 `acceptance` 槽位分别保存自己的 `current_scenario_assignment_id`、`current_scenario_assignment_revision_id` 和 `current_authorization_epoch`；这些引用只能在对应的受控转派事务中连同工作项和槽位 `expected_revision` 一起更新，不依赖场景任命的责任主体可以使用空任命引用；
- `acceptance_required`、当前已确认验收方案修订、当前提交修订和当前验收轮次的只读投影；验收标准、提交成果和证据分别以 D-06C 的不可变实体为真源，不在工作项主记录中保存第二份可修改副本；
- 当前下游影响上下文修订和摘要的只读投影；父子、汇总、依赖、关闭门槛和自动动作关系变化时，必须按 D-06C 原子更新当前头，不能直接覆盖该投影；
- status、priority、due_at 和 blocking_reason；
- visibility_scope 和 action_scope；
- expected_revision、idempotency_key 和内容摘要；
- parent_work_item_id 或依赖关系；
- 创建、分派、提交、验收、关闭和重开的完整事件。

纬理后续办理或验收工作项时，服务端读取相应责任槽位，校验该槽位的当前场景任命、修订和授权版本，并在本次工作项事件中保存实际通过校验的 `slot_id`、`scenario_assignment_id`、`scenario_assignment_revision_id` 和 `authorization_epoch`。`origin_*` 字段和历史事件不得通过责任槽位当前引用或 `scenario_assignment` 的当前修订指针改写，也不得用当前授权范围解释历史动作。

工作项主状态建议：

    generated
      -> planned
      -> assigned
      -> in_progress
      -> submitted_for_acceptance
      -> accepted
      -> closed

允许的受控分支：

- blocked 保持为状态，问题分析保存为 analysis_recorded 事件；处理后回到 in_progress，重新分派后回到 assigned；
- submitted_for_acceptance 退回时保存 returned 事件并回到 in_progress；
- `submitted_for_acceptance` 尚无有效结果时，办理人可以通过受控撤回返回 `in_progress`，记录 `submission_withdrawn`；验收方案、下游影响上下文、证据检查或仍允许继续办理的目标对象当前版本被有权事务改变时，系统记录 `acceptance_context_invalidated` 并返回 `in_progress`；目标已经取消、终止或禁止继续时进入 `blocked` 或受控取消路径。上述路径都不是验收退回，不生成 `returned` 或有效验收结果；
- 需要升级的状态 → escalated → decision_pending；决定保存为 decision_recorded 事件，再按决定进入 assigned、in_progress 或 closed；
- closed 重开时保存 reopened 事件，并按责任是否变化进入 assigned 或 in_progress；
- cancelled 是受控终态，必须保存取消主体、依据和对源对象的影响。

禁止删除已经产生业务历史的工作项。

状态转换必须由服务端按“当前状态 + 办理主体 + 权限 + 场景范围 + 必需依据”校验：

| 转换 | 可以发起的主体 | 前置条件 | 必需依据或结果 |
|---|---|---|---|
| 领域事件 → generated | 领域应用服务 | 领域事务已经满足生成规则 | source_event_id、目标对象和幂等键 |
| generated → planned | 有效场景内的纬理；无计划需求时由系统跳过 | 场景任命有效，目标在范围内 | 目标、依赖、风险、顺序和验收条件建议 |
| planned / generated → assigned | 治理事项由 mdm_lead；业务场景由业务责任主体或获得派发授权的纬理 | 责任对象和可派发人员明确；需要正式验收时，业务结果责任主体已经确认非空验收方案 | 责任人、协作人、committed_due_at、分派依据和适用时的已确认验收方案修订 |
| assigned → in_progress | 被分派责任人 | 当前用户是有效办理人 | 开始事件 |
| in_progress → blocked | 办理人；有效场景内的纬理 | 存在实际阻塞 | 阻塞事实、影响、证据和所需协助 |
| blocked → blocked，记录 analysis_recorded 事件 | 办理人、有效场景内的纬理或被分派冲突处理人 | 正在分析阻塞 | 现象、原因假设、证据、影响和建议 |
| blocked → in_progress | 办理人或原分派主体 | 阻塞已经处理 | 处理结果和恢复依据 |
| assigned → assigned，记录 reassigned 事件 | 当前业务责任主体；仍具有独立有效派发权的原分派主体；有效场景内有派发权的纬理 | 责任调整已经由有权主体决定，目标责任槽位和授权依据有效 | 新责任人、旧新办理槽位、原因、决定主体、实际录入人和批准依据；期限不自动变化 |
| blocked / in_progress → assigned，记录 reassigned 事件 | 当前业务责任主体；仍具有独立有效派发权的原分派主体；有效场景内有派发权的纬理 | 责任调整获批 | 新责任人、旧新办理槽位、期限、原因、决定主体、实际录入人和批准依据 |
| in_progress → submitted_for_acceptance | 办理人 | `acceptance_required=true`，已确认验收方案和下游影响上下文未变化，成果和必需证据完整且可以冻结 | 不可变提交修订、验收轮次、结果、完成证据、下游影响上下文修订和自检结论 |
| submitted_for_acceptance → accepted | 当前占用验收槽位的业务结果责任主体或其有效直接验收主体；纬理只有在场景任命包含受托验收状态变更能力、验收方案明确采用 `delegated_state_transition` 且 D-06B 至 D-06D 全部门槛通过时 | 提交修订未变化，系统计算总体结果为 `pass`，权限、职责分离、下游影响上下文、证据和全部冻结上下文校验通过 | 逐项验收结论、有效验收结果、状态效果、决定主体、实际决定人、实际录入人和授权依据 |
| submitted_for_acceptance → submitted_for_acceptance，记录 acceptance_reassigned 事件 | 业务结果责任主体 | 原验收主体已经失效或正式调整，提交内容、验收条件和下游影响上下文未变化；旧轮次已经终结，新槽位具名人员和决定权限有效 | 旧新验收槽位修订、旧新验收主体、`decision_authority_ref`、允许结果、有效期、决定主体、实际录入人、原因和依据；针对新槽位建立新验收轮次 |
| submitted_for_acceptance → in_progress，记录 returned 事件 | 当前占用验收槽位的业务结果责任主体或其有效直接验收主体；纬理适用与通过决定相同的受托验收门槛 | 系统计算总体结果为 `return`，且权限、职责分离、下游影响上下文、证据和全部冻结上下文校验通过 | 退回项、缺口、有效验收结果、状态效果、依据、决定主体、实际决定人和实际录入人；期限不自动变化，另行调整时必须保存有权主体和依据 |
| submitted_for_acceptance → in_progress，记录 submission_withdrawn 事件 | 当前办理人 | 尚无有效验收结果，提交和轮次仍为当前修订，办理人需要修改成果、证据或参与信息 | 撤回原因、旧提交和轮次摘要、新办理参与周期；不得生成 returned 或有效验收结果，期限不自动变化 |
| submitted_for_acceptance → in_progress，记录 acceptance_context_invalidated 事件 | 系统状态机；触发变化的有权领域事务提供决定依据 | 尚无有效验收结果，验收方案、下游影响上下文、证据检查结果或仍允许继续办理的目标对象当前版本等冻结上下文已经变化 | 触发来源、变化前后修订及摘要、旧轮次和重新提交待办；不得生成 returned 或有效验收结果，期限不自动变化；目标已经取消、终止或禁止继续时改走 blocked 或受控取消路径 |
| in_progress → closed，记录 objective_completion_recorded 事件 | 系统状态机；办理人只能发起核对请求 | 版本化工作类型策略固定 `acceptance_required=false`；服务端在锁内重算的下游影响闭包仍为空且修订未变化；事项不形成业务决定、不改变领域对象；客观完成条件已经核对 | 工作类型策略修订、下游影响上下文修订及摘要、客观完成事实、实际办理人和系统核对结果；不得建立 `accepted` 或验收结果 |
| accepted → closed | 工作项责任主体或系统状态机 | 验收通过，关联领域动作已经成功；服务端锁内重算的领域动作门槛不存在 `pending_revalidation`、未知关系或未满足的 `active` 门槛，且门槛当前修订未变化 | 领域结果引用、领域动作门槛修订及摘要、全部门槛核对结果和关闭依据 |
| 任一允许状态 → escalated | 领域规则指定主体、mdm_lead 或有效场景内获授权的纬理 | 协调失败、超期或达到升级规则 | 升级原因、影响和冻结材料摘要 |
| escalated → decision_pending | decision_group 或其受控受理人员 | 决策包完整且摘要已冻结 | 受理记录、决定范围和当前摘要 |
| decision_pending → assigned / in_progress / closed，记录 decision_recorded 事件 | decision_group | 决定已经形成且摘要未变化 | 决定、依据、适用范围和后续责任 |
| closed → assigned / in_progress，记录 reopened 事件 | 原验收主体或领域有权主体 | 新证据、错误关闭或来源变化 | 重开原因、新修订、责任和影响 |
| 非终局状态 → cancelled | 原分派主体或领域有权主体 | 目标撤销、重复事项或上游正式取消 | 取消原因、上游依据和恢复影响 |

字段所有权建议：

- `handling` 责任槽位和 committed_due_at 由当前业务责任主体、仍有独立派发权的原分派主体或获得派发授权的纬理按上述状态转换确定；查询投影不得反向覆盖责任槽位；
- `acceptance` 责任槽位由业务结果责任主体确定，并以当前槽位修订中的具名 `person_id`、`decision_authority_ref`、允许结果和有效期判断当前直接验收主体。纬理可以在有效任命包含相应能力时成为验收准备人或验收记录人；纬理只有同时满足场景任命能力上限、工作项 `delegated_state_transition` 精确委托和 D-06B 至 D-06D 全部门槛时，才能成为改变状态的受托验收决定人。纬理不能自行指定、替换或继续转委托验收主体；
- 验收方案和标准由业务结果责任主体确认。纬理可以起草候选，但工作项主记录只保存当前指针的只读投影；任何正式变化均建立不可变方案修订，并按 D-06C 处理已经开始或已经提交的工作；
- blocking_reason 由办理人或纬理基于事实提交；
- PMO 只写 tracking_note、tracking_risk 和 escalation_recommendation，并可以记录已获批准的期限；不能单方面修改办理人、正式期限、业务状态或验收结论；
- 验收、关闭、取消和重开均绑定 expected_revision，旧页面不能覆盖新状态。

### 7.4 我的待办和全局治理队列

接口和页面应把以下概念分开：

- 我的待办：当前用户既可见又可以办理的工作项；
- 我的参与：当前用户负责、协作、验收或关注，但此刻不能办理的工作项；
- 全局治理队列：管理员、mdm_lead 和经授权的 PMO 按权限查看的完整队列；
- 决策队列：decision_group 只查看已升级且决策包已经冻结的事项。

查询结果至少分别返回：

- visible_items；
- actionable_items；
- total；
- summary_by_status；
- summary_by_domain；
- 分页游标；
- 每项的 can_view、can_act 和不能办理的明确原因。

全局治理队列不能使用固定 20 条截断来代表“全部”。摘要使用数据库聚合，明细使用稳定排序和游标分页。

### 7.5 组织和员工主数据业务流程

组织、员工、岗位、任职和工作角色分别建立可审计变更集：

    起草变更集
      |
      v
    结构检查和影响计算
      |
      v
    受影响部门或人员核对
      |
      v
    行政人事复核
      |
      v
    有权主体批准
      |
      v
    定时或立即生效
      |
      +--> 发布不可变版本
      +--> 生成账号、角色、场景任命和未完成工作项的影响清单

高影响变更至少包括：

- 人员离职或停职；
- 部门撤销、合并或负责人变化；
- 办公室跨部门调整；
- 主岗或归属部门变化；
- 正式工作角色职责、适用范围或状态变化；名称变化必须检查流程绑定、岗位映射和历史显示，但不得据此自动重授或撤销系统权限；
- 与未完成治理工作项、冲突或版本发布有关的人员变化。

高影响变更必须由起草人之外的复核人处理。具体批准主体仍待行政人事部确认。

员工表格编辑只改变当前草稿修订。提交审核时锁定行集合、修订号和内容摘要；审核、批准和发布任一阶段发现草稿变化，都必须退回最新修订重新核对。发布事务同时生成不可变员工主数据版本、字段级差异、影响清单和审计事件。查看历史版本、比较任意两个版本和以历史版本为依据建立纠正草稿，不等于把数据库直接回滚到旧状态。

### 7.6 冲突和精确变更对比

每个进入协调或决定阶段的冲突必须形成冻结决策包。决策包至少包括：

- 冲突编号、类型、打开原因、打开时间和当前修订；
- 目标身份类型、目标身份和目标内容摘要：发布前流程冲突绑定不可变 import_revision_id，发布后流程冲突绑定 process_version_id；发布前数据冲突绑定不可变 data_model_draft_revision_id 及出现项集合摘要，发布后数据冲突绑定 data_model_version_id；组织冲突绑定组织版本或不可变组织变更修订；
- 双方对象稳定标识；
- 双方部门、办公室、责任人和提交人快照；
- 双方完整定义、约束、来源主张、使用场景和证据；
- 每个冲突字段的 A/B 值；
- 受影响流程、业务行为、数据对象、字段、表单、上下游部门和工作项；
- 协调方案、双方确认、反对理由；
- 提交决定时的修订号和内容摘要；
- 决定、依据、适用范围和后续责任。

任何决定都必须绑定被冻结的目标身份、冲突修订号和内容摘要。三者中任一项与提交时的当前值不一致，旧页面提交应返回版本冲突，要求用户重新打开最新决策包。正式发布后，系统通过只追加的 promotion 记录把原 import_revision_id 关联到 process_version_id，或把原 data_model_draft_revision_id 关联到 data_model_version_id；promotion 不得改写原冻结决策包的目标身份、摘要、双方材料或决定依据。

流程和数据的语义差异不能只比较名称。每条差异至少包含：

    对象类型
    + 稳定标识
    + 字段路径
    + 变更类型
    + 旧值
    + 新值
    + 来源版本
    + 目标修订
    + 影响说明
    + 证据
    + 是否需要重新确认

语义差异至少覆盖：

- 流程基本信息；
- A1 业务行为的新增、删除、修改和重排；
- 执行部门、办公室、岗位和工作角色；
- 触发条件、完成标准和异常处理；
- 普通关系、判断分支、循环、并行和跨部门承接；
- 数据对象、字段和产生、使用、更新关系；
- 表单、主表、明细表和字段引用；
- 生命周期、责任和来源主张；
- 变更理由、证据和受影响范围。

查看边界：

- 管理员和 PMO 全量只读，但员工敏感字段脱敏；
- decision_group 只查看已升级事项的冻结决策包；
- 受影响部门只查看与本部门责任有关的内容；
- 纬理只查看有效场景任命范围内的内容。

| 结构准入检查 | mdm_lead | mdm_lead 只对结构和准入规则负责 | 导入者、归口部门审核员 | 管理员、PMO |
| 治理案例和首批工作项建立 | 系统事务 | 3000 系统责任人对生成规则负责，待确认 | mdm_lead、归口部门 | 管理员、PMO |
| 部门业务事实确认 | department_mdm_reviewer 记录决定 | 该部门最终负责人 | department_contact、业务人员 | mdm_lead、管理员、PMO |
| 前期规划和计划编排 | 纬理 | 任命范围对应的业务责任主体，按已发布责任记录解析并冻结 | MDM 工作组、相关部门 | PMO、管理员 |

## 8. 数据架构设计

### 8.1 数据治理对象分层

目标数据架构必须把来源、出现项、企业身份、关系和发布模型分开：

    来源材料和导入批次
             |
             v
    不可变导入修订 import_revision_id
             |
             v
    待审核数据对象、字段和关系出现项
             |
             +--> 待核对匹配建议
             |
             v
    流程发布 promotion
      import_revision_id -> process_version_id
             |
             v
    企业数据对象 / 企业字段身份
             |
             +--> 数据关系、责任、来源和使用场景
             |
             v
    已发布数据模型版本

| 层次 | 作用 | 主要身份 |
|---|---|---|
| 来源层 | 保存来源材料、导入尝试、不可变导入修订、摘要、导入者和当时部门快照 | source_artifact_id、import_attempt_id、import_revision_id |
| 流程版本层 | 保存 3000 中不可变的流程治理版本和导入修订提升关系 | process_version_id、promotion_id |
| 出现项层 | 标记每个不可变导入修订中实际出现的数据对象、字段、表单使用关系和来源关系 | object_occurrence_id、field_occurrence_id、relation_occurrence_id |
| 企业身份层 | 保存经过核对的企业数据对象和字段稳定身份 | enterprise_object_id、enterprise_field_id |
| 关系层 | 保存出现项与企业身份、对象与对象、字段与字段之间的受控关系 | relation_id |
| 治理请求层 | 保存纠正、关联、合并、拆分和责任确认请求 | data_request_id |
| 发布层 | 保存经过核对的数据模型快照和版本 | data_model_version_id |
| 证据审计层 | 保存判断依据、操作主体、时间、修订和结果 | evidence_ref、event_id |

### 8.2 “标记每一个数据”的准确含义

3000 应为每个不可变导入修订中的数据对象、字段和关系出现项生成稳定技术标识，并保存：

- 来源 import_revision_id、导入修订摘要，以及发布后绑定的 process_version_id；
- 3001 中的局部引用或 JSON 路径；
- 对象或字段名称、定义、类型和约束快照；
- 当前出现项规范化后的 occurrence_digest、摘要算法版本和上一次已核对摘要；
- 所属流程、A1 业务行为、表单和使用方式；
- 导入者、导入时部门和归口依据；
- 当前治理状态；
- 关联的企业数据身份，未确认时为空；
- 与上一流程版本出现项的沿革关系；
- 证据、确认人、确认时间和修订。

“每一个数据”在本轮范围内指结构化定义中的数据对象、字段及其使用或来源关系，不指各业务系统中的每一条业务记录值。表单项如果已经通过 data_field_ref 引用字段，不再重复创建企业字段，只保存表单使用关系。

### 8.3 稳定身份规则

1. 3001 提供的局部引用只在该流程版本和其受控沿革中有意义。
2. 每个不可变导入修订中的每个局部引用只创建一个出现项。重复提交相同内容只返回原结果或新增导入尝试记录，不创建重复出现项。
3. 企业数据身份由人工核对后建立。名称、定义、字段集合、标识规则、责任、生命周期和使用场景只能作为匹配证据。
4. 同名数据可以是不同企业对象；不同名称也可以指向同一企业对象。
5. 新导入修订保留新的出现项，并通过多对多 occurrence_lineage_edge 连接旧修订。沿革类型至少包括 unchanged、revised、split_from、merged_from 和 superseded，并记录来源修订、目标修订、摘要、依据和确认人。predecessor_occurrence_id 只能作为一对一查询优化，不能作为正式沿革真源。
6. 已发布企业身份不能物理删除。错误身份通过 retired、redirect、split 或新版本恢复。
7. 对外稳定身份使用应用生成、不可从名称反推的编号。可在技术规格中从 UUIDv7 或 ULID 中选择；内容摘要只用于完整性和变化检测。
8. V3 缺少明确数据对象时，只建立表单字段出现项和待补关联问题，不根据字段名称擅自创建企业数据对象。
9. 只有局部引用、occurrence_digest 和摘要算法版本都满足沿用规则时，系统才可以延续原绑定；否则状态转为 needs_recheck。

建议分别设置唯一约束：

- 对象出现项：import_revision_id + data_ref；
- 字段出现项：object_occurrence_id + field_ref；
- 使用关系和来源关系出现项：import_revision_id + link_ref 或 source_ref；
- promotion：一个 import_revision_id 在一个正式发布分支中只能绑定一个 process_version_id。

每个出现项必须有明确的身份处理状态：

- unmatched：尚未发现可能的企业身份；
- suggested：系统提出待核对匹配建议；
- confirmed：有权人员已经确认；
- rejected：已经确认不是建议的企业身份；
- needs_recheck：来源摘要或关键依据变化，需要重新核对。

允许“出现项已经标记、企业身份仍待定”，不允许为了提高关联率而自动合并。

### 8.4 目标逻辑实体

以下名称用于说明结构，最终物理表名应在技术规格中冻结：

| 逻辑实体 | 关键字段或关系 |
|---|---|
| data_source_artifact | 来源类型、来源名称、内容摘要、结构版本和保留策略 |
| data_import_attempt | 每次调用的导入人、导入部门快照、幂等键、结果和失败原因 |
| data_import_revision | 去重后的不可变内容、结构版本、内容摘要和来源材料 |
| process_version_promotion | 导入修订与正式 process_version_id 的不可变绑定 |
| data_object_occurrence | 导入修订、局部引用、JSON 路径、局部摘要、对象快照和治理状态 |
| data_field_occurrence | 对象出现项、局部引用、字段快照、表单使用和沿革 |
| data_relation_occurrence | 导入修订、局部关系引用、端点类型、业务行为、关系快照和摘要 |
| form_item_occurrence | 导入修订、form_ref、item_ref、表单位置、使用方式、来源关系、JSON 路径和摘要 |
| form_field_usage_occurrence | 表单项出现项与字段出现项或待解析字段之间的使用关系 |
| occurrence_lineage_edge | 前序和后序出现项、多对多沿革类型、版本、摘要、依据和确认 |
| enterprise_data_object | 企业对象稳定编号、名称、定义、状态和当前发布版本 |
| enterprise_data_field | 企业字段稳定编号、所属企业对象、定义、类型和关键性 |
| data_identity_link | 出现项与企业身份的关联、状态、置信证据和核对记录 |
| data_relationship | 来源、目标、关系类型、方向、基数、证据、状态和有效版本 |
| data_responsibility | 归口组织单元、根部门、维护组织、目标工作角色、办理人快照、权威来源主张和有效期 |
| data_governance_request | correction、link、unlink、merge、split、responsibility_change 等请求及其工作项 |
| data_request_party | 每个受影响组织、责任角色、办理状态和当前冻结摘要 |
| data_request_party_decision | 实际确认人、决定、依据、时间和所确认的冻结摘要 |
| data_identity_operation | 纠正、关联、撤销关联、合并、拆分和归口调整的前后身份、影响、执行版本及补偿关系 |
| data_identity_alias | 旧身份到当前身份的可追溯重定向 |

| data_model_version_promotion | 数据模型草稿修订与正式 data_model_version_id 的只追加绑定 |
| data_model_version | 发布范围、对象、字段、关系、责任快照和发布依据 |

data_relation_occurrence 的来源端点和目标端点不能都强制引用本地出现项。端点状态至少支持：已绑定本地出现项、已绑定企业数据身份、只有外部来源描述、待跨 JSON 解析、已确认无法关联。这样才能保存对方流程尚未导入时的外部部门、外流程、外部数据名称或外部系统事实。

字段出现项只能绑定到其已确认企业对象下的企业字段。对象身份发生改变、合并或拆分时，受影响字段绑定必须转为 needs_recheck。

### 8.5 数据关系

首批关系类型应受控，不允许用户自由填写无法计算影响的关系名。建议至少包括：

- contains：对象包含字段或明细对象；
- produces：流程或业务行为产生数据；
- consumes：流程或业务行为使用数据；
- updates：流程或业务行为更新数据；
- references：字段或对象引用另一个对象；
- derives_from：数据由另一个数据推导；
- transforms_to：经过规则转换为另一个数据；
- equivalent_to：经过核对的等价关系；
- synchronized_with：两个受控对象之间存在同步关系；
- owned_by、maintained_by：责任关系。

每条关系必须记录来源对象、目标对象、方向、基数、适用范围、来源版本、证据、状态、确认主体和生效版本。自动发现只能产生 proposed 状态。

### 8.6 跨 JSON 匹配

匹配引擎可以使用：

- 名称和别名；
- 业务定义；
- 业务标识规则；
- 字段集合和关键字段；
- 数据类型、约束和生命周期；
- 归口部门、维护部门和权威来源主张；
- 产生、使用和更新场景；
- 表单位置和证据；
- 已核对的历史沿革。

匹配结果必须输出可解释证据和不确定性，不得直接更新企业身份：

    未关联出现项
      |
      v
    生成匹配建议
      |
      +--> 提出新建企业身份建议
      +--> 提出关联既有身份建议
      +--> 保持未定
      +--> 发起拆分请求
      |
      v
    归口部门业务对接人核对
      |
      v
    MDM 工作组复核
      |
      v
    执行正式身份操作
      |
      v
    进入数据模型发布版本

### 8.7 业务归口和业务对接人

归口路由建议按以下顺序判断：

1. 已经发布且适用于该对象的明确业务归口部门；
2. 已经确认且仍有效的数据责任记录；
3. 导入者所在部门快照，作为待核对默认值；
4. 流程责任部门或当前流程归口部门，只作为归口建议依据；
5. 无法判断时进入 MDM 工作组分诊队列。

导入者所在部门不能自动成为永久权威部门。系统必须保存 ownership_basis，明确本次归口是“已发布责任”“已确认数据责任”“导入部门默认”“流程责任建议”还是“人工分派”。

归口至少分开保存：

- origin_import_department_id：导入时人员所属部门，不可修改；
- proposed_owner_org_unit_id：当前待核对归口；
- confirmed_owner_org_unit_id：已经发布的归口；
- root_department_id：服务端权限范围解析结果；
- ownership_basis：本次归口所依据的事实或建议。

未来办公室进入组织模型后，责任记录使用稳定 org_unit_id，并同时保存根部门、目标工作角色和办理时人员快照。归口调整作为 responsibility_change 治理请求处理，不直接覆盖原归口历史。

首期建议复用 department_contact 作为 3000 中的办理角色，同时在企业架构中建立独立的“业务对接人”正式工作角色。两者不能自动互推：行政人事或业务部门确认正式工作角色，管理员依据授权文件配置 3000 RBAC 角色。

### 8.8 纠正、关联、合并和拆分

每个数据治理请求必须先区分性质：

- 要求：根据已经发布的结构规则、质量门槛或有权决定，责任部门必须处理；系统明确是否阻断发布和完成期限；
- 建议：MDM 工作组提出的改进方向；责任部门可以不采纳，但必须记录理由和依据；
- 待核对匹配：系统根据名称、结构和场景发现的关联线索；任何人核对前都不能形成正式关联。

请求统一绑定治理案例、目标对象、出现项、import_revision_id 或 process_version_id、data_model_draft_revision_id 或当前 data_model_version_id、发起主体、目标组织、目标角色、结构化建议、证据、expected_revision 和幂等键。尚未发布的请求不得用空的正式版本号代替草稿修订身份。

目标协同链如下：

    MDM 工作组或数据质量审计人发起请求
      |
      v
    目标组织的 department_contact 组织核对和整改
      |
      v
    department_mdm_reviewer 记录有权主体的部门确认
      |
      +--> 多部门事项：各部门分别确认
      |
      +--> 无法一致：data_conflict_handler 协调
      |
      +--> 重大争议：decision_group 决定
      |
      v
    MDM 工作组检查结构、证据和责任链
      |
      v
    mdm_lead 发布新的数据模型版本

MDM 工作组检查结构和发布条件，不代替业务部门判断数据含义、责任或权威来源。待办完成状态由治理案例和新版本结果投影产生，不能通过手工勾选替代正式处理结果。

请求主状态建议为：

    draft
      -> opened
      -> routed
      -> department_responded
      -> party_confirmation_pending
      -> party_confirmation_complete
      -> mdm_reviewed
      -> adopted_in_version
      -> closed

允许的分支包括 returned、rejected、disputed、escalated、cancelled 和 reopened。建议被拒绝时必须记录理由；要求被拒绝或逾期时按规则进入协调或升级。任何状态变化都产生只追加事件，并使对应工作项同步变化。

每个受影响组织必须对同一个冻结摘要独立作出决定。请求总状态由 data_request_party_decision 计算，不能由一个人员填写的“部门已确认”总状态代替。请求修订变化后，尚未作出的决定转到新修订；已经作出的旧决定保留但不能自动沿用。

#### 纠正 correction

纠正分成两条路径：

- 流程或表单事实错误：请求绑定出现项、导入修订、流程版本、来源位置、问题和证据；业务部门修改制度、表单源文件或当前草稿后重新导入，并通过新流程版本生效；
- 企业身份、责任、关系或治理结论错误：请求绑定当前企业身份和数据模型版本，通过新的 data_identity_operation 和数据模型版本纠正，不反向改写流程事实。

两条路径都不得原地覆盖已发布版本，并且都要保留原错误、纠正依据、受影响对象、处理人、核对人和新旧版本关系。

#### 关联 link

- 用于确认某个出现项属于既有企业对象或字段；
- 关联不删除出现项，出现项仍保留来源和流程上下文；
- 关联必须保存依据、确认主体和适用版本；
- 跨部门或低置信度关联应由双方业务对接人核对；
- 关联错误可以通过新修订撤销，不改写历史发布版本。

#### 合并 merge

- 用于确认两个已经建立的企业身份实际表示同一对象；
- 合并前生成影响清单，包括流程、业务行为、字段、关系、表单、责任、冲突和未完成工作项；
- 跨部门合并至少需要双方归口部门确认和 MDM 工作组复核；
- 合并保留一个目标身份，来源身份进入 redirected 或 retired，并保存别名和重定向；
- 不物理删除来源身份、关系或历史版本；
- 合并后发布新的数据模型版本，旧流程版本仍能解析到当时身份和当前重定向。

#### 拆分 split

- 用于恢复错误合并，或把一个过宽企业身份分为多个对象；
- 拆分必须逐个重新分配出现项、字段、关系和责任；
- 拆分前后均生成影响清单和可逆映射；
- 跨部门拆分需要受影响部门核对；
- 拆分通过新数据模型版本生效，不改写历史版本。

### 8.9 数据模型发布

数据模型进入发布前必须满足：

- 纳入范围内的所有对象、字段、表单使用和来源关系出现项都有身份处理结论；
- 关键字段、归口、维护责任和权威来源主张已经核对；
- 跨部门关系和多方请求由所有受影响组织分别确认；
- 不存在开放的阻断、退回、争议或升级未决事项；
- 非阻断例外已经记录批准主体、适用范围、依据和失效条件；
- MDM 工作组完成结构、证据和责任链复核；
- mdm_lead 绑定固定待发布快照、修订号和内容摘要执行原子发布。

数据模型发布版本至少冻结：

- 企业数据对象和字段；
- 对象和字段关系；
- 流程、业务行为和表单中的使用关系；
- 归口、维护、责任和权威来源主张；
- 已批准的非阻断例外、适用范围和失效条件；
- 本次新增、修改、合并、拆分和退役差异；
- 部门核对、MDM 复核和发布依据。

流程版本和数据模型版本分别发布，通过明确绑定关系连接。流程发布不能运行时读取可变的数据地图当前状态；数据模型发布也不能改变已发布流程版本中的原始事实。

### 8.10 数据关联工作区

MDM 工作组需要一个面向治理的关联工作区，而不是只看字段列表。建议提供四个互相联动的视图：

| 视图 | 主要内容 | 可执行动作 |
|---|---|---|
| 待核对出现项 | 尚未关联、需要重新核对或缺少归口的数据对象、字段和关系 | 新建企业身份、提出关联、发起纠正 |
| 数据关联图 | 企业数据对象、字段、流程版本、业务行为、表单、组织和关系 | 查看证据、影响和当前发布版本 |
| 治理请求 | 纠正、关联、合并、拆分和归口调整的状态、责任、期限和回复 | 分派、补证据、协调、复核和升级 |
| 数据模型版本 | 当前版本、历史版本、结构化差异和未解决问题 | 预览、核对和按权限发布 |

关联图默认展示已经确认的企业身份和正式关系。待核对建议使用不同视觉状态，并明确显示“尚未确认”；用户不能通过拖线直接形成正式关系。所有写操作都先生成结构化请求和影响预览。

筛选至少包括部门或办公室、流程版本、业务行为、数据对象、字段、关系类型、治理状态、责任状态和数据模型版本。右侧详情同时显示来源位置、当前定义、责任、上下游、证据、关联工作项和历史决定。

## 9. 数字化治理技术架构设计

### 9.1 总体技术选择

建议继续采用模块化单体，原因如下：

- 当前业务事务跨身份、流程、待办、冲突和审计，单数据库事务仍有实际价值；
- 当前规模和团队维护方式不支持为每个领域引入独立部署、消息中间件和分布式追踪的额外成本；
- 当前最主要风险来自边界混杂、运行期迁移、连接池和历史路径，不来自单体本身；
- 通过模块所有权、应用服务和只追加事件，可以先获得可测试、可追溯和可演进的结构。

本阶段不引入微服务，也不要求图数据库。企业数据关系先使用 MySQL 关系表作为真源，通过图形查询投影支持浏览。只有在真实数据量和查询证明关系数据库无法满足时，才评估专用图数据库。

### 9.2 目标模块

| 模块 | 主责 | 不能越界的内容 |
|---|---|---|
| identity-access | 登录、会话、账号、固定 RBAC、访问审计 | 不维护业务岗位或业务工作角色 |
| organization-people | 组织、人员、岗位、任职、正式工作角色和版本 | 不直接授予系统权限 |
| process-governance | 流程导入、草稿、核对、承接、审核和发布 | 不读取运行时原始 3001 JSON |
| data-governance | 出现项、企业身份、关系、责任和数据模型版本 | 不保存业务记录值 |
| work-coordination | 治理案例、工作项、纬理场景协同和 PMO 跟踪 | 不复制领域结论 |
| conflict-decision | 冲突、冻结决策包、语义差异和决定 | 不修改被比较的历史版本 |
| audit-evidence | 只追加事件、证据引用、操作审计和发布记录 | 不保存 Secret 或无关业务内容 |
| reporting-read-models | 我的待办、全局队列、数据关联图和管理视图 | 不成为写入真源 |

模块依赖方向固定为：

    HTTP Interface
      -> Application Orchestrator
        -> Domain Module Interface
          -> Repository Interface
            -> MySQL Implementation

规则：

- HTTP 路由只处理输入、身份、状态码和返回结构，不直接编排多表 SQL；
- 领域模块只通过小而稳定的命令或查询接口交互，不引用其他模块的仓储实现；
- 跨模块事务由应用编排层通过统一 Unit of Work 组织，并使用固定锁顺序；
- 每个仓储只能写本模块拥有的表，不能直接修改其他模块的数据；
- work-coordination 保存正式治理工作项及其事件；
- reporting-read-models 只消费事件形成查询投影，不反向写领域对象或工作项；
- identity-access、audit-evidence 和可观测性能力由组合根注入，不让领域模块反向依赖 Express 路由。

每个模块应分为：

- 路由层：HTTP 输入、身份和返回格式；
- 应用服务层：用例、权限交集、事务和幂等；
- 领域层：状态机、规则和差异语义；
- 仓储层：SQL 和行锁；
- 事件与投影层：只追加事件和本模块只读模型更新。

### 9.3 数据库和迁移

启用前应完成：

1. 建立全局 MySQL 连接池和显式依赖注入。当前服务端存在 22 处 createPool 调用，分布在 17 个文件中；不能继续让每个仓储和路由独立管理连接。
2. 禁止请求期执行 CREATE TABLE 或自动结构修补。部署使用带版本、校验和、dry-run、apply 和受控回退的迁移。
3. 扩展并统一现有 schema_migrations 登记表。当前表只有迁移键和执行时间；目标增加校验和、执行主体、开始和结束时间、结果、失败分类及补偿状态。
4. 启动时只读检查所需迁移和治理模型版本。结构不兼容时 readiness 失败，不能在第一个业务请求中修改数据库。
5. 明确每个模块的表所有权。跨模块写入通过应用服务和事务完成，报表使用只读投影。
6. 对导入、发布、合并、拆分、决定和组织生效使用数据库事务、行锁、expected_revision 和幂等键。
7. 保留发布前备份、迁移数量核对、关键字段核对、引用关系核对和失败补偿。

### 9.4 事件、待办和一致性

导入提交、领域状态变化和首批工作项必须在同一事务中完成，保证 API 返回成功时管理员已经能看到正式工作项。

成功审计事件必须与对应业务写入同时提交或同时回滚。审计事件至少冻结：

- 账号、人员、有效 3000 RBAC 角色和组织快照；
- 目标类型、稳定标识、版本和修订；
- 治理案例、工作项和数据治理请求标识；
- 旧摘要、新摘要或结构化差异；
- 原因、依据和证据引用；
- request_id、correlation_id 和 idempotency_key；
- 操作时间、结果和失败分类。

governance_work_item 是分派、推进、验收和关闭等协同状态的正式记录；reporting-read-models 只根据其事件形成“我的待办”和“全局治理队列”等查询投影，不能反向写工作项。

建议使用事务内 outbox：

    领域事务
      +--> 写领域对象
      +--> 写领域事件
      +--> 写首批工作项
      +--> 写 outbox
      |
      v
    提交成功
      |
      +--> 同步可见首批工作项
      |
      +--> 后台幂等更新汇总、关系图和管理视图

要求：

- 首批工作项同步提交，不能只依赖最终一致的后台任务；
- 汇总、关系图和报表投影可以异步更新；
- outbox 消费使用事件编号和唯一约束保证重复执行不重复派发；
- 定期运行对账任务，比对领域状态、开放工作项和投影数量；
- 对账只报告和修复投影，不静默改变业务结论。

近期 outbox 消费者与 3000 运行在同一进程中，不新增独立服务，但必须能够安全支持以后多实例：

- 使用租约或等价抢占字段领取事件，同一事件同一时刻只能由一个消费者处理；
- 失败采用有上限的指数退避，超过次数进入隔离队列，保留错误分类并触发告警；
- 毒消息不能阻塞后续无关事件，人工补偿必须生成新的操作和审计记录；
- 优雅退出时停止领取新事件，完成或释放当前租约；
- 记录消费者心跳、最老未处理事件时间、积压数量、重试次数和隔离数量；
- 多实例不得依赖进程内锁或内存游标；
- readiness 在消费者长期无心跳、最老事件超过启用阈值或隔离事件未处理时失败。

跨模块事务在技术规格中冻结隔离级别、固定锁顺序、锁等待上限、死锁重试次数和不可重试错误。所有重试继续使用同一个幂等键，不能重复创建版本、工作项或审计成功事件。

现有角色工作台的十五秒内存缓存不能用于保证“导入后立即可见”。工作项写入成功后必须显式失效相关用户、部门和全局队列缓存；导入 API 返回成功后的下一次全局队列读取必须命中新版本。多实例时使用数据库投影版本或共享失效信号，不能各自等待 TTL。

### 9.5 权限判定

每次读取和写入都应按以下交集判断：

    固定 RBAC 最大权限
      ∩ 有效组织和数据范围
      ∩ 当前对象状态允许的动作
      ∩ 有效场景任命或任务责任
      ∩ 字段敏感级别和最小必要原则

要求：

- 前端按钮隐藏不能替代服务端校验；
- admin 的全局可见和业务只读分别实现；
- PMO 的项目跟踪写权限不能调用领域内容修改接口；
- 纬理的每次写操作校验 scenario_assignment、动作、对象范围和有效期；
- decision_group 只能处理已经升级且内容摘要未变化的决策包；
- 部门范围角色使用明确 scope_department_id；部门下办公室可以校验其祖先部门，公司级办公室必须使用显式部门范围或 global 授权，不能依赖祖先推导；
- 高敏感员工字段使用字段级授权、脱敏和访问审计。

### 9.6 精确差异服务

建立独立 semantic-diff 应用服务：

- 输入必须是两个不可变版本或一个不可变版本与冻结修订；
- 先按稳定对象引用配对，再比较字段和关系；
- 输出 add、remove、modify、move、link、unlink、merge、split 等受控变更类型；
- 输出旧值、新值、路径、证据影响、责任影响和需重新核对的对象；
- 结果保存摘要。进入冲突协调或决定阶段时冻结完整差异快照；
- 后续内容发生变化时，旧快照仍可读，但不能继续提交决定；
- 差异算法使用固定测试样本覆盖新增、删除、重排、责任变化、关系变化和数据字段变化。

### 9.7 前端演进

不建议在启用前一次性重写前端。近期继续遵守单文件 HTML、CSS 和 JavaScript 约束：

1. 在现有 index.html 内部使用闭包或命名空间建立 ApiClient、Router、SessionState、RoleWorkbenchView、OrganizationView、DataGovernanceView 和 DiffView 等逻辑边界。
2. 在同一文件内统一文本、属性和 HTML 安全渲染函数，并按业务区整理状态、加载、渲染、事件和缓存；保持现有嵌入式流程编辑器边界。
3. 先用特征测试覆盖现有行为，再逐个迁移逻辑边界，避免全文件重写。
4. 只有项目明确改变单文件约束，并通过 ADR 说明构建、部署、缓存和回退后，才把模块和 CSS 提取为外部文件或引入前端框架。

页面必须明确展示：

- 可见但不可办理的原因；
- 对象当前版本和修订；
- 旧值、新值和影响；
- 当前责任人、归口依据、期限和阻塞；
- 自动建议、人工确认事实和待确认事项的不同状态；
- 保存失败、版本冲突、权限变化和会话失效后的恢复方法。

### 9.8 会话和安全

启用前应完成：

- 用持久会话存储替换 express-session 默认 MemoryStore。当前单机阶段优先使用 MySQL 会话存储；需要多实例或更高吞吐时再评估 Redis；
- 服务重启后按安全策略恢复或失效会话，并记录明确原因；
- 登录限速从单进程内存状态升级为可共享、可审计的限制；
- 保留 CSRF、Cookie 安全属性和基本安全头；
- 前端模块化后逐步去除 CSP 中 unsafe-inline；
- 对导入内容、字段长度、枚举、引用和文件摘要执行服务端校验；
- 不在日志、审计载荷和错误响应中保存密码、API Key、Session、员工敏感字段或完整业务材料；
- 账号、角色、组织归属或场景任命变化后，重新计算有效权限并按风险使旧会话失效。

### 9.9 健康检查和可观测性

建议拆分：

- /health/live：只证明进程可响应；
- /health/ready：检查 MySQL、必要迁移、治理模型版本、关键读模型和功能标志兼容；
- /api/health：保留面向现有运维入口的兼容输出，但不能单独作为启用证据。

增加：

- request_id 和结构化运行日志；
- 接口延迟、错误率、连接池等待、迁移状态、工作项积压和 outbox 积压指标；
- 导入、发布、合并、拆分、冲突决定和权限变化的审计事件；
- 不包含业务正文的失败分类；
- 工作项与领域对象对账报告；
- 备份、恢复和迁移演练结果。

### 9.10 容量和时延门槛

首轮启用至少沿用并扩展当前本地并发基线：

| 场景 | 初始验证负载 | 通过门槛 |
|---|---|---|
| 登录 | 10 个虚拟用户、5 轮 | 可用率 100%，P95 不超过 500 毫秒 |
| 我的待办和全局治理队列首屏 | 10 个虚拟用户、5 轮；每页 50 项；至少 10,000 条历史工作项 | 可用率 100%，P95 不超过 250 毫秒 |
| 数据关联详情 | 10 个虚拟用户、5 轮；首屏 100 个节点、200 条关系；至少 10,000 个出现项 | 可用率 100%，P95 不超过 500 毫秒 |
| 普通治理写入 | 10 个并发用户；不同对象和同一对象冲突样本均覆盖 | 非冲突写入 P95 不超过 1 秒；冲突请求返回明确 409，不出现覆盖 |
| 单流程导入 | 不超过现有 2 MB 请求限制；最多 2,000 个对象、字段、表单使用和来源关系出现项 | P95 不超过 5 秒；失败时业务记录、工作项和成功审计全部回滚 |
| 单流程语义差异 | 两个版本合计最多 2,000 个可比较对象和关系 | P95 不超过 2 秒；超过范围转受控后台任务，不阻塞 HTTP 进程 |
| outbox 投影 | 连续产生 1,000 个事件 | 投影延迟 P95 不超过 2 秒；积压超过 100 条或最老事件超过 30 秒告警 |
| 连接池 | 上述混合负载 | 连接等待 P95 不超过 50 毫秒；无连接泄漏；优雅退出完成 |

这些是首轮最低技术门槛，不是永久容量承诺。阶段 0 使用真实脱敏样本重新校准后，采用“本表门槛”和“经批准的新门槛”中更严格者。任何放宽都必须记录数据规模、原因、批准主体和影响。

## 10. 迁移和兼容设计

### 10.1 总体原则

- 所有迁移先盘点、备份和 dry-run；
- 采用新增结构、回填、双读比对、切换、观察和退役顺序；
- 不清空或猜测无法映射的旧值；
- 无法自动迁移的记录进入待核对清单；
- 旧标识通过桥接表或别名保留；
- 兼容期内不进行双真源人工维护；
- 物理删除和遗留表清理必须等到兼容截止条件满足后另行批准。

### 10.2 组织和人员迁移

1. 盘点 MySQL departments、person、user_accounts、person_roles，以及遗留 SQLite org_unit、position、person_position_assignment。
2. 以当前受控组织架构、正式工作角色目录和项目治理角色映射为迁移输入，生成只读导入预览。花名册和其他人事资料只作为员工首版编制参考，不作为必须逐条迁入或对账一致的真源。
3. 对账三个公司级办公室以及现有“公司领导”部门记录。公司领导和公司级办公室人员的主要行政归属、公司级任职和 RBAC 范围必须人工确认，不能根据岗位或办公室名称自动赋予全局权限。
4. 保留现有 department_id，通过桥接关系连接新的 org_unit_id，不在首轮改写现有部门权限引用。
5. 行政人事部通过表格工作区编制首个员工主数据版本。现有 MySQL person、花名册和其他人事资料分别标明来源，只提供参考；系统不要求它们数量相等，不自动选择一侧覆盖另一侧，也不自动发布。
6. 现有账号继续绑定原 person_id，不重新生成账号或角色授权。现有 person 保留稳定 person_id 并预装为未发布首版草稿参考行；行政人事部可以批量修改、排除或补充。账号存在不能自动认定为员工事实已经发布。
7. 对部门下办公室验证祖先根部门；对公司级办公室验证显式 scope_department_id 或 global 范围。兼岗和次要办公室不得扩大原权限。
8. MySQL 正式切换前或同一切换窗口先冻结遗留 SQLite 组织和岗位写入口，再启用 3000 行政人事发布。观察期只允许 SQLite 只读兼容和结果比对，禁止双写。
9. 切换行政人事发布后，开户接口只允许引用已发布人员。
10. 完整观察期和兼容截止条件满足后，再逐步移除遗留 SQLite 读取路由。

### 10.3 固定角色模型迁移

如新增 PMO 权限包或纬理受限权限，应发布新的治理模型版本，不修改 v3 的含义：

- 以 docs/organization/信息化项目人员角色映射.md 为项目治理组织成员迁移输入，逐项核对成员、任命主体、任期和人员匹配状态；
- PMO 指信息化项目管理工作室或相应项目治理组织，不等同于组织架构中的项目管理部；
- 若迁移材料中出现“Facilitator”“业务协同促进人”或“纬理”，只生成指向同一个稳定工作角色身份的待核对名称映射，不得按文本分别创建多个工作角色；
- 启用前应确认当前没有正式纬理场景任命和授权事件；如发现遗留记录且无法取得当时的不可变任命与权限依据，只能标为 `authorization_evidence_status=unproven` 的只读历史，不能据此恢复或产生写权限；
- 盘点所有有效账号、角色、部门范围、有效期和未完成事项；
- 明确旧角色到新角色的保留关系，禁止把历史 retired 角色自动映射为新权限；
- 纬理场景任命不能从人员岗位或名称自动生成；
- 新角色授权必须有依据、授权人和有效期；
- 角色模型切换后使受影响会话重新登录；
- 回退时关闭新权限入口，保留已经产生的只读历史和审计，不删除记录。

### 10.4 待办迁移

- 盘点 mdm_todos、process_mapping_todos、审核任务、承接状态、冲突、质量问题和输入基线问题；
- 为每个当前开放事项生成唯一 source_ref 和幂等键；
- 统一工作项只保存协同状态和领域引用，不复制审核结论；
- 回填后按领域状态逐项对账，报告缺失、重复、无责任人和无目标对象的事项；
- 先以影子读模型与旧角色工作台比对，再切换“我的待办”和“全局治理队列”；
- 回退时恢复旧查询入口，新工作项保留只读，不反向覆盖旧领域表。

### 10.5 数据出现项和企业身份迁移

- 对每个受支持的不可变流程版本扫描数据对象和字段；
- 优先使用原局部引用生成出现项；缺少引用时建立待修复记录，不按名称自动连接；
- 当前 data_map_objects、data_map_contexts 和 data_map_fields 先进入 legacy_data_map_staging 或等价迁移暂存层，保留旧 ID、旧上下文、原值和来源；
- 只有旧记录能够明确绑定不可变导入修订或 process_version_id、局部引用和来源位置时，才生成出现项；否则保持 legacy_unresolved 并建立待核对工作项；
- 未经有权主体核对的旧对象或字段不能直接成为企业身份；
- 已有人工确认的责任和权威来源主张连同证据迁移；
- 同名跨部门对象、重复键覆盖风险和已物理删除记录单独报告；
- 新模型发布前执行出现项数量、字段数量、摘要、引用完整性、孤儿关系、重复身份、旧新身份桥接、重定向环和跨版本沿革核对；
- 合并、拆分和关系变更必须先在样本副本中演练。

### 10.6 必测迁移场景

每个影响 3000 数据结构、状态、标识、权限或导入格式的版本至少验证：

1. 上一受支持版本导入当前版本；
2. 当前版本导出后重新导入；
3. 重复执行迁移或等价操作；
4. 迁移失败后恢复；
5. 执行前备份和执行后数量、关键字段、版本、引用关系核对；
6. 旧账号、旧角色和未完成工作项不丢失；
7. 旧 process_version_id 继续可读且不被当前草稿覆盖；
8. 合并和拆分后历史身份可追溯；
9. 功能标志关闭后新功能不可写，旧主线仍可用；
10. 回退后不出现跨版本双写或重复派发。

### 10.7 分批切换和回退控制

每一阶段使用独立功能标志。具体标志名称在技术规格中冻结，不使用一个“3000 已启用”总开关一次放开全部能力。

| 阶段 | 切换前提 | 切换方式 | 回退触发 | 回退和补偿 |
|---|---|---|---|---|
| 技术底座 | 备份可恢复；迁移 dry-run 通过；旧接口特征测试通过 | 先启用共享池、持久会话和 readiness，业务行为保持不变 | 连接耗尽、会话异常、readiness 误判或错误率超门槛 | 切回上一应用和配置；新增迁移登记保留；非事务性 DDL 按预先登记的反向脚本或前向修复补偿 |
| 组织和人员 | 文档真源与 MySQL 差异清单关闭或保持明确待核对；SQLite 写入口已冻结 | 先影子读取和对账，再切 MySQL 唯一写入，SQLite 仅只读兼容 | 人员、根部门、岗位或权限范围不一致 | 关闭新写入口，恢复旧只读服务；新 MySQL 记录保留只读，不反写 SQLite |
| 统一工作项 | 旧领域事项已生成幂等 source_ref；新旧数量和责任人对账通过 | 先生成影子投影，再切我的待办和全局队列 | 缺失、重复、责任错配或导入后不可见 | 停止新投影消费，恢复旧查询；新工作项和事件只读保留，按对账结果前向修复 |
| 数据身份 | 导入修订、promotion 和出现项回填通过；旧数据进入暂存层 | 按试点范围开启出现项、匹配建议和治理请求写入 | 自动误合并、孤儿关系、摘要不一致或回退链失败 | 关闭新写入口；保持出现项、请求和操作历史只读；不删除身份或把结果回写旧表 |
| 精确差异和 V7 | 预览、受控提升、正式发布分别通过权限、迁移和真实试点 | 按环境、试点部门和能力逐个开启现有 V7 预览与正式标志及差异服务 | 过期修订可提交、差异错误、权限越界或正式发布失败 | 分别关闭预览、提升或正式发布入口；已产生的正式数据只读保留，不删除列、表或版本 |

每次切换记录：

- 负责人、时间窗、功能标志旧值和新值；
- 备份位置和恢复验证；
- 迁移编号、校验和及非事务性 DDL 补偿办法；
- 切换前后数量、摘要、外键、孤儿记录和权限结果；
- 回退触发阈值、执行步骤、决定人和结果；
- 兼容截止条件和旧入口退役决定。
