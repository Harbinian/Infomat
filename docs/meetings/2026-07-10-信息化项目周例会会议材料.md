## 一、展示文档结构化输出范例

本次使用《数据库数据更正申请与责任考核管理制度（精简审批版）》说明制度文件经过结构化整理后能形成什么。会议只展示业务结果，不展示 JSON、内部字段名或模型参数。

### 范例结果

| 结构化对象 | 结果 |
| ---------- | ---- |
| 业务流程 | 1 条：数据库数据更正申请与责任考核 |
| 业务步骤 | 9 个，从发现核实到整改关闭 |
| 判断与分支 | 1 个风险分级判断节点、4 条后续分支 |
| 表单与字段 | 4 张表单、62 个字段 |
| 跨部门承接 | 3 条 |
| 原文依据 | 13 条可定位依据 |
| 待确认事项 | 1 项：正式制度编号待补 |

### 九步业务流程

1. 发现与部门核实。
2. 申请材料编制与部门确认。
3. 业务归口复核。
4. 系统技术评估与分级授权。
5. 执行准备。
6. 数据更正执行。
7. 业务验证确认。
8. 台账归档与绩效评价。
9. 整改复盘与关闭。

风险分级节点保留四条路径：一级、二级按授权执行；三级经分管领导或相关业务负责人确认；四级重大风险提交总经理或专题会议决策；材料不完整、风险不清或回退措施不足时退回补充。

### 现场要说明清楚

- 制度目标和适用范围属于文档信息，不应被拆成流程步骤。
- “谁在什么场景做什么、使用什么材料、形成什么结果”才进入业务步骤。
- 基本原则、禁止行为和风险规则进入执行标准及原文依据，不污染流程图。
- 申请单、评估记录、台账和复盘表进入表单与字段结构，后续可以继续编辑和导入。

## 二、核对组织人员标准和主数据标准

向行政人事部、工程技术部各下发一项评价任务。两部门从各自业务使用角度核对组织人员标准和主数据标准，统一在 2026-07-14 前完成评价。

| 责任部门 | 评价重点 | 提交结果 | 3002 状态 |
| -------- | -------- | -------- | --------- |
| 行政人事部 | 组织、部门、岗位、人员的定义、编码、关键属性、来源、维护责任、状态和例外处理 | 评价结论与问题清单 | 已下发，待处理 |
| 工程技术部 | 组织人员信息及相关主数据在工程技术业务中的适用性、字段完整性、维护责任和使用约束 | 评价结论与问题清单 | 已下发，待处理 |

评价结论只使用三种口径：通过、有条件通过、需修订。选择有条件通过或需修订时，必须写清建议修改项、判断依据和责任接口。

## 三、发布调研范围清单

发布 DLV-004《调研范围与对象清单》，要求九个业务部门在 2026-07-14 前给出具体期待由信息化系统管理的业务流程。本次只收业务流程期待，不要求部门先判断应该使用 OA、MES、ERP 或 PLM。

### 回执部门

- 工程技术部
- 质量管理部
- 财务部
- 行政人事部
- 经营发展部
- 物资保障部
- 项目管理部
- 复材车间
- 运维安环部

### 每条流程至少写清

| 字段 | 填写要求 |
| ---- | -------- |
| 具体流程名称 | 使用业务人员日常能理解的名称 |
| 触发场景 | 什么情况发生时启动这项工作 |
| 主要参与部门 | 谁发起、谁处理、谁确认 |
| 当前处理方式 | 当前使用表单、台账、群消息、邮件或已有系统的情况 |
| 期待系统管理的环节 | 希望系统帮助登记、流转、审批、提醒、查询、统计或追溯的具体环节 |
| 预期结果 | 希望减少什么问题，或希望形成什么可查结果 |

每个部门至少提交一条具体流程；没有新增期待的部门也要明确反馈“本轮无新增流程期待”。九个部门行动项已进入 3002，状态为待处理，截止日期统一为 2026-07-14。
