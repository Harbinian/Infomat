# 文档类型规则

## 目录

1. 技术方案
2. 需求规格
3. 系统、数据与接口设计
4. SOP 和操作指导书
5. 制度与流程
6. 实施、上线和迁移方案
7. 验收、审计和整改材料
8. 报告与会议纪要
9. UI 文案、问题卡和用户手册

## 共同行文要求

所有文档优先使用目标读者熟悉的常用字词。专业术语、固定名称、字段、编号和受控引文保持不变；目标读者可能不理解时，在术语后说明它的实际含义、业务影响或操作要求。

抽象概念使用常用字词后仍难理解时，可以补充生活化实例。实例必须明确标记为例子，不得替代正式定义、业务规则、技术结论或验收证据。制度、合同和其他受控原文只能在原文外增加实例说明。生活化实例不使用幽默、情绪或夸张表达。

## 1. 技术方案

至少说明：

1. 背景和需要解决的问题；
2. 建设目标和可检查结果；
3. 适用范围和不在本期处理的事项；
4. 总体方案、业务流程和系统边界；
5. 数据、接口、权限和安全要求；
6. 实施步骤、验收标准、风险和限制。

不得用“提升效率、加强协同、实现闭环”替代具体目标。写清谁使用、谁维护、失败影响谁，以及如何检查方案达到目标。

## 2. 需求规格

优先使用：

> 在【触发条件】下，【系统或角色】应【执行动作】，以【对象】为输入，并产生【可验证结果】。

每条需求尽量具备唯一编号和验收条件。写清：

- 正常路径和异常路径；
- 权限主体和数据范围；
- 输入、输出、状态变化和失败反馈；
- 重复提交、并发、超时或外部系统不可用时的处理。

讨论意见、建议和待确认内容不得写成已确认需求。

## 3. 系统、数据与接口设计

系统设计应区分业务职责与技术组件职责。不要用组件名称替代业务主体。

数据设计应说明：

- 数据对象、字段含义、来源和维护责任；
- 唯一性、空值、默认值、状态和生命周期；
- 索引、约束、审计、迁移和回滚要求。

接口设计应说明：

- 发起方、接收方、触发条件和认证方式；
- 请求、响应、错误码、幂等、超时和重试；
- 字段映射、失败处理、审计和兼容性。

接口字段、枚举、路径和错误码保持原样，不做中文同义替换。

## 4. SOP 和操作指导书

每个步骤说明：

- 操作人；
- 前置条件；
- 操作动作；
- 输入、工具或系统入口；
- 输出或判断标准；
- 异常处理；
- 记录和归档要求。

避免只写“进行检查”“完成处理”“按要求执行”。主体、条件或系统发生变化时拆分步骤。

## 5. 制度与流程

明确：

- 适用范围；
- 角色、职责和授权边界；
- 发起条件；
- 审核、审批、批准、确认和监督关系；
- 办理时限；
- 记录、证据和归档要求；
- 例外、撤回、驳回、作废或升级处理；
- 责任追溯。

制度原文属于受控内容时，只能在原文外增加通俗解释。

## 6. 实施、上线和迁移方案

写清：

- 实施对象、范围、负责人和时间窗口；
- 前置检查、备份、迁移或发布步骤；
- 数据校验、健康检查和业务验收；
- 失败判定、暂停条件、回滚步骤和责任人；
- 变更记录、通知对象和证据保留。

不要把“计划执行”写成“已经完成”，也不要把技术验证替代业务验收。

## 7. 验收、审计和整改材料

区分：

- 验收或审计依据；
- 已取得的证据；
- 已确认事实；
- 分析判断；
- 不符合项或风险；
- 整改动作、责任人和期限；
- 复核方式和关闭条件。

结论必须能够由数据、记录、状态或验收条件支持。没有证据时写明“尚无证据”或“需补充”，不得补造依据。

## 8. 报告与会议纪要

分别记录：

- 已确认事实；
- 分析判断；
- 讨论意见；
- 未决问题；
- 决策事项；
- 行动项、责任人和完成期限；
- 验证方式。

不得把讨论意见写成决策，不得把建议写成已安排动作。引用发言时保留原话；概括发言时标明概括主体。

## 9. UI 文案、问题卡和用户手册

UI 文案应让用户知道：

- 当前状态；
- 需要执行的动作；
- 操作对象和入口；
- 成功或失败结果；
- 无权限、空状态和异常情况下的处理。

问题卡应写清发现位置、问题原因、处理动作、责任主体和完成条件。内部实现术语不能替代业务人员认识的对象。

用户手册按真实界面顺序说明“谁在什么条件下，到哪里执行什么操作，看到什么结果”。不要用系统未提供的菜单、按钮或反馈。
