# 受控写作规则

按当前文稿的问题读取对应章节。事实和责任保护始终适用，写法与组织形式由目标读者及受控模板决定。

## 1. 事实与引文保护

不得自行改变或补造业务规则、技术参数、标准编号、数据口径、日期、责任、审批关系、系统边界、输入输出、状态、异常、验收条件或证据位置。信息不足时保留原意，并标记“需确认”或“原文未说明”；建议不得改写成决定。

制度原文、合同条款、会议原话及法规标准的直接引文逐字保留。文件名、路径、编号、日期、参数、字段、枚举和错误码不做文风替换。用户授权修改规则或技术对象时按任务处理对应变更，不把逐字保护扩大为禁止授权修改。

压缩可以删除重复、宣传、套话和无依据评价，不能删掉主体、对象、条件、时序、因果、例外、记录、归档或责任追溯要求。

## 2. 主体、动作和责任链

行为句应能看清谁在什么条件下对什么对象执行动作，并产生什么结果。条件和依据靠近所约束的动作；主体、审批阶段或责任链变化时重新写明，必要时拆句。只有不会误判责任时才省略重复主体。

人员、部门和系统动作分开表达。人工判断、复核、审批与系统自动校验、生成、同步不能混写。指代有歧义时改用具体名称；无法确定时标记待确认。

例如：“检验结果不符合要求时，质量工程师创建质量偏差记录，并提交工艺工程师评审。”不要改成让“记录”承担创建和审批动作的句子。

优先使用具体动词和正常语序，不通过倒装、宾语前置或堆叠名词压缩内容。多主体、多分支流程可用步骤或表格；不按动作数量机械决定格式。

## 3. 术语与常用字词

术语口径依次采用受控原文或用户确认、项目术语表及契约、文档明确约定、本技能通用解释。标准术语重复不是问题，不为避免重复而换名。疑似同义词可能代表不同对象时保留并提出具体待确认项。

首次出现的术语和缩写按读者需要解释其全称、实际作用或边界；不为本专业读者熟悉的词补通用教程。跨部门读者不能仅靠另一组专业词理解定义。

项目没有专门定义时，可用以下通用区分：

| 动作 | 含义 |
|---|---|
| 审核 | 检查内容是否符合要求 |
| 审批 | 按授权决定是否同意 |
| 确认 | 核实事实、状态或结果 |
| 批准 | 正式授权执行或生效 |
| 评审 | 相关人员对方案、问题或结果综合判断 |

复杂或跨来源文稿可用内部术语表核对标准名称、缩写、含义、允许变体及依据。仅在读者、用户或模板需要时输出该表。

## 4. 生活化实例

先用常用字词解释实际含义；仍难理解时才补充准确且有帮助的实例。用“例如”等文字表明是解释，与正式规则、事实和证据分开。

例如解释版本冲突时，可以说明“后提交者使用的旧副本不能覆盖已经修改的新内容”。类比不能暗示原文没有的系统能力、责任、参数或结果；必要时说明差异，不能准确类比时不使用。受控原文内部不增加实例、情绪或幽默。

## 5. 按风险复核

对改写部分及其直接关联内容核对事实、引文、数据、术语、责任、条件、时序和异常是否保留。只修正有依据的问题，不把同一清单重复检查多轮。

会造成误操作、错认责任、遗漏条件或虚构结论的问题，应修正或明确标记待确认后再交付。原文缺少事实时可交付标有缺口的草稿，不要求凭空补齐，也不把一般文风偏好设为阻断项。清单和表格是辅助方法，不是每次改写的固定产物。
