# 四项成果输出模板

方括号内容是填写说明，不能当作业务事实。缺项使用“待确认”并给出问题编号；JSON 不接受的占位文字不得塞入枚举、布尔、时间或技术引用。下方表格可按需要增加行、分组，不保留没有用途的空白表。

默认交付制度正文、工作平衡报告、待确认事项三份 Markdown，以及一份完整 JSON。只有用户指定 Word 时才生成 Word，从同源 Markdown 正文按指定模板生成，未另指定模板时使用[制度编写规范](document-standard.md)的原文 5.2 版式；修改正文后重新生成，不手改 Word。对外清稿仍保留以下人工插图和交付说明要求。

## A 制度正文 Markdown

文件建议名：`<流程短名>-procedure-draft.md`。正文标题后仅用一行说明“待核对草案；关联流程标识……；本次修订标记……”，不制作封面。编号、版本和生效日期仅在明确提供时注明，不自行签发。

**两个面向要分开**：编制**工作稿**（md）按下面的模板写，可保留标记行、问题号与如实说明；**对外清稿**（发给部门的 Word／PDF，以及作为其来源的那份正文）按本节末“对外清稿”处理，不带待决项与编制痕迹。

```markdown
# [制度名称]

> 待核对草案；关联流程：[process_ref]；编制修订：[本次修订标记]。

## 1 目的

[针对本流程要解决的问题及预期结果，不写泛化口号。]

## 2 适用范围

[适用对象、部门或业务范围、开始条件、结束成果及不包含的边界。]

## 3 术语和定义

[仅列本制度需要解释的术语；确无术语时写“无”，不复制技术字段词典。]

## 4 职责

| 部门或角色 | 具体职责 | 配合职责与交接对象 |
|---|---|---|
| [已确认主体] | [具体工作与结果] | [已确认配合关系，未知关联问题号] |

## 5 规定

### 5.1 [第一环节名称]

[主体]在[条件]下，依据[已确认依据]对[对象]实施[具体动作]，形成[输出]；[完成标准]达成后交由[后续主体]办理。发生[异常]时，按[已确认退回或升级路径]处理。

[继续按实际步骤编写5.2等条款。无依据的阈值、审批或期限不得补造。]

## 6 流程

本流程图由3000或3001生成，待人工选取并插入。图件必须与本次确认的流程内容一致。本稿不包含流程图，不表示图件已经生成或插入。

## 7 规定表格

| 表单编号 | 表单名称 | 用途 | 载体 |
|---|---|---|---|
| [已知编号或待确认Q-xxx] | [名称] | [对应步骤及作用] | [电子流程／纸质] |

## 8 记录控制

| 记录或表单 | 载体 | 留存部门 | 保管岗位或规则 | 保存期限 | 依据 |
|---|---|---|---|---|---|
| [名称] | [电子／纸质] | [部门] | [已确认责任] | [明确期限] | [短引注，如“附录 A 15.4.6”] |
```

第 4 章职责必须能够在第 5 章和 JSON 行为中找到对应；第 7 章表单与 JSON 中名称、编号、处理行为一致；第 8 章覆盖本制度涉及的记录及关联表单。缺少流程数据以外的正式发文信息时登记待定，不借用编制规范自身的编号和保存期限。

**载体是无纸化的落点，必须逐张明确**：先复用材料和已有设计，缺少影响设计的选择时再收集公司有没有 OA、暂由什么承接（常见为钉钉）、哪张表单仍需纸质签署等关联信息。写在第 7 章列内，并在表下用一段话说明流转方式；第 8 章的载体列与之一致，纸质件要交代扫描件是否随电子档案归档。没有确认过载体时按设计口径写明一种，不默认“纸质及电子”、也不为它制定待确认项。

**第 8 章的期限不要留空指或“待确认”字样**。有口径的按口径写实；附录类对照表里没有直接条目的，按最接近的条目推定写实值，并在待确认清单里留痕说明是推定。依据列用短引注（“附录 A 15.4.6”），条目全称放表下注释，否则列宽会把表压成一条竖线。

**附件：表单样例**。本流程新建（含拟新建）的表单，在正文后加“附件　表单样例”，逐张给出：载体、办理关系（环节／操作／说明）、**空白样张**、**字段要求**（字段／类型／必填／填写说明）。样张用表格画出表样式——首行合并成表单名，字段按“标签＋填写栏”成对排，必填项标`〔必填〕`并在附件开头说明含义；明细区按列铺开，给一行占位（纯空行在 Word 里会塌成一条线）。样张由 JSON 的 `forms` 生成，重跑覆盖，不手改。

**对外清稿**（编制人明确要求时，或本包已进入送部门核对阶段）：在“待核对草案”稿基础上清理——

| 清掉 | 怎么处理 |
|---|---|
| Word 批注 | 全部取消；批注内容移入待确认清单 |
| 问题号（`Q-xxx`） | 正文与附件不带；问题号只留在待确认清单与确认请求里，靠条款位置回指 |
| “待确认／待核对”字样 | 有口径的写实并留痕，无口径的登记进清单，正文不留字样 |
| 编制过程说明 | “本稿不包含流程图”“未套用某写法”“材料里本没有”这类自述一律删 |
| 技术标识 | JSON 字段名（`proposed_design`）、工具名（3001／3000）、`process_ref` |
| 内部信息 | 编制人姓名、花名册岗位、内部工作目录 |

第 6 章在清稿里写成正常制度语句（“本程序流程见附页流程图”），但**清稿不等于图已插入**——图没插之前不得发出，这一点要明确告诉编制人，别让清理动作看起来像已补齐。

八章结构的来源和原文疑点见[制度编写规范](document-standard.md)。

## B 3001 JSON

文件建议名：`<流程短名>-process-v8.json`。以 3001 空白模板为骨架，按 V8 结构填充，输出一个完整、可解析的对象。

- 顶层版本必须为 `process-governance-v8`；仅一条 `process`。
- 导入文件不含接口包装、Markdown 文字、注释或省略号。
- 稳定标识与另外三份文件关联一致；对象改名后标识保持不变。
- 对空值、待定值及暂未编码的内容逐项说明，阶段稿与最终待核对稿分开标记。
- 伴随 JSON 给出独立说明：关联修订、节点／业务行为／控制节点／关系／数据对象／字段／表单计数、待确认数量、实际执行过的检查。检查说明不写入 JSON。
- 交付前用 `scripts/validate-process-v8.mjs` 做离线校验，并如实记录结果。技术通过后仍写“待业务核对”，不新增审批标记。

生成空白骨架并校验：

```powershell
node .agents/skills/single-process-authoring/scripts/validate-process-v8.mjs --emit-template <流程短名>-process-v8.json
node .agents/skills/single-process-authoring/scripts/validate-process-v8.mjs <流程短名>-process-v8.json
```

## D 待确认事项 Markdown

文件建议名：`<流程短名>-pending-items.md`。问题标识保持稳定，已解决问题保留处理结论，不因为换阶段重新编号。

| 问题号 | 类别 | 来源或冲突位置 | 关联对象/条款 | 需要回答的一件事 | 为什么影响后续 | 需确认主体 | 状态 | 解决依据 |
|---|---|---|---|---|---|---|---|---|
| Q-001 | 业务事实/设计决定/结构/评分/负荷数据 | [来源] | [稳定标识] | [明确问题] | [具体影响] | [已知主体；未知写待指定] | 待确认/已解决/暂缓 | [答复及确认记录；无则留待定] |

只给已知有权主体安排确认，不自动指定他人责任、承诺时限或声称已经通知。清单明确“影响完整 JSON 交付的事项”“仅影响报告结论的事项”和“尚未编码内容”，避免将文件结构完整误认作业务完整。

**部门评审线下进行，不进本清单**。要外部门表态或供数的事项不进待确认清单、不登记问题号，也不在制度正文留痕；清单只登记编制方自己能闭合的缺口。

| 类别 | 例子 | 状态怎么写 |
|---|---|---|
| 编制方自己的缺口 | 自检发现的遗漏、自造的错字、评分未经复核、图件未生成 | 「未解决」——这类才挡交付 |
| 编制方待对齐 | 与现有文件对同一事给出不同规定的实质冲突（两类文件各有一套口径） | 「编制方待对齐」——**不写成“待部门确认”**，写明双方出处与取证经过 |

要外部门表态或供数的事项（主体职责、判据、时限、保管口径、归口岗位、负荷参数、表单归口）由编制方按设计口径直接写入成果；它们既不是阻断项，也不占问题号。部门评审在公司内部线下进行，属编制流程之外。

**登记“与源材料冲突”之前先查证出处**。看到“同族文件写法不一致”“源材料像是错的”这类线索，先回到实际文件取证：把原始文件解包／按文件时间排序，确认这个字样最早出现在谁身上。经验教训是——本批生成脚本引入的错字曾被登记成“两批前缀冲突、需外部裁决”，发给受控编号归口后对方无从回答，因为那个冲突根本不存在。查不出外部出处的，按编制方自己的错误处理并改正，不进清单；**改正时连生成脚本一起改**，否则重跑会把错字写回来。确属外部不一致的，写明双方来源与取证经过再登记。

## E 四项成果一致性复核

复核是**双向**的。离线校验器只检查 JSON 内部的结构与引用，「制度写了、JSON 没写」或「编号与公司编号体系冲突」这类跨文件差异不会产生任何校验错误，必须人工对照。

**JSON → 制度**（JSON 里的每一项在制度中有对应表述）：

流程名称与范围；部门岗位与职责；行为顺序和分支；表单名称与编号；字段定义和引用；记录控制；稳定标识；修订标记；尚未确认事项。

**制度 → JSON**（制度里写明的每一项事实在 JSON 中有对应编码）：

| 制度中的事实 | JSON 对应位置 | 容易漏的地方 |
|---|---|---|
| 时限、期限、反馈时点 | 对应行为的 `timing` | 制度逐条写了期限，而 `timing` 整列为空 |
| 触发条件 | `trigger` | 只在第 5 章出现，未回填 |
| 完成标准 | `completion_standard` | 制度写了多档结论，JSON 只有一句 |
| 退回、并行、会签 | `loop`／`parallel` 关系、`countersign_*` | 制度写了会签而 JSON 无会签设置 |
| 判据数值（阈值、分档、授权层级） | 无对应字段 | 保留在制度正文与待确认清单，不得塞入不相干字段 |
| 记录控制与保管期限 | 无对应字段 | 同上 |

**受控编号要再做一次外部核对**：技术标识只需文档内唯一，但文件编号、表单编号还要与公司编号体系和平行文件一致。逐项比对本程序的文件编号与各表单编号，是否与同系列文件（同一发文部门的其他程序文件、编号管理规定、模板）的编号规则一致。发现不一致时**先查证出处再登记**（见 D 节）。确属外部不一致的写明双方来源，**不静默改写其中一侧**；查出是自己产物引入的错字，按自己的错误改正并连生成脚本一并改。

报告不得出现 JSON 或已确认协作事实中找不到的工作，也不得遗漏已经识别的协作贡献。实际更改职责、路径或字段时，给出四项成果的受影响位置；未重新核对的报告段落标为过期。技能文本自检、本地离线校验、3001 页面业务提示处理和正式审核分别记录；部门评审线下进行，不在本包内记录。
