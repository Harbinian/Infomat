# 续接与修正

以下每种模式可单独进入。先确认本次要求的当前文件是否齐备；文件缺失时暂停精确修改，继续不依赖该文件的澄清，不凭记忆补内容。

## 1 中断后继续

依据已提供的最新 JSON、四项成果中已有的文件和上次续接摘要，继续同一个单流程编制。先核对 `process_ref`、版本、修订和当前阶段，说明实际读到哪些文件；最新 JSON 与旧摘要的冲突不能自行确定时，提出关键问题，不能用旧内容覆盖新文件。复用已确认内容，保留稳定标识和待确认问题号，不从头访谈。简短说明当前位置、缺项和已过期成果，直接完成可确定的工作；仍缺关键决定时再进入必要访谈。

## 1b 续编旧稿与切换版本

先按原文件的 V7、V8 或 V9 版本读取和校验，保留来源、稳定标识、数组顺序及迁移归档。V9候选与目标接收支持分开；取得配套规则和模板后另存转换稿，不仅改版本号，不改写 `migration.source_schema_version` 为目标版本。

`--promote`仍仅做V7→V8标识转换，不证明导入迁移完成，也不转换V9。页面如何规范化以本次目标实际代码与差异结果为准，不固定旧版行为。摘要按文件版本从本机结构计算，不能混用或当作运行实例证明，见[结构版本与兼容](structure-versioning.md)。

## 2 保存续接摘要

停止新增业务问题，输出可保存的续接摘要：资料清单及读取范围、目标版本与摘要、当前草稿修订、`process_ref` 及关键对象标识、阶段进度、已确认决定与来源、待确认事项、未编码内容、六维评分及复核状态、工作量情景和参数来源、实际校验记录、过期成果、下一条问题。同时指出需要保存的最新 JSON 和 Markdown，不声称已在 3001 或下次会话中自动保存。没有完整 JSON 时如实标注。

## 3 按校验结果修正

输入是当前完整 JSON ＋ 问题清单 ＋ 相关确认。问题清单有两个来源，处理口径一致：

| 来源 | 形态 | 边界 |
|---|---|---|
| 本地离线校验 | `scripts/validate-process-v8.mjs` 输出的 `path`、`keyword`、`message`、`error_id` | 只能报结构、引用、端点、节点类型、字段归属等可机器判定的问题 |
| 3001 页面 | 导入后的结构错误、页面业务提示 | 页面业务提示可能涉及业务缺项，不等于结构错误 |

先保持 `process_ref`、既有稳定标识、未受影响业务内容及数组顺序，仅修正可由当前规则确定的问题。把问题分成结构／引用／节点语义错误、业务待确认、页面提示三类：可确定的技术错误直接修复并简短说明，不要求逐阶段确认；需要补充业务事实时可以集中收集关联信息，关键业务新决定仍明确确认。不得为通过检查删除对象、清空数组、虚构岗位、改待定为已确认或重新编号。修正后输出完整 JSON 及受影响的制度、报告、待确认项位置；尚未实际回到 3001 复验时只写“待复验”，不宣称通过。

## 4 修改已经确认的决定

先定位影响的制度条款、`behavior_ref`、关系、数据字段、表单、主责／协作贡献、评分和周期参数，说明直接影响。当前请求已明确决定及授权时直接应用，不重复确认；尚未明确的新责任、权限或关键分支选择仍须确认。保留未受影响内容和稳定标识，更新四项成果，并标注仍需重新校验的部分。用户要求与材料冲突时先指出，不静默覆盖。

## 5 只补充工作量数据

本轮只补充工作平衡报告，流程与制度设计暂不改变。以最新 JSON 和协作确认记录建立贡献清单，复用已有参数；缺少的业务量、投入时间、返工、参与人数或容量可集中收集，必要访谈默认每轮收口一个关键决定。区分实测、估计和待补，低／常规／高情景需自洽。未知不当 0，不将等待计成人工，不将六维分数乘到工时。若发现流程事实必须改变，先登记建议，等确认后再另行修改制度与 JSON。

## 6 输出阶段草稿

输出当前阶段草稿及简短交接说明，不新增未确认事实。能合法编码的当前内容按本轮明确的目标结构输出；无合法待定表示的必填值不能猜填，相关内容保留在 Markdown 并逐项列出“尚未编码内容”。明确这不是完整最终包。提供本轮摘要、待确认项和下一阶段依赖，保留后续继续编制所需稳定标识。

## 7 生成最终待核对包

按四项成果模板复核并输出：制度正文 Markdown、完整单流程目标版本 JSON、工作平衡报告 Markdown、待确认事项 Markdown。默认不生成 Word 或封面；用户指定 Word 时，由同源正文按指定模板或[制度编写规范](document-standard.md)中的版式生成。制度不含绘制的流程图，第 6 章保留人工插图边界。报告包含六维逐项依据、主责及协作、典型路径与周期负荷。若仍有阻止完整交付的问题，明确输出阶段草稿及未完成项，不把它包装为最终完整成果。

交付前对 JSON 运行本地离线校验，并按[四项成果模板](output-templates.md)第 E 节做**双向**一致性复核：JSON → 制度，以及制度 → JSON。第二向不可省——校验器不会因为「制度写了期限或会签、JSON 没有对应编码」而报错，只有人工逐条回查才能发现。受控编号另做一次外部核对，比对同系列文件的编号规则。逐项说明实际执行过的检查与待 3001 检查的边界。一次先输出一个完整文件，避免 JSON 中断和遗漏。

## 8 切换目标结构版本

目标 3001 变更版本或摘要时，先取得配套规则、模板和结构，比较兼容要求，列出受影响字段和不可自动迁移内容。不只改 `schema_version`，不按旧版输出或丢弃新字段，也不自动降级。规则不完整时暂停 JSON 改版，业务访谈仍可继续。原文件保留，转换稿另存；导入和源文件保护以实际检查为准，检查通过后仍需业务核对。

版本或摘要不一致时，用空白模板与离线校验器核对：`--emit-template` 输出的骨架带当前服务的结构版本，`validate-process-v8.mjs` 输出的摘要可与本轮明确取得的同版本目标摘要比对。摘要不同即表示目标已变，按本模式处理。
