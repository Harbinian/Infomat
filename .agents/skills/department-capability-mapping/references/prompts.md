# 部门能力、流程、系统映射提示词套件

## 项目术语口径

在任何交付物标题、图例、表头、统计卡片、节点标签、悬停提示和审查文字中，统一使用以下要素名称，不得改写为编号前置或其他简称：

| 编码 | 统一名称 |
|---|---|
| D1 | 部门（D1） |
| D2 | 办公室（D2） |
| L1 | 能力域（L1） |
| L2 | 业务能力（L2） |
| L3 | 业务流程（L3） |
| A1 | 业务行为（A1） |
| A2 | 业务行为（A2） |
| S1 | 应用系统（S1） |
| S2 | 应用模块（S2） |

办公室（D2）和应用模块（S2）只在组织或系统资料支持时纳入。业务行为（A1）/业务行为（A2）属于下游行为拆解层，本提示词只在用户明确要求时展开。

## 原文识别增强规则

- 封面/正文合并：当同一制度存在 `*封面.docx` 与 `*正文.docx`（或等价拆分）时，必须视为同一份制度文件；文件号/版次优先从封面提取，条款与流程细节从正文提取，最终引用仍统一为 `文件号-版次《文件名》`。
- 图片型证据提示：当 docx 内含图片（`word/media/*`）时，默认存在流程图/表单截图等非纯文本证据；对涉及流程节点、表单字段、泳道角色的结论，证据类型必须标注为 `原文明确-流程图` / `原文明确-表单`，或明确写“图中未明确/待补”，不得用推断补齐。
- 文件名仅作弱证据：不得把文件名中的编码/版次直接当作已核验的文件号/版次；允许临时以文件名推断填充，但必须在备注或待确认问题中标注“文件名推断，待核验”，并在后续以封面/页眉/正文或编制表校验。

## 1. 向部门收集资料

请不要直接要求部门提交“业务能力、业务流程、系统映射关系”。这类抽象工作由信息化/架构人员完成。

请部门按以下清单提交现有资料：

1. 本部门正在执行的规章、管理规则、管理程序、管理标准、操作规程。
2. 与业务执行有关的流程图、流程说明、流程模型。
3. 表单、台账、记录模板、审批单、检查单、统计报表。
4. 现有系统中的菜单、页面、字段、报表或截图。
5. 部门认为“没有制度但实际在做”的关键工作清单。

提交时请尽量保留原文件名、文件号、版次、适用范围和附件，不需要部门自行抽象能力层。

## 2. 文档盘点提示词

你是企业信息化架构师。请基于我提供的部门制度、程序、标准、表单、流程说明等资料，先完成文档盘点。

输出表格字段：

- 序号
- 文件名称
- 文件号
- 版次
- 文件类型
- 责任部门
- 流程组/主题
- 是否有流程附件
- 是否有表单/台账
- 备注

要求：

- 文件号和版次必须来自文件正文、页眉、封面或体系文件编制表。
- 如果文件号缺失，标注“待分配编号”。
- 如果文件为空、损坏或无法读取，明确标注。
- 不要在此阶段急于抽象能力，先把证据目录建好。

## 3. 能力层抽象提示词

你是企业业务架构师。请基于部门提交的制度、流程、标准、表单和台账资料，抽象该部门的业务能力层。

要求：

- 能力域（L1）控制在5-9个，表达稳定的治理主题。
- 业务能力（L2）使用名词性短语，表达部门”能够持续完成什么管理工作”。
- 业务能力（L2）命名必须经过事实校验：优先使用制度标题、条款标题、表单名称、职责描述或正文中反复出现的业务用词。
- 如果为了架构表达增加“治理、绩效、资源、生命周期、风险、合规”等抽象词，必须能从引用条款中证明该扩展含义；证明不足时，改回原文口径，把扩展含义放在流程描述或抽象理由中。
- 业务流程（L3）使用具体工作表达，表达“实际如何做、如何流转、如何记录”。
- 不要把文件名直接当能力名，也不要把表单名直接当流程名。
- 如果多个制度共同服务同一管理目的，可以归并为一个流程。

输出：

| 能力域（L1） | 业务能力（L2） | 业务流程（L3） | 对应制度/表单 | 抽象理由 | 能力命名校验 |

## 4. 流程制度依据提示词

请为每一条业务流程补充可追溯制度依据。

要求：

- 制度依据必须具体到：`文件号-版次《文件名》§条款号`。
- 如果文件号待分配，写：`待分配编号《文件名》§条款号`。
- 如果文件为空或未提供，写：`文件为空，条款待补` 或 `文件未提供，条款待补`。
- 不要只写文件名称。
- 条款号应来自原文编号，例如 `§6.1`、`§6.2.3`、`§7.1`。
- 如果一条流程由多个文件共同支撑，用分号分隔。

输出字段：

| 业务流程（L3） | 制度依据（文件号/条款） | 证据充分性 | 待确认问题 |

## 5. 应用系统映射提示词

请将业务流程映射到员工侧应用系统。

系统口径只能使用：

- OA
- MES
- PLM
- ERP

规则：

- 不要把MDM写入应用系统字段。MDM不是面向全体员工的信息化系统。
- 如果一个流程需要多个系统，用 `、` 分隔，例如 `OA、ERP`。
- 如果四类系统都不适合，应用系统字段留空，并说明原因。
- MES可以作为现场任务管理平台，也可以承载设备设施状态、巡检维修、能源计量、监测或设备数据采集。
- OA适合审批、通知、培训、报告、归档、责任留痕、事故调查和整改闭环。
- PLM适合建设项目、工程设计、技术方案、设计审查、项目技术资料协同。
- ERP适合费用、预算、采购、库存、备件、耗材、供应链、财务落账。

输出字段：

| 业务流程（L3） | 应用系统（S1） | 系统设计依据 | 不适合其他系统的原因 |

## 6. MDM建设要求提示词

请注意：MDM不作为员工侧应用系统参与流程映射。请单独从业务资料中识别MDM建设要求。

请识别以下主数据对象：

- 通用稳定对象：客户、供应商、合同、项目、订单、产品/物料、组织、岗位/人员、表单模板、编码规则、分类、状态、有效期等。
- 部门特化对象：从资料中抽取该部门确实维护或反复引用的对象，例如设备、设施、能源计量器具、消防设施、危险源、风险点、环境因素、污染源、排口、法规条款等；不要把示例强行套给所有部门。
- 编码对象：需要统一编码、分类、层级、责任部门、状态、有效期的对象。
- 跨系统引用对象：需要被OA、MES、PLM、ERP共同引用的数据。

输出字段：

| 主数据对象 | 来源业务流程（L3） | 关键字段 | 数据责任部门 | 维护系统/入口 | 消费系统 | 治理要求 |

要求：

- 明确黄金源、维护责任、状态生命周期、版本/有效期和停用规则。
- 不要把MDM描述成审批、检查、整改、培训等过程办理系统。

## 7. Markdown映射交付提示词

请形成一份独立的部门、能力、流程、系统映射关系Markdown文档。

必须包含：

- 文档来源与口径说明
- 全域映射表
- 汇总统计
- 能力域（L1）分布
- 系统承载分布
- 与既有映射口径差异
- 分层结构说明
- 后续使用建议

全域映射表字段：

| 序号 | 部门（D1） | 能力域（L1） | 业务能力（L2） | 业务流程（L3） | 制度依据（文件号/条款） | 应用系统（S1） | 系统设计依据 |

约束：

- 应用系统只能是OA、MES、PLM、ERP或空。
- 不要在应用系统字段出现MDM、EHS、文控系统、能源管理系统、环保监测系统等非本次口径系统。
- 留空项必须在说明中解释。

## 8. HTML桑基图交付提示词

请仿照既有说明会网页风格，生成一个独立HTML桑基图页面。

页面要求：

- 使用ECharts桑基图。
- 提供”全域总览”和按能力域（L1）切换的明细视图。
- 全域总览建议结构：部门（D1）→ 能力域（L1）→ 业务能力（L2）→ 应用系统（S1）。
- 明细视图建议结构：部门（D1）→ 业务能力（L2）→ 业务流程（L3）→ 应用系统（S1）。
- 页面里的能力域页签、筛选器、分组标题和卡片标题必须写出覆盖层级范围，例如 `能力域（L1-L3）`；不得裸写“能力域”让审核人猜层级。
- 桑基图的业务流程（L3）列必须在可见标签中加入序号或稳定 L3 编号，例如 `L3-04 月度绩效评分...` 或 `04 月度绩效评分...`，不得只在 tooltip 或隐藏字段中保留编号。
- 默认采用标准从左到右桑基图布局。流程节点较多、横向阅读拥挤时，可以提供自上而下作为可选布局切换，但除非用户明确要求，不把自上而下设为默认。
- 不得为了减少拥挤而删除“业务能力”层；全域总览仍应保留 `部门（D1）→ 能力域（L1）→ 业务能力（L2）→ 应用系统（S1）`。如节点过多，可对业务能力节点使用编号/短标签，并在悬停提示和下方明细表中保留完整名称。
- 右侧系统节点只允许出现OA、MES、PLM、ERP。
- 应用系统为空的流程不绘制到系统节点，但必须保留在下方表格。
- 每个桑基图节点、连线、悬停提示和明细表行都必须展示依据。原文明确项展示制度依据、原文摘录或对象链；推断项展示推断依据、原文锚点和缺失证据。
- 页面必须有证据图例：原文明确项使用正常配色；`上下文推断`、`分析拆分`、文件名推断、系统落位推断等推断项必须使用不同警示色；`未见...证据，待补` 或证据不足项使用更强提示色或描边。推断项不能和原文明确项同色。

页面必须包含：

- 标题、口径说明、草案状态。
- 证据颜色图例，说明原文明确、推断/分析拆分、证据不足三类视觉含义。
- 统计卡片：部门（D1）、能力域（L1）、业务能力（L2）、业务流程（L3）、应用系统（S1）。
- 切换按钮。
- 桑基图。
- 能力域（L1）规模和系统承载分布。
- 明细表。

明细表字段：

| 序号 | 部门（D1） | 能力域（L1） | 业务能力（L2） | 业务流程（L3） | 制度依据（文件号/条款） | 原文或推断依据 | 应用系统（S1） | 系统设计依据 |

交互要求：

- 悬停流程连线时显示业务流程、制度依据、原文或推断依据、系统设计依据。
- 悬停系统节点时显示系统设计依据和应用系统落位依据；推断落位必须用推断色标识。
- 桑基图节点密集时应提供能力域筛选或横向/纵向布局切换；默认读法仍保持从左到右。
- 表格中长文本必须自动换行，不能遮挡或溢出。
- 明细表必须包含序号列；常见桌面宽度下优先自适应显示，不应依赖横向滚动。必要时压缩“业务流程”和“制度依据（文件号/条款）”列宽并自动换行。
- 桑基图中的应用系统节点标签（OA、MES、PLM、ERP）必须完整显示，不能被容器右边界截断；必要时增加右侧留白、扩大标签宽度或调整系统节点标签位置。

## 9. 可视化审查提示词

请审查这份部门能力流程系统桑基图是否适合作为其他部门模板。

重点检查：

- 是否只出现允许的应用系统（S1）口径。
- 是否把后台主数据能力误写成应用系统。
- 是否每条流程都有文件号/条款级依据。
- 是否每个节点、连线、tooltip 和明细行都显示原文或推断依据。
- 是否把推断项用不同颜色和图例清楚标识，且没有与原文明确项同色。
- 能力域页签、筛选器、分组标题和卡片标题是否标明层级范围，例如 `能力域（L1-L3）`。
- 业务流程（L3）节点可见标签是否带序号或稳定 L3 编号，便于和明细表逐条对应。
- 是否存在流程和系统强行对应。
- 业务能力（L2）名称是否与制度标题、条款标题或正文业务用词一致；是否存在未经证明的泛化命名。
- MES是否合理区分任务管理、设备数据、能源计量、现场执行等用法。
- 图、表、统计数是否一致。
- 桑基图在节点密集时是否提供能力域筛选或可选布局切换，且默认读法是否保持从左到右。
- 表格是否可读，长文本是否换行。
- 明细表是否包含序号，且在常见桌面宽度下不需要横向滚动。
- 桑基图应用系统标签是否完整显示，无截断。
- 页面风格是否接近既有说明会网页。

输出：

| 问题 | 严重程度 | 位置 | 修改建议 |

## 10. 一体化主提示词

你是企业信息化业务架构师和数据治理顾问。请基于我提供的部门制度、程序、标准、表单、台账、流程说明和既有映射口径，完成部门（D1）、能力域（L1）、业务能力（L2）、业务流程（L3）、应用系统（S1）和MDM建设要求分析。

工作要求：

1. 不要求部门自行抽象能力层，能力和流程由你根据制度资料识别。
2. 先盘点文件，再抽象能力，不要直接跳到系统设计。
3. 业务能力（L2）是抽象类，业务流程（L3）是具体类。
4. 业务能力命名必须先做事实校验：与制度标题、条款标题或正文业务用词对齐；不能用未经条款证明的抽象词扩大含义。
5. 每条流程必须追溯到具体制度依据，格式为 `文件号-版次《文件名》§条款号`。
6. 应用系统只能使用 OA、MES、PLM、ERP；不适合则留空。
7. MDM不是员工侧应用系统，不得出现在应用系统字段。MDM建设要求单独输出。
8. MES可以作为任务管理平台，也可以收集和承载设备设施、能源计量、监测等现场数据。
9. 对每条流程给出系统设计依据。
10. 输出Markdown映射文档和HTML桑基图时，保持口径一致，并检查系统标签不被截断。
11. 对不确定、缺文件号、空文件、条款待补的地方如实标注。

最终输出：

- 部门能力层与MDM建设要求。
- 部门-能力-流程-系统映射关系Markdown。
- 桑基图HTML。
- 校验清单：流程数、能力命名事实校验、证据覆盖、系统口径、图表标签显示、留空项、待确认问题。

## 11. 增量更新提示词

你是企业信息化业务架构师。请以增量方式更新部门能力流程系统映射，不要全量重做。

### 第一步：变更检测

1. 读取现有的 `{部门名}部门-能力-流程-系统映射关系.md`，提取已有 业务流程（L3）清单和制度依据列表。
2. 读取或生成源文件清单：`文件路径 / 文件名称 / 文件号 / 版次 / 文件大小 / 修改时间 / 正文哈希 / 备注`。正文哈希可基于提取出的正文文本计算，不要求包含二进制格式噪声。
3. 对比源文件目录、编制表 xlsx 和上一版源文件清单，识别：
   - 新增文件（新文件号）
   - 升版文件（同文件号、新版次）
   - 废止文件（文件号从目录中消失）
   - 条款修订（同文件号版次、但正文哈希或关键条款内容变更）
4. 如果文件号和版次相同但正文哈希变化，不得判定为“无变化”，必须作为条款修订进入影响分析。
5. 输出变更清单，列出每个变更的影响范围（能力域（L1）/业务能力（L2）/业务流程（L3））。

### 第二步：增量处理

- 仅读取变更的源文件，不重读未变更文件。
- 新增文件 → 按标准流程盘点、抽象能力、映射流程、补充证据。
- 升版文件 → 对比新旧版次差异，更新受影响的能力名称、流程描述、制度依据条款号。
- 废止文件 → 在映射表中标记对应流程为"已废止"（使用删除线前缀），不得删除行。
- 条款修订 → 仅更新对应流程的证据引用和流程描述。

### 第三步：输出

- 在原映射文档末尾追加 `## 变更记录` 章节，格式如下：

```
### YYYY-MM-DD 变更

| 变更类型 | 影响范围 | 说明 |
|---|---|---|
| 新增制度 | 业务能力（L2）: {能力名} | {文件号} {版次} 新增，补充 业务流程（L3） |
| 文件升版 | 业务流程（L3）: {流程名} | {文件号} V{x}→V{y}，{变更摘要} |
| 文件废止 | 业务流程（L3）: {流程名} | 标记为已废止，保留历史记录 |
```

- 更新映射表中的受影响行。
- 汇总统计数字重新计算。
- 仅当映射数据实际变化时才重新渲染桑基图 HTML。

### 禁止事项

- 禁止重读或重抽象未变更的源文件。
- 禁止删除已废止的流程行。
- 禁止在无映射数据变更时重渲染桑基图。
- 禁止改写整个文档；增量运行只追加变更记录和更新受影响行。
