# 业务行为映射提示词套件

## 项目术语口径

在任何交付物标题、图例、表头、统计卡片、节点标签、悬停提示和审查文字中，统一使用以下要素名称，不得改写为编号前置或其他简称：

| 编码 | 统一名称 |
|---|---|
| D1 | 部门（D1） |
| D2 | 办公室（D2） |
| L1 | 能力域（L1） |
| L2 | 业务能力（L2） |
| L3 | 业务流程（L3） |
| A1 | 业务行为（A1） |
| A2 | 业务行为（A2） |
| S1 | 应用系统（S1） |
| S2 | 应用模块（S2） |

业务行为（A1）是本技能的主拆解层。业务行为（A2）只在用户要求更深拆分时启用。办公室（D2）和应用模块（S2）只在组织或系统资料支持时纳入。

## 原文识别增强规则

- 封面/正文合并：当同一制度存在 `*封面.docx` 与 `*正文.docx`（或等价拆分）时，必须视为同一份制度文件；文件号/版次优先从封面提取，条款与流程细节从正文提取。引用与制度依据字段保持统一，不得把封面与正文当作两份制度。
- 图片型证据提示：当 docx 内含图片（`word/media/*`）时，默认存在流程图/表单截图等非纯文本证据；凡引用流程节点、泳道、审批节点、表单字段等信息，证据类型必须标注为 `原文明确-流程图` / `原文明确-表单`，或明确写“图中未明确/待补”，不得用上下文推断补齐。
- 文件名仅作弱证据：不得把文件名中的编码/版次直接当作已核验的文件号/版次；允许临时以文件名推断填充，但必须在 `核验提醒` 或 `备注` 标注“文件名推断，待核验”，并要求部门确认封面/页眉/正文中的正式编号与版次。

## 1. 业务行为（A1）分解提示词

你是企业业务架构师。请基于已完成的部门 业务流程（L3）映射，将每条 业务流程（L3）分解为 业务行为（A1）。

交付口径：输出为“部门审核稿”。不要假装所有判断已经最终定稿；要把原文依据、上下文推断、需要部门确认的点写清楚，便于部门逐条审核、修正和反馈。

前提：
- 已存在 `{部门名}部门-能力-流程-系统映射关系.md`
- 已存在对应的制度源文件

分解规则：
- 一个 业务行为（A1） = 一个角色完成一个可独立描述的任务动作，不是 UI 操作。
- 每条 业务流程（L3）拆出 3–8 个 业务行为（A1），按时间顺序或逻辑顺序排列。
- 业务行为（A1）编号格式：`{稳定业务流程（L3）编号}-A{两位序号}`，如 `0103-A01`。
- 稳定 业务流程（L3）编号优先使用上游映射中的 `业务流程（L3）编号` 或 `业务流程编号`；如果上游只有表格 `序号`，需用 `部门（D1）+ 能力域（L1）+ 业务能力（L2）+ 业务流程（L3）+ 制度依据` 生成并保留一个稳定 L3Key，不得因为表格排序、筛选或插入行而重排既有 业务行为（A1）编号。
- 抽象出来的 业务行为（A1） 也必须锚定原文对象或原文动作。`汇总核算`、`确认`、`处理`、`跟踪`、`形成结果` 等抽象动词不能单独证明输出物、审批类型、执行角色或目标部门；必须在依据、备注或核验提醒中说明抽象自哪个表单、台账、报告、流程节点、条款短语或审批链。

每个 业务行为（A1） 必须填写：

| 字段 | 说明 |
|---|---|
| 业务行为（A1）编号 | `{稳定业务流程（L3）编号}-A{两位序号}` |
| 业务行为（A1） | 角色+动作，如"提交危险作业申请"；当 `输入来源部门` 或 `输出目标部门` 非空时，必须在末尾追加跨部门标记：`【跨部门：入←{输入来源部门或空} 出→{输出目标部门或空}】`，空值省略对应半句 |
| 执行角色 | 岗位或角色名称 |
| 执行角色依据 | 原文职责、流程图泳道/节点、表单填报角色或推断说明 |
| 触发情景 | 什么事件触发此行为 |
| 触发情景依据 | 原文时点/事件、流程图分支/节点或推断说明 |
| 前置条件 | 执行前必须满足的状态条件（与触发情景分开） |
| 前置条件依据 | 原文条件、上游流程节点、表单状态或推断说明 |
| 数据输入 | 行为消费的数据对象或表单 |
| 数据输出 | 行为产出的数据对象或表单 |
| 输入来源部门 | 有受控传递证据时，填写该数据/表单/台账输出物从哪个部门传入；空=本部门内部或未见受控传递证据 |
| 输出目标部门 | 有受控传递证据时，填写该数据/表单/台账输出物传出到哪个部门；空=本部门内部或未见受控传递证据 |
| 审批类型 | 无审批 / 单人审批 / 多级审批 / 会签 |
| 应用系统（S1） | OA/MES/PLM/ERP 或空，多个用`、`分隔；为空时在备注说明 |
| 应用模块（S2） | 应用系统（S1）下的模块/菜单/页面；仅在有资料或系统设计依据时填写 |
| 制度依据 | `文件号-版次《文件名》§条款号` |
| 证据类型 | 原文明确-正文 / 原文明确-流程图 / 原文明确-表单 / 上下文推断 / 分析拆分 |
| 验收标准 | 仅限L3最终环节或跨部门交接前最后环节必填；可为完成条件、输出验收、交接条件、记录闭环标准 |
| 验收标准依据 | 来源条款/流程图/表单；关口环节制度未明确时写“制度未明确，待补验收标准”；普通过程环节写“不适用-过程环节” |
| 核验提醒 | 面向部门审核的确认事项，如具体岗位、关口验收、证据不足、推断待确认 |
| 部门确认意见 | 留给部门填写，可为空或“待部门填写” |
| 是否调整 | 待确认 / 无需调整 / 需要调整 |
| 调整建议 | 部门修正后的岗位、行为、触发、前置条件或验收标准建议 |
| 备注 | 制度未覆盖的灰色地带 |

约束：
- 每个 业务行为（A1） 必须说明系统支撑、记录载体或结果回写。只有在制度条款或流程逻辑支持时，才把应用系统（S1）填写为 OA/MES/PLM/ERP；四类系统都不适合时允许留空，但必须在备注中说明记录载体或不适配原因。
- 应用模块（S2）只能作为已确认应用系统（S1）下的模块/菜单/页面，不得用来替代不确定的应用系统（S1）。
- 不得为了避免空值而强行挂系统。现场人工行为可以存在后续系统回写，但应有证据或明确标注为分析推断。
- `输入来源部门` 或 `输出目标部门` 非空时，`业务行为（A1）` 字段必须带跨部门标记，作为跨部门流程设计的后续 join 线索；不得只依赖独立字段让审核人自己对照。
- `输入来源部门` / `输出目标部门` 只能依据受控传递证据填写：制度条款、流程图箭头、表单流转、台账交接、签收、通知、下发、反馈、接收等能证明输出物跨部门移动的证据。
- 不得把依据来源、附件清单、执行主体、协作参与方、审批方、归档方、外部动作责任方直接写成 `输入来源部门` / `输出目标部门`。若仅能证明“依据某部门文件/由某部门负责/需某部门参与”，写入 `前置条件依据`、`制度依据`、`备注` 或 `核验提醒`，并标注“未见受控传递证据，待补”。
- `审批类型` 只能按原文、流程图、表单签批栏或审批链证据填写。源对象只有一个审批/批准角色且无其他校对、审核、审定、会签、签发、复核节点时，才可写 `单人审批`；同一对象出现多个节点时写 `多级审批` 或 `会签`；未见审批/审核/批准/签发节点时写 `无审批` 或 “未见审批链证据，待补”。
- 当 `证据类型` 为 `上下文推断` 或 `分析拆分`，却填写 `单人审批`、`多级审批` 或 `会签` 时，必须在依据、备注或核验提醒中写明审批链证据。不能因为 `输出目标部门` 是某个人或部门，就推断审批类型。
- 触发情景和前置条件必须分开填写，不能合并。
- 执行角色必须是具体岗位/角色；如果原文只写部门、办公室、中心、小组、委员会等组织名称，保留原文但在核验提醒中写“请部门确认具体岗位/责任人：当前为部门/组织”。
- 不要把所有“无审批”业务行为（A1）都要求验收标准。验收标准仅限于某个业务流程（L3）的最终环节，或跨部门交接前的最后一个环节。草案编制、资料收集、内部沟通、过程跟踪等中间动作通常不单独设置验收标准，除非制度原文明确规定。
- 关口型无审批环节如果制度没有验收标准，不得编造，写“待补”，并在核验提醒中写“请部门确认是否需要验收/完成标准”。
- 跟踪类任务（跟踪、进度、监测、监督、闭环、催办、提醒）优先作为信息化系统能力设计，由OA/MES/PLM/ERP中的对应系统通过待办提醒、到期预警、状态看板、进度展示、超期提示或闭环记录实现，不要人为补一个验收标准。
- 不允许笼统写“原文明确”。必须区分 `原文明确-正文`、`原文明确-流程图`、`原文明确-表单`、`上下文推断`、`分析拆分`。
- 如果依据来自流程图图片，证据类型写 `原文明确-流程图`，依据中说明可见泳道、节点、判断条件或箭头关系；不要只写条款号。
- 证据类型为“上下文推断”或“分析拆分”的 业务行为（A1），必须在备注或对应依据字段中说明推断依据、原文锚点和原文缺失情况；若找不到原文锚点，不得把抽象动作写成确定结论。
- Never invent：不得为了让表格看起来完整而编造执行角色、触发情景、前置条件或验收标准。
- 语气要求：页面和表格使用“请部门确认”“待部门填写”“建议补充”这类审核稿口径，不使用“错误”“报警”等定责式措辞。

## 3. 跨部门事务建模提示词

请识别 业务行为（A1）中的跨部门数据流和事务。

### 受控传递证据优先

先确认是否存在受控传递证据，再填写跨部门字段。受控传递证据包括制度条款、流程图箭头、表单流转、台账交接、签收、通知、下发、反馈、接收等。没有受控传递证据时，不得凭业务逻辑推断跨部门输入/输出。

### 本部门内部行为 + 跨部门数据流

使用 业务行为（A1）主记录的 `输入来源部门` 和 `输出目标部门` 字段。受控输出物从/到其他部门，但行为本身由本部门执行。若来源只是制度依据、附件清单、职责主体、协作对象、审批人或归档对象，不填写跨部门字段，改写为依据、备注或核验提醒。

### 本部门参与、其他部门主导

当 业务行为（A1）中我方角色为"参与审核"、"协同签认"时：
- `执行角色` 填写我方参与角色
- `证据类型` 标注 `原文明确-正文` 或 `原文明确-流程图`（如果我方制度正文或流程图描述了此参与）
- 不得展开对方的内部行为

### 跨部门事务子表

当 `输入来源部门` 或 `输出目标部门` 非空时，填写：

| 协作部门 | 协作事项 | 我方职责 | 对方职责 | 数据交换方向 | 受控传递证据 |
|---|---|---|---|---|---|

没有受控传递证据的事项不要写入跨部门事务子表；登记为“未见受控传递证据，待补”，并说明缺少的是传递流程、接收角色、签收/通知记录，还是输出物名称。

## 5. 增量更新提示词

你是企业业务架构师。请以增量方式更新标准映射文档中的 业务行为（A1）映射，不要全量重做。

### 第一步：变更检测

1. 读取现有 `{部门名}部门-能力-流程-系统映射关系.md` 中的 `## 业务行为（A1）映射（BBM增补）` 章节，提取已有 业务行为（A1）编号清单和稳定 L3Key/业务流程（L3）编号对应关系。
2. 读取 业务流程（L3）映射文件的 `## 变更记录`，识别新增/修订/废止的 业务流程（L3）。
3. 对比源文件的文件号、版次、正文哈希或关键条款内容，识别制度依据变更。
4. 对新增 业务流程（L3） 分配稳定 业务流程（L3）编号；对既有 业务流程（L3）不因表格排序或序号变化而重排 业务行为（A1）编号。
5. 输出 业务行为（A1）层面的变更清单。

### 第二步：增量处理

- 新增 业务流程（L3） → 按标准流程分解 业务行为（A1）。
- 修订 业务流程（L3） → 仅重新分解该 业务流程（L3） 下的 业务行为（A1）；未变更的 业务行为（A1）保留不动。
- 废止 业务流程（L3） → 标记其下所有 业务行为（A1）为"已废止"（删除线前缀），不删除。
- 制度依据升版 → 重新验证受影响 业务行为（A1）的证据引用和审批流节点。
- 证据类型变更（如原"分析拆分"的 业务行为（A1）在新版制度中有了明确条款、流程图节点或表单字段）→ 更新为 `原文明确-正文` / `原文明确-流程图` / `原文明确-表单`，并更新依据。

### 第三步：输出

- 在 `{部门名}部门-能力-流程-系统映射关系.md` 的 业务行为（A1）章节末尾追加变更记录。
- 仅重渲染实际变更的流程图 md 文件。
- 仅当 业务行为（A1）数据变化或用户明确要求版式修正时，更新 H5/HTML 页面中的 业务行为（A1）域明细桑基图。

### 禁止事项

- 禁止重分解未变更的 业务流程（L3）。
- 禁止删除已废止的 业务行为（A1）行。
- 禁止在无 业务行为（A1）数据变更时重渲染桑基图。
- 禁止另建 `{部门名}A1业务行为映射关系.md`；业务行为（A1）主表、子表和变更记录必须并入 `{部门名}部门-能力-流程-系统映射关系.md`。

## 6. 完整性校验报告提示词

请基于所有已完成部门的 `{部门名}部门-能力-流程-系统映射关系.md` 中的 业务行为（A1）章节，生成跨部门完整性校验报告。

前提：所有目标部门的 业务流程（L3）映射和同一标准映射文档内的 业务行为（A1）映射均已完成。

### 校验规则

对每条跨部门引用（A 部门 业务行为（A1）的 `输入来源部门` 或 `输出目标部门` 指向 B 部门）：

1. 先核对 A 部门该跨部门字段是否有受控传递证据；若没有，标为 `待补证据`，不要当作已确认跨部门引用。
2. 在 B 部门标准映射文档的 业务行为（A1）章节中搜索对应的协作事项或数据交换。
3. 如果 B 部门存在对应 业务行为（A1）且覆盖了该交互 → 通过。
4. 如果 B 部门无对应 业务行为（A1）、无制度支撑、或尚未建模 → `未命中`，并说明可能是资料缺失、未建模、引用对象不是受控输出物，或对方部门非主责。

### 报告字段

| 来源部门 | 目标部门 | 触发业务行为（A1） | 数据类型 | 传递证据状态 | B部门状态 | 风险等级 | 建议 |
|---|---|---|---|---|---|---|---|

风险等级：
- `高`：核心业务依赖，B 部门无对应支撑可能导致流程断裂
- `中`：数据/报表依赖，影响信息完整性但不阻断核心业务
- `低`：信息性引用，缺少不影响主流程

### 输出

独立 Markdown 文件 `跨部门业务行为（A1）完整性校验报告.md`，包含：
- 通过项汇总
- 待补证据/未命中项明细（按风险等级排序）
- 每项的具体建议
- 未映射部门的清单（标注"待启动"或"资料未提交"）

## 7. 业务行为（A1）桑基图 HTML 交付提示词

请在已有部门能力桑基图基础上增加 业务行为（A1）域明细视图，生成独立 HTML 页面或更新既有 HTML。

### 使用入口

当用户在 BBM/业务行为（A1） 工作之后提出以下请求时，继续使用 `business-behavior-mapping` 完成 H5/HTML 更新：

- “BBM执行后更新H5”
- “更新HTML”
- “更新桑基图”
- “把业务行为（A1）加到页面”
- “像DCM一样更新H5页面”

不要因为目标文件是 HTML/H5 就切回 `department-capability-mapping` 重新做部门能力映射。DCM 只作为上游 能力域（L1）/业务能力（L2）/业务流程（L3）/应用系统（S1） 数据、既有页面结构和视觉风格参考；业务行为（A1）层页面更新由 BBM 负责。

输入资料：

- 已完成的 `{部门名}部门-能力-流程-系统映射关系.md`
- 同一标准映射文档中已完成或本次更新的 `## 业务行为（A1）映射（BBM增补）` 章节
- 既有部门能力桑基图 HTML/H5 页面（如存在）

输出策略：

- 既有 H5 页面存在时，优先原地更新。
- 既有 H5 页面不存在时，新建标准文件名 `{部门名}部门能力流程系统桑基图.html`。
- 不要新建 `{部门名}部门能力流程行为系统桑基图.html`。业务行为（A1）是同一张部门能力流程系统桑基图中的明细层，不是第二套可视化口径。
- 如果目录里已经同时存在 `{部门名}部门能力流程系统桑基图.html` 和 `{部门名}部门能力流程行为系统桑基图.html`，应把业务行为（A1）明细视图合并回 `{部门名}部门能力流程系统桑基图.html`，校验可用后删除重复的“行为系统”HTML。
- Markdown 同理：如果目录里已经同时存在 `{部门名}部门-能力-流程-系统映射关系.md` 和 `{部门名}A1业务行为映射关系.md`，应把 A1 主表、子表和变更记录合并回 `{部门名}部门-能力-流程-系统映射关系.md` 的 `## 业务行为（A1）映射（BBM增补）` 章节，校验后删除重复的 A1 Markdown。
- 全域总览继续沿用 DCM 结构；业务行为（A1）只进入 能力域（L1-L3）明细视图或专门的 业务行为（A1）明细视图。

结构要求：

- 全域总览保持 `部门（D1）→ 能力域（L1）→ 业务能力（L2）→ 应用系统（S1）`，不要在全域总览塞入 业务行为（A1）节点。
- 能力域（L1）明细视图使用 `业务能力（L2）→ 业务流程（L3）→ 业务行为（A1）→ 应用系统（S1）`。
- 页面里的能力域页签、筛选器、分组标题和卡片标题必须写出覆盖层级范围，例如 `能力域（L1-L3）` 或 `能力域（L1-A1）`，不得裸写“能力域”让审核人猜层级。
- 桑基图的业务流程（L3）列必须在可见标签中加入序号或稳定 L3 编号，例如 `L3-04 月度绩效评分...` 或 `04 月度绩效评分...`，不得只在 tooltip 或隐藏字段中保留编号。
- 如存在应用模块（S2）依据，可在悬停提示或明细表中展示为应用系统（S1）下的模块信息，不用应用模块（S2）替代应用系统（S1）。
- 业务行为（A1）节点可使用短行为标签，但必须让读者看到业务动作和执行角色；完整 业务行为（A1）放在悬停提示和下方明细表中。
- 业务行为（A1）节点前端展示必须使用 `A1序号/稳定编号 + 业务行为（A1） + 执行角色`，例如 `A04 编制公司月度综合打分表｜经营发展部部长`；不得只显示 业务行为（A1）编号，也不得完全隐藏序号。完整 `业务行为（A1）编号` 仍需放在 tooltip 和明细表追溯。
- 当 `输入来源部门` 或 `输出目标部门` 非空时，业务行为（A1）节点的可见标签需包含跨部门标记（可用 `【跨部门】` 简写），tooltip 与下方明细表必须展示 `输入来源部门`、`输出目标部门` 的完整值。
- 只有通过受控传递证据核验的 `输入来源部门` / `输出目标部门` 才进入跨部门可视化标签、tooltip 和明细表；证据不足的依据来源、职责主体或外部执行方放入 `核验提醒` / `备注`，不要画成跨部门流。
- 每个桑基图节点、连线、tooltip 和明细表行都必须展示依据。原文明确项展示制度依据、原文摘录或对象链；推断项展示推断依据、原文锚点和缺失证据。
- `证据类型` 为 `上下文推断` 或 `分析拆分` 的节点、连线、徽标、明细表行必须使用不同于原文明确项的警示色，并在页面图例中解释。证据不足或 `未见...证据，待补` 的项应再用更强提示色或描边，不能和原文明确项同色。
- 业务行为（A1）这一层/这一列必须绑定行为名称字段，并追加可见序号，不得只绑定编号字段。如果数据数组形如 `[业务行为（A1）编号, 业务行为（A1）, 执行角色, ...]`，桑基图显示标签应由第 1 项提取短序号并拼接第 2 项和第 3 项，即 `A序号 + 业务行为（A1） + 执行角色`，不能只取第 1 项编号。
- 如果图表内部需要唯一节点键，可以把业务行为（A1）编号作为隐藏 key、`meta.id` 或内部 `name`，但必须用 `label.formatter` 等方式把可见标签改成 `业务行为（A1）+ 执行角色`。编号只能出现在悬停提示或单独命名为 `业务行为（A1）编号` 的列中。
- 只允许 OA、MES、PLM、ERP 作为系统节点；应用系统（S1）为空的 业务行为（A1）不画到系统节点，但保留在明细表。
- 默认采用从左到右布局；节点拥挤时可提供自上而下切换，但不默认改成自上而下。
- 如果执行角色是部门、办公室、中心、小组、委员会等组织名，而不是具体岗位/角色，桑基图节点和明细表必须显示“请部门确认具体岗位/责任人”。

悬停提示至少包含：

- 业务行为（A1）编号
- 业务行为（A1）
- 执行角色
- 触发情景
- 前置条件
- 审批类型
- 验收标准
- 制度依据
- 证据类型
- 原文或推断依据
- 应用系统（S1）或记录载体说明
- 应用模块（S2）
- 核验提醒

明细表字段：

| 序号 | 业务行为（A1）编号 | 业务能力（L2） | 业务流程（L3） | 业务行为（A1） | 执行角色 | 触发情景 | 前置条件 | 审批类型 | 验收标准 | 制度依据 | 证据类型 | 原文或推断依据 | 应用系统（S1） | 应用模块（S2） | 核验提醒 | 部门确认意见 | 是否调整 | 调整建议 | 备注 |

版式要求：

- 明细表必须包含序号列。
- `业务行为（A1）`列显示行为名称/动作文本；追溯编号只能放在`业务行为（A1）编号`列，不能把编号填进`业务行为（A1）`列。
- 常见桌面宽度下优先自动换行，不依赖横向滚动；必要时压缩 `业务流程（L3）`、`触发情景`、`前置条件`、`制度依据` 列宽。
- 明细表用浅色填充或左侧色带区分不同 业务流程（L3），提高连续阅读时的辨识度。
- 无审批且处于L3最终环节或跨部门交接前最后环节、但缺少验收标准的行为，必须在明细表中给出“请部门确认是否需要验收/完成标准”；普通过程环节不得误提醒。
- 跟踪类任务在明细表中可提示“由系统待办提醒/进度展示承载”，不要标成缺验收标准。
- 明细表应包含部门反馈入口：`部门确认意见 / 是否调整 / 调整建议`，默认可填“待部门填写 / 待确认 / ”。
- 系统节点标签 OA/MES/PLM/ERP 必须完整显示，不能被边界截断。
- 图、表、统计数字必须与 业务行为（A1）映射数据一致。
- 每个部门输出目录中只保留一张标准桑基图 HTML：`{部门名}部门能力流程系统桑基图.html`。不得同时交付“部门能力流程系统桑基图”和“部门能力流程行为系统桑基图”两张口径相近的页面。
- 每个部门输出目录中只保留一份标准映射 Markdown：`{部门名}部门-能力-流程-系统映射关系.md`。不得同时交付“部门-能力-流程-系统映射关系”和“A1业务行为映射关系”两份口径相近的 Markdown。
