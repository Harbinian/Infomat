## 二、范围判断：什么允许直接修

bug 必须具有可核验依据：实际实现违反已确认行为、受支持技术契约、权限或数据完整性约束，或存在可证明的资源、错误处理、输入保护、构建、CSP、验证工具缺陷。记录准确路径、触发条件、预期依据、实际结果和影响；能复现时先复现，无法安全复现时提供明确源码路径和等价隔离证据，不把猜测写成确定缺陷。

允许为修复本轮相关 bug 增加必要的最小依赖改动、回归入口和已失实的技术说明。新增文件必须能说明其与该 bug 的直接关系。修复应保持现有业务语义、旧数据、公开标识和兼容合同；缺少业务依据时，只记录待确认，不自行选择规则。

以下事项不算 bug，不得以“收尾”“最佳实践”“架构完整”“性能提升”或“提高代码质量”为理由实施：

- 新功能、界面美化、布局重做、便利性增强、业务范围扩大。
- 未获授权的 B 卡剩余架构改造、模块拆分、抽象统一、目录整理、全仓扫描治理。
- 集中限流或日志平台引入、依赖升级、新服务、数据模型或审批链变化。
- 为完成状态好看而补造业务事实、迁移规则、权限、验收或开启记录。

对于非 bug 的建议，只在最终报告中简短登记“不在本轮范围”，不实施，不反复研究。B 卡尚未结项不等于必须把剩余设计全部实现；R 完成也不自动令 B 卡完成。
