# PMO项目计划管控体系建设方案 V1

## 1. 项目名称

数字化项目计划管控与甘特图体系建设项目

## 2. 项目定位

本项目不是单纯制作一张甘特图，而是帮助 PMO 组建立一套可持续运行的项目计划管控机制。

目标是用统一的 WBS、资源池、里程碑、风险台账、问题台账、变更台账、周推进表和 H5 看板，持续管理数字化底座项目进度，降低管理难度，提升汇报效率。

## 3. 建设目标

1. 建立数字化底座项目统一 WBS 结构。
2. 建立 Office Project 可导入的标准计划表。
3. 建立 PMO 周更新、月汇报、阶段门评审机制。
4. 建立 H5 甘特图看板，提高查阅、筛选、汇报效率。
5. 建立风险、问题、变更台账，避免把所有管理信息塞进 Project。
6. 建立资源池简化规则，避免人名、供应商组合、临时角色污染 Project 资源池。
7. 建立组织协同与部门配合机制，明确 RACI、阶段性确认、历史问题治理台账、默认处理规则和升级路径。

## 6. PMO工作机制

### 6.1 组织协同与部门配合机制

项目不默认各部门因参与信息化建设获得额外奖励。PMO 的协同机制应建立在风险共担、收益可见、边界清楚、阶段确认四件事上，避免把配合要求写成笼统口号。

部门配合任务必须同时明确五个要素：

- 输入：需要部门提供的资料、样本、人员或判断。
- 输出：交付结果的具体形态，例如清单、确认单、字段口径、测试记录。
- 期限：到日期或到阶段门，不使用“尽快”“持续配合”作为任务期限。
- 默认处理：逾期不反馈时，采用 PMO 给出的默认版本进入下一轮评审。
- 升级路径：超过约定期限仍有争议时，提交项目决策组处理。

RACI 口径如下：

| 角色 | 含义 | 项目中的要求 |
|---|---|---|
| R Responsible | 直接办理 | 准备材料、组织讨论、完成修改 |
| A Accountable | 最终负责 | 对本部门口径和阶段性结论负责 |
| C Consulted | 被咨询 | 提供意见，意见须有业务依据 |
| I Informed | 被告知 | 接收信息，不阻塞任务推进 |

历史数据问题与上线后新增问题分开处理：

- 上线前发现的历史数据问题，进入数据治理台账，先按影响范围、修复成本和上线影响分级，不直接追溯个人责任。
- 上线后因新流程、新规则、新录入形成的问题，进入问题台账和责任闭环。
- 业务签字是阶段性确认，不代表无限责任。建议签字口径为：“本部门确认该版本内容可作为下一阶段设计、开发或测试依据。后续如因业务变化、政策变化或跨系统约束调整导致变更，按项目变更流程处理。”

PMO 周会公开跨部门阻塞项，但不做情绪化追责。周会记录只保留事实、影响、责任边界、下一步动作和升级条件。

项目决策组只处理 PMO 层面无法闭环的事项，包括跨部门争议、阶段门放行、重大范围变更、关键资源冲突和供应商责任边界争议。

供应商不得以公司内部争议为由整体等待。未争议部分继续设计、配置、开发或测试；有争议部分进入问题台账或变更台账，按期限升级。

### 6.2 周更新机制

每周只更新重点任务，不建议维护全部 300+ 行任务。

周更新字段包括：

- 任务状态
- 实际开始时间
- 实际完成时间
- 完成百分比
- 本周进展
- 下周计划
- 风险问题
- 需 PMO 协调事项
- 逾期未反馈事项及默认处理建议

### 6.3 月度汇报机制

每月只汇报 5 件事：

1. 本月完成了哪些里程碑；
2. 下月要完成哪些关键节点；
3. 哪些任务延期；
4. 哪些风险需要决策组协调；
5. 整体项目是否仍在关键路径上。

### 6.4 变更控制机制

以下事项必须进入变更台账：

| 变更类型 | 示例 |
|---|---|
| 范围变更 | 新增 QMS、增加 AI 数字员工 |
| 时间变更 | MES 上线节点调整 |
| 资源变更 | 供应商延迟进场、关键人员无法投入 |
| 技术路线变更 | MDM 平台建设重启或采购路径变更、QMS 低代码平台变更 |
| 重大依赖变更 | PLM 深化延迟影响 MES 工艺模块 |

### 6.5 部门配合动机与交换条件

部门配合不应只靠口头动员。PMO 应把“为什么要配合、配合到什么程度、配合后能减少什么风险”说清楚。

| 配合对象 | 可能抵触点 | PMO应提供的交换条件 |
|---|---|---|
| 生产相关部门 | 担心调研、试运行和停机窗口影响生产节奏 | 明确最小配合时间、试运行范围、回退方案和不影响当期生产的边界 |
| 工艺/技术相关部门 | 担心模型、参数、图纸和工艺规则被误用 | 明确脱敏范围、使用场景、确认权限和变更留痕 |
| 质量相关部门 | 担心电子化后问题更容易暴露 | 区分历史问题治理与上线后新增问题责任，先建立整改台账 |
| 财务相关部门 | 担心业务口径变化影响核算和审计 | 明确主数据、单据流、权限和审计追溯口径 |
| 采购相关部门 | 担心供应商和物料规则调整增加工作量 | 提供编码规则、供应商责任边界和批量整理工具 |
| 基础设施/网络/安全相关部门 | 担心上线压力集中、故障责任不清 | 明确验收标准、监控指标、应急预案和供应商配合责任 |
| 人力/综合相关部门 | 担心组织、人员、权限数据反复确认 | 明确人员主数据来源、变更频率和默认确认规则 |
| 信息化项目组 | 担心被所有部门问题兜底 | 用 RACI、问题台账和阶段门把责任边界显性化 |
| 供应商 | 倾向等待客户内部完全统一后再推进 | 未争议部分继续推进，争议部分限期确认并纳入台账 |

## 7. 资源池简化原则

Project 资源池只保留工作组级资源，不放具体人名和供应商组合。

建议进入资源池：

- 信息化项目组
- 信息化项目管理工作室
- MDM工作组
- PLM工作组
- MES工作组
- ERP·OA工作组
- 数据质量工作组
- 基础设施工作组
- 技术架构组
- 变更控制组
- 网络工程组

供应商放入“供应商”字段，不进入资源池。

## 8. 降低管理难度的核心规则

1. Project 只管进度、里程碑和关键依赖。
2. 风险、问题、变更分别用独立台账闭环。
3. 每周只维护 A 类重点任务。
4. 管理版 Project 控制在 80-120 行。
5. 执行版 Project 按阶段使用，不作为日常全量维护对象。
6. H5 看板作为查阅和汇报层，不承担全部管理职责。
7. 每次重大调整都要记录版本号和变更原因。
8. 不把 PMO 周会做成公开批评会，只公开事实、影响和待决策事项。
9. 业务部门未按期反馈时，采用“默认方案先进入下一轮评审”的规则，避免任务无限等待。
10. 区分“可以上线后优化”和“上线前必须闭环”。主数据编码、权限、接口口径、备份恢复、回退预案不得作为普通优化项后置。
11. A/B/C 类交付物评审必须有交付物、评审人、结论和后续动作，不用口头通过替代记录。
