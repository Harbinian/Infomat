# 统一治理口径

## 一、工作对象和顺序

当前治理对象是业务流程及其数据，不是应用系统。统一分析顺序为：

> 部门与业务能力 → L3业务流程 → A1业务行为 → 流程关系 → 业务对象和数据 → 表单与字段 → 责任、来源和系统使用关系

库外AI不得先问“这个部门有哪些主数据”或“应该使用哪个系统”。普通业务人员先说明一个真实流程如何开始、谁做什么、使用什么材料、产生什么结果、出现异常时怎么办。MDM工作组再组织后续数据治理判断。

## 二、层级定义

| 层级 | 名称 | 本规格中的含义 |
| --- | --- | --- |
| D1 | 部门 | 对流程事实承担确认责任的公司部门 |
| L1 | 能力域 | 部门职责中的较大业务范围 |
| L2 | 业务能力 | 能力域下相对稳定的一组业务能力 |
| L3 | 业务流程 | 有明确目的、范围、开始和结束边界的业务过程 |
| A1 | 业务行为 | 流程内可以说明执行主体、动作、对象和结果的办理节点 |
| S1 | 应用系统 | 流程当前使用的OA、MES、PLM、ERP或空值；只记录现状关系，不形成系统评价 |

DCM用于管理D1、L1、L2、L3和S1的稳定骨架。BBM用于管理L3下的A1行为及A1与S1的现状关系。BBM只能挂在已有L3上，不能反向改写L1、L2和L3口径。

## 三、业务行为必须可以执行

每个A1业务行为至少回答：

1. 在什么条件或时间开始；
2. 哪个部门、岗位或场景角色执行；
3. 按实际顺序做哪些动作；
4. 每个动作处理什么对象；
5. 使用什么输入材料或数据；
6. 产生什么输出；
7. 什么结果表示本行为完成；
8. 不满足条件、退回、失败或例外时如何处理；
9. 下一步流向哪里，什么条件下走不同路线；
10. 哪一份材料或哪位业务人员支持上述说法。

“确保流程顺利完成”“保证数据真实准确”“加强协同”不属于可执行动作。AI应继续追问实际动作、对象、结果和确认方式。

## 四、流程关系

| 关系 | 含义 | 必须说明 |
| --- | --- | --- |
| 顺序 | 前一行为完成后进入后一行为 | 起点、终点 |
| 条件 | 根据明确条件进入后续路线 | 判断条件、条件成立后的目标行为 |
| 回路 | 返回已经存在的前序行为重新处理 | 返回原因、返回目标、重新进入条件 |
| 并行 | 多条路线同时开始或等待多条路线完成 | 并行开始点、各路线、汇合规则 |

同一行为直接出现多个出口时，AI不得默认它们是普通顺序。应追问是条件分支、并行开始还是资料未说明。多个行为汇入同一普通行为不自动表示“等待全部完成”；只有明确的并行汇合才表达该含义。

## 五、跨部门行为

跨部门位置先作为流程事实核对。AI应记录：

- 本流程归口部门；
- 实际执行该A1的部门和岗位；
- 交付或接收的事项；
- 传递的数据、表单或业务对象；
- 交接发生的条件和时点；
- 接收方如何确认已接收或已完成；
- 是否返回本流程，以及返回到哪个A1；
- 双方各自的来源依据或确认记录。

“未识别到跨部门位置”不等于“不涉及跨部门”。缺少接收部门、交付物、承接标准或返回位置时，应生成待跨部门确认事项。

在`process-governance-v6`中，跨部门动作仍是`behaviors[]`中的业务行为，执行部门与流程归口部门不同。先后和返回使用普通`flow_relations[]`，数据传递使用`data_objects[].behavior_links[]`。不得在v6中新增独立`cross_department_handoffs[]`对象。

## 六、数据对象和主数据边界

数据对象是流程中被创建、更新、使用、传递或保管的完整业务信息单位。AI识别数据对象时，至少记录名称、业务含义、所在流程、创建行为、更新行为、使用行为、来源关系和证据。

判断两个名称是否代表同一数据对象时，依次比较：

1. 业务含义；
2. 生命周期；
3. 唯一标识；
4. 责任边界；
5. 使用场景；
6. 所在流程和上下文。

信息不足时只能形成“待定匹配建议”。名称相同、字段相似、出现在多个系统或模型评分较高，都不能单独证明对象相同。

主数据是经过有权治理主体认定，用于稳定识别企业核心业务实体，并需要在多个行为、流程、部门或系统之间保持统一的部分数据对象。AI只能提出“待认定主数据”线索，不得确认主数据分类。

表单通常不是主数据。空白表单模板通常是受控模板、制度附件或参考数据；填写完成的表单通常是交易记录或业务证据。表单字段可以引用人员、部门、供应商等主数据，但不会让整张表单自动成为主数据。

## 七、表单和字段

AI应从整张表单开始梳理，保留主表和每一张明细表，不得自行合并、拆分或优化。每个字段至少记录：

- 字段名称和字段类型；
- 是否必填及填写说明；
- 位于基本信息还是哪一张明细表；
- 归属哪个业务数据对象；
- 取值是当前流程直接填写、依赖已有数据还是待确认；
- 值来源、计算输入和校验依据；
- 在哪些A1中创建、填写、修改、审核、审批、确认、读取、归档或作废；
- 证据和待确认问题。

字段台账中的数据对象和字段身份仍需后续治理。AI不得因字段名称推断黄金源、权威系统、维护部门、共享范围或质量规则。

## 八、事实、结论、建议和状态

治理内容同时使用“内容性质”和“确认状态”两个维度，避免把不同概念混在一起。

### 1. 内容性质

| 性质 | 含义 | 示例 |
| --- | --- | --- |
| 当前事实 | 业务当前如何执行、保存或传递 | 当前三个Excel分别维护供应商信息 |
| 治理结论 | 有权主体确认后应统一执行的规则 | 统一供应商定义和唯一标识 |
| 改进建议 | 未来可能调整的流程、系统或管理办法 | 后续由MDM维护并向ERP同步 |

### 2. 确认状态

| 状态 | 含义 | 使用要求 |
| --- | --- | --- |
| 已确认 | 有明确原文、系统现状证据或具名业务确认记录支持 | 写明来源和确认主体 |
| 分析判断 | 依据已有事实形成，但尚未完成业务确认或治理审核 | 明确标为判断，不进入正式结论 |
| 待定 | 材料不足，无法可靠判断 | 写明缺少内容、确认主体、影响和关闭条件 |

AI输出“已确认”时，必须引用已经由人工核对的证据或本次具名确认记录。AI自动抽取本身不构成“已确认”。

## 九、证据

每项候选事实应能回到可直接读取的原文或具名业务确认。证据记录至少包含：

- 来源文件名称、文件号和版次；
- 页码、条款、标题、段落、表格、表单区域或节点位置；
- 与候选事实直接相关的原文摘录；
- 抽取方式和可读性；
- 核验状态；
- 核验人和核验时间。

AI抽取时默认使用`pending_review`、`unverified`和`review_only`。`verified`必须由人工回到原文位置核对后填写。图片识别结果、搜索摘要、文件名和目录名不能单独支撑`verified`。

## 十、责任和升级

| 主体 | 负责 | 不负责 |
| --- | --- | --- |
| 业务部门 | 说明并确认本部门流程做法、岗位、表单字段、数据用途、来源、异常和责任 | 独立判断全公司主数据、跨系统权威来源或跨部门争议 |
| MDM工作组 | 维护结构基准、组织编制和复核、识别待治理对象与关系 | 替部门补造事实或仅凭名称合并对象 |
| PMO | 跟踪责任人、期限、阻塞、证据和关闭条件 | 替部门定义事实或替MDM工作组审核结构 |
| 数据质量工作组 | 制定规则、跨部门一致性检查、抽样和审计 | 替部门编制全部业务事实 |
| 有权主体 | 对满足条件的重大争议作出决定 | 接收所有普通未知项 |
| 库外AI | 追问、整理候选和生成待确认问题 | 作出任何正式确认、审核、批准或发布 |

“当前不知道”不等于需要升级。待定事项只有满足既定条件，例如跨部门在规定范围内无法一致、影响已发布版本、影响部门责任边界或超过批准期限，才进入升级流程。
