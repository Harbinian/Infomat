# 输出字段与结构规则

## 一、输出分层

库外AI输出分为三层：

| 层级 | 输出 | 是否必须 | 边界 |
| --- | --- | --- | --- |
| 人工阅读层 | 范围摘要、来源清单、事实/判断/待定摘要、问题清单 | 必须 | 便于部门核对，不替代机器JSON |
| 机器候选层 | `document-structured-output-v2` JSON | 材料整理和正式交接时必须 | 未审核候选，不生成正式结构块投影 |
| 3001承接层 | `process-governance-v6` JSON | 进入3001编制后产生 | 由3001校验和下载，不要求库外AI直接生成 |

## 二、默认机器输出

库外AI默认机器输出固定为`document-structured-output-v2`，详细结构见：

- `schemas/document-structured-output.schema.json`
- `schemas/document-structured-output-schema.md`

顶层对象及用途如下：

| 顶层字段 | 内容 | AI处理要求 |
| --- | --- | --- |
| `schema_version` | 固定结构版本 | 必须为`document-structured-output-v2` |
| `draft` | 本次结构化草稿的技术信息 | 不写审核、批准或发布状态 |
| `document_profile` | 文件编号、名称、目的、范围和关联资料 | 原文未说明时保持待确认 |
| `terms` | 术语和定义 | 原文术语与解释分开；不得自行改名 |
| `processes` | L3流程候选 | 每项保留证据，进入3001前拆成单流程 |
| `steps` | A1行为和判断节点 | 与所属L3保持稳定引用 |
| `work_role_bindings` | 工作角色候选或确认关系 | AI只生成候选，不生成正式编码或`confirmed` |
| `step_transitions` | 判断分支 | 记录条件和目标；目标未知时生成问题 |
| `behavior_details` | 行为边界、审批和完成标准 | 每个A1按可执行性逐项检查 |
| `cross_dept_handoffs` | 文档审阅阶段的跨部门候选 | 只能是待确认候选；进入v6时按当前迁移规则转换 |
| `forms` | 表单 | 保留现状、拟设计和历史待确认差异 |
| `form_tables` | 主表和明细表 | 每张明细表独立保留 |
| `form_table_fields` | 表格字段 | 记录字段归属、取值来源和证据 |
| `form_fields` | 表单字段 | 不从字段名直接认定主数据 |
| `evidence_catalog` | 证据目录 | AI默认`pending_review/unverified/review_only` |
| `mdm_requirement_catalog` | 主数据治理需求候选 | 只记录待治理要求，不写成已确认结论 |
| `pending_issues` | 待确认问题 | 每个缺口绑定对象、字段、证据和确认主体 |
| `structure_block_projection` | 流程输入基线投影视图 | 库外AI不得生成正式投影 |

## 三、处理范围和来源

人工阅读层首先输出：

| 字段 | 要求 |
| --- | --- |
| 任务编号 | 来自T01任务单，不由AI新建业务编号 |
| 流程候选 | 一个明确L3；多个候选时先等待用户选择 |
| 归口部门 | 使用统一部门名称；未知时写待确认 |
| 编制人/核对人 | 来自任务单，不根据材料姓名推测 |
| 纳入来源 | 文件名、文件号、版次、位置、授权、脱敏、SHA-256 |
| 排除或阻断来源 | 状态、原因和解除条件 |
| 本轮非目标 | 明确不处理的流程、部门、对象和系统事项 |

## 四、L3流程候选字段

每个L3至少包含：

| 字段 | 内容要求 | 缺失处理 |
| --- | --- | --- |
| 稳定技术标识 | JSON内部唯一引用 | 技术阻断，不得重复或随改名重建 |
| 流程名称 | 业务人员能够识别的名称 | 原文候选保留并生成命名确认问题 |
| 归口部门 | 对流程事实承担归口核对的部门 | 待部门确认 |
| L1/L2 | 已有确认口径或待映射候选 | 不得由AI单方面确认 |
| 目的 | 流程要产生的业务结果 | 继续追问，不写“提升效率”等空泛目标 |
| 范围 | 明确开始、结束、纳入和不纳入内容 | 生成边界确认问题 |
| 分类状态 | 未分类、待复核或已确认 | AI不得写已确认，除非有人工确认记录 |
| 证据引用 | 直接支持该流程候选的位置 | 无证据则保持待确认 |

## 五、A1业务行为字段

每个A1至少包含：

| 字段 | 内容要求 |
| --- | --- |
| `behavior_ref`或等价稳定标识 | 本文件内唯一，修订时保持稳定 |
| 行为名称 | 简短说明办理动作，不使用部门职责口号 |
| 节点类型 | 普通行为、判断、并行开始、并行汇合 |
| 执行主体 | 部门、岗位或场景角色；控制节点不伪造执行部门 |
| 触发 | 事件、条件或时间 |
| 前置条件 | 开始办理前必须具备的状态或材料 |
| 输入 | 使用的材料、数据、表单或上一行为结果 |
| 具体做什么 | 按实际顺序写动作、处理对象和结果 |
| 时限 | 明确时限或待确认，不补造数字 |
| 完成标准 | 可以由记录、状态或结果检查的条件 |
| 输出 | 产生或更新的业务结果、数据或表单 |
| 异常处理 | 失败、驳回、退回、作废、缺料、超时等处理 |
| 会签 | 是否要求全部目标部门会签及部门范围 |
| 证据 | 支持行为、主体和规则的来源位置 |

当主体、条件、对象或结果责任变化时，应拆分为不同A1或明确的流程关系。AI提出拆分时只能作为建议，由业务人员确认。

## 六、流程关系字段

| 字段 | 内容要求 |
| --- | --- |
| 稳定关系标识 | 本文件内唯一 |
| 关系类型 | `sequence`、`condition`、`loop`或`parallel` |
| 起点 | 已存在A1或控制节点 |
| 终点 | 已存在A1或控制节点 |
| 条件 | 条件关系和回路必须具体；顺序关系可为空但不得误表分支 |
| 证据或确认记录 | 支持该流向和条件的依据 |

自环、断裂端点和完全重复关系属于技术阻断。普通行为直接一对多、多个无条件出口、条件缺失和非回路闭环至少形成待确认问题。

## 七、数据对象字段

进入3001 v6后的活动字段包括：

| 字段 | 允许值或要求 |
| --- | --- |
| `data_ref` | 本文件内唯一稳定标识 |
| `data_name` | 业务可识别名称，不用字段名代替完整对象 |
| `description` | 业务含义和范围 |
| `information_type` | `pending_confirmation`、`business_information`、`business_conclusion`、`business_status`、`identifier`、`file_attachment`、`other_information_output` |
| `behavior_links[].operation` | `create`、`update`、`use`、`pending_confirmation` |
| `source_relations` | 来源部门、来源流程、来源行为、来源数据和可用时点 |

一个数据对象最多只能有一个已确认创建行为。`pending_confirmation`不得与已确认操作并存。同名对象不得自动归并。

以下内容属于后续治理问题，不是AI可确认的v6字段：

- 是否属于主数据或参考数据；
- 是否与其他流程对象相同；
- 唯一标识和匹配规则；
- 责任部门和维护岗位；
- 权威来源或黄金源；
- 质量规则、共享范围和访问边界；
- 生命周期和保留规则。

AI可以收集相关线索并写入`pending_issues`或`mdm_requirement_catalog`候选，但不得写成治理结论。

## 八、表单和字段的v6承接字段

### 1. 表单

| 字段 | 要求 |
| --- | --- |
| `form_ref` | 本文件内唯一 |
| `form_name` | 表单或记录的正式名称 |
| `form_no` | 原有编号；没有时保持空或待确认，不自行编码 |
| `form_design_state` | `unspecified`、`current_state`、`proposed_design` |
| `behavior_links` | 在各A1中的创建、填写、修改、审核、审批、确认、读取、归档或作废关系 |
| `areas` | 基本信息和每一张明细表 |

### 2. 区域和字段

| 字段 | 要求 |
| --- | --- |
| `area_type` | 空值、`基本信息`或`明细清单` |
| `area_title` | 明细表名称；基本信息可使用表单区域名称 |
| `item_name` | 字段原名 |
| `item_type` | 原表单类型或业务可理解类型 |
| `required` | 仅在材料或业务确认明确时填写 |
| `instructions` | 填写、校验或显示规则 |
| `business_data_ref` | 字段归属的数据对象；未知时待确认 |
| `value_origin_mode` | `direct_current_process`、`depends_on_data`或`pending_confirmation` |
| `source_links` | 值来源、计算输入或校验依据 |

外部系统来源只能证明当前取值位置，不能证明权威来源或未来系统归属。

## 九、证据字段

每条证据至少包含：

| 字段 | 要求 |
| --- | --- |
| 证据标识 | 本文件内唯一 |
| 来源文件 | 文件名、文件号、版次 |
| 来源位置 | 页码、条款、标题、段落、表格、字段组或节点 |
| 原文摘录 | 只保留直接支持候选的必要内容，不润色原文 |
| 提取质量 | 完整、部分、失败或不可读 |
| 证据状态 | 默认`pending_review`；人工核对后才可`verified` |
| 核验状态 | 默认`unverified` |
| 下游用途 | 默认`review_only` |
| 核验人和时间 | 人工核对后填写 |

`partial`、`failed`和`blocked_unreadable`来源不得支撑正式字段。OCR或图像识别结果不得直接标为`verified`。

## 十、待确认问题字段

每个问题必须能定位到具体对象和字段，至少包含：

- `stable_key`；
- `structured_object_type`；
- `structured_object_key`；
- `target_block`；
- `target_field`；
- `evidence_status`；
- `issue_type`；
- `question_for_user`；
- 来源锚点；
- 需要确认的角色或部门；
- 影响范围；
- 关闭条件。

问题句应让业务人员知道到哪里核对、需要回答什么、回答后影响什么。不得向业务人员暴露中间JSON、抽取脚本或内部实现文件名。

## 十一、3001 v6边界

`process-governance-v6`根对象固定包含：

- `schema_version`
- `export_meta`
- `process`
- `behaviors[]`
- `flow_relations[]`
- `data_objects[]`
- `forms[]`
- `terms[]`
- `migration`

AI不得向v6增加审核状态、审核意见、批准标记、图坐标、评分结果、浏览器状态、v7生命周期字段或独立跨部门交接对象。

文档结构化v2中的旧交接、参考材料、内部流程调用和工作角色等内容，进入3001时按当前迁移规则在页面内存中转换或只读归档。源文件不得修改，重复导入不得产生重复对象。

## 十二、文件命名和摘要

库外AI阶段文件建议使用：

```text
未审核-部门-流程名称-AI候选-YYYYMMDD-HHMM.json
未审核-部门-流程名称-问题清单-YYYYMMDD-HHMM.md
未审核-部门-流程名称-部门复核-YYYYMMDD-HHMM.md
```

进入3001后，以3001实际下载文件名为准。每次交接登记文件字节级SHA-256。摘要用于核对交接文件是否一致，不写入业务JSON。
