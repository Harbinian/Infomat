# 信息化的第一步——制造信息

| 项目 | 内容 |
| ---- | ---- |
| 会议名称 | 数字化底座项目首次 PMO 周例会 |
| 会议材料周期 | 2026-07-02 至 2026-07-08（周四至下周三） |
| 项目周报统计窗口 | 2026-07-02 至 2026-07-08 |
| 后续例会节奏 | 每周四召开，周三 13:00 前收议题材料 |
| 主持 | PMO |
| 参会范围 | 信息化项目管理工作室、MDM 工作组、各专项工作组、各部门接口人 |
| 会议依据 | DLV-002 项目启动会纪要、DLV-003 项目治理与调研机制管理办法、PMO 当前任务基线、MDM 平台前端页面 |
| 会议输出 | 部门接口人确认、标准信息输入卡、行动项台账、责任池、材料缺口清单；能进 MDM 现有入口的再补录 |

今天不是追责会，也不是系统培训会；今天要做的是把部门掌握的业务事实，做成第一批可跟踪、可核对的标准信息。

---

## 一、今天为什么开会

信息化的第一步不是买系统，也不是先画大图，而是制造标准信息。这里说的制造信息，不是编造材料，是把制度、表单、台账和现场做法里的事实整理成统一口径：这件事叫什么，谁负责，按什么做，结果留下什么，交给谁。

首次周例会先做一件事：让每个部门交出第一批标准信息样本。说得清的，今天就记下来；说不清的，先标成待确认；缺材料的，先记成材料缺口。

| 现场承诺 | 怎么理解 |
| -------- | -------- |
| 不考术语 | WBS、阶段门、主数据、L3、A1 这些词不用先学会，PMO 负责翻译成标准信息项 |
| 不追历史旧账 | 主动说出来的历史流程问题、历史数据问题和边界问题，先按治理事项处理 |
| 不要求一次定稿 | 本周先形成第一版标准信息，证据、表述和责任边界后面可以继续补 |

## 二、今天每个部门只做三件事

| 动作 | 今天做到什么 |
| ---- | ------------ |
| 确认接口人 | 写清谁本周负责收材料、问问题、反馈进展 |
| 填一张标准信息输入卡 | 至少写一条当前困难、一条流程问题、一类基础信息、一条双轨风险 |
| 保存一张标准信息草稿 | 现场环境支持就先在 MDM 保存；如果暂时走不到这一步，先填输入卡，后面由 PMO 帮着补证据 |

不会填不是扣分项。找不到制度、说不清责任、不确定字段名称，都可以先写成“待补事项”。今天先把业务事实留下来，后面再慢慢补成标准信息。

## 三、为什么资料多，但还不是标准信息

资料多不等于信息可用。标准信息至少要说清：谁做、做什么、交给谁、留下什么证据。

| 指标 | 数量 |
| ---- | ---: |
| 资料目录 | 408 |
| 各类文件 | 918 |
| 还不能直接落系统的流程 | 236 |
| 能看懂但暂不能自动化的流程 | 160 |

以上为当前初筛数据，用于说明治理工作量，不作为部门评价依据。具体明细以后续 PMO 台账和受控源文件为准。

| 现状问题 | 对部门意味着什么 | 真实例子 | 不处理会导致什么 |
| -------- | ---------------- | -------- | ---------------- |
| 责任对象写得太泛 | 原文写“有关部门”“相关责任人”，会上就会问：到底找谁？谁拍板？ | 财务部《GLTX-CW-02-A资产管理程序》§5.2.7 写到，盘点后要提出整改措施，并“会同有关部门对相关责任人提出具体处理意见”。原文没说“有关部门”是哪几个，也没说责任人由谁确认。 | 盘盈盘亏一出来，资产归口、财务、使用部门都可能等别人先表态。后续也很难形成明确处理项，只能卡在“等确认”。 |
| 参与范围说不清 | 原文写“多部门、多专业”，但不列名单，发起人就不知道该拉谁一起评估。 | 工程技术部《GLG1201产品设计和开发管理规则》§5.5.4 和 §5.5.5 写到，更改涉及多部门、多专业时，组织相关部门、专业判别和评估。原文没列哪些变化必须找哪些部门、哪些专业参加。 | 设计更改发起后，少拉一个专业，后面就可能有人说“这个更改没让我们评估”。到系统里会变成会签对象不全，流程退回重走。 |
| 异常处理没闭环 | 原文只写“通知相关部门处理”，没有说通知谁、多久处理完、处理完谁确认。 | 物资保障部《GLTX-WZ-02-A工具量具管理程序》§5.2.1 写到，验收发现不合格工具时，“应及时通知相关部门处理”。原文没写相关部门是谁，也没写隔离、退换、复验或关闭凭证。 | 仓库发现不合格工具后，采购、申请人、技术员可能都以为别人会处理。系统只能发一个模糊提醒，工具是否隔离、是否退换、能不能再入库都说不清。 |
| 问题跟踪缺关闭标准 | 原文有“谁跟踪”，但没写“谁验收解决”。问题就容易一直显示处理中。 | 项目管理部《交付组管理流程》写到，问题汇总到关键件问题跟踪表后，分配给对应项目助理，由主管项目助理跟踪解决并反馈进度；附表里有“希望解决时间”“问题责任部门”“负责人”“跟踪项目助理”。原文没写问题解决后由谁验收、用什么证据关闭、逾期怎么升级。 | 关键件卡住时，大家知道有人在跟，但不知道什么时候算解决。台账里会堆出一批“处理中”的事项，PMO 很难判断哪个真逾期、哪个已经办完。 |
| 时间和交接物不踏实 | 原文写“及时做好交接”，但没说几天内交、交什么、谁签收。 | 行政人事部《GLTX-XZ-05-A岗位变动管理规定》§5 和流程 6 写到，调动员工应及时做好工作交接；流程 6 只写“通知调动人员本人办理工作交接”，记录表单栏为空。原文没说账号、资料、在办事项、台账由谁交给谁，也没说交接期限。 | 员工调岗后，原岗位资料、系统权限、未办事项可能还留在个人手里。旧部门说人已经调走，新部门说材料没接到，最后变成线下追人。 |

## 四、制造标准信息，到底解决什么

先解决四件事：谁做、做什么、用什么证据、做完交给谁。

文档结构化不是重排 Word，也不是重复抄材料。它是在制造标准信息：把制度、表单、台账、流程图里的内容拆成流程、字段、责任和证据，后面才好核处理项、权限、接口和验收。

| 基础工作 | 要制造哪类标准信息 | 后面影响什么 |
| -------- | -------------- | ------------ |
| 流程治理 | 把一件事从谁发起、谁审核、谁执行、谁确认、结果交给谁说清楚 | 蓝图设计、流程优化、系统功能范围、处理项和审批节点 |
| 数据治理 | 把常用台账、字段、编号、主数据对象、维护部门说清楚 | 数据标准、导入模板、接口字段、主数据维护责任 |
| 证据治理 | 把每个判断能回到哪份制度、哪张表、哪条台账说清楚 | 需求评审、争议处理、上线验收、后续审计 |
| 责任治理 | 把谁填、谁审、谁维护、谁接收、谁升级说清楚 | 权限设计、角色工作台、行动项跟踪、责任池 |
| 问题治理 | 把说不清、责任边界暂不清晰、缺材料、跨部门卡住的问题编号跟踪 | PMO 周会、风险升级、整改闭环 |

合格制度是标准信息的原料。按照当前文档结构化模型，制度至少要能拆出制度说明、术语、流程与行为、跨部门承接、附表结构、字段和证据。下面这张表作为会后查阅标准，现场只讲“谁做、做什么、证据在哪、交给谁”。

| 合格制度要写清什么 | 标准信息怎么形成 | 写到什么程度才算够 |
| ------------------ | -------------------- | ------------------ |
| 这份制度叫什么、编号是什么、管到哪里 | 形成制度名称、制度编号、目的、范围和承继关系 | 名称唯一，范围能说清适用部门、业务场景和被替代或引用的制度 |
| 关键术语是什么意思 | 形成术语清单，并标明术语适用位置 | 业务人员读完知道同一个词在本制度里指什么，不靠各自理解 |
| 管的是哪几条流程 | 对应到 L1 能力域、L2 业务能力和 L3 流程 | 每条流程能看出起点、终点、业务边界，不把一堆动作揉成一句话 |
| 每一步谁来做、拿什么来做、做完交什么 | 拆成 A1 业务行为，记录执行角色、输入材料、输出结果 | 每个行为能分配给具体角色，能形成处理项或检查项 |
| 什么情况下要审核、审批、会签或确认 | 记录审批要求、前置条件、触发场景和执行标准 | 写清谁看、看什么、通过后产生什么结果，不只写“按规定审批” |
| 涉及其他部门时，谁交给谁、交什么、怎么确认 | 形成跨部门承接记录和承接标准 | 能看出来源部门、接收部门、交接物、时限和确认方式 |
| 用哪些表单、台账和附表 | 形成表单、主表、明细表和归档规则 | 表单用途、填写要求、归档位置、留存要求能落到实际记录 |
| 表单里有哪些字段，字段从哪来、谁维护 | 形成字段中文名、字段类型、数据对象和字段证据说明 | 字段不只是一个栏位名，还能说清填写口径、来源和维护责任 |
| 每个判断能回到哪里核对 | 形成证据类型、来源名称、来源位置、确认人和记录时间 | 能回到制度条款、表单位置、台账记录、流程图或会议记录，不靠口头解释 |

## 五、MDM 今天只保存第一批草稿

今天先别管 MDM 有多少菜单。只走一遍最短路径：打开地址，用自己的工号登录，看角色工作台，点“我现在该做什么”，再进流程治理，保存一张标准信息草稿。

如果现场环境暂时走不到这一步，就先填输入卡，不把它说成系统问题。草稿保存后也不会直接定责，不会自动改制度；它只是把口头说法先留住，后面再补证据、补责任、补字段口径。

| 步骤 | 屏幕上做什么 |
| ---- | ------------ |
| 1 | 打开 PMO 通知里的 MDM 地址 |
| 2 | 用工号和一次性初始密码登录 |
| 3 | 先看角色工作台 |
| 4 | 点击“我现在该做什么” |
| 5 | 进入流程治理 / 文档结构化输出 |
| 6 | 填写并保存第一张标准信息草稿 |

## 六、第一张标准信息草稿最低填写标准

至少填完下面这些，就可以保存草稿。先别追求漂亮，先让别人看得懂、查得到、接得上。

| 字段 | 最低填写要求 | 示例 |
| ---- | ------------ | ---- |
| 流程名称 | 写一个真实业务事项 | 工具量具不合格处理 |
| 为什么新增 | 写为什么现在说不清，或者为什么需要补 | 制度只写通知相关部门处理，未写谁处理、怎么关闭 |
| 依据类型 | 有制度选制度，有表单选表单，只有现场做法就选现场实际 | 制度 |
| 依据说明 | 写文件编号、名称、条款或来源；暂时没有就写暂缺原因 | GLTX-WZ-02-A《工具量具管理程序》§5.2.1 |
| 第一步怎么做 | 写谁先做什么 | 仓库验收发现不合格工具并记录 |
| 输出结果 | 写做完留下什么 | 不合格工具处理记录或退换货凭证 |
| 暂缺证据说明 | 证据没带到现场时，写清后续要补什么 | 待补验收记录样表和退换货凭证样例 |

## 七、现场填第一张标准信息输入卡

空白项不是失败，空白项就是还没制造完成的信息。

| 填写项 | 请照这个口径填写 | 示例 |
| ------ | ---------------- | ---- |
| 部门名称 | 写部门全称 | 示例部门 |
| 接口人 | 写本周负责收材料、问问题、反馈进展的人 | 张三 |
| 当前困难 | 用一句话说明目前最影响推进的一件事 | 现有台账字段不统一，汇总时需要反复确认 |
| 流程问题 | 写一个流程断点 | 申请、审核、确认之间没有统一交接记录 |
| 基础信息准备 | 写一类已有或需要补的台账、字段、编号、清单或表单 | 人员岗位清单、部门职责说明、常用业务台账 |
| 双轨风险 | 写一个可能导致“系统一套、线下一套”的场景 | 基础数据不统一，系统上线后仍保留线下表格 |
| 需 PMO 协调 | 写需要跨部门、跨工作组或决策组协调的事项 | 明确跨部门交接时由谁确认最终版本 |

## 八、填不出来怎么办

如果现场填不出来，不算失败。填不出来的内容，本身就是一条需要继续制造的标准信息。

| 现场情况 | 先怎么写 |
| -------- | -------- |
| 找不到制度 | 写“材料缺口”，PMO 帮助追来源 |
| 不知道谁负责 | 写“责任边界待确认” |
| 不确定是不是本部门 | 写“需 PMO 协调确认” |
| 不知道字段叫什么 | 先写业务叫法，后面再统一字段名称 |
| 只知道线下做法 | 先写实际做法，再补制度依据 |

PMO 现场处理时，部门暂时说不清楚的，登记为待确认，并请部门推荐可能了解情况的人；部门说历史问题的，符合条件先进入责任池；部门说没有材料的，登记材料缺口，找可替代证据；部门说不是本部门负责的，先记录事实和影响，不现场争论归属。

提交后不会直接定责，也不会自动改制度。不要求大家在 MDM 里找一个不存在的按钮。先由 PMO 放进行动项台账、责任池、材料缺口清单或后续访谈清单。能进 MDM 现有入口的，再由 MDM 工作组确认后补录；不能进的，就留在 PMO 台账里继续跟，直到它能变成可核对的标准信息。

## 十、会后怎么跟踪

今天留下的不是口头意见，而是一批标准信息的半成品。能直接确认的，进入台账；还缺口径的，继续补证据、补责任、补字段。

| 去向 | 会后怎么处理 |
| ---- | ------------ |
| 行动项台账 | 责任人、截止时间、交付物和状态进入 PMO 周会跟踪，避免信息停在口头 |
| 责任池 | 历史问题、责任边界不清和跨部门争议先放入责任池，不在会上硬定归属 |
| 材料缺口清单 | 缺制度、缺表单、缺台账、缺截图的事项，先记清楚来源和补充责任 |
| 制度或表单待补说明 | 原文没写清的地方，先形成待补说明，不直接改成系统功能需求 |
| 后续访谈清单 | 现场说不清、需要找人的内容，转成访谈对象和补证据任务 |
| MDM 现有入口 | 只有已确认能承接的事项，才补录到当前已有页面；不把未设计功能写成承诺 |
