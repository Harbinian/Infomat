# 信息化项目工作开展原则

> 部门主备岗、周例会时间、行动项、期限调整、完成确认和数据提交责任，自2026年7月29日起按 `pmo/信息化项目_协同工作规则.md` 执行。本文件与该规则不一致时，以该规则为准。
> 适用项目：数字化底座、PLM、MES、ERP/OA、主数据治理、基础设施、AI 算力、H5 甘特图 / Microsoft Project 管理体系。  
> 适用对象：项目决策组、PMO、信息化项目组、技术架构组、基础设施工作组、数据治理组、业务部门、采购/财务/审计、供应商项目经理。  
> 核心判断：本项目不是单纯的信息化建设，而是一次组织权责、流程边界、数据责任和供应商履约关系的重构。  
> 基本前提：项目可能没有额外奖励，因此不能假设各部门会天然积极配合。项目推进必须建立在“风险共担、收益可见、边界清晰、证据闭环、阶段确认”的基础上。

---

## 1. 总原则：字表合一，行胜于言

本项目所有工作必须遵循：

> 说明书 = 任务表 = Microsoft Project = H5 看板 = PMO 周会追责 = 合同履约。

任何只存在于口头解释、会议纪要或说明文档中，但没有进入任务表、Project 前置关系、H5 看板字段、阶段门或合同技术附件的内容，均不应视为有效执行基线。

### 1.1 不靠口头解释推进

不能再依赖以下口头解释：

- “WBS 2 虽然没结束，但核心招采已经完成。”
- “WBS 3 虽然没完全冻结，但 V0.8 可以支撑设计。”
- “WBS 5 虽然没终验，但基础资源已经可用。”
- “WBS 9 到日期就可以启动。”
- “本期不上 MDM 平台，但还是可以做主数据联调。”

这些解释必须转化为任务表中的硬节点：

- `2.1.7 核心招采满足 WBS 9 联调准备条件`
- `主数据 V0.8 / V0.9 / V1.0 / V1.1`
- `5.1.7 基础资源先行交付验收`
- `9.0.8 WBS 9 联调启动评审`
- `集成过渡期规则中心可用确认`

### 1.2 WBS 该拆就拆

任务数量不是第一矛盾。真正的风险是关键路径被一级摘要任务掩盖，导致计划看似完整、执行无法追责。

凡是影响以下事项的内容，必须拆成任务或里程碑：

1. 合同签订；
2. 付款节点；
3. 生产割接；
4. 主数据冻结；
5. 接口开发；
6. 测试环境交付；
7. 联调启动；
8. 上线放行；
9. 灾备验收；
10. 总体验收。

### 1.3 禁止关键任务依赖一级摘要

一级摘要任务跨度长、范围广，不得作为关键路径前置。

必须禁止：

- WBS 9 直接依赖 WBS 2 一级摘要；
- 系统开发直接依赖 WBS 3 一级摘要；
- 测试环境部署直接依赖 WBS 5 一级摘要；
- WBS 9 按日期自动启动。

## 2. 人性原则：无奖励时，不要假设主动配合

本项目可能没有额外奖励。各部门的真实动机通常不是“把项目做好”，而是：

- 少背锅；
- 少加班；
- 少被改流程；
- 少暴露历史问题；
- 少承担无限责任；
- 少被别的部门拿数据考核；
- 不让本部门成为项目延期原因。

项目推进必须承认这个现实。

### 2.1 不要只讲公司收益

“数字化转型”“管理提升”“系统集成”这些说法对部门一线推动力有限。应改为讲清楚部门收益：

| 部门 | 应讲清的收益 |
|---|---|
| 生产 | 减少找单、找料、重复确认，避免系统上线影响现场 |
| 工艺/技术 | 保留 EBOM/PBOM/MBOM 和工艺路线的话语权 |
| 质量 | 异常闭环有证据，质量追溯更清楚 |
| 财务 | 付款有依据，审计风险降低 |
| 采购 | 技术附件清楚，减少供应商投诉和招标争议 |
| 仓储 | 物料、库位、出入库数据更清楚 |
| 基础设施 | 访问矩阵前置，减少上线前临时开口 |
| 信息化 | 责任边界清楚，不再总背锅 |
| 供应商 | 边界明确、按节点回款、减少无限返工 |

### 2.2 配合不是情怀，是交换

各部门愿意配合，通常因为以下原因：

1. 避免成为项目延期责任部门；
2. 保护本部门利益；
3. 获得专业规则话语权；
4. 减少未来重复劳动；
5. 降低上线后被动救火概率；
6. 避免历史问题在上线后集中爆雷。

PMO 应把配合动作包装成“部门风险管理”，而不是“帮信息化干活”。

推荐话术：

> 这不是让贵部门替信息化填表，而是防止后续系统上线后，所有数据错误都回流到贵部门处理。现在确认，是为了避免以后被动救火。

### 2.3 历史问题不应直接追责

系统上线会暴露历史问题。如果上线前暴露历史问题就追责，各部门会倾向于隐藏问题。

因此应建立“历史问题免责池”：

1. 上线前发现的历史数据问题，进入治理台账，不直接追究个人或部门责任；
2. 上线后新增且未按流程处理的问题，进入责任闭环；
3. 历史问题以治理为主，不以问责为主；
4. 重大历史风险应报告项目决策组，但不做情绪化追责。

## 3. 组织协同原则：责任清楚，但不要制造签字恐惧

### 3.1 签字是阶段性确认，不是无限背责

很多部门不愿签字，不是不同意，而是怕以后出事。

推荐签字语：

> 本部门确认该版本内容可作为下一阶段设计、开发、测试或联调依据。后续如因业务变化、政策变化、跨系统约束调整或项目基线变更导致调整，按项目变更流程处理。

不要让业务部门觉得“一签字就是终身负责”。

### 3.2 建立 RACI，而不是泛泛“请配合”

所有关键事项必须明确 RACI：

| 角色 | 含义 |
|---|---|
| R | Responsible，实际执行 |
| A | Accountable，最终负责 |
| C | Consulted，参与确认 |
| I | Informed，知会 |

示例：

| 事项 | A | R | C | I |
|---|---|---|---|---|
| 物料编码规则 | 工艺/技术部门 | 数据治理组 | ERP/MES/PLM/采购/仓储 | PMO |
| EBOM/PBOM/MBOM 边界 | 技术/工艺部门 | PLM/MES 工作组 | ERP/生产/质量 | PMO |
| 组织人员数据 | 人力/综合管理 | OA 工作组 | ERP/PLM/MES | PMO |
| 接口字段映射 | 技术架构组 | 供应商/集成实施方 | 业务 Owner | PMO |
| 访问矩阵 | 基础设施/安全组 | 网络工程组 | 各系统供应商 | PMO |
| 付款放行 | 财务/采购 | PMO | 业务/技术验收人 | 项目决策组 |

### 3.3 主备对接人不承担部门最终决定责任

部门主对接人和备岗人员负责日常沟通、传达和跟踪，但不得代替部门负责人作出部门最终业务决定。

规则：

1. 主对接人负责收集资料、组织反馈、传达信息和跟踪行动项；
2. 主对接人无法履职时，由已确认的备岗人员按交接记录代岗；
3. 部门负责人负责部门业务结论、资源安排和阶段性确认；
4. 部门内部专业意见由部门负责人决定；
5. 跨部门争议进入项目决策组；
6. PMO 不得要求主对接人或备岗人员承担部门级决策责任。

## 4. PMO 工作原则：公开阻塞，不公开羞辱

### 4.1 PMO 的角色

PMO 不是催进度的人，而是：

1. 组织资源的人；
2. 暴露阻塞的人；
3. 保护边界的人；
4. 固化证据的人；
5. 切断甩锅链条的人；
6. 把口头解释转成任务、字段、前置关系和验收证据的人。

### 4.2 周会不逐条跟踪全部任务

PMO 周会重点跟踪：

1. 阶段门未通过事项；
2. `Text10` 重点视图中的红色任务；
3. `Flag1 = 是` 且延期的任务；
4. A 类交付物未通过事项；
5. 主数据 A 类重大变更；
6. WBS 9.0 联调启动条件缺口；
7. 供应商进度受阻预警函；
8. 临时放行事项；
9. 访问矩阵和备份验证未完成事项；
10. 影响 2028-01-31 总体验收的关键路径变化。

### 4.3 周会顺序

建议 PMO 周会按以下顺序：

1. 阶段门看板；
2. 核心招采看板；
3. 主数据版本看板；
4. 基础资源分批交付看板；
5. 联调启动条件看板；
6. 高风险阻塞项看板；
7. 合同付款与临时放行看板。

## 5. 部门配合原则：让各部门看到自己的收益和边界

### 5.1 生产部门

核心关注：不能停线、不能增加现场录入负担、不能让系统卡住实物流。

推进原则：

1. MES 上线必须有旁路和应急方案；
2. 现场操作必须尽量减少重复录入；
3. 系统异常不得直接卡死生产；
4. 生产部门参与现场可用性验收；
5. 报工、扫码、工序流转必须用现场真实场景测试。

### 5.2 工艺/技术部门

核心关注：专业规则不能被 IT 代定，BOM 和工艺路线不能被过度固化。

推进原则：

1. EBOM/PBOM/MBOM 边界由技术/工艺主导，信息化负责固化；
2. 工艺路线、工装、工艺资源、仿真模型等规则必须由专业部门确认；
3. 主数据签字为阶段性确认，不是无限责任；
4. Fluent Benchmark 必须明确工程技术部配合边界、脱敏模型、License 和 Solver 支持矩阵。

### 5.3 质量部门

核心关注：质量追溯清楚，异常闭环有证据，但流程不能变成生产卡点。

推进原则：

1. 检验项、质量判定规则由质量部门主导；
2. 异常处理必须有升级机制和时限；
3. 低代码平台不应等同为 QMS 专属系统，应作为流程导向业务系统的通用运行底座，并与 MES/PLM/ERP 的数据边界统一；
4. 质量流程上线前必须做业务穿透测试。

### 5.4 财务部门

核心关注：合规付款、资产安全、审计风险、验收证据。

推进原则：

1. 阶段门必须与付款节点对应；
2. A 类交付物必须有签字和证据；
3. GPU 视同到货必须有保险和所有权安排；
4. 付款放行必须区分无争议部分和争议部分；
5. “技术上说完成”不能替代财务付款证据。

### 5.5 采购部门

核心关注：招采合规、技术参数可解释、需求不要反复变。

推进原则：

1. 采购包边界必须前置评审；
2. 合同技术附件必须统一模板；
3. 评分标准、偏离审批、验收标准必须明确；
4. 供应商联合责任边界必须写清；
5. 不能让采购在需求不清时独自承担招标风险。

### 5.6 基础设施、网络、安全部门

核心关注：不能临上线才开端口，不能随意临时放通，性能、备份、安全问题不能全部甩给基础设施。

推进原则：

1. 必须建立资源落位表；
2. 必须建立跨系统访问矩阵；
3. 未进入访问矩阵的接口，不允许上线临时开通生产访问；
4. 测试环境部署依赖基础资源先行交付；
5. G4 前必须完成备份 Agent 安装和首次备份验证；
6. G5 前必须完成灾备、安全和恢复演练。

### 5.7 人力/综合管理部门

核心关注：组织人员数据不要反复维护，OA 不要变成综合管理单独背责。

推进原则：

1. 组织、人员、岗位、部门主数据必须由人力/综合确认；
2. OA、ERP、PLM、MES 的人员组织数据应统一来源；
3. 离职、调岗、外协人员要有统一同步机制；
4. OA 是统一入口，不是综合管理部门独自背责。

### 5.8 信息化部门

核心关注：项目不能烂尾，不能被所有部门甩锅，不能被供应商牵着走。

推进原则：

1. 信息化负责组织和固化，不替业务定义专业规则；
2. 所有关键口径必须进任务表、阶段门和 H5 看板；
3. 不接受没有证据的“已完成”；
4. 对供应商执行阶段门、偏离审批、交付物分级和责任归因；
5. 对内部部门执行 RACI、截止时间、默认规则和升级路径。

## 6. 供应商博弈原则

供应商真实动机是：能回款、不超范围、不无限返工、不为其他供应商背锅、顺利验收、减少长期驻场消耗。

常见博弈行为：

1. 需求不清时先模糊承诺，中标后谈变更；
2. 接口问题先说对方系统没准备好；
3. 性能问题先说硬件、数据库或网络不行；
4. 数据问题先说业主主数据不规范；
5. 验收前集中补文档，推动“先验收后整改”；
6. 阶段门延误时把责任归到业主业务部门未确认。

应对原则：

1. 合同技术附件必须细化；
2. 付款与阶段门绑定，但不得机械锁死；
3. 供应商主张延期必须提前书面预警；
4. 无争议部分继续推进，争议部分单独挂账；
5. A 类交付物不得由供应商自评通过；
6. 偏离审批必须有原厂证明和等效方案；
7. 联调启动必须由 9.0.8 评审放行。

## 7. 阶段门与付款原则

### 7.1 阶段门必须有牙齿

阶段门必须绑定：

1. 合同签订；
2. 供应商付款；
3. 详细设计放行；
4. 接口开发放行；
5. 生产割接放行；
6. 上线放行；
7. 终验付款。

### 7.2 但阶段门不能设计成付款死锁

尤其 G3 主数据 V1.0 冻结，不得机械锁死所有接口开发款。

推荐：

| 款项 | 控制方式 |
|---|---|
| 接口详细设计款 | 可基于 V0.8/V0.9 有条件支付 |
| 接口开发首付款 | 原则上不超过接口相关合同额 30%，须签署后续适配承诺 |
| 接口开发中期款 | 必须依赖 V1.0 冻结 |
| 接口联调款 | 必须依赖 V1.1 联调版标准 |
| 接口终验款 | 必须依赖业务穿透测试、异常关闭、接口验收 |

### 7.3 临时放行原则

供应商主张非自身原因导致阶段门延期时，必须：

1. 至少提前 5 个工作日提交书面《进度受阻预警函》；
2. 提供可量化工时记录、会议纪要、待确认事项清单；
3. 经 PMO、监理或第三方评审单位、业主项目总监三方确认；
4. 临时放行比例原则上不超过该阶段应付款项 80%；
5. 签署《无条件适配后续标准承诺书》；
6. 争议部分单独挂账，不扩大为项目群停摆。

## 8. 主数据治理原则

### 8.1 主数据是业务责任，不是信息化单独责任

Data Owner 必须来自业务部门。信息化负责组织、固化和系统实现，不替业务定义规则。

| 主数据对象 | 建议 Owner |
|---|---|
| 物料/零件 | 技术/工艺部门 |
| EBOM | 设计/技术部门 |
| PBOM/MBOM | 工艺部门 |
| 工装 | 工装管理/制造部门 |
| 设备 | 设备管理部门 |
| 供应商 | 采购部门 |
| 客户 | 销售/项目管理部门 |
| 组织/人员 | 人力/综合管理部门 |
| 仓库/库位 | 仓储部门 |
| 质量检验项 | 质量部门 |

### 8.2 一次确认，多处复用

主数据治理必须承诺：

> 本次确认的主数据规则，应在 PLM、MES、ERP、OA、QMS 和 H5 看板中复用，避免不同系统反复要求业务部门确认同一批数据。

---

## 9. 数据问题处理原则

### 9.1 数据分级处理

| 数据类型 | 处理策略 |
|---|---|
| 上线必需数据 | 上线前清理完成 |
| 核心业务数据 | 联调前达到可用质量 |
| 历史查询数据 | 可迁移但标识质量等级 |
| 低频历史数据 | 可归档，不强行清洗 |
| 不确定数据 | 建异常台账和责任人 |

### 9.2 历史问题免责，新问题闭环

原则：

- 上线前发现的历史数据问题，进入治理台账，不直接作为个人或部门追责依据；
- 上线后新增且未按流程处理的问题，进入责任闭环；
- 历史问题不免责治理责任，但不做情绪化追责。

## 10. 沟通与会议原则

### 10.1 少开泛会，多做决策会

每次会议必须明确：

1. 本次要决策什么；
2. 会前材料是什么；
3. 参会人代表什么权限；
4. 会后谁签字；
5. 什么时候反馈；
6. 不反馈的默认处理规则。

固定周例会没有新增议题时，不要求部门临时制作材料。PMO只核对未关闭行动项、近期节点和需要协调的问题，会议可以提前结束，但不得因没有新增议题而取消。

### 10.2 给业务部门选择题，不给开放题

不要问：

> 请确认物料编码规则。

应改为：

> 物料编码建议采用 A 方案：机型 + 大类 + 流水；或 B 方案：物料大类 + 属性 + 流水。请确认是否存在必须保留的历史编码段。

### 10.3 逾期反馈必须有默认规则

推荐口径：

> 本表请于周三 17:00 前反馈。逾期未反馈的，PMO 将按当前版本提交阶段门评审；后续变更按项目变更流程处理。

## 11. 上线原则

### 11.1 可以分阶段上线，但不能无条件上线

| 可后续优化 | 不能后续补 |
|---|---|
| 报表美化 | 主数据基线 |
| 页面体验优化 | 备份恢复验证 |
| 非关键流程效率 | 权限和访问控制 |
| 次要字段展示 | 核心接口 |
| 驾驶舱指标扩展 | 业务穿透测试 |
| AI 应用深化 | ERP/MES/PLM 核心闭环 |

### 11.2 WBS 9 不得日期驱动

只有 `9.0.8 WBS 9 联调启动评审` 通过后，才能进入跨系统业务场景联调。

## 12. H5 看板原则

H5 看板不是展示工具，而是自动审计工具。

必须支持：

1. 核心招采关键路径视图；
2. 主数据版本变更视图；
3. 基础资源分批交付视图；
4. 联调启动条件视图；
5. 阶段门控制视图；
6. 合同付款控制视图；
7. 风险与阻塞项视图。

必须读取：

- `Text10 = 所属视图分类`
- `Text11 = 阶段门编号`
- `Flag1 = 是否关键路径控制`
- `Text13 = 版本控制对象`
- `Text14 = 变更等级`
- `Text15 = 联调启动条件`

## 13. 最终执行口径

本项目工作开展必须坚持：

1. 不假设主动配合，要设计配合动机；
2. 不依赖口头解释，要转成任务和字段；
3. 不把阶段门做成流程图，要绑定付款和上线；
4. 不把付款绑定做成死锁，要设置责任归因和临时放行；
5. 不让业务签无限责任，要做阶段性确认；
6. 不让历史问题阻碍暴露，要建立历史问题免责池；
7. 不让供应商利用内部争议，要设争议裁决和无争议推进机制；
8. 不让 H5 只是甘特图，要具备自动诊断能力；
9. 不让 PMO 变成催办员，要成为边界、证据和追责机制的组织者；
10. 不让项目停留在“计划完整”，要做到“基线可执行”。
